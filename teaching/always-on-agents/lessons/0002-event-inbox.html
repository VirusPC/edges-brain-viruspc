Event inbox

先挡住争跑和丢事件：所有来源写入一份耐用列表，再由唯一的 worker 取出并开 run。

第 2 课 · 约 10 分钟 · 主来源：William Hu · Building always-on agents

学完这一课，你能做到

看到一个新事件，能分清 handler 该立刻做什么、worker 该做什么。你能说出「来源直接叫 Agent」会挡住的两种失败，能判断该续上已有 session 还是新开一份，也能列出 run 中途又来事件时的三种处理，并且不编造原文没有的偏好。

为什么不能让来源直接叫 Agent

多数普通 Agent 只在用户发来一条消息时才跑。always-on agent 则可能被许多类事件叫醒，包括 webhook、预定任务和后台作业。 原文 · Event inbox

一种诱人的做法，是让每个事件源直接去叫 Agent。原文指出这样会有几种失败。它举了两个例子：两个事件同时到达，会启动互相竞争的 run；一旦崩溃，还可能把事件整件弄丢。 原文 · Event inbox

三件套：耐用列表、handler、worker

所以所有来源不要直接叫 Agent，而是先把事件送到 event inbox，再由 worker 取出。原文把最简单的形态写成三件事： 原文 · Event inbox

  1. 一份耐用的事件列表通常是一张数据库表。inbox 还应当跟踪每条事件的状态。事件可以按来源给出的唯一标识去重。关系型数据库很适合做 inbox，每条事件作为新行追加。 原文 · Event inbox
  2. 一个 handler通常是一个 HTTP 接口，负责把事件写入这份列表。 原文 · Event inbox
  3. 一个 worker通常是一个后台服务，负责从列表里读取待办。 原文 · Event inbox

新事件到来时，handler 把它写入 inbox，并叫醒 worker。worker 读出待办，开一次 run，把事件交给 Agent 循环，等这次 run 结束，再把对应事件标成完成。 原文 · Event inbox 原文建议先从「一人一个 inbox」起步；若需要更多并行，再继续拆分。 原文 · Event inbox

四条最佳实践

实现细节会变复杂，原文给了几条应当先记住的做法。 原文 · Event inbox

handler 要很快确认收到

有些来源，例如 webhook 提供方，会把慢响应当成失败。handler 仍可以做一些轻量检查，但更深的验证，例如检查提示词注入，应当放到这次 run 里做。 原文 · Event inbox

inbox 是真相来源

worker 被叫醒时，应当先从 inbox 拉最新的事件。这样，如果 worker 在一次 run 做到一半时死掉，新的 worker 可以拾起同一条事件再试。 原文 · Event inbox

同一时间只有一个在工作的 worker

一个 inbox 同一时间只应有一个在工作的 worker。这样可以避免两次 run 做重复的劳动，或互相覆盖。 原文 · Event inbox

若新事件在一次 run 做到一半时到来，原文并列了三种处理：把它推到下一次 run，把它并进当前这次 run，或者打断并重来。原文没有推荐其中一种，课里也不编造偏好。 原文 · Event inbox

把待办事件批次合并

worker 应当把积压的待办事件批次合在一起。例如用户连续发来好几条消息，worker 可以把它们合并成一次 run，这样 Agent 只需回复一次。 原文 · Event inbox

续上 session，还是新开一份

怎样决定续上旧 session 还是新开一份？原文写得很具体：接着先前工作的事件，例如用户的答复，会续上已有 session；其余通常新开一份。 原文 · Event inbox

合上原文，60 秒这样讲

「always-on agent 会被许多类事件叫醒，不要让来源直接去叫它：同时到达会争出两次 run，崩溃还可能把事件弄丢。所有来源先经过 handler，写入一份会记状态、可按来源标识去重的耐用 inbox。handler 要很快确认收到，深检查放到 run 里做。inbox 是真相来源，worker 醒来先拉最新待办；它若中途死了，新的 worker 可以拿同一事件再试。一个 inbox 同一时间只有一个在工作的 worker。中途又来事件时，可以推到下一次、并进当前这次，或打断重来，原文把三种并列，没有推荐哪一种。积压的待办可以批次合并。用户答复这类接着先前工作的事件续上已有 session，其余通常新开一份。」
