# 多 Agent 仓库修改的 worktree 隔离与写入前核验

> 技能安装和生成索引也会改仓库里已跟踪的文件。写之前先确认这是当前任务自己的工作树。

## 背景

2026-11-14，各台设备把 Edges 升到 0.6.0。升级过程中，助手在现有仓库检出里覆盖了已跟踪的技能文件。当天 19:14–19:15（北京时间），peng cheng 指出很多工作区没有严格另建 worktree，而是直接在当前目录上改，并要求把这件事写成笔记和记忆。意图是把「写之前先核验、不满足就不写」留成以后每次修改仓库都要遵守的规则。

## 主题

这场谈的是：多个 Agent 改同一个仓库时，怎样避免直接在已有检出上写入，包括那些看起来不像写代码的安装和生成。

- 难点一：`edges --scope` 被误当成技能安装的落点，安装因此没有落到预期位置。覆盖不是安装器写进去的。助手随后手动把 npm 技能复制进现有仓库已跟踪的 `.agents/skills`，才盖掉旧文件和框架软链。
- 难点二：命令行里的全局安装，和仓库里那份已跟踪的技能副本，不是同一次更新。仓内旧副本仍可能盖住全局装上的新版本。
- 难点三：工作区显示 dirty，以及主仓历史改写之后的分叉，都容易被当成「这次 worktree 没建好所以要回退」。这两件事要分开看。
- 难点四：覆盖已经发生之后再逐字节撤回，只能处理对得上的那一部分。它不能代替写入前的隔离。

## 过程

### 时刻不详 升级时把技能复制进现有检出

各台设备做 Edges 0.6.0 升级时，助手以为 `edges --scope` 会决定技能安装的当前目录，随后把 npm 包里的技能复制进现有仓库已经跟踪的 `.agents/skills`。这次复制覆盖了旧文件和框架软链，把现有目录弄脏了。

当时摆在桌上的做法有三条：

- 继续把 npm 技能复制进仓库里已跟踪的技能目录。这条已经发生。它不做为正确做法，是因为会盖掉旧文件和框架软链，而且 `edges --scope` 本来就不决定安装器的当前目录。
- 按 npm 包逐字节对照，只撤回助手自己覆盖的文件，保留用户原来的改动，并留下备份。后来实际采用的是这一条。
- 改用包内安装器，写明这是全局安装，装完再核验没有写进仓库。撤回之后采用的是这一条。

撤回和全局安装做完之后，对话里把三件容易混在一起的事分开了。这些区分没有单独的钟点，不另编时刻：

- 命令行或全局安装更新的是它自己的安装目标。它不等于更新仓库里那份已跟踪的技能副本。仓内旧副本仍可能遮蔽刚装上的全局版本。仓内副本要换版，走正式 PR，不应在现有目录上再覆盖一次。
- 工作区显示 dirty，只说明子仓的 checkout 比父仓记下的 pin 新，不等于那些路径上有未提交的文件修改。
- 主仓旧历史被改写之后，克隆之间出现分叉。这是另一件事，不要把它说成没有建 worktree 造成的。

对话没有给出更早的钟点，上面这段统一记为时刻不详。

北京时间 19:14，用户指出很多工作区没有严格创建 worktree，而是直接在当前目录上改。助手承认，这次把技能复制进现有检出，同样违反了隔离纪律。助手当时约定：以后在本机已有 checkout 上写仓库之前，先核验这是当前任务自己的 worktree 和独立分支；不满足就不写。当时没有再比较别的隔离方式。

北京时间 19:15，用户明确要求加一篇笔记，并且把规则记住。本篇对话材料截到这一刻。当时没有宣布各台设备都已修好。

## 结果

- 助手自己覆盖的技能文件，已按 npm 包逐字节对照撤回。用户原有改动保留，并留了备份。
- 撤回之后，用包内安装器做了写明目标的全局安装，并核验过。
- 到 19:10 叫停为止，历史对齐没有发生，子仓回退也没有发生。
- 19:14 确认了本机写入前的 worktree 核验：不满足就不写。19:15 要求把规则写成笔记和记忆。本篇是那份笔记。
- 仓库里已跟踪的技能副本没有靠这次全局安装换掉。旧副本仍可能遮蔽全局版本。要换版需要正式 PR，不应再次覆盖。
- 没有得出「各台设备都已修好」。也没有得出「所有未提交改动都是这次覆盖造成的」。
- 没有做 agent 运行态测试。
- 技能文件上，助手自己的覆盖已经撤回。历史和子仓没有做回退。

## 所学

- 写仓库之前先看当前路径是不是这次任务自己的工作树。技能安装、生成索引这类会改已跟踪文件的操作，和改代码一样要先核验。不满足就先停，不把「事后对照撤回」当成隔离。事后撤回只能处理已经对上的覆盖，对话里没有把它当成可以继续先写再救的方案。
- `edges --scope` 选择的是 Edges 材料写到哪个 scope，不是 npm 或安装器的当前目录。把包内技能复制进现有检出的 `.agents/skills` 会覆盖旧文件和框架软链，所以不采用。全局安装要写明目标目录，并检查仓库状态没有被这次安装改掉。
- 全局安装和仓内已跟踪副本是两份东西。只装全局，仓内旧文件还在，仍可能被工具先读到。更新仓内副本用正式 PR，不在当前检出上再盖一次。
- 父仓显示子仓 dirty，可能只是子仓 checkout 比 pin 新。这不等于子仓里有未提交文件，也不等于应该把子仓退回 pin。主仓历史改写造成的分叉单独处理，不并进 worktree 事故。
- 已有、来源尚未说清的改动保持原样。clean、reset、stash 都会把这些改动挪走，对话里不采用。
- 云端已经是独立 clone 的任务，本身就是分开的工作目录，不必再套一层本机 worktree。只读查询不必建 worktree。本机多个 Agent 仍不能共用同一个工作树写入，同一个分支也不能挂两个 worktree。

## 行动指南

### 主题行动指南

#### 背景

多个 Agent 会在同一些仓库的已有检出上继续工作。除了改代码，技能安装和生成索引也会改已跟踪文件。

#### 核心问题

在已有本机 checkout 上做任何会改仓库 tracked 内容的事之前，怎样确认写入点已经按任务隔开；没有隔开时怎样停下来。

#### 核心解决方案

1. 先核验再写。看 git 仓库顶层和当前路径是不是同一个检出，看 `git worktree list`、当前分支，以及这次动手前的 status 基线。必须是当前任务自己的 worktree，加上只给这个任务用的分支。多个 Agent 不共用同一工作树写入，同一分支不挂两个 worktree。可选项是不核验、直接在当前目录改，以后再对照恢复。不采用。这次覆盖就是在现有目录上发生的，事后撤回没有代替隔离。
2. 核验不满足就停写，先把这次任务隔离开，再写。可选项是先写入、发现污染后再逐字节撤回。不采用。撤回只能处理对得上的文件，而且对话要求不靠事后恢复。
3. 全局环境安装写明目标目录，并检查它没有把文件写进仓库检出。可选项是把 npm 包里的技能复制进仓库已跟踪的技能目录，并以为 `edges --scope` 已经选好了安装位置。不采用。`--scope` 不决定安装器的当前目录，复制会覆盖旧文件和框架软链。
4. 仓库里那份已跟踪副本要换版时，另开 PR。可选项是在当前检出上再覆盖一次，指望全局安装顺便更新它。不采用。全局安装不更新这份副本，旧文件仍可能遮蔽全局版本。
5. 已有改动留在原地。内容变更通过 PR 进入仓库。可选项是顺手 clean、reset 或 stash 掉看起来脏的内容，或把子仓退回父仓 pin，把历史分叉一并「对齐」掉。不采用。dirty 可能只是子仓 checkout 比 pin 新；历史改写造成的分叉是另一件事。用户在 19:10 叫停了可能包含回退的完全对齐。

#### 验收标准

- 动手改 tracked 文件之前，记录过 git 顶层、当前路径、`git worktree list`、分支和 status 基线。
- 写入发生在当前任务自己的 worktree 和独立分支上；没有第二个 Agent 同时写这棵工作树；这个分支没有挂在两个 worktree 上。
- 核验不满足时，仓库里没有新增这次任务的写入。
- 全局安装的目标目录写明了，且安装前后仓库 status 里没有出现这次安装写入的路径。
- 仓内已跟踪技能副本若要换版，有单独的 PR，而不是在现有检出上覆盖。
- 动手前已经存在的用户改动还在，没有被 clean、reset 或 stash 清掉。
- 子仓只是比父仓 pin 新时，没有被回退；历史改写造成的分叉没有被写成 worktree 事故。

### 细节与其他

#### 若这次只读仓库，不改 tracked 文件

则：不必建 worktree。只读不需要把检出再隔离一份。当时没有把只读也套进 worktree 的做法拿来比较。

#### 若任务已经在云端的独立 clone 里

则：这个 clone 已经和本机其他检出隔开，不必再嵌套一个本机 worktree。可选项是在云端 clone 里再 `git worktree add` 一层。不采用。对话把云端独立 clone 视为已经隔离。

#### 若核验时发现当前路径不是本任务自己的 worktree，或分支不是本任务自己的分支

则：停写。先为这个任务建立独立 worktree 和独立分支，再改文件。可选项是先改、再搬到新分支。不采用。搬动不能撤回已经盖掉的文件。

#### 若多个 Agent 要写同一个工作树，或同一个分支已经挂了两个 worktree

则：后到的一方停写，换自己的工作树和分支。不和别人共用这一棵工作树，也不在已占用的分支上再挂一个 worktree。

#### 若要做全局安装

则：写明安装目标，并确认它不在仓库 checkout 里。装完再看仓库 status，这次安装不应往检出写入。可选项是把 npm 技能手动复制进已跟踪的 `.agents/skills`，并以为 `edges --scope` 已经决定了落点。不采用。`--scope` 只说明落点不符合预期；覆盖发生在随后的手动复制，不是安装器写入。

#### 若要生成索引，或做其它会改 tracked 内容的仓内变更

则：写在当前任务自己的 worktree 和独立分支上，和正式的仓库内容变更一起走 PR。核验不满足就停写。可选项是规定生成目标一律不得落在仓库里。不采用。合法的索引生成就是仓内容，隔离之后可以发生在任务 worktree 内。

#### 若父仓把子仓显示为 dirty，且差异只是子仓 checkout 比父仓 pin 新

则：不要把它记成未提交的文件修改，也不要因此回退子仓。要更新 pin，另开 PR。可选项是把子仓重置到父仓 pin，使父仓变干净。不采用。19:10 叫停时，历史对齐和子仓回退都还没有发生。

#### 若主仓旧历史被改写后，克隆之间出现分叉

则：按历史分叉单独处理。不要把它写成「因为没有 worktree」。对话里这两件事被明确分开。

#### 若检出里已有说不清来源的改动

则：保留，不执行 clean、reset 或 stash。可选项是先 stash 再开始自己的修改，做完再恢复。不采用。对话要求已有用户改动留下来，不顺手清理未知改动。
