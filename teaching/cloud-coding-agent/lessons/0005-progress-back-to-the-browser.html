进度怎么回到网页

Agent 在 Sandbox 里打出的每一行字，要经过服务器、数据库，再被浏览器定时拉走，才出现在你眼前。这一课把这条链路一段段拆开，顺带看清任务状态是谁在改、“停止”按钮到底停住了什么，以及为什么它不用 WebSocket。

第 5 课 · 约 12 分钟 · 研究对象：vercel-labs/coding-agent-template · 前置：第 1 课、第 2 课、第 4 课

学完这一课，你能做到

从 CLI 的标准输出一路讲到网页上的那一行字：谁去拉、用什么协议、写进哪张表、怎么写、浏览器多久问一次；说出任务的五种状态分别由谁、在什么时候写入；解释“点了停止”之后后台为什么不一定停；讲清“写库 + 轮询”的理由和代价，并给出一个更好的方案。

先看全貌：一条“拉”出来的链路

  1. CLI 往标准输出写字 Sandbox Claude 和 Cursor 写的是 stream-json，每行一个 JSON；其余几家是普通文字（第 4 课）。
  2. 服务器上的 SDK 开一条长连接去拉 @vercel/sandbox 0.0.21 runCommand 传了 stdout 时，SDK 在后台对 GET /v1/sandboxes/{id}/cmd/{cmdId}/logs 发请求，要求返回 application/x-ndjson，逐行解析后把每段输出写进传入的 Writable（sandbox.js L130–L157，api-client.js L164–L200）。
  3. 适配文件逐块解析 agents/*.ts 在 Writable.write() 里按换行切开、JSON.parse，把文字和工具调用攒成一段，写进 task_messages 的那一行（lib/sandbox/agents/claude.ts L310–L405）。
  4. 两张表、两种写法 数据库 平台自己的步骤日志进 tasks.logs（一个 JSON 数组列，lib/db/schema.ts L96）；Agent 的回复进 task_messages.content（一个文本列，lib/db/schema.ts L360–L370）。
  5. 浏览器定时来问 React 任务详情每 5 秒、聊天消息每 3 秒、侧边栏任务列表每 5 秒，各一个 setInterval（lib/hooks/use-task.ts L73–L83 components/task-chat.tsx L264–L273 components/app-layout.tsx L152–L159）。
  6. 渲染 logs-pane / task-chat 日志面板直接读 task.logs 过滤显示（components/logs-pane.tsx L160–L162），聊天区把消息交给 Streamdown 渲染成 Markdown（components/task-chat.tsx L23）。

整条链路里，Sandbox 从来不主动联系服务器。没有回调地址、没有 webhook，数据全是服务器那一侧拉出来的；浏览器也从不直接碰 Sandbox 和数据库，只问 Next.js 的接口。所以真正把三方串起来的只有两样东西：服务器函数里那条拉日志的长连接，和数据库。 这也解释了第 2 课的一个现象：如果服务器函数中途没了，那条长连接也就断了，Sandbox 里的 CLI 可能还在跑，却再也没有人去读它的输出。

第二段：服务器写库，两张表两种写法

平台步骤日志 → tasks.logs。所有“正在克隆”“安装依赖”“Sandbox 已关闭”之类的话都走 TaskLogger。它的 append() 做三件事：先脱敏（第 4 课），再 SELECT 出这一整行任务，最后把旧数组加上新的一条、UPDATE 整列写回（lib/utils/task-logger.ts L16–L55）。updateProgress() 和带消息的 updateStatus() 也是同样的“读出来、拼上、写回去”（lib/utils/task-logger.ts L79–L131）。写失败一律吞掉，不影响主流程。

Agent 回复 → task_messages.content。Claude 开跑前先插一条内容为空的 agent 消息（lib/sandbox/agents/claude.ts L266–L275），之后每解析出一段文字或一次工具调用，就把累计到目前为止的全部文字写进这一行（lib/sandbox/agents/claude.ts L335–L345）。Copilot 更密：每一行输出就发一次 UPDATE，注释写着“throttled via catch”，但代码里并没有任何节流，只是把错误吞掉（lib/sandbox/agents/copilot.ts L236–L243）。这些 UPDATE 都没有 await，发出去就不管了。

并发与放大：三个问题（都是读代码推断，没有实测）

一、日志会被覆盖。“先读后写”中间没有锁，也没有事务。同一时刻往同一个任务写日志的不止一个人：后台流程本身、提前 1 分钟提醒超时的计时器（app/api/tasks/route.ts L278–L287）、用户点停止时停止接口自己的 TaskLogger（app/api/tasks/[taskId]/route.ts L68–L72）。两个写入者同时读到旧数组，各自加一条再写回，后写的那次就把先写的那条抹掉了。正确写法是让数据库自己追加（Postgres 可以用 logs || 新条目 这样的单条 UPDATE），或者干脆一条日志一行。

二、Agent 回复可能“倒退”。每次写的都是“全部累计内容”，而且不等上一次写完就发下一次。数据库不保证按发出的顺序完成，如果较早、较短的那次最后才落地，这一行就停在一个旧版本上。Claude 跑完以后没有再补写一次最终内容，所以这个旧版本可能就是用户最后看到的。

三、写放大是平方级的。第 n 条日志要把前面 n−1 条一起读出来、再一起写回去，一个任务写 N 条日志，总共搬运的大约是 N²/2 条。Agent 的回复也一样，每来一段就把整段重写一遍。任务越长、日志越多，每多一行就越贵。

都是手写的 setInterval + fetch，项目依赖里没有 SWR 或 React Query，也没有 EventSource、WebSocket（我在 components、app、lib 里搜过）。三个定时器都不看任务状态：任务早就完成了，只要页面开着，它们就照拉不误。另外还有一些慢一点的：PR 检查状态 30 秒，Sandbox 健康检查 2 秒（只在有预览地址时），登录信息 60 秒。

把这几件事放在一起算一笔账：一个开着页面的用户，每分钟大约发 12 + 20 + 12 = 44 次请求；侧边栏那一路每次都把他名下所有任务的全部日志从数据库读出来、经网络发给浏览器。任务一多、日志一长，读放大比写放大还厉害。这是按代码算的估计，没有实测。 实时性也因此有上限：一行输出从 CLI 打出来，到出现在网页上，最坏要等一个轮询周期（日志 5 秒、消息 3 秒），再加上数据库写入和 SDK 拉取的延迟。

任务状态机：五个值，谁在什么时候改

状态只有五种取值：pending、processing、completed、error、stopped（lib/db/schema.ts L90–L95）。

状态谁写、什么时候
pending创建任务的接口插入新行时，progress: 0 app/api/tasks/route.ts L74–L90
processing后台流程一开头 app/api/tasks/route.ts L397–L399；追问接口一进来就把状态改回它、进度清零 app/api/tasks/[taskId]/continue/route.ts L76–L85

进度百分比不是算出来的，是写死的里程碑。后台流程在每一步之前写一个固定数：10 初始化，15 创建 Sandbox（app/api/tasks/route.ts L440），然后由 createSandbox 通过 onProgress 回调写 20、25、30、35（npm 失败重试时 37）、42、44（lib/sandbox/creation.ts L58–L59 lib/sandbox/creation.ts L137–L138 lib/sandbox/creation.ts L561–L562），50 开始跑 Agent（app/api/tasks/route.ts L527），最后 100。从 50 到 100 之间是 Agent 干活的全部时间，进度条一动不动。onProgress 回调顺手查一次“是不是已经被停了”（app/api/tasks/route.ts L467–L474）。

状态机的两个漏洞（读代码推断）

一、终态可以被覆盖。所有写状态的地方都是无条件的 UPDATE … WHERE id = ?，没有“只有从 processing 才能变成 completed”这样的条件。下一节会看到，stopped 之后后台流程还可能写出 completed 或 error。

二、可能永远停在 processing。后台流程跑在 after() 里，Next.js 文档写明 after 只能活到这条路由的最长时长（after · Duration），而 vercel.json 给创建任务的接口设的是 300 秒（vercel.json L1–L8，第 2 课）。可 README 说时长可以选“5 分钟到 5 小时”（README.md L63），默认值 MAX_SANDBOX_DURATION 是 300 分钟（lib/constants.ts L5）。赛跑计时器按用户选的分钟数计时，远远晚于函数被平台终止的时刻。函数被终止时，没有任何代码有机会把状态改成 error，任务就一直显示“进行中”。追问接口没有在 vercel.json 里配置，按平台默认值也是 300 秒（Vercel 函数时长）。Cursor 文件里“Sandbox 超时是 5 分钟”的注释（lib/sandbox/agents/cursor.ts L485–L487），按推断说的其实是函数的 5 分钟。

停止任务：按钮停住了什么

  1. 浏览器发 PATCH task-chat.tsx PATCH /api/tasks/{id}，body 是 { action: 'stop' }；成功就弹“已停止”，注释说“状态会通过轮询更新”（components/task-chat.tsx L552–L577）。
  2. 接口改状态 [taskId]/route.ts 校验任务属于当前用户、状态是 processing，写一条日志，把状态改成 stopped、error 字段写“Task was stopped by user”（app/api/tasks/[taskId]/route.ts L61–L84）。
  3. 去“杀” Sandbox sandbox-registry.ts 调 killSandbox(taskId)。它查的是这个函数实例内存里的一张表，找到了才 sandbox.stop()（lib/sandbox/sandbox-registry.ts L25–L60）。文件开头自己写着：这张表“只用于同一次 serverless 执行里的即时操作”（lib/sandbox/sandbox-registry.ts L3–L9）。

问题就在第 3 步。停止请求是一次新的请求，会落到哪个函数实例上，代码控制不了。落到别的实例上，表里查不到这个任务；如果那个实例的表里恰好有别的任务的 Sandbox，代码会走一个“兜底”分支：把第一条记录从表里删掉，不调用 stop()，然后返回成功（lib/sandbox/sandbox-registry.ts L28–L40）。于是日志里写着“Sandbox killed successfully”，其实谁也没被关掉，还顺手让另一个任务从表里消失了。数据库里明明存着 sandboxId，另一个“停止 Sandbox”接口就是用 Sandbox.get({ sandboxId }) 重连再 stop() 的（app/api/tasks/[taskId]/stop-sandbox/route.ts L35–L44），停止任务的接口却没这么做。 Vercel 的 Fluid compute 会让一个实例同时处理多个请求（Vercel 文档），所以停止请求有可能恰好落在同一个实例上，这时 stop() 会真的执行。能不能停住，看运气。这是推断。

后台流程那边呢？它只靠查数据库里的状态来发现自己被停了，而查的位置全在 Agent 开跑之前：开始前、生成分支名后、建 Sandbox 的每个进度回调里、建完以后、跑 Agent 之前（app/api/tasks/route.ts L419–L431 app/api/tasks/route.ts L467–L474 app/api/tasks/route.ts L488–L500 app/api/tasks/route.ts L520–L524）。Agent 一旦开跑，就再也没有检查。于是按推断有三种结局：

  • Sandbox 没被关掉（落到别的实例上）：Agent 照常跑完、照常推送到任务分支，最后 updateStatus('completed') 把 stopped 覆盖掉（app/api/tasks/route.ts L690–L696）。用户以为停了，分支上却多了提交。
  • Sandbox 被关掉，跑的是 Codex、Gemini、opencode、Copilot：命令失败，适配文件返回失败，流程进 catch，把状态写成 error（app/api/tasks/route.ts L697–L705 app/api/tasks/route.ts L730–L735）。
  • Sandbox 被关掉，跑的是 Claude：日志流断了，result 行永远不会来，第 4 课那个没有出口的等待循环就一直转（lib/sandbox/agents/claude.ts L428–L430），直到函数被平台终止。状态保持 stopped，但这个实例上的 after() 一直空转到 300 秒。

这和第 2 课讲的赛跑计时器是同一个毛病：Promise.race 只决定“谁先给出结果”，输掉的那一方并不会被取消（app/api/tasks/route.ts L295–L312）。停止、超时都只是在数据库里改了个字，没有一个真正能叫停正在跑的代码的机制。

为什么是“写库 + 轮询”，而不是 WebSocket 或 SSE

代码和 README 都没有写明这个设计理由，下面的动机分析是推断，但每一条约束都有出处：

  • 干活的函数活不长，也不和浏览器连着。后台流程在 after() 里跑，浏览器的那次请求早就结束了，两者之间没有可以推消息的连接。函数最多活 300 秒（Hobby 上限就是 300 秒，Pro 默认 300 秒、最多 800 秒，Vercel 函数时长）。
  • 函数实例之间不共享内存。浏览器的轮询请求和干活的 after() 多半落在不同实例上，内存里的东西对方看不到。模板自己的 Sandbox 注册表就踩了这个坑。能被所有实例同时看到的，只有数据库。
  • 轮询最简单，而且天然能“断线重连”。用户关掉页面、换台电脑、过一小时再回来，进度都还在库里。不需要额外的消息服务。

代价前面都看到了：最多几秒的延迟；日志“先读后写”带来的覆盖和平方级写放大；侧边栏每 5 秒把所有任务的全部日志拉一遍的读放大；任务结束后轮询也不停；以及“停止”没有通道能通知到正在跑的那段代码。

现在还是不是这样？平台条件变了一部分。Vercel Functions 在 2026-06-22 开放了 WebSocket 公测（更新日志），但文档写明：一条连接固定在接受它的那个实例上，函数到最长时长时连接会被关闭，客户端必须自己重连（WebSockets）。也就是说，长任务的进度仍然需要一个持久的地方存着，WebSocket 只能替代“浏览器每几秒问一次”这一段，替代不了数据库。 这份代码固定在 2026-02-12 的提交，比 WebSocket 公测早四个多月，所以当时 Vercel 函数上确实没有原生 WebSocket 可用。

别家怎么做，以及“如果自己做”

产品进度怎么到界面出处
Open SWE（LangChain）推流。2026-06 的一次提交把“自己写的 SSE + React Query 轮询”换成了 LangGraph 的 v2 事件流，经带登录态的代理转给浏览器；Agent 本身跑在 LangGraph 的持久化 run 里，每一步都存检查点open-swe 提交 abf354b
Cursor Cloud Agents API推流。每一次 run 一个 SSE 流（status、assistant、tool_call、heartbeat、result 等事件），断线后带 Last-Event-ID 续上；超过保留期返回 410，改为直接读 run 的最终状态Cloud Agents API
Vercel 自己的 durable harness先写持久日志，再从日志推流：“Your app's browser streams the turn from the session's log”，换了 Sandbox 也不中断；函数崩了由另一个函数从日志接着跑Security、Agent harnesses
Codex Cloud网页端界面能实时看任务日志，但用的是推流还是轮询，我没有查到官方公开说明，这里不下结论—
如果自己做（参考答法）

一、日志改成“只追加的事件表”。task_events(task_id, seq, type, payload, created_at)，每条事件一行 INSERT，seq 单调递增。写入不再“先读后写”，没有覆盖，也没有平方级放大。Agent 回复也拆成一段段事件，不再整段重写。

二、前端按游标增量拉。GET /api/tasks/{id}/events?after=最后一个 seq，只拿新的那几条。任务进入终态就停止轮询。侧边栏只取 id、title、status、progress 这几列，不带日志。

三、想要实时，再在上面加 SSE。同一个接口支持 text/event-stream，每条事件的 id 就是 seq，浏览器断线后用 Last-Event-ID 自动续上（MDN · SSE）。SSE 只是“通知有新事件”，事实仍以事件表为准，所以连接被函数时长切断也没关系。多实例之间要即时唤醒，可以用 Redis Streams 的 XADD / XREAD BLOCK（Redis Streams）或 Postgres 的 LISTEN / NOTIFY（NOTIFY）。

四、指挥流程不放在请求的尾巴上。放进队列或 Workflow 这种能跨函数实例接着跑的地方（第 2 课），每一步写事件、做检查点。

五、停止要真的能停。停止接口用库里的 sandboxId 重连并 stop()；后台流程在每个步骤之间、以及等待 Agent 的循环里都检查停止标志；状态迁移带条件，例如 UPDATE … SET status='completed' WHERE id=? AND status='processing'，终态不能被覆盖。

面试时 60 秒这样讲

“这个模板的进度链路是‘拉’出来的，Sandbox 从不回调服务器。后台流程跑在 Next.js 的 after() 里，用 Sandbox SDK 启动 CLI；传了 stdout 的命令，SDK 会对 Sandbox 的 /cmd/{id}/logs 开一条 NDJSON 长连接，把输出一段段交给适配文件解析。Claude、Cursor、Copilot 能边跑边写库，Codex、Gemini、opencode 要等跑完一次性拿到输出。写库分两张表：平台步骤进 tasks.logs 这个 JSON 数组列，Agent 回复进 task_messages。浏览器用三个 setInterval 轮询：任务详情 5 秒、消息 3 秒、侧边栏 5 秒。状态有五种，进度是写死的里程碑。之所以写库加轮询，是因为干活的函数活不长、实例之间不共享内存，数据库是唯一的公共地方。代价是：日志‘先读后写’会互相覆盖、写放大是平方级的，轮询拿的是全量数据，停止按钮靠实例内存找 Sandbox，常常停不住，后台流程跑完还会把状态改回 completed。我会改成只追加的事件表加游标增量拉，需要实时再叠一层 SSE，用 Last-Event-ID 续传，停止走 sandboxId 加带条件的状态迁移。”

面试官可能的追问（附参考答法）

问：轮询和 SSE 怎么选？
答：先看数据有没有一个持久的地方。有了事件表，轮询和 SSE 就只是“浏览器怎么知道有新东西”的两种方式：轮询最简单，CDN、代理、断线都不用操心，代价是延迟和空请求；SSE 是单向推送，用普通 HTTP，浏览器原生支持断线自动重连和 Last-Event-ID，很适合“Agent 往外吐进度”这种单向场景。WebSocket 是双向的，但在 serverless 上连接绑定实例、有时长上限，收益不大。我的默认选择是：事件表 + 增量轮询起步，体验要求高了再加 SSE。

问：tasks.logs 用 JSON 数组列有什么问题？
答：三点。一是并发追加没有原子性，“先读后写”会丢日志；二是每次追加都要把整个数组读出来、写回去，成本随日志长度平方增长；三是读的时候也只能整列拿，没法“只要第 100 条以后的”。改成一条日志一行、带自增序号，三个问题一起解决。

问：用户点了停止，你怎么保证真的停了？
答：三层。第一，停止接口不依赖内存，用库里的 sandboxId 直接调 Sandbox API 关机，这是唯一能立刻掐断 Agent 的办法。第二，指挥流程在每个步骤之间、等待循环里查停止标志，查到就退出，不再推送。第三，状态迁移带条件，终态写一次就不能再改，这样即使有漏网的代码跑完，也不会把 stopped 改回 completed。

问：任务要跑一个小时，而函数最多跑 5 到 15 分钟，怎么办？
答：指挥者不能是一个请求。要么用队列加检查点，一个函数快到时限就把状态存下、下一个接着跑；要么用 Vercel Workflow 这类能暂停和恢复的执行环境；要么指挥逻辑本身挪进 Sandbox 里（它能活几个小时），服务器只负责启动和读事件。Vercel 的 durable harness 就是第一种思路：会话日志是事实，函数崩了由另一个函数从日志接着跑。
