# 评测与任务卡里已证实的失败模式

> 把已经跑出结果的评测、以及任务卡里记下的事故和缺口，收成一份能核对证据的清单。重点不是把计划中的失败讲成已经发现的失败，而是分清测到了什么、任务卡里还有什么没测、哪些现在还不能算已证实的失败模式。

## 背景

2026-11-18，peng cheng 在「Agent Eval 专家」里问：通过 eval 发现了 Edges 项目的哪些 failure mode。助手先只翻了公开仓里已经跑出结果的评测记录，随后用户补充自己似乎记过很多和 failure mode 有关的任务卡，于是又把两个仓库的任务卡筛了一遍，和评测清单对照。最后用户问哪些讲出来会显得扎实，助手按「测了什么、没测什么、哪个结论站得住」作了归纳。助手两次提议把清单写成评测目录下的分类，并给每类配回归题草稿，用户都没有采纳。

## 主题

整理 Edges 在已有评测和任务卡里、能够拿出证据的失败模式，并标出评测覆盖不到的类型，以及目前还不能写成「已发现」的条目。

- 难点一：评测主要停在「找记忆」和「用记忆」，任务卡记下的却大多是环境、接入和理解偏差，两边对不上时，不能把某一边的清单当成全貌。
- 难点二：有些类型只写在规则或完成标准里，或者相关评测还没跑，不能当成已经发生过的失败。
- 难点三：现有评测没有测「有没有记忆」对任务完成率的影响，所以不能从这些结果推出项目记忆已经提升了任务质量。

## 过程

### 17:19 先从已跑完的评测里找

用户请助手在 edges 项目里查找评测发现的失败模式。助手只读了 GitHub 上的两个公开仓库，没有读私有仓，也没有调 Langfuse。随后给出当时能拿出证据的五类，前两类集中在「找记忆」和「用记忆」：

1. 检索不全，或停得太早。在真实历史问题上（Harbor 真实记忆消融），分层和平铺两组都只选到大约一半该选的记忆，recall@5 分别是 54.1% 和 52.4%。合成集的逐条复核（TRACE_ANALYSIS）里有两种具体表现：一种是在子层索引里已经看到了标题，却没有点开正文；另一种是读完根层就结束，没往下找子层。另外，仓库检索冒烟有 1 题得 0 分，Agent 被旧的 locomo-smoke 文档带走，没找到官方入口那条记忆。
2. 读到了，最后没用上。同一份合成集分析里，「食盒」这道题的正文已经出现在命令输出里，Agent 却只选了一条记忆，回答漏掉了周四锁定的规则。在 10-25 全文注入实验里，M08、M09、M11 三题即使把记忆全文塞进去，照样答错。这几题考的是：规则真正写在 skill 里而不在记忆里、评测文件该放哪、改动必须走 PR。
3. 检索到无关记忆，可能起干扰作用。在没有相关记忆的题上，平铺组有 2/21 次误选了记忆，分层组是 0 次。MemoryBench 冒烟里有一题因为取回了不相关的历史回答，分数从 5 掉到 3。
4. 全文注入成本太高。质量确实涨了，依赖记忆的题从 33% 升到 75%，但输入 token 的中位数多了 246%，所以这个策略被否决了。否决的是注入方式，不是记忆本身。
5. 评测本身有毛病。`user_disagreement_llm` 这个裁判在拿不到上一条助手回复时会直接记 0，所以整体的异议率不可信。合成集 v2 的标准答案按「必要证据」定义，提示词却让 Agent 选「相关」记忆，这会把 precision 上的「错误」算多。另外还有同一个模型给自己打分、样本太小、标注是 AI 做的而不是真人等问题。

助手随后补了两件不能写成「已发现失败模式」的事：「违反 AGENTS.md 硬约束」和「过时记忆把 Agent 带偏」现在都不能算已发现。skills 和 Agent 的回归评测还压在待办里没跑；过时记忆那类题在 10-25 那轮反而一次都没出现带偏。这些评测测的都是检索和问答，没测过「有没有记忆」对任务完成率的影响。真实题的逐次日志不在公开仓里，所以真实集只能看到汇总数字。助手提议把清单整理成一个 Page，放进 `.harness/evaluation/` 作为失败模式分类，用户没有答应，而是提到任务卡。

### 17:36 再对照任务卡

用户说似乎记录过很多和 failure mode 有关的 task。助手把两个仓库一共 252 张任务卡全筛了一遍，真正记了失败、事故或已知缺口的大约二十张，其中大部分属于评测从来没测过的类型。当时按类型列、并各附代表性条目的是：

- 工具、环境和沙箱故障，卡最多。例如：pi 不在沙箱里跑，跑出了被测仓库副本，这个已修；软链登记和 scope 大小写的修复因为合入时序问题一直没进 main；compose 把本机绝对路径写进了 AGENTS.md，换一台机器就失效；Langfuse v4 下 trace 接口返回 404，容易误以为 trace 没写进去。
- 接入和分发缺口。例如：在 ChatGPT 这类窗口里，入库类 skill 跑不起来，当时还没修；npm 包第一次发布时没带 skills，已修；OpenCode 和 Pi 没有设备 tags，观测分组会漏掉这两个客户端；跨客户端接入时不能只信 Agent 自己说「读到了」。
- 执行偏离用户意图。Routines 卡里，Agent 把一句「是的」理解成了「Edges 要自建调度器」。这和 `user_disagreement_llm` 里的「理解偏差」是同一类问题，但一直没做成评测题。
- 例程漏检，复盘没人检查。AI 资讯例程漏掉了 Claude Research 一篇讲 memory 的文章；另有一张卡是增加复盘的复盘，让 badcase 能进 eval 和回归。助手把这张卡看成把任务卡里的失败变成评测题的入口。
- 旧记忆带偏，还只是假设。记忆查询 Dropout 担心检索会被旧偏好锚住；行为类记忆和项目知识分开，则担心换了模型后，行为类记忆反而起反作用。两个都没做实验。
- 工作流和路径不一致。本地改完没 push 导致 compose 同步不上；各模块对显式路径的规则也不统一。

助手说明有几类没找到具体事故卡：违反硬约束（例如直推公开仓 main、改了 `posts/`、多个 Agent 共用一个工作树）、编造内容、没走 grill 或 plan 导致失败。这几类在任务卡里只是写在规则和完成标准里，不能当成已经发生过的失败。两边合起来看：评测测到的主要是「找记忆」和「用记忆」；任务卡记下的却大多是环境、接入、理解偏差这些评测完全没覆盖的东西。助手再次提议把这些卡转成一份失败模式分类，再给每一类配一两道回归题的草稿，放进 `.harness/evaluation/` 并走 PR。用户没有采纳，转而问哪些讲出来会显得扎实。

### 17:46 哪些结论经得起追问

助手的答复是：真正加分的不是把失败清单念一遍，而是能讲清楚测了什么、没测什么、哪个结论站得住。当时点名最经得起追问的是：先否决了全文注入这种看起来有效的方案（质量上升，但输入 token 中位数多了 246%）；分层记忆在真实集上并不明显更好（recall@5 为 54.1% 对 52.4%，置信区间跨零），不能把「做了分层」本身当成果；把「没找到」和「找到了却没用」拆开了，指标不只看最终对错；先修评测再信分数（pi 跑出被测仓库副本造成污染后加了沙箱；裁判拿不到上一条回复就记 0，整体异议率不可信）；分得清评测覆盖了什么、任务卡里还有什么没测，并且知道「违反硬约束」「过时记忆带偏」目前没有事故证据，也还没做成回归题。不太建议当已有结论来讲的，是 LoCoMo、MemoryBench 那两次冒烟，以及还没跑的 Dropout、skills 回归，因为它们更像计划或对照实验，经不起对样本量、以及是不是测了 Edges 本身的追问。助手提议按「问题、实验、结果、因此改了什么」压成一段 90 秒口述稿，用户没有再回，对话结束。

## 结果

当场整理出了「评测里能拿出证据的五类」和「任务卡里大约二十张相关卡的类型对照」，以及哪些还不能写成已发现的失败模式。没有写成评测目录下的分类页，没有配回归题草稿，也没有写成口述稿。私有仓和 Langfuse 仍未读；真实集的逐次日志仍不在公开仓。

## 所学

已证实的评测结论，主要集中在记忆检索和问答：会漏检索或过早停止，会读到却不用，会误检无关记忆，全文注入能提质量但代价不可接受，评测工具本身也会把分数打歪。分层相对于平铺，在那次真实集上没有拿出足够的优势。

任务卡补上的，大多是评测没覆盖的执行链路问题：沙箱和路径、接入和分发、把用户的短确认理解成另一件事、例程漏检。这些可以当成已知缺口或已修事故来用，但还不是评测题。

「违反硬约束」「过时记忆带偏」「没走 grill 或 plan」在当时找不到具体事故卡，或相关实验还没跑，不能写成已经发现的失败。现有评测也还不能支持「项目记忆提升了任务质量」这种说法。

LoCoMo、MemoryBench 的冒烟，以及尚未跑的 Dropout 和 skills 回归，更适合当作计划或对照，不适合当作已经站得住的发现。

## 行动指南

### 主题行动指南

#### 背景

以后要汇报、设计回归，或判断某条记忆相关改动有没有被现有评测撑住时，需要一份能核对证据、并能分清覆盖边界的清单。

#### 核心问题

如何区分「评测已经证实的失败」「任务卡记下但还没测到的缺口」和「只存在于计划或规则里的假设」，避免把未测或未发生的事情写成已发现的失败模式。

#### 核心解决方案

1. 先用已跑完、能指向具体题目或报告的评测结论，再拿任务卡补执行链路上评测没覆盖的类型。不要只用评测清单，或只用任务卡，去代表全部失败模式。当时未另建新的评测体系，因为用户要的是先把已有材料找出来。
2. 把「没找到」和「找到了却没用」分开记录；把「否决某种做法」写成否决的是哪一层（例如否决的是全文注入，不是记忆本身）。
3. 没有事故卡、没有跑过的回归、只有担心而没有实验的条目，留在假设或待办，不写进「已发现」。
4. 在测过「有没有记忆对任务完成率的影响」之前，不把检索和问答上的结果推广成任务质量结论。
5. 若要把任务卡里的失败做成回归题，优先从已经发生、且评测还没覆盖的类型入手，例如理解偏差、接入其实没接上、例程漏检。助手当时提议直接写成分类页并配题，用户没有采纳，本篇只保留这条选用顺序，不代替那次未做的落页。

#### 验收标准

- 能按证据来源说出评测五类和任务卡主要类型，并且不把两边混成同一组已测结果。
- 能明确指出至少两类当时不能写成已发现失败模式的条目，以及理由。
- 能说明全文注入被否决的是成本，以及分层在真实集上为什么还不能称为明显更好。
- 引用真实集数字时，能同时说明逐次日志不在公开仓，只能用汇总数字。

### 细节与其他

#### 若只想引用记忆检索的数字

则：真实集 recall@5 用 54.1%（分层）对 52.4%（平铺），并注明这是 Harbor 真实记忆消融的汇总，且置信区间跨零。不要把合成集里的个案（例如「食盒」题、M08/M09/M11）说成真实集的统计结果。

#### 若要讲评测工具不可信的例子

则：优先用 `user_disagreement_llm` 在缺少上一条助手回复时直接记 0，以及 pi 跑出被测仓库副本造成污染这两件已经发生的事。不要把「同一个模型给自己打分、样本小、AI 标注」这些方法学问题，说成某一道题的具体事故。

#### 若有人把「违反硬约束」或「过时记忆带偏」当成已发现失败

则：指出当时没有对应事故卡，或 10-25 那轮没有出现带偏；skills 和 Agent 回归、Dropout 相关实验当时还没跑。

#### 若要把这份清单再做成评测页或回归题

则：这是当时助手提议、用户未采纳的步骤，需要另行确认落点和题量后再做。不要默认同一篇笔记已经完成那项工作。当时提议的路径是 `.harness/evaluation/`，与当前仓库里评估报告所在的 `evaluations/` 也不一定是同一处，落点要重新核对。
