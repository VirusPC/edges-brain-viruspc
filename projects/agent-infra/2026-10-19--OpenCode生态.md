## 结论

1. 生态主体是 **B 类（GUI / 外壳）**：OpenWork、OpenChamber 已破万星。**A 类（沙箱里无头跑）**数量少但商业意义大：Kortix、Ramp Inspect、background-agents。
2. A 类的标准架构：沙箱（Modal / Daytona / E2B / Vercel）里跑 `opencode serve`，外层用 HTTP / SDK 驱动，Cloudflare DO 做控制面。background-agents 是可以直接参考的开源实现。
3. 真正的硬分叉基本只有 Kilo Code；大多数项目选择**包装 + 锁版本**。
4. 最大的短期风险是 **v1 → v2 迁移**：新项目直接面向 v2 API 设计，并锁定版本。

分类：**A** 把原版 CLI / server 无头包进沙箱或云端；**B** 基于 server / SDK 的桌面、IDE、GUI、聊天外壳；**C** 硬分叉；**D** 插件生态。

## 为什么选 OpenCode

1. **server-first + 类型化 SDK + 插件系统**：TUI、桌面端都只是客户端，容易造新客户端。
2. **不绑定模型**：任意 provider，还能接 ChatGPT、Gemini、Copilot 订阅。
3. **MIT**：允许硬分叉商用（Kilo）。
4. **ACP**：可被 OpenHands、Zed 等 ACP 宿主调用。
5. 社区规模大（217k★），源码可读。

## 风险

- **2.0 大版本迁移**：OpenWork 为此同时维护 v1 / v2 双引擎和聊天记录迁移，OpenChamber 也有 v2 相关代码，说明 server API 和存储格式有破坏性变化。包装层要锁版本（参考 Kilo 的 `.opencode-version`）。
- **发版极快**：直接追 latest 容易遇到回归。
- **仓库迁移和重名**：sst → anomalyco；还和已归档的 opencode-ai/opencode（Crush）重名。
- **非 JS SDK 落后**。
- **第三方订阅认证插件有合规风险**：antigravity-auth 已归档（原因未核实 ⚠️）。
- 部分包装项目已停更（VibeKit），或许可证不明（OpenWork、Suna 都是 NOASSERTION），引用前单独看 LICENSE。
