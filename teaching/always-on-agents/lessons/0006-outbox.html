Outbox

后台把结果交给用户，而不是把逐步推理全部推过去。多数情况一个 send 工具就够；要控制节奏或从错误里恢复时，再做正式 outbox。

第 6 课 · 约 10 分钟 · 主来源：William Hu · Building always-on agents

学完这一课，你能做到

看到一次已经做完的 run，能判断它属于三种结束方式中的哪一种。你能说明什么时候一个 send 工具就够、什么时候才值得做正式 outbox，也知道 dispatcher 做什么，以及消息该先偏安静，再用 evals 找平衡。

后台给出结果，而不是全过程

多数普通 Agent 会把回复随着生成过程流式推给用户，让人跟着看模型怎样推理、调用工具、写下答案。always-on agent 则把大部分工作放在后台。用户得到的是结果，加上少量细节，而不是完整的逐步拆解。 原文 · Outbox

一次 run 的三种结束方式

一次 run 可以用下面三种方式之一结束。 原文 · Outbox

  1. 把一条消息写入 outbox准备把结果交给用户。 原文 · Outbox
  2. 判断这次什么也不必送不是每一次醒来都必须打扰用户。 原文 · Outbox
  3. 发出一次 deferred tool call请人批准，或请人再补一句。第 5 课已经走完这条往返。 原文 · Outbox

send 工具，还是正式 outbox

多数 always-on agent 用一个 send 工具就够：它把消息直接送给用户。只有在你想控制发送的节奏，或让 Agent 能从投递错误里恢复时，才需要一份正式的 outbox。 原文 · Outbox

正式 outbox 是一张待发消息表，和 event inbox 相对。对面还有一个 dispatcher，通常是一个后台服务，和 inbox 一侧的 worker 相对。dispatcher 读取待发消息，决定交哪些，再送给用户。 原文 · Outbox

一次 deferred tool call 提出的请求，既可以经过 outbox，也可以直接显示在界面上。原文把这两种都写成可以，并没有规定必须走哪一条。 原文 · Outbox

该发多少：先偏安静，再用 evals 找平衡

投递之外，还要调整 Agent 发送消息的数量。发太多会变得吵闹；发太少又会漏掉用户需要知道的事。原文建议用 evals 来找到平衡。 原文 · Outbox

实际中，更好的做法是让 Agent 先偏安静，再逐渐多获得一些用户的注意。 原文 · Outbox

合上原文，60 秒这样讲

「always-on 把大部分工作放在后台，用户看到的是结果和少量细节，而不是逐步推理。一次 run 有三种结束方式：写入 outbox、判断什么也不必送，或发出 deferred tool call。多数情况一个直接送达的 send 工具就够；只有需要控制节奏，或从投递错误里恢复时，才做正式 outbox。正式 outbox 和 dispatcher，分别相当于 inbox 和 worker。deferred tool call 的请求可以走 outbox，也可以直接出现在界面上。发太多会吵，发太少会漏，用 evals 找平衡，并且先偏安静。」
