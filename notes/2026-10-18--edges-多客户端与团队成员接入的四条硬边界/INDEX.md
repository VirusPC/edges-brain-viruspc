# Edges 多客户端与团队成员接入的四条硬边界

## 背景

2026-10-18 凌晨（Asia/Shanghai），用户 peng cheng 先让 Grok Bot 把 edges CLI 发成 npm 包（已拆成任务卡与实现 PR），随后问：「要开始考虑多客户端、团队成员的接入问题了？」并补了一句「今天很多事都是围绕这个在聊」。以下是助手当时的判断，用户认同主线，但四条边界尚未逐条拍板。

## 主线

Edges 正在从「一个人用的外脑」变成「多个客户端都能接进来的入口」。近几天的话题都在为这件事铺路：

- ChatGPT / Claude 等外部客户端想直连 edges（connector 方向）；
- connector 服务端要在自有小主机上跑；
- CLI 准备发到 npm，让别的机器一行命令装上；
- 本机 Grok Bot 与云端 Agent 共用同一套仓库与记忆。

单人、单助手时，「用户本人充当 harness」还能兜住；一旦多客户端或团队成员接入，缺的就是身份、权限、写盘边界和冲突策略。

## 先定四条硬边界，不先写大架构

1. **谁能写**：个人凭据与团队凭据分开，各自的写权限范围要清楚。
2. **写到哪**：内容目录与 `main` 分开；外部客户端的写入一律只开 PR，不直推（与现有「main 受保护、看板也走 PR」一致）。
3. **输入是否可信**：外部聊天正文、网页内容一律当不可信数据，不能直接驱动写盘或执行。
4. **并发怎么串行**：多个客户端同时改同一篇笔记或同一张任务卡时，靠什么排队或检测冲突（例如每任务独立分支 + PR 合并时解决）。

## 风险对比

- npm 发包解决的是「别人能装 CLI」，影响面是只读工具分发。
- 多客户端接入解决的是「别人能改你的外脑」，风险更高，应先用小范围试点把上面四条磨清楚，再决定 connector 要不要对团队开放。
