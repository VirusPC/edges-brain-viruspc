睡醒循环与五个原语

always-on 只是用户体验：Agent 大半时间在睡，一次 run 怎么经过五个原语再睡回去。

第 1 课 · 约 10 分钟 · 主来源：William Hu · Building always-on agents

学完这一课，你能做到

不看原文，用 60 秒讲清：Agent 大半时间在睡；每次醒来是一次 run，发生在一份 session 里；事件先进入 event inbox，再由 worker 开跑。你还能一眼说出五个原语各自挡住什么失败，画出一次 deferred tool call 的往返，并记得 memory 只存查不回来的东西，以及那四类记忆。这是吃透这篇原文的骨架。

always-on 只是体验

原文开头就把「一直开着」说成体验，而不是运行方式：An always-on agent is not actually “always on.” This is just a description of the user experience. 真正发生的是：Agent 大半时间在睡，偶尔醒来干一段活，再睡回去。循环可以一直转，用户才觉得它一直在。 原文 · The cycle behind the always-on agent

这类 Agent 仍然走和其他 Agent 相同的核心循环。不一样的是周围的架构：由一组原语决定它何时醒来、两次 run 之间留下什么、以及做完的结果怎样到达用户。原文把这种形态概括成 stateful 且 proactive：能跨多次 session 管住上下文，也能在没有人盯着的时候行动。 原文开篇 底下的模型循环并没有换一套。换的是叫醒它、记住它、约束它、把结果送出去的那一层。

run 和 session

每一次醒来干活，叫做一次 run：Agent 收到一个事件，把活做完，再把这次发生的事存下来。run 发生在一份 session 里。session 是消息和工具调用的 transcript。run 一结束，Agent 就睡回去，这个循环再重复：睡、醒、存、再睡。 原文 · The cycle behind the always-on agent

怎么决定续上旧 session 还是新开一份？原文写得很具体：Events that continue earlier work, such as a reply from the user, resume an existing session, while everything else starts a new session. 也就是说，用户答复这类「接着先前工作」的事件会续上已有 session；其余通常新开。 原文 · Event inbox

五个原语一眼看完

围着这个循环的，是五个核心原语：event inbox、timers、memory、permissions、outbox。先记住各自挡住什么，再看一个事件怎么把它们串起来。

原语挡住什么，或原文给它的位置
event inbox来源若直接叫 Agent：同时到达的事件会争出两次 run；崩溃可能把事件弄丢。 原文 · Event inbox
timers和 inbox 一起，让 Agent 能主动醒来。timer 自己不开 run；未到期的事也不该进 inbox，因为 inbox 只放已经能做的事件。 原文 · Timers
memory接住多次互不相连的 run 之间的连续性。规则是只存查不回来的东西；已在别的系统里的，存指针。 原文 · Memory
permissions原文说这里风险最高：一次 run 握着用户的访问权，而且本来就是无人值守。每次工具调用要决定自己继续、拦住，还是等人批准。 原文 · Permissions
outbox后台工作不把逐步推理全推给用户，只给结果和少量细节。正式 outbox 用于控制发送节奏，以及从投递错误里恢复；多数情况一个 send 工具就够。发太多会吵，发太少会漏。 原文 · Outbox

一个事件怎么走完一圈

原文在「How everything fits together」里把协作写成下面这条路径。你可以按这个顺序在图 2 上指。

  1. 事件先进入 event inbox 来源可能是用户消息、webhook、后台任务，或到期的 timer。不要让来源直接叫 Agent。handler 把事件写入这份耐用列表，并叫醒 worker。 原文 · Event inbox
  2. 唯一的 worker 开一次 run 一个 inbox 同一时间只应有一个在工作的 worker，以免两次 run 互相覆盖。worker 读出待办，在新的或已有的 session 里叫醒 Agent，等这次 run 结束，再把对应事件标成完成。 原文 · Event inbox / How everything fits together
  3. 先读 memory，在 permissions 内行动，再写回 memory 开头先加载 context overhead（system prompt、工具定义、memory 文件）作为基线。行动时走 credential proxy，必要时用 auto mode 拦住危险动作，或用 deferred tool call 请人拍板。学到的东西写回 memory。 原文 · Memory / Permissions
  4. run 以三种方式之一结束 把一条消息推进 outbox；判断这次什么也不必送；或发出一次 deferred tool call。若写入了 outbox，由 dispatcher 决定交哪些给用户。用户若答复，答复再作为事件回到 inbox。一次 run 也可以给自己设一个 timer，到期后同样先变成 inbox 里的事件。 原文 · Outbox / How everything fits together

这一圈里必须先记住的三处细节

memory 只存查不回来的东西。 四类是：user instructions（单独文件，每次开头都加载，因为用户不总在场）；user notes（角色、偏好、纠正，变多后拆文件，开头只加载索引）；past messages（避免把已经说过的话再讲一遍）；task progress（每个进行中的任务一份进度，新 run 接着上次）。已有 session 还会带回先前 run 里的消息和工具调用；新 session 只有 context overhead 加上触发事件。session 太长就 compact 或新开，两种都会丢细节，所以途中要把该留的写入 memory。 原文 · Memory / Inside the context window 原文还提到 dreaming：在 run 之外回顾过去的 session，整理 memory。本课不展开，补充阅读见 The components of agent memory。

deferred tool call 是一次完整往返，不是把当前 run 挂着空等。 调用被推迟时，这次 run 结束，session 保存在调用做到一半的地方；请求交给用户；答复作为事件回到 inbox；新的 run 接着原来的 session。等待期间，worker 仍可拾起别的事件。 原文 · Permissions · Deferred tool calls

inbox 是真相来源，worker 要尽快确认、且同时只有一个。 handler 应很快确认收到（有些 webhook 会把慢响应当成失败）；提示词注入这类更深的检查放到 run 里做。worker 醒来应先从 inbox 拉最新待办——这样它若中途死了，新的 worker 可以拿同一事件重试。积压的事件可以批次合并。run 做到一半又来了新事件，原文并列了三种处理：推到下一次、并进当前这次，或打断重来，没有推荐哪一种。 原文 · Event inbox

合上原文，60 秒这样讲

「这篇原文说，always-on 只是用户体验，不是进程一直醒着。Agent 大半时间在睡。一次醒来叫做 run：收到事件，把活做完，把这次发生的事存下来，再睡回去。run 发生在一份 session 里，也就是消息和工具调用的 transcript。用户答复会续上已有 session，别的事件通常新开一份。围着这个循环的是五个原语。所有来源先写进 event inbox，由唯一的 worker 取出并开 run，这样才不会同时抢跑，崩溃时也不容易把事件弄丢。timer 自己不开 run，由 scheduler 到期后写成 inbox 里的事件，Agent 才能主动跟进，未到期的事也不会提前挤进 inbox。memory 只存查不回来的东西，用来跨多次断裂的 run 保持连续，分成 user instructions、user notes、past messages 和 task progress。permissions 处理无人值守时的风险：凭证走环境外的 credential proxy，危险动作可用 auto mode 拦住，要人拍板时用 deferred tool call——结束这次 run 并保存 session，等人的答复作为新事件再续上。outbox 把结果交给用户，而不是把逐步推理全推过去；正式的 outbox 主要用于控制节奏和从投递错误里恢复。每次 run 都很短，循环可以一直转，这才让人觉得它一直在。」
