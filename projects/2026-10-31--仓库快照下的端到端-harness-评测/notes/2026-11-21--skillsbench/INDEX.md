# 《SkillsBench》论文十问

## 这篇笔记回答什么

把可复用的专家操作流程打包成 Skill 交给 Agent，究竟能带来多少增益，什么时候反而有害？作者的 v4 实验表明，在筛选过的专业终端任务上，人工精选 Skills 的平均得分由 33.9% 升至 50.5%，增加 16.6 个百分点，但不是所有任务都受益（表 2、§5.1.3）。我的判断是：论文有力支持“在特定 Agent 栈上，高质量程序性知识包值得实测”。它还不足以证明任意 Skill 都有效，也不足以证明文档越短必然越好，或自动生成 Skills 普遍无用。

**Skill（技能包）**是针对一类任务的文件系统程序性知识包。必需文件是 `SKILL.md`，可以附带脚本、模板和参考材料。它不修改模型权重，也不等于单独一个可执行工具（§2、附录 M.1）。**Harness（执行框架）**连接语言模型与环境，负责工具调用、状态管理，以及发现和载入 Skills（§2）。**Curated Skills** 是经人工筛选的专家技能包。**Self-generated Skills** 是 Agent 先生成、再交给求解会话使用的技能包（§4、附录 D.6）。**Oracle** 是证明任务可解的参考方案。**Verifier** 是对产物运行断言的程序化验证器。参考答案和测试不向求解 Agent 开放（图 3、附录 B、M）。百分点是两个条件的分数直接相减。归一化增益 `g = (有技能 − 无技能) / (1 − 无技能)`，表示填补原有性能缺口的比例，不是普通相对增长率（§4，式 1）。

## 论文十问

### Q1. 论文试图解决什么问题？

论文要把“Agent 本身会不会完成任务”和“加入 Skill 是否真的有帮助”分开测量，回答同一模型与执行框架在有无技能包时的性能差异（§1）。作者指出，已有综合 Agent 基准常把模型、框架和外部增强混成一个完成分数，不能直接回答部署一个技能包是否值得（§1、§7）。SkillsBench 因而把技能包作为独立评测对象，在相同任务环境中做有技能和无技能的配对评测（§3–4）。

### Q2. 这是否是一个新的问题？

利用外部知识、工具和程序指导来改善 Agent，并不是新问题。论文也把 CoALA、Voyager、检索增强和工具使用列为前驱（§7）。作者主张的新意，是把符合 Agent Skills 文件规范、可以跨模型复用的程序包作为一等评测制品，并系统测量它相对无技能条件的净增益（§1–2、§7）。配对比较本身已有先例。因此“首个”应限定为作者宣称的这种 Skills 专门基准，不能扩张成第一次研究 Agent 增强。

### Q3. 这篇文章要验证一个什么科学假设？

论文是基准构建和经验研究，没有提出单一的形式化假说。核心可检验命题是：独立编写、面向一类任务的程序性知识，能够在不改模型权重的情况下提升专家型任务表现（§1、§3）。进一步的经验命题是，增益依赖模型、框架、领域和技能包设计，不是一个通用常数（§5–6）。自动生成条件检验的是“Agent 临时为自己编写技能包，能否替代专家精选包”，不是所有可能的技能学习算法（附录 D.6）。

### Q4. 有哪些相关研究？如何归类？谁是这一课题在领域内值得关注的研究员？

论文把相关工作分为端到端 Agent 基准、程序性增强与工具使用，以及 Skills 生态和评测方法。端到端基准包括 Terminal-Bench、SWE-bench、AgentBench，以及网页和图形界面基准。程序性增强包括 CoALA、Voyager、ReAct、Reflexion、RAG、Toolformer 和 DSPy（§7、参考文献）。Agent Skills、MCP 规范，以及 Claude Code、Codex、Gemini CLI，属于技能包规范和执行基础设施，不应与测量数据集混为一谈（§7）。可以从通讯作者 Xiangyi Li 跟踪本项目，也可以沿论文引用阅读 Carlos E. Jimenez 等人的 SWE-bench、Theodore Sumers 等人的 CoALA、Guanzhi Wang 等人的 Voyager。这些是依据本文引用给出的阅读入口，不是论文提供的研究员声望排名。

### Q5. 论文中提到的解决方案之关键是什么？

关键是固定同一组模型与框架、任务数据、容器和验证器，只改变任务技能包是否可访问，从而把技能增益定义为两个条件的得分差（图 3、§4、附录 N）。为了避免把答案藏进 Skill，作者要求技能包适用于任务类别，并且独立于具体基准题编写。他们检查实例专属路径、常数、预期输出和解题命令等泄漏。任务说明不直接点名该用哪个 Skill（§3、附录 M.7）。每个任务打包说明、环境、参考解和程序验证器。Agent 必须通过框架自行发现和使用技能，而不是拿到一份已经标好答案的提示词（图 3、附录 B–C）。

### Q6. 论文中的实验是如何设计的？

主实验在 87 项任务上比较无技能与精选技能，覆盖 OpenHands、Claude Code、Codex CLI、Gemini CLI 四种框架的 18 个模型与框架配置。每个任务、条件和配置选取三次公开试验，共 9,396 个结果槽位（§4、附录 D.1、表 5）。评分先在每项任务内部平均验证奖励，再对固定任务清单等权平均，同时报告绝对差和归一化增益。奖励允许位于 0 到 1 之间，不能直接把主表分数解读成严格的全题成功比例（附录 N.4、表 16）。程序验证替代了语言模型裁判。未评分、陈旧或限流轨迹被审计后重跑。超时只在没有健康替代结果时作为失败补位（§4、附录 N.3）。另外还有三个专用框架配置的自生成技能诊断，以及按技能数量、文档长度、领域和失败轨迹做的分析。自生成条件不计入主实验汇总（附录 D.6、F、J）。

### Q7. 用于定量评估的数据集是什么？代码有没有开源？

定量数据集就是 SkillsBench 本身。当前评测清单含 87 项任务、8 个领域，覆盖软件、工业与物理系统、自然科学、办公室、金融、数学与运筹、安全和媒体内容。它不是只有问答文本的考试题集（§3、图 4、表 19）。这些任务由 142 名贡献者提交的 400 个候选任务筛选而来，准入要求包括真实工作流、可执行参考解和程序化检查（图 2、§3、附录 B、M）。作者声明已经开放基准、BenchFlow 框架以及公开轨迹和结果。独立检索可以定位 [benchflow-ai/skillsbench](https://github.com/benchflow-ai/skillsbench) 和 [benchflow/skillsbench 数据集](https://huggingface.co/datasets/benchflow/skillsbench)。本次没有运行代码或复现分数（§1、§8、附录 L）。附录 A 的 2,014,000 条来源分区技能记录是生态调查快照，而且只在各来源内部去重。它不是主实验使用了两百万个技能，也不是跨来源去重后的唯一技能数量（附录 A.1）。

### Q8. 论文中的实验及结果有没有很好地支持需要验证的科学假设？

我的评价是，对“精选知识包在该任务分布上能提升表现”的支持较强。18 个配置的总体差值都为正，平均由 33.9% 到 50.5%，但 87 项任务中有 13 项任务的平均差值为负（表 2、§5.1.3）。任务准入本来就要求能体现技能效用，低区分度任务会被排除，选用的又是高质量技能包。因此这个均值不能无偏代表任意日常任务和公共技能库（§3、附录 A.4、B.5、B.10）。把更多文本或额外脚本提供给模型，本身也是干预。论文承认还缺少等长度随机文本、无关材料或只检索文档等对照，所以还不能把全部增益归因于 Skill 的组织形式（§6.1）。数量和长度结果来自不同任务分组，不是同一任务随机增减模块的严格因果实验。自生成条件又混入了发现失败、创建与求解互相干扰，以及配置差别，不能据此认定模型天生不能生成有效技能（表 8–9、附录 D.6）。主图采用二项 Wald 区间，而不是针对任务聚类和有无技能差值的配对重采样区间。对泛化和差异显著性的论证仍可以加强（附录 G）。

### Q9. 这篇论文到底有什么贡献？

作者的贡献可以分为可复用任务资产、配对评测协议和经验诊断。它不只给 Agent 排名，还让“这个外部知识包带来的增益是多少”成为可以单独报告的量（§1、§8）。我认为最有价值的是把独立编写、泄漏检查、可执行环境和公开轨迹组合起来，使技能收益和失败更容易审计。论文还给出有操作价值的失败分类：流程过重、压过模型原有的更强策略、引入难以调试的求解器。这提示技能作者需要适用边界和轻量回退（§5.1.3、附录 F.3）。“短包优于大全”和“小模型可以替代大模型”应视为当前任务与配置中的经验现象，不能上升为无条件的设计定律或规模定律（§5.1.3、表 8–9）。

### Q10. 下一步呢？有什么工作可以继续深入？

作者建议加入等长度对照，拆分步骤、示例和代码资源各自的贡献，扩展到图形界面、多模态和更真实的技能选择，并研究多个技能组合时的相助与冲突（§6.1）。我的优先建议是先保留一组不按技能增益筛选的新任务，冻结后再做盲测，并在同一任务上随机比较精简版、完整版、纯参考资料版和带脚本版。自生成实验应统一创建成本、推理档位、文件状态和原生发现机制，先确认生成包确实被载入，再分别衡量“会不会写”和“写出来有没有用”（附录 D.6）。部署时则应以具体的模型与框架为单位报告收益、成本和负迁移，并验证作者提出的复杂度契约：声明预期工具和 token 成本、适用条件，以及轻量回退路径（§6）。

## 证据边界

1. 本笔记的数字全部来自 v4。当前是 87 项任务、8 个领域、18 个配置（§3–4、表 2）。不能把其他版本的任务数或模型榜单与这里的增益拼接。
2. 16.6 是百分点，不是“提升 16.6%”。25.5% 是逐配置计算后再做宏平均的归一化增益，也不是普通相对提升率（表 2 注释、§4）。
3. 全部配置的总体均值上升，不意味着全部任务上升。13 项任务的平均增益为负（§5.1.3）。也不能用前十项最受益任务的正 67.0 个百分点，替代总体的正 16.6 个百分点（表 13）。
4. 表 8 中，一个技能、二至三个技能、至少四个技能的分组增益分别为正 18.0、正 19.0、正 10.1 个百分点。表 9 中最详尽文档的分组只有 5 项任务。这些都是跨任务分组统计，不是等难度的随机试验，因此还没有证明技能越多越好，也没有证明越短越好。
5. 表 6 的三个自生成配置确实低于各自的无技能基线。附录 D.6 明确披露：部分生成包没有被发现，Claude Code 的创建与求解共享沙盒，自生成推理档位也不同。这衡量的是具体的生成、发现和求解管线。
6. 表 15 和附录 L.3 显示，token 与费用有升有降，而且部分配置没有定价记录。不能从总体表现提升推出全部配置都更便宜。
7. 附录 B.3 用全部断言通过的二值示例，图 3 却把奖励写成检查通过比例，附录 N.4 又允许连续奖励。表 16 的严格 Solved 比例是无技能 31.3%、精选技能 47.7%，与主表的 33.9%、50.5% 不同。引用主结果时应称“作者主表的任务宏平均得分”，不能宣称相同比例的任务全部成功。本次也没有靠运行代码消除这个口径张力。
