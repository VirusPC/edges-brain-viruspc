# 基于目录的记忆划分：人把上文放进一个大仓库就够

> 日期: 2026-10-11  
> 来源: peng cheng spark（Notes记录员聊天）

【讨论主题】

后面「按目录划分记忆」会非常重要。人可能不必再依赖聊天窗口当长期记忆——把自己的上文（上下文、决策、笔记、任务轨迹）存在一个大仓库里，按目录分区，就够用了。

【主要内容】

(事实与共识)

- 主张：记忆边界跟目录边界对齐；目录即作用域（项目 / 主题 / 私密 / 公开 / 任务看板等），而不是全塞进一份扁平日志或单一 bot memory。
- 终点形态的直觉：一个人一个（或少量）大仓库当外置脑；日常上文写入仓库目录树，agent 与人共用同一套可 diff、可 PR、可检索（按协议）的结构。
- 与已有落点的连续性（不是从零发明）：
  - Edges 已当外置脑：`notes/`、`.edges/tasks/`、`.edges/memory/`、`AGENTS.md`。
  - 类型索引下沉到目录下的 `AGENTS.md`（见下「相关」）。
  - 多 Agent 管理本质是上下文管理——目录划分是把上下文边界做成人和 agent 都能看见的物理边界。

【认知更新】

(洞察与 Edge 雏形)

- 聊天 transcript 是易挥发的上文；目录树是可版本化、可交接、可审计的上文。长期竞争力可能在「仓库布局约定」而不在「某个产品记住了你说过什么」。
- 「一个大仓库就够」不等于「一个目录乱炖」——价值在分区：读什么、不读什么、对谁可见，由路径表达；否则大仓库会变成第二个不可推理的上下文黑洞。
- 与「多 Agent = 上下文管理」互证：Agent 边界 ≈ 上下文边界 ≈ 目录边界；拆任务时先定目录/作用域，再定谁读写。

【行动指南】

(决策与后续动作)

- 新沉淀默认先问落哪个目录（notes / tasks / `.edges/memory/` 类型目录 / private），少写进仅存在于 bot 侧的共享 memory。
- 推目录约定时，优先复用并强化已有 Edges 布局与 `AGENTS.md` 索引，而不是再开一套平行「记忆产品」。
- 若要升格成协议：可交给 Agent Memory 专家或项目 memory 系列，明确「目录 = 记忆作用域」的读写与检索规则；本笔记先作 spark，未 grill。

【补充说明】

开放点（未拍板）：几个仓 vs 一个仓多分目录；私密如何与公开同树隔离；agent 默认装载哪些目录、何时升载；目录划分与 embedding/检索的关系。
