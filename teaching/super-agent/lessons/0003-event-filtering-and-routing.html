事件过滤与路由

五个模块里，事件驱动用来实现「主动」。第 3 节先问四个递进的问题；这一课只解决前两个：如何过滤大量噪音，以及如何把事件送给对的 Worker。

第 3 课 · 约 10 分钟 · 主来源：DeepSeek Harness 团队 · Super-agent 设计探索（第 3.1–3.2 节）

学完这一课，你能做到

能讲清：主动性首先来自把主要输入从「人在 Session 里逐条键入」改成环境里的 Trigger；为什么不能对每个事件都先叫大模型；程序层与语义层怎样分工；什么是 Thread；已订阅的后续事件为什么要直通 Worker，而 Router 仍只分派尚未被订阅的新事件；以及订阅为什么是多对多。

先改驱动方式：输入变成 Trigger

要让 Super-agent 具备主动性，首先需要改变系统的驱动方式。驱动 Agent 的主要输入不再是人类在 Session 中逐条键入的提示词，而是环境中的半结构化事件。在 Super-agent 中，群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果等环境事件被称为 Trigger。通过监听并响应 Trigger，Agent 不必再像单 Session 模式下那样，等人类下达指令才被动执行一次。 原文 · 第 3 节

围绕一条环境事件从进入到处理的生命周期，原文依次讨论四个递进的问题。这一课覆盖前两个：如何用程序与模型结合的两级策略过滤大量噪音（3.1），以及如何通过订阅与直通把事件路由给 Worker（3.2）。后两个——怎样组织上下文、怎样提前行动——留给第 4 课。

先过滤：绝大多数事件并不需要介入

接入真实的群聊与代码平台后，环境事件流呈现出显著的「高噪音、低触发率」特征，绝大多数日常消息并不需要 Agent 介入。如果对每个事件都调用大模型从头判断，延迟和算力成本都会难以承受。原文借鉴计算机系统里的 Fast Path / Slow Path：大模型推理是一条灵活但高成本的 Slow Path；把已经明确且稳定的高频判断固化为确定性代码，则构成低延迟、低成本的 Fast Path。 原文 · 第 3.1 节

因此，事件进入系统后的第一步是过滤：在调用大模型之前，先用确定性策略筛除噪音，只把需要语义理解的候选事件交给模型判断。两级机制是：

  • 程序层策略（Fast Path）：针对事件来源、群组范围、用户或机器人白名单等确定性条件，直接用代码做快速准入检查。例如对不同来源分别设置「仅响应明确请求」「作为候选事件」或「直接忽略」，在调用模型前滤除大部分无关消息。
  • 语义层策略（Slow Path）：通过程序层准入的候选事件交给 LLM，由它根据用提示词编写的策略和上下文判断是否需要行动。语义层同时是面向人类的自然语言扩展点，方便随时通过提示词开关或新增策略。

再路由：已有归属的事件不要再劳烦 Router

第 2 课的全局 Router 层负责维持跨信道的连续性，但如果已分配任务的每个后续事件仍需经由 Router 层转发，这一全局节点依然会承受大量负载，推高系统的响应延迟。因此，Fast / Slow Path 同样适用于过滤后的事件路由：全局 Router 层只负责新任务的冷启动与跨任务协调，已确定归属关系的后续事件由程序直接发往对应的 Worker 会话，无需再经 Router 层转发。 原文 · 第 3.2 节

在实际工作流中，同一个 GitHub Pull Request、同一个 IM 话题或同一封往来邮件串下的连续事件构成一条事件流，即 Thread。Router 层根据某个 Thread 的初始事件创建 Worker Session 后，该 Worker 会直接订阅对应的 Thread，于是事件路由分成两条路径：

  • 已订阅（Fast Path）：同一 Thread 下的后续事件由程序直通已订阅的 Worker，无需 Router 层再次调用工具转发。若新事件超出了当前任务的范围，Worker 也可取消订阅，或交回 Router 层重新分派。
  • 未订阅（Slow Path）：Router 层仍可观测所有事件以掌握全局状态，但仅负责判断和分派尚未被订阅的新事件。

此外，Thread 与 Worker 之间的订阅是多对多的关系。一个 Worker 可以同时订阅多个相关的 Thread，同一个 Thread 也可以被多个 Worker 订阅。当多个 Worker 在同一个工作环境或讨论中发生交集时，该 Thread 下的新事件会同时直通给所有订阅它的 Worker，使它们无需点对点通信，也有机会获知彼此的操作并自行解决冲突。而在输出侧，Worker 仍将关键结论汇报给 Router 层，由 Router 层统一向用户回复并同步全局记忆。

合上原文，60 秒这样讲

「主动性先来自改驱动方式：主要输入不再是人在 Session 里逐条键入的提示词，而是环境里的半结构化事件，原文叫 Trigger。真实群聊和代码平台里的事件高噪音、低触发率，不能对每条都先叫大模型。先用程序层策略做 Fast Path，按来源、群组、白名单等确定性条件滤掉大部分无关消息；通过的候选再交给 LLM，用提示词写的策略做 Slow Path，同时把语义层留成可以随时增删规则的自然语言扩展点。过滤之后还要路由。如果已分配任务的每个后续事件都再经 Router 转发，全局节点仍会拥塞。同一个 PR、同一个 IM 话题或同一封邮件串构成一条 Thread。Router 用 Thread 的初始事件创建 Worker 并让它订阅后，后续事件由程序直通该 Worker；Router 仍可观测全部事件，但只分派尚未被订阅的新事件。订阅是多对多的。Worker 的对外回复仍然交给 Router 统一说出。」
