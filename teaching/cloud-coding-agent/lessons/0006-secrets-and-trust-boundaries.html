密钥与信任边界

最后一课。先画出整个系统里“谁信任谁”，再跟着每一把秘密从生到死走一遍，看它在哪一步越过了不该越过的线。最后把六课合成一张总图、一段两分钟的面试陈述。

学完这一课，你能做到

画出这个产品的信任边界图，说清每条线上流动的是什么；讲出 GitHub 令牌、用户 API key、平台密钥、MCP secret 各自怎么加密、存在哪、怎么被送进 Sandbox、最后留在哪；指出“临时改写 process.env”在多租户下为什么危险；说出认证、授权、速率限制各自的漏洞；并且能不看笔记，用两分钟把六课的整套架构讲完。

先看全图：七个部件，十条线

第 1 课的六个部件再加上 MCP 服务器，就是全部。这一次不看“步骤”，而看“信任”：哪一块被当成自己人，哪一块必须当成可能已经被攻破。

一句话概括这张图：真正的信任边界在服务器和 Sandbox 之间（线 ③），而模板把几乎所有能花钱、能改代码的秘密都送过了这条线。第 4 课说“笼子就是 Sandbox”，这一课要补上后半句：笼子挡住的是 Agent 碰宿主机，挡不住 Agent 带着笼子里的钥匙从开着的门（线 ⑤–⑧）走出去。 好的一面也要说：几把“总钥匙”（ENCRYPTION_KEY、JWE_SECRET、SANDBOX_VERCEL_TOKEN、GitHub client secret）确实只在服务器上用，SANDBOX_VERCEL_TOKEN 只在调 Sandbox 接口时读取（creation.ts L83–L85）。GitHub 令牌也只发往 github.com：拼克隆地址时检查了主机名（config.ts L76–L80）。

每类秘密的一生

先说两把“总钥匙”，因为后面每一把秘密都靠它们保护：

保护什么算法密钥来源值得挑的地方
登录会话（浏览器 cookie）JWE，alg: 'dir' + enc: 'A256GCM'（直接用共享密钥做 AES-GCM 加密，带完整性校验）lib/jwe/encrypt.ts L12–L15环境变量 JWE_SECRET，base64 编码会话里只有创建时间、登录方式和用户信息（含内部用户 id）lib/session/types.ts L12–L16。所以谁拿到 JWE_SECRET，谁就能给任意用户 id 造一张 cookie，冒充任何人。
数据库里的令牌、API key、MCP secretAES-256-CBC，每次随机 16 字节 IV，存成“IV:密文”的十六进制 lib/crypto.ts L20–L35环境变量 ENCRYPTION_KEY，必须是 64 个十六进制字符（32 字节）lib/crypto.ts L6–L18全站一把密钥。README 却写“using per-user encryption”（README.md L357），这是又一处文档和代码不一致。CBC 模式不带完整性校验，密文被改了也发现不了；存储格式里没有“密钥版本号”，按推断换密钥就得把全库重新加密一遍。

一、GitHub OAuth 令牌：从登录一路走进 .git/config

  1. 登录，要的是 repo 范围 服务器 生成随机 state，存进 10 分钟有效的 HttpOnly cookie，然后跳转 GitHub，申请的范围是 repo,read:user,user:email。按 GitHub 文档，repo 是“对公开和私有仓库的完全访问”，还包括组织的一部分资源（Scopes for OAuth apps）。 app/api/auth/signin/github/route.ts L18–L64
  2. 回调，用 client secret 换令牌 服务器 → GitHub 比对 URL 里的 state 和 cookie 里的 state，再带着 GITHUB_CLIENT_SECRET 向 GitHub 换 access token。 app/api/auth/github/callback/route.ts L27–L72
  3. 加密存库 数据库 用 GitHub 登录的人，令牌加密后存进 users.accessToken；用 Vercel 登录、再“连接 GitHub”的人，存进 accounts 表。算法就是上表的 AES-256-CBC。 lib/session/create-github.ts L55–L65 callback/route.ts L145
  4. 提交任务时解密 服务器 在 POST /api/tasks 里、进入 after() 之前取出：先查 accounts，再查 users，解密成明文，作为参数传给后台流程。 app/api/tasks/route.ts L213–L216 lib/github/user-token.ts L21–L57
  5. 写进克隆地址 Sandbox 里 把令牌放进 URL 的用户名、密码写成 x-oauth-basic，然后在 Sandbox 里 git clone --depth 1。这是第 4 课说的第四种走法。 lib/sandbox/config.ts L69–L86 lib/sandbox/creation.ts L121–L127
  6. 留在 .git/config，一直到机器消失 Sandbox 里 git 会把克隆地址原样记成 origin，后面的 git push origin 分支名 正是靠它推上去的。Agent 只要 git remote -v 就能看到。选 Copilot 时，它还被放进 GH_TOKEN / GITHUB_TOKEN。 lib/sandbox/git.ts L48 lib/sandbox/agents/index.ts L49–L54
  7. 服务器自己也用它 服务器 → GitHub 开 PR、查检查结果、合并时，服务器用同一把令牌建 Octokit。 lib/github/client.ts L9–L19
  8. 什么时候失效 GitHub OAuth app 的令牌默认不过期，GitHub 只在“一年没用过”时自动吊销（Token expiration and revocation）。用户注销时，服务器会调 GitHub 接口吊销这把令牌，这一点做得对；但“断开 GitHub”只是删掉数据库里那一行，并不吊销。 signout/route.ts L11–L27 disconnect/route.ts L28

所以这把令牌的真实寿命是：从登录起，到用户注销或 GitHub 一年后清理为止；它的真实范围是：用户能碰的所有仓库。而它在每个任务里都以明文躺在 Sandbox 的磁盘上。按推断，Keep Alive 留着的机器里，令牌在被吊销之前一直可用。

二、用户 API key：设置页 → 加密存库 → 换进 process.env

  1. 设置页保存，只写不读 服务器 → 数据库 POST /api/api-keys 校验提供方后加密存进 keys 表；GET 只返回“哪一家、什么时候存的”，从不把值发回浏览器。这是全项目做得最干净的一处。 app/api/api-keys/route.ts L37–L89 L19–L30
  2. 提交任务时取出：先拿平台的，再用自己的覆盖 服务器 getUserApiKeys() 先把 process.env 里的平台密钥当默认值，再用用户自己存的逐个覆盖。注意“默认值读的是 process.env”，下一节会用到。 lib/api-keys/user-keys.ts L22–L60
  3. 临时换进 process.env 服务器 后台流程调用 executeAgentInSandbox，它把用户的 key 写进服务器进程的 process.env，六个适配文件再从 process.env 读出来，用第 4 课讲的四种走法送进 Sandbox（命令前缀、runCommand 的 env、明文配置文件、克隆地址）。函数结束时在 finally 里改回去。 lib/sandbox/agents/index.ts L56–L75 L149–L158

三、平台密钥：Vercel 项目环境变量

平台密钥是部署者填在 Vercel 项目环境变量里的那一批（README.md L190–L199）。要分两类看：

  • 只留在服务器上的：JWE_SECRET、ENCRYPTION_KEY、SANDBOX_VERCEL_TOKEN、OAuth 的 client secret。我在代码里没找到把它们送进 Sandbox 的地方。
  • 会进 Sandbox 的：模型密钥。README 写明这些 key 可以“set globally (fallback for all users)”（README.md L240–L246）。用户没存自己的 key 时，平台的 AI_GATEWAY_API_KEY 就是 Claude、Codex 在 Sandbox 里用的那一把，写在命令行和 ~/.config/claude/config.json 里（claude.ts L152–L158）。
后果：每个登录用户都拿得到平台的模型密钥

任务详情页有一个终端接口：检查“任务是你的”之后，就在你的 Sandbox 里用 sh -c 执行你给的任意命令，并把标准输出原样返回（terminal/route.ts L72–L102）。所以任何用户提交一个 Claude 任务、开着 Keep Alive，再在终端里读一下那个配置文件，就能拿到平台的网关密钥。每天 5 次的限制只限制“提交任务”，挡不住拿到密钥以后去别处用。这是读代码推断，没有实测。README 说“no shared credentials”（README.md L356），对 GitHub 令牌成立，对模型密钥不成立。

四、MCP secret：connectors 表

  1. 登记时加密 服务器 → 数据库 表单提交到 server action，oauthClientSecret 和 env（先转成 JSON 字符串）分别加密后存进 connectors 表。 lib/actions/connectors.ts L63–L65
  2. 读列表时解密发回浏览器 服务器 → 浏览器 和 API key 的“只写不读”相反，GET /api/connectors 把 secret 和环境变量解密后整个返回。 app/api/connectors/route.ts L23–L33
  3. 任务开始时解密 服务器 后台流程查出当前用户所有“已连接”的服务器，解密 env 和 oauthClientSecret，交给适配文件。 app/api/tasks/route.ts L536–L578
  4. 写进各家配置，client secret 直接当令牌用 Sandbox 里 六家的写法见第 4 课的表。Claude 这条把 oauthClientSecret 直接拼成 Authorization: Bearer …。按 OAuth 的本意，client secret 是用来向授权服务器换访问令牌的，不该直接当令牌发出去；这里实际上是“用户填什么，就当 Bearer 令牌发什么”。 lib/sandbox/agents/claude.ts L131–L133
顺带更正一个旧疑点

备课笔记里曾怀疑：route.ts 第 213 行注释说 after() 里“拿不到 session”，可第 540 行在 after() 里又调用了 getServerSession()，MCP 读取会不会静默失效？查了 Next.js 文档：在 Route Handler 里，after() 的回调可以直接调用 cookies() 和 headers()，只有 Server Component 里不行（Next.js · after · With request APIs）。所以按文档，第 540 行和 Copilot 那里取令牌（index.ts L53）应该都能拿到 session，是第 213 行的注释过于保守。没有实测。

临时改写 process.env：多租户下的串号风险

上一节第三步的做法，在一台只跑一个任务的机器上没问题。问题在于，Vercel 的函数实例并不是“一个请求一个进程”。Fluid compute 是 2025 年 4 月 23 日以后新项目的默认设置，它的一个特性就是“多个调用共享同一个实例”（Vercel · Fluid compute）。而 process.env 是整个进程共用的一个对象。

代码是这样写的：先把当前值存进 originalEnv，再用用户的 key 覆盖，跑完 Agent 以后在 finally 里把 originalEnv 写回去（index.ts L56–L75，L149–L158）。Agent 一跑就是几分钟，中间全是 await，别的请求完全可以插进来。下面是我推出来的一条时间线，这是推断，没有实测。设平台密钥为 P，用户 A 存了自己的 key，用户 B 没存：

时刻发生了什么进程里的 AI_GATEWAY_API_KEY
1A 的任务开始跑 Agent，存下原值 P，写入 A 的 keyA 的 key
2B 提交任务，getUserApiKeys() 把 process.env 当作“系统默认值”读走（user-keys.ts L22–L31）A 的 key（B 拿到的也是它）
3B 的任务开始跑 Agent，存下“原值”，这时原值已经是 A 的 keyA 的 key
4A 跑完，写回 PP
5B 跑完，写回它存下的“原值”A 的 key，一直留在进程里

结果有三个：A 的 key 进了 B 的 Sandbox，而 B 能用终端接口读到它；之后这个实例上所有没存 key 的用户都在花 A 的钱；服务器自己起分支名、写提交说明的小模型调用（route.ts L651–L659）也用上了 A 的 key。时刻 1 和 3 之间不需要精确踩点，只要两个任务在同一个实例上重叠就行。

还有一个不需要并发就会出现的小毛病。如果平台没配某个变量，originalEnv 里存的是 undefined；可是给 process.env 赋值 undefined，Node 会把它变成字符串 "undefined"。我在 Node 20 上验证过这一点。于是第一个任务跑完以后，没配的变量全都变成了一个非空字符串：适配文件里“没有 key 就报错”的检查会被绕过，后面的报错会变得莫名其妙。这一条对行为的影响是推断。 正确写法很简单：不要碰 process.env。把 key 作为参数一路传给适配文件，或者每个任务建一个自己的 env 对象。真要恢复，原值是 undefined 时应该 delete process.env.X。

日志脱敏：管到哪里，漏在哪里

第 4 课已经讲过脱敏规则的毛病：[sk-] 写成了字符组、保留前后各 4 位、对话表不过滤、Codex 第 94 行把格式不对的 key 前 15 位写进报错。这里把“哪些出口经过脱敏”整体排一遍：

出口经过 redactSensitiveInfo 吗代码
tasks.logs（任务日志，网页上滚动的那一栏）经过。所有 info、error、updateProgress、updateStatus 都走 createLogEntrylogging.ts L76–L82 task-logger.ts L16–L55
task_messages（对话气泡里 Agent 的回答）不经过。Claude 的流式输出、最后的回答原样写库claude.ts L331–L345 route.ts L620–L630
终端接口的返回不经过。stdout、stderr 原样发回浏览器terminal/route.ts L95–L102
GET /api/connectors不经过，而且是主动解密后返回connectors/route.ts L23–L33
服务器的 console 日志（Vercel 后台可见）不经过。不过我没找到直接打印密钥的 console 语句—

规则本身，我把那个函数原样拷出来，用假数据跑了一遍（logging.ts L6–L74）。下面这些情况一个字都没被遮住：

  • 前面没有变量名的裸 key，比如输出里单独出现一串 sk-ant-…。所有规则都要求前面有 API_KEY、TOKEN 之类的名字，只有 GitHub 克隆地址那条例外（L18）。
  • JSON 写法，比如 {"apiKey": "…"}。键名后面紧跟引号，通用规则（L62–L71）对不上。而 Claude 的配置文件恰好就是这种格式。
  • 名字里不带 KEY、TOKEN、SECRET、PASSWORD 的，比如 MCP 环境变量里一条 DATABASE_URL=postgres://用户:密码@…。
  • 值里有点号、斜杠、加号的，比如 base64 形式的密钥：值只认字母、数字、下划线和连字符，碰到第一个点号就停；不足 8 位时整条放过。

思路上的问题是：这套规则靠“猜长相”。GitHub Copilot 的做法是靠“认值”：它明确说会遮住 secret 的值（Copilot · Configure secrets and variables）。模板手里其实有每个任务用到的全部明文，完全可以按值做精确替换，再对所有出口（日志、对话、终端）统一过一遍。

认证、授权与速率限制

认证：谁能登录，会话怎么存

  • 登录方式：GitHub OAuth 和 Vercel OAuth 两种，由 NEXT_PUBLIC_AUTH_PROVIDERS 决定开哪几种，默认只开 GitHub（providers.ts L9）。GitHub 这条用 state 防跨站伪造；Vercel 这条另外用了 PKCE（signin/vercel L14–L31）。
  • 会话：没有服务器端会话表，状态全在加密 cookie 里：一年有效、HttpOnly、生产环境 Secure、SameSite=Lax（create.ts L49–L66）。好处是省一次查库，代价是没法从服务器端踢人下线：一张 cookie 被偷，一年内都能用，除非整站换 JWE_SECRET。
  • 注销是 GET 请求（signout/route.ts L7）。别的网站放一张指向它的图片就能让你掉线，顺带吊销 GitHub 令牌。危害不大，但不规范。
  • 连接 GitHub 时会合并账号：如果这个 GitHub 账号已经属于另一个用户，回调会把那个用户的任务、连接器、账号、密钥全部搬过来，再删掉旧用户（callback/route.ts L154–L186）。前提是你能登录那个 GitHub 账号，所以本身不算越权，但这是一个容易被忽略的“数据整体转移”入口。

授权：每条接口都查“任务是不是你的”吗

我把 app/api/tasks/[taskId]/ 下的 31 个 route.ts（30 个子目录加根目录，共 33 个处理函数）逐个看了一遍：全部都检查了归属。其中 27 个把 userId 和“未删除”直接写进查询条件；lsp、restart-dev、start-sandbox、stop-sandbox 四个是先查出任务、再比对 userId，没有排除已软删除的任务（例如 stop-sandbox L19–L28）。这只是不一致，不是越权。列 Sandbox 的接口也只返回自己的（sandboxes/route.ts L14–L30）。

真正的缝在“创建任务”：客户端能自己填 sandboxId

POST /api/tasks 把请求体整个展开交给校验（route.ts L71–L82），而校验规则 insertTaskSchema 允许的字段里有 sandboxId、branchName、prUrl、prNumber、agentSessionId，甚至任务 id（schema.ts L117–L147）。这类漏洞叫“批量赋值”。

接下来是一条推断出来、没有实测的链：终端接口查到“任务是你的”以后，用平台的 SANDBOX_VERCEL_TOKEN 按 task.sandboxId 去连机器（terminal/route.ts L42–L61）。所有用户的 Sandbox 都在平台同一个 Vercel 项目下，这把令牌都能连。如果你建任务时填了别人的 sandboxId，又让克隆失败（比如给一个不存在的仓库），那么正常流程里覆盖 sandboxId 的那一步（route.ts L507–L518）就不会执行，你的任务就指向了别人的机器。而且不止终端：[taskId]/ 下有 21 个路由用 Sandbox.get 连机器，包括读写文件和停机（例如 stop-sandbox L36–L40）。前提是知道别人的 sandboxId，我没找到泄露它的途径，所以实际风险取决于这个编号能不能猜到。修法是：接受的字段只列白名单，sandboxId 只由服务器写，连机器前再核对“这台机器属于这个任务”。

速率限制：每天 5 条，但算法有四个洞

规则是：今天建的任务数，加上今天发的用户消息数，不能超过上限，默认 5（rate-limit.ts L21–L43，constants.ts L2）。

  • 新任务算两次：建任务时既插一行任务，又把第一条提示词插成一条用户消息（route.ts L401–L411）。按推断，默认 5 实际只能建 3 个新任务（0 → 2 → 4 → 6）。
  • 删掉就退额度：两项计数都排除了已删除的任务（L24、L36）。跑完删掉，额度就回来了，而 Sandbox 的钱已经花出去了。
  • 先查后插，不是原子操作：同时发几个请求，可能都在插入前通过检查（route.ts L57–L91）。这是推断。
  • 时长由客户端说了算：传给后台的是 validatedData.maxDuration || maxSandboxDuration（route.ts L229），而校验规则给 maxDuration 设了默认值 300、没设上限（schema.ts L126）。所以管理员按用户配的时长（settings.ts L69–L72）永远用不上，客户端还能自己填一个很大的数。实际能跑多久还受 Sandbox 本身的上限约束。

此外，终端、文件读写这些接口完全不限速。限速只管“提交任务和追问”这两个入口（continue/route.ts L30）。

对照现代做法：威胁 → 模板现状 → 推荐做法

下表的“推荐做法”只写我在官方文档里核对过的内容。模板锁定的是 2026 年 2 月的代码，那时 Vercel Sandbox 的凭据代理功能刚发布（第 4 课），所以这张表更像“今天重写会怎么做”，而不是指责模板。

威胁模板现状推荐做法（附出处）
提示词注入让 Agent 把模型 key 发到外网key 以明文进 Sandbox，出站网络全开凭据代理加出站白名单。Vercel Sandbox 的 networkPolicy 可以设成只允许列出的域名，并在防火墙层给指定域名的请求注入请求头，文档原话是 “The secrets never enter the sandbox, so code running inside it cannot exfiltrate them.” 策略还能在运行中更新。需要注意的是：默认是全放开；按 SNI 匹配域名，所以文档提醒了“域名前置”的绕过可能；按 IP 段放行的流量不走凭据注入（Vercel · Sandbox firewall）。
GitHub 令牌被读走后能碰所有仓库OAuth app 的 repo 范围令牌，默认不过期，写在 .git/config改用 GitHub App 安装令牌。创建时可以只限定这一个仓库、只给需要的权限，令牌一小时后自动过期（Generating an installation access token）。再进一步，令牌不进 Sandbox：由服务器在 Sandbox 外面 push，或者用上面的凭据代理给 github.com 注入请求头。
安装依赖阶段需要秘密，Agent 阶段不该有同一台机器、同一段时间里一直都有按阶段给秘密。OpenAI 旧版的 Codex Cloud 环境文档写明：secret 只在准备脚本阶段可用，Agent 阶段开始前就被移除；Agent 阶段默认不能上网，可以按域名白名单打开，还能只放行 GET、HEAD、OPTIONS 这几种请求（Codex cloud environments，Codex · Agent internet access）。
Agent 推送危险改动令牌能 push 到任何分支；PR 由用户点按钮才开（第 1 课）限制推送范围、强制人工审查。GitHub Copilot 的云端 Agent 默认只拿当前仓库范围的令牌，只能推到 copilot/ 开头的分支，合并前必须有人审查；防火墙默认开启，文档也承认它有局限（Copilot · Risks and mitigations，Customize the agent firewall，Give access to resources）。
秘密出现在日志和对话里按长相猜，只管日志表，保留前后 4 位按值遮盖，覆盖所有出口。Copilot 会遮住 secret 的值（Configure secrets and variables）。注意 Copilot 的 secret 同样是以环境变量的形式在整个会话里可见，它靠的是防火墙和按值遮盖，而不是“看不见”。
多个用户的 key 串号改写进程共用的 process.env每个任务一个独立的 env 对象，作为参数传下去，用完即弃。这是通用工程做法，不需要出处。
平台密钥被普通用户拿走用户没存 key 时，平台 key 进 Sandbox，终端可读平台 key 永远不进 Sandbox。要么必须用户自带 key，要么用凭据代理在机器外面注入，再给每个用户单独计量和限额。
客户端篡改服务器字段请求体整个展开给校验，能写 sandboxId、maxDuration只接受白名单字段，服务器字段只由服务器写，时长取“用户请求”和“管理员上限”的较小值。
数据库和总钥匙一起泄露一把全站 AES-CBC 密钥，没有版本号信封加密：每条记录一把数据密钥，再由托管的密钥服务加密；密文里带版本号，方便轮换；用带完整性校验的模式（如 AES-GCM）。这是通用做法，模板的 README 声称“per-user encryption”，代码并没有做到。

面试里怎么说：两分钟讲完整个架构

“这类云端 coding agent 产品，我拿 Vercel 的开源模板 coding-agent-template 拆过一遍。它分三层：一个 Next.js 应用负责网页和接口，一个 Postgres 存任务状态，每个任务在 Vercel Sandbox 里开一台 Firecracker microVM 去真正跑 Agent。

一个任务的一生是这样的：用户提交以后，接口先限速、校验、写一条‘待处理’的任务，立刻回应浏览器；真正的工作放在 Next.js 的 after() 里，在同一次函数调用的剩余时间里继续跑。后台流程创建 Sandbox，用用户的 GitHub 令牌克隆仓库，现装选中的 Agent CLI，比如 Claude Code 或 Codex，用免确认模式让它改代码，然后 commit、push 到新分支，用户再点按钮开 PR。

进度怎么回到网页？没有 WebSocket，每一步都写数据库，浏览器每 5 秒轮询一次。六家 CLI 的差别被收在六个适配文件里，各自负责安装、写配置、拼命令和解析输出。

它的安全模型是：既然 Agent 在机器里什么都能做，那么边界就是这台 microVM 本身。microVM 挡住了它碰宿主机和别的租户，但模板把 GitHub 令牌、模型 key、MCP secret 都以明文送进了机器，出站网络又全开，所以一次提示词注入就可能把它们带走。还有几个工程问题：临时改写进程共用的 process.env 会在并发时串号；客户端能写 sandboxId 这类服务器字段；日志脱敏只管日志表。

如果我来重做，会改三件事：第一，秘密不进 Sandbox，用 Vercel Sandbox 现在的凭据代理在出站时注入，并把网络改成白名单；第二，GitHub 用 App 安装令牌，只限这个仓库、一小时过期；第三，用工作流引擎或队列替代 after()，摆脱函数时长的限制，再用推送替代轮询。”

这段大约 600 字，正常语速两分钟出头。如果面试官只给一分钟，就只讲第二段和第四段。

常见追问和建议回答

追问建议回答
为什么用轮询，不用 WebSocket？Serverless 函数不适合长期挂着连接，任务又跑在 after() 里，没有一个常驻进程能往外推。轮询最简单，代价是最多 5 秒延迟和大量空查询。要改可以用托管的推送服务，或者让 Agent 输出写进一个支持订阅的存储（第 5 课）。
为什么用 microVM，不用 Docker 容器？容器和宿主机共用一个内核，Agent 能执行任意代码，内核漏洞就是逃逸通道。microVM 有自己的内核，隔离更强，Firecracker 启动又足够快，适合每个任务开一台（第 3 课）。
提示词注入怎么防？防不住“注入本身”，只能限制注入以后能造成的损失：秘密不进机器、出站白名单、令牌只限一个仓库并短期过期、只推新分支、合并前强制人工审查。这是 Copilot 和 Codex 的共同思路。
GitHub 令牌最安全的给法？GitHub App 安装令牌：限定仓库和权限，一小时过期。最好连这个都不进 Sandbox，由服务器在外面 push，或者由防火墙注入请求头。
多租户下用户的 API key 怎么隔离？存的时候加密、只写不读；用的时候作为参数传给这个任务，不写进任何进程共享的地方；最好不进机器，由代理按用户注入，同时按用户计量。模板在“存”这一步做得好，在“用”这一步改写了 process.env。
函数最长 300 秒，任务跑得更久怎么办？模板就是被这个卡住的：after() 和整个流程都算在一次函数调用里（第 2 课）。正解是把编排挪出请求，用队列或持久化工作流，每一步可以重试和续跑；Sandbox 本身可以活得比函数长。
成本怎么控制？三处花钱：Sandbox 时长、模型调用、函数时长。要做按用户的限额且原子计数；时长上限由服务器定；任务结束立刻关机，而不是空转到超时（模板只结束进程，第 2 课）；平台 key 不要兜底给所有人。
如果只能改一件事，你改什么？让秘密不再进入 Sandbox。它同时解决提示词注入外泄、平台 key 被拿走、日志脱敏漏网三类问题，而且现在 Vercel Sandbox 已经原生支持。
