## 1. 摘要

**结论定位：本轮是无 harness 的内容级 smoke，只能说明「memory 内容本身有用」，不能回答「在 harness 里用 memory 划不划算」。** 在「每请求全文注入」这一设定下，不将完整 memory 记为值得默认开启。

Smoke（每题每组 1 轮，共 30×2=60）在 MiniMax-M2.5 上：

| 门槛（README 默认） | 结果 |
|---|---|
| memory-dependent：B−A ≥ +10pp | **通过**：33.3% → 75.0%（**+41.7pp**） |
| 输入 token 中位数增量 ≤ 15% | **未通过**：1453 → 5032（**+246%**） |
| 端到端耗时中位数增量 ≤ 10% | **通过**：4102.5ms → 4261ms（**+3.9%**） |
| memory-irrelevant：B 质量不低于 A | **通过**：60% → 70% |

质量增益真实且集中在依赖 memory 正文的题；代价来自把约 8.3k 字符的 `.harness/memory` **整包注入每题 prompt**，远超 token 门槛。否决的是 naive 全文注入，不是 harness 内按需用 memory。下一步高优先级是用真实 harness 重跑；C 组只是近似。

## 2. 背景与目的

用户问题：`.harness` 里的 memory 是否在 token 与耗时增量可接受时，对回答质量有正向帮助。#372 已落地方法、真实题库与 Langfuse Dataset `harness-memory-ablation/v1`。本报告是首轮 A/B 实测（C 组标为后续，本轮未跑）。

## 5. 分析

1. **Memory 正文有信息增益。** dependent 上 A 仅 33%，B 75%；B 独胜多为约定细节（Compose 沉淀入口、brain 改名、CLI/Langfuse 约定等）——与「主真源在 memory」的出题意图一致。
2. **Token 爆炸来自注入策略，不是「读到 memory」本身。** B 每题固定多注入 ~8.3k 字符 memory，prompt 中位从 1.5k→5.0k。阈值假设的是「增量可控的发现路径」，不是 naive 全文塞入。因此失败的是**当前实现方式**，不能据此否定 memory 资产价值。
3. **耗时未恶化。** 中位略增；均值反而更低，因 A 在部分 irrelevant 长答上拖尾。注入更长上下文并未系统性拖慢 MiniMax-M2.5。
4. **Irrelevant 未帮倒忙。** B 略好（+1 题），未见明显幻觉带偏。
5. **Conflict-stale 上 B 更好（8/8 vs 6/8）。** 本轮 B 注入的是**现行** memory，不是故意冲突副本；该类主要用于观察带偏，本轮未观察到 memory 把模型带向过期说法。
6. **两侧皆败题。** `M08`/`M09` 更偏 skill / evaluations 落点，可能未完整进注入的 memory 切片；`M11` 硬约束多在 AGENTS（A/B 皆有）但仍判 partial；irrelevant 失败与 memory 无关，属题面/模型能力。

## 6. 局限与效度威胁

### 6.1 本轮不是真实 harness（主威胁）

- 直接调 MiniMax API，把 `AGENTS.md` + memory **全文**拼进 prompt，做单轮问答。
- 没有 Agent 运行时，没有读文件 / 搜索 / 开 PR 等工具。
- 没有 harness 按 `AGENTS.md` 索引、再按需读 memory 条目的机制。
- 因此本轮测的是「内容放进上下文有没有用」，不是「在 harness 里用 memory 划不划算」。

### 6.2 由此带来的偏差

- **Token 结论偏悲观**：真实 harness 通常先看索引再按需读少数条目；全文注入的 prompt 中位 +246% **不等于**真实成本。
- **质量可能偏乐观**：答案要点已在上下文里，模型可照抄；真实场景要自己判断是否读、读哪一条，增益可能更低。
- **测不到「做事时守不守约定」**：单轮问答没有改仓库、开 PR、跑工具等动作，硬约束违反次数这类指标本轮基本空窗。

### 6.3 其它局限

- **Smoke 1 轮**：无重复中位数，方差未知；不能当最终定论。
- **条件 C 仍是近似**：只放索引或检索注入仍走 API prompt，不是真实 harness 的按需读文件。
- **Judge 未人工校准**：MiniMax 自评，无 Kappa；partial 边界题可能噪声。
- **未挂 Dataset Experiment**：便于 UI 对比的 run 视图缺失，仅有 observations+scores+本地 JSON。
- **SDK score 初写 list 不可见**：已 CLI 回填 60 条；早期 SDK `gen.score` 行为未再深挖。

## 7. 结论与建议

1. **本轮能说的**：memory 内容本身有用（dependent +41.7pp；irrelevant 未帮倒忙）。
2. **本轮不能说的**：在真实 harness 里用 memory 是否划算；token/质量数字都不能直接当 harness 成本与收益。
3. **不要**在「每请求全文注入 `.harness/memory`」设定下，把 memory 标成默认开启（token 门槛未过）。这否决的是注入方式，不是 memory 资产。
4. **要**保留并继续建设 memory 资产。
5. **下一步（高优先级）**：在真实 harness（Cursor / Codex CLI、Claude Code、或 edges Agent）里 A/B worktree 对照；让 Agent 自己决定是否读 memory；token/耗时取 harness 实际 tracing（可进 Langfuse）；题集加多步任务测违约定行为。详见 README「后续改进」第 1 条。
6. **次优先近似**：条件 C（仅索引 / 检索注入）可作对照，但仍不是真实 harness；若 C 能保住大部分 dependent 增益且 prompt Δ≤15%，再讨论「默认开启索引 + 按需正文」。
7. 可选：对 `M08/M09` 核对真源是否应进 memory；人工抽检 6–9 题校准 judge；额度允许时 dependent 子集补到 3 轮。
