# Memory + 文件系统 + 树：Related Work 调研

调研日期：2026-09-15。对象：前文讨论的 runa-memory-init 系列设计，以及已检查的 edges 中 project-memory 协议。本文研究公开论文和官方项目资料；不是基准复现，也不以名称相似推定实现相同。2026 年新论文按预印本证据看待，除非另有明确发表信息。

## 1. 结论先行

**“Memory + 文件系统 + 树”已经有明确的相关工作；值得继续研究的不是三者第一次结合，而是代码仓库目录能否成为可靠的记忆作用域先验。**

最值得优先阅读的五项是：

| 工作 | 为什么与你最相关 | 主要边界 |
| --- | --- | --- |
| [ByteRover](https://arxiv.org/abs/2604.01599) | Markdown Context Tree、agent 自主整理、显式关联、渐进检索 | 按知识主题组织，不等于代码目录作用域 |
| [OpenViking](https://github.com/volcengine/OpenViking) | 目录摘要、多层加载、目录内检索，统一 memory/resources/skills | 独立的虚拟上下文文件系统 |
| [Letta Context Repositories](https://www.letta.com/blog/context-repositories/) | 实际本地文件、Git 版本、描述式导航、记忆整理 | agent 的独立记忆仓库，不是知识附着到源码子树 |
| [Filesystem-Based Memory](https://arxiv.org/abs/2607.26637) | 直接研究文件系统记忆的组织、增长和维护效果 | 对话与具身任务，不是代码仓库实验 |
| [HORMA](https://arxiv.org/abs/2606.11680) | 层次化经验、摘要链接原始轨迹、学习导航策略 | 主要解决长上下文 working memory |

这里的“接近”是机制比较，不是性能排序。这些系统的模型、任务和评价器不同，不能拼成一个统一排行榜。

## 2. 先明确：你的树表达什么？

依据前文已经确认的设计，本文采用以下比较基线：Memory 节点附着于实际目录，覆盖该目录子树；父节点 AGENTS.md 显式索引最近的子 Memory 节点；节点内部通过类型索引访问独立记忆文件；下层补充上层，而不是覆盖上层；记忆优先记录不能简单从代码或 Git 重建的经验、原因和约束。

协议参考：[edges PROTOCOL.md](https://github.com/VirusPC/edges/blob/main/packages/skills/edges-memory-init/references/PROTOCOL.md)、[ask](https://github.com/VirusPC/edges/blob/main/packages/skills/edges-memory-ask/SKILL.md)、[remember](https://github.com/VirusPC/edges/blob/main/packages/skills/edges-memory-remember/SKILL.md)。这些链接指向可变的 main；本文不声称本次重新审计了所有实现。

关键是区分五种“树”：

| 树的含义 | 父子关系表达什么 | 对应工作 |
| --- | --- | --- |
| 代码作用域树 | 哪些代码受这条知识约束 | 你的设计；嵌套 AGENTS.md 是相邻机制 |
| 语义分类树 | 哪些知识在概念上属于同一主题 | ByteRover、MemTree |
| 文档摘要树 | 哪些内容可以被上层概括 | RAPTOR、MemWalker |
| 时间索引树 | 哪些经验属于相邻时间范围 | MemForest |
| 上下文命名空间 | 资源、用户记忆、技能放在哪里 | OpenViking、Letta |

这是本文的分析分类，并非互斥的产品分类。一个系统可以同时使用几种树。

**目录作用域不等于语义相似性。** 两段代码可能位置相邻但职责不同；同一条鉴权约束也可能跨越 API、后台任务和测试目录。因此，目录可以作为检索和知识归属的先验，不能成为相关性的唯一裁判。

## 3. 最直接的 Related Work

### 3.1 ByteRover：最接近“文件化、可演化的知识树”

2026-04 预印本。Context Tree 采用 Domain → Topic → Subtopic → Entry，条目是 Markdown，并带关联、来源和生命周期信息；配合全文索引、缓存和逐级升级的检索策略。实验是 LoCoMo、LongMemEval，不是代码修复。其 LongMemEval 表中部分比较结果来自不同论文、模型和评价器，不能据此作严格横向排名。[论文，§3–5](https://arxiv.org/html/2604.01599v1)

**对你的启发：** 可借鉴条目的来源记录和跨节点链接。但若把主题分类树直接套进源码目录，会混淆“放在哪里”和“适用于哪里”。你更需要明确 scope，而不只是增加分类层级。

### 3.2 OpenViking：最接近“目录导航 + 分层上下文加载”

官方实现提供 `viking://` 虚拟文件系统，统一资源、记忆和技能。L0 摘要、L1 概览、L2 原文支持按需展开；向量搜索用于找候选目录，再探索内容。因此它不是“树替代向量”，而是结合两者。官方公开了 LoCoMo、tau2-bench 等评测，但不直接证明源码目录作用域的价值。[官方仓库与设计入口](https://github.com/volcengine/OpenViking)

**对你的启发：** AGENTS.md 的链接描述承担路由提示功能，可以独立评估其质量。不要把“有索引”直接等同于“索引足以准确选路”。同时，父节点的导航摘要和必须遵循的硬约束，最好保持明确区分。

### 3.3 Letta Context Repositories：Git-native memory 已有直接先例

2026-02-12 官方技术文章介绍本地克隆的 Git 记忆仓库：文件树和描述辅助导航，`system/` 内容常驻，其余渐进读取；还提供反思与碎片整理机制。文章描述 worktree 并行写入和 Git 合并，但没有提供目录附着记忆的对照实验。[官方文章](https://www.letta.com/blog/context-repositories/)

**对你的启发：** “记忆是可审阅、可回滚的文件”很有工程价值，但不是独有贡献。Git 能解决部分版本与文本协作问题，不能自动判断两条记忆是否在语义上矛盾。当前 doctor 的结构修复也不能等同于语义整理。

### 3.4 Filesystem-Based Memory：最重要的实证校准

2026-07-29 预印本，将记忆管理、搜索、任务执行分开研究，比较组织化文件、原始记录和 chunk 检索，并观察随经验增长的变化。在其对话与具身任务设置中，大规模材料上的组织化存储约减半检索成本，但没有测得组织本身稳定提升答案质量；组织维护也受模型和工具接口影响。[论文，§2–4](https://arxiv.org/html/2607.26637v1)

**对你的启发：** 成功率、检索成本、维护成本必须分开报告。即使树不提高成功率，只要它以更少读取、更低维护代价达到同等效果，依然是有效结果；反之，目录看起来整齐不能作为效果证据。

### 3.5 HORMA：把“如何走树”变成可训练策略

2026-06-10 预印本。将经验组织为文件系统式层次结构，摘要实体链接原始轨迹；区分结构构建和导航检索，并用强化学习训练轻量导航 agent。实验覆盖 ALFWorld、LoCoMo、LongMemEval，定位更接近长任务 working memory，而非源码子树约束。[论文](https://arxiv.org/html/2606.11680v1)

**对你的启发：** “进入哪个子节点、何时回溯、何时停止读取”确实可以成为优化对象。建议先记录导航轨迹、建立固定策略基线，再考虑训练；否则难以判断收益来自树、检索器还是更大的计算投入。

## 4. 树算法的学术来源

| 工作 | 已有机制 | 可借鉴方向 | 不能直接迁移的部分 |
| --- | --- | --- | --- |
| [MemWalker，2023](https://arxiv.org/abs/2310.05029) | 把长文本构成摘要节点树，由 LLM 交互式导航 | 显式选路、读取与停止策略 | 长文本读取不等于长期记忆更新 |
| [RAPTOR，2024](https://arxiv.org/abs/2401.18059) | 递归 embedding、聚类、摘要，跨抽象层检索 | 大子树的多粒度概览 | 聚类父节点不是代码规则的适用域 |
| [MemTree，2024/2025](https://arxiv.org/abs/2410.14052) | 根据语义 embedding 动态组织节点及聚合内容 | 新记忆归类、抽象层次调整 | 不宜为语义聚类而自动移动源码或修改知识权限 |
| [MemForest，2026](https://arxiv.org/abs/2605.23986) | 时间树、并行抽取、局部 dirty-path 刷新 | 变更后只重建受影响的派生索引或摘要 | 对数深度依赖平衡树；不代表端到端处理为对数复杂度 |
| [A-MEM，2025](https://arxiv.org/abs/2502.12110) | 结构化笔记、动态链接、旧记忆表示更新；论文标注 NeurIPS 2025 | 跨目录关联及反向链接 | 它是网络式记忆，不是树作用域的实验验证 |

注意：MemForest 内部也把时间索引称为 MemTree；这和 2024 年的语义树 MemTree 不是同一个工作。

由这些工作得到的设计判断是：**保留目录树作为稳定的归属结构，在树上增加少量显式跨链接，可能比强迫所有相关性都服从目录关系更合适。** 这是建议，不是已测得的结论。跨链接用于发现信息，并不自动扩大约束的适用范围。

另一个重要参照是 [PageIndex File System，2026-05](https://pageindex.ai/blog/pageindex-filesystem)：官方描述了面向多文档的查询相关虚拟层级，允许同一文档出现在多个视图中；相关能力被标为 enterprise release，不能直接视作开源版既有能力。其启发是“检索视图可以变化”，不必让真实目录随每个查询变化。

## 5. 不能遗漏的工程基线

### 嵌套 AGENTS.md

嵌套目录说明和路径相关指令已有明确先例。AGENTS.md 官方页面采用就近文件优先的冲突描述；这与你当前“子节点只能补充祖先”的协议不同。[官方规范入口](https://agents.md/)

因此，你的显式父子链接解决的是发现和导航问题；它不自动保证不同 harness 对冲突的解释完全一致。测试应分别覆盖“读不读得到”和“读到以后如何合并”。

### Claude Code auto memory

官方实现把 `MEMORY.md` 作为入口，主题文件按需读取；同仓库的 worktree 和子目录共享一个 auto-memory 目录，默认是机器本地记忆。因而“入口索引 + 独立文件 + 渐进读取”已经存在，但这不等同于每个源码子树有自己的记忆节点。[官方文档](https://code.claude.com/docs/en/memory)

### Cline Memory Bank

项目内 Markdown 记录需求、架构、当前进度等，官方模板要求每次任务开始读取全部 memory-bank 文件。它适合作为项目级集中记忆基线，而不是递归作用域基线。[官方文档](https://docs.cline.bot/best-practices/memory-bank)

最公平的对照不应只有“无记忆”和“全量塞入”。应加入一个同样有描述、按需读取、可按 scope 过滤的扁平文件方案，检验树是否提供额外收益。

## 6. 对应代码仓库任务的工作与评测

| 工作 | 实际研究对象 | 对你的用途 | 评价边界 |
| --- | --- | --- | --- |
| [RepoMem / Improving Code Localization with Repository Memory](https://arxiv.org/abs/2510.01003) | 历史提交、关联 issue、活跃代码区域的功能摘要；标注 ICLR 2026 | 证明仓库历史是有用的记忆来源，作为定位任务基线 | 定位改善不能等同于修复成功率改善 |
| [Confucius Code Agent](https://arxiv.org/abs/2512.10398) | 大仓库 agent、层次上下文管理、持久笔记 | 参考如何把记忆接入真实 coding agent | 整体 scaffold 的成绩不能全归因于长期记忆 |
| [SWE-ContextBench](https://arxiv.org/abs/2602.08316v3) | 1,100 个基础任务、376 个关联任务，51 仓库、9 语言，研究历史经验复用 | 当前最适合承接“经验如何帮助相关代码任务”的现成基准之一 | 仍需自行控制写入策略、检索预算和信息泄漏 |

不要只用 LoCoMo 得分证明你的系统有效：它主要检测对话事实记忆，无法直接检验模块约束、代码重构后的记忆迁移或跨目录误用。

也不要把“重复同一道题读上次笔记”与“迁移到新的关联任务”混为一谈。前者可以衡量恢复和缓存效果，后者才更接近这里的长期仓库学习目标。

## 7. 可以主张什么，不宜主张什么

| 表述 | 当前判断 |
| --- | --- |
| 首次把记忆存成 Markdown | 不成立：已有直接工程先例 |
| 首次将记忆组织成树 | 不成立：已有多条学术路线 |
| 首次渐进加载记忆 | 不成立：已有索引式、分层式实现 |
| 首次用 Git 管理记忆 | 不成立：Letta 等已有明确描述 |
| 将代码目录作用域、显式父子导航、分类型记忆和维护协议组合起来 | 可以准确描述自己的设计，但不能仅凭此次检索宣称首次 |
| 这种组合降低上下文污染、检索成本和维护成本 | 有意义、可检验的研究假设，尚需实验 |

建议使用的定位：

> 一个以代码仓库目录为作用域先验的持久记忆协议：通过显式父子索引组织稀疏记忆节点，在按需读取经验的同时保留祖先约束，并使记忆能够随代码一起审阅与维护。

更有研究价值的问题是：**相比语义检索或扁平 scope 过滤，目录作用域先验在什么任务和仓库结构下更有效，又在什么情况下造成漏检？**

## 8. 最小但有说服力的实验设计

以下均为本报告建议，不是现有论文已经证明的结果。

### 8.1 先分离“组织方式”和“写入质量”

第一阶段固定同一批记忆内容、生成模型和 token 预算，只改变组织与检索方式。第二阶段再比较各系统自行生成和维护记忆的端到端效果。

| 组别 | 设置 | 要回答的问题 |
| --- | --- | --- |
| A | 无持久记忆 | 记忆总体是否有价值？ |
| B | 扁平 Markdown + 描述索引 + 按需检索 | 文件化经验本身贡献多少？ |
| C | B + 显式 scope 元数据过滤 | 作用域过滤是否已足够？ |
| D | 目录附着节点 + 父子索引 + 同样的 scope 语义 | 树导航比扁平过滤多带来什么？ |
| E | D + 显式跨节点关联 | 能否修复跨目录任务的漏检？ |
| Oracle | 人工指定相关记忆 | 当前瓶颈在检索还是使用记忆？ |

分别统计定位阶段和执行阶段：任务尚未定位到文件时，不能把正确目录偷偷提供给树检索器。目录识别的成本和错误也要计入结果。

### 8.2 任务应覆盖边界条件

1. 同模块经验迁移：历史坑点帮助解决新 issue。
2. 兄弟模块隔离：相似代码使用不同约定，检查误用率。
3. 跨模块任务：共享约束涉及多个不相邻目录。
4. 目录重构：移动、重命名、拆分后，检查悬空链接与错误作用域。
5. 事实更新：旧经验被新证据纠正后，检查旧知识是否仍被当作有效。
6. 长期增长：重复、冲突、噪声逐步加入，观察成本曲线而不是只看终点。

### 8.3 指标与防泄漏

- 任务结果：测试通过率、定位准确率、相对无记忆的负迁移率。
- 检索行为：相关记忆召回、作用域误用、读取文件数、回溯次数、输入 token。
- 维护质量：链接完整性、重复率、过期知识使用率、人工修复量。
- 总成本：初始化 + 写入整理 + 检索 + 执行 + 重构维护，不只报查询成本。
- 控制项：相同底层模型、工具权限、任务快照、预算；多次重复并报告不确定性。
- 时间边界：只允许当前任务前已出现的历史；目标补丁、未来提交和隐藏测试结果不得进入记忆。跨任务更新应有明确的时间顺序与来源记录。

## 9. 对前文算法设想的收紧

| 设想 | 更严谨的版本 |
| --- | --- |
| 用修改文件的 LCA 自动决定记忆落点 | LCA 仅生成候选；需判断知识实际适用范围，不自动新建节点 |
| 子节点覆盖父节点 | 与当前补充式协议不同；若需要覆盖，属于协议变更 |
| 沿祖先链是 O(h)，所以检索很便宜 | O(h) 只描述节点遍历；宽索引、读取 token、选路和回溯另计 |
| 树检索天然 O(log N) | 真实目录不保证平衡，语义检索也可能多分支探索 |
| Git diff 自动失效相关记忆 | diff 只能触发复核候选；文件变化不等于知识错误，依赖也可能在树外 |
| 将子节点经验总结到父节点 | 导航摘要可以上卷，约束不能未经判断就扩大适用域 |
| doctor 等于 consolidation | 结构修复和语义合并、纠错、遗忘应分别设计 |

## 10. 推荐阅读路线

想理解最接近的实现：ByteRover → OpenViking → Letta。

想把算法空间具体化：MemWalker → MemTree → MemForest → A-MEM。

想做可信实验：Filesystem-Based Memory → SWE-ContextBench → RepoMem。

最终建议：**先证明“作用域正确、读取经济、随仓库演化可维护”，再增加自组织、摘要上卷或训练式导航。** 最有潜力的贡献是目录先验与长期代码经验之间的可测关系，而不是文件格式或树这一数据结构本身。

## 调研限制

本次以论文原文、摘要和官方文档核对机制，没有运行相关实现或复现成绩；没有进行穷尽式专利或优先权检索。官方产品文章证明其公开描述的设计，不等同于同行评审或独立性能验证。本文未核验所有项目的开源实现与论文版本是否逐项对应，因此没有将论文机制一律标为“当前开源可直接使用”。
