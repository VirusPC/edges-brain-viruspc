四个特征与五个模块

先抓住原文第 1 节的骨架：现有单会话 Agent 卡在人的注意力上；Super-agent 是跨会话、跨任务的连续实体；它有四个基础特征，五个模块只先记名字和指向。

第 1 课 · 约 10 分钟 · 主来源：DeepSeek Harness 团队 · Super-agent 设计探索（第 1 节）

这篇文章是什么，不是什么

原文第一句就写明：这是一篇面向工程实践的架构思路探讨，并非对 DeepSeek Harness 现有产品功能的介绍。下面出现的内部实例，只用来理解这种形态，不要读成产品功能清单。

学完这一课，你能做到

不看原文，能讲清：为什么以单一 Session 为基本单位会撞上人的注意力天花板；Super-agent 指的是哪一种连续实体；连续、高效、主动、持久在原文里各是什么意思；为什么单个 ReAct Loop 撑不住这四件事；五个模块叫什么、各自先指向哪一类能力。这是吃透这篇原文的骨架。

单任务越来越省人，多任务还卡在人身上

原文从过去一年的变化讲起。以 Coding Agent 为代表的单任务 Agent 已经证明，模型能够使用工具解决复杂问题，而且越来越少需要人持续盯着、一步步插手。模型的多 Agent 协同能力也在提升，使跨会话的组织与调度变得可行。于是人的角色正往上移：更少参与底层执行，更多做高层的决策与验收。 原文 · 第 1 节

模型能力的这一提升，也催生了新的应用形态。个人助手开始直接接入日常的消息、日程、邮件与工作平台，持续观察信息流并协助处理事务。原文强调：这种持续在线、事件驱动的工作模式并不局限于个人场景，在软件开发等商业场景中同样很有价值。

可是，现有的主流 Agent 设计还难以在多任务和团队协作的规模上撑住这一模式。Agent 的工作仍然以单一 Session 为基本单位，不同 Session 彼此独立。用户要并行推进多项工作时，必须手动切换，并自己记住各个 Session 的上下文。作者写道，据他们观察，一个人通常只能同时跟进 3 到 5 个活跃 Session。 原文 · 第 1 节 「3 到 5 个」是原文给出的观察，用来说明多任务会撞上人的注意力。它不是一条普遍定律，课里也不要把它讲成架构必须遵守的硬上限。

在这种设计下，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。如果只在现有的本地单会话 Agent 上，借助 CLI、MCP 或外部连接器做简单扩展，Agent 虽然也能接入外部消息，但仍会受制于单会话同步阻塞、多任务上下文混乱、本地设备离线即停止运行等问题，需要大量人工维护。

Super-agent：跨会话、跨任务的连续实体

要突破这些限制，原文认为需要打破 Agent 与单次手动会话的绑定，使它成为一个能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。原文把这种 Agent 形态及其系统架构称为 Super-agent。 原文 · 第 1 节

也就是说，Super-agent 不只是一个更长的 Session，而是一种形态，加上支撑它的架构。课里说到这个词，都按「形态 + 架构」来理解，不要把它缩成某一个产品开关。

原文用他们内部基于 DeepSeek Harness 运行的 Super-agent 实例举了两个例子：同一个开发任务可以在 IM 和 GitHub 之间连续推进；这个实例还会持续观察公共群聊中的反馈，在无人 @ 的情况下主动定位根因并提交修复 Pull Request。这些是原文用来说明形态的例子，仍然不是产品功能介绍。

四个基础特征，按原文的意思记

具体来说，原文认为 Super-agent 具备以下四个基础特征。不要只记住这四个字，要记住原文给每个字的意思。 原文 · 第 1 节

特征原文里的意思
连续用户可以直接在 IM 聊天、GitHub 评论等熟悉的工作界面与它交互，感觉始终只存在一个 Agent，不需要去想「Session X 的上下文中是否有 Y 信息」。例如，用户先在 IM 上提出采用方案 A，随后在 GitHub Pull Request 评论里改为方案 B，它能理解并调整执行方向。
高效交互响应迅速，同时能并行、高质量地完成多个复杂任务。无需等上一个命令或任务完成，就能接受下一条指令。
主动无需等待用户逐条下达指令，能持续观察环境事件并主动推进值得处理的事项，不需要介入时则保持安静。
持久始终在线、直接接入用户真实的工作环境，并在长期运行中遇到异常时自动恢复。

四个词很容易被平时的用法带偏。「连续」在这里不是「一个 Session 永远不要停」，而是用户不必自己管理 Session 分界；「高效」同时包含响应快和多任务并行；「主动」必须连着「不需要时保持安静」一起记；「持久」同时包含始终在线、接入真实环境、异常时能恢复。后面几课再讲这些特征是怎样被做出来的。 Anthropic 的《Building always-on agents》也把「一直在」首先写成用户体验，而不是一个永不停止的推理循环。本课先按本篇，把「始终在线」记在「持久」这个特征里，机制放到后面讲。

单个 ReAct Loop 撑不住，五个模块先记框架

原文写得很干脆：单个 ReAct Loop 无法同时支持上述四个特征，底层需要一套相应的架构。相似的设计约束会导出相似的架构选择。无论是面向个人的助手，还是面向软件开发等商业场景的 Agent，如果目标是构建一个持续在线、并发响应环境事件的系统，那么在底层就可能会采用相近的架构。这一过程中面临的许多问题，与传统计算机系统长期探讨的问题很相似，因此经典的系统设计思想在这里同样适用。 原文 · 第 1 节

在具体落地中，这套架构会有不同的变体，但原文认为以下五个模块构成了支撑上述四个基础特征的基本框架。第 1 课只记住它们的名字，以及原文给它们的职责指向，先不进入各节内部。

模块对应原文章节在框架里先指向什么
双层架构第 2 节兼顾连续交互与高效并发
事件驱动第 3 节实现主动响应
面向人的交互第 4 节在交互过程中同时做到连续与高效
计算、状态与环境的分离第 5 节与 Watchdog 一起，实现跨设备的持久在线与异常自愈
Watchdog第 6 节与上一模块一起，实现跨设备的持久在线与异常自愈

原文把第 5 节和第 6 节写在同一句里：二者共同支撑「持久」。不要在第 1 课就把「在线」和「自愈」拆成互不相干的两套东西，也不要提前讲 Router、过滤或 daemon 的内部做法。

合上原文，60 秒这样讲

「这篇原文开篇就声明：它是面向工程实践的架构思路探讨，不是 DeepSeek Harness 现有产品功能的介绍。现有主流 Agent 仍以单一 Session 为基本单位，Session 彼此独立。用户并行推进多项工作时，必须手动切换并记住各个 Session 的上下文。作者观察到，一个人通常只能同时跟进 3 到 5 个活跃 Session——这是观察，不是定律。于是单任务的上限取决于模型能力，多任务的上限取决于人的注意力。只在本地单会话 Agent 上接 CLI、MCP 或连接器，仍会碰到同步阻塞、多任务上下文混乱、设备离线即停止这些问题。要突破限制，就要打破 Agent 与单次手动会话的绑定，使它成为能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。原文把这种形态及其系统架构称为 Super-agent。它有四个基础特征：连续，是用户在 IM、GitHub 评论等熟悉界面里感觉始终只有一个 Agent，不必去想某条信息在哪个 Session 里；高效，是响应快，并能并行、高质量地完成多个复杂任务，不必等上一件做完再接受新指令；主动，是持续观察环境事件并推进值得处理的事项，不需要介入时保持安静；持久，是始终在线、直接接入真实工作环境，遇到异常能自动恢复。单个 ReAct Loop 无法同时支持这四个特征，底下需要一套架构。五个模块构成基本框架：双层架构兼顾连续与高效，事件驱动实现主动，面向人的交互让连续和高效同时落在交互体验上，计算、状态与环境的分离以及 Watchdog 一起支撑跨设备的持久在线与异常自愈。」
