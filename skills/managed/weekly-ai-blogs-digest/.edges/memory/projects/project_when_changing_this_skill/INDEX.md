这份文档回答：每次修改 weekly-ai-blogs-digest 这个技能时，要先考虑哪些事情，才不会把流程、数据或站点改乱。结论是：修改必须由技能本身来串联流程，先更新数据契约再改实现，找出并重算所有受影响的下游，用没有本次对话上下文的新智能体（Agent）按现行技能从头生成来验收，并且按「先改技能、再生成数据、最后改站点」的顺序一路做到发布上线。下面九条是每次改动前要逐项检查的约定。

**Why:**

这些约定来自本技能几次真实返工。订阅没有写进 OPML 订阅清单（一种用于导出和导入信息源订阅的文件格式）时，按现行技能重跑会丢掉只写在某一期稿件里的补录，DeepSeek Harness 的三条就曾经因此漏掉。在技能或站点里为旧格式写兼容分支，会让规则和数据各走一套，以后更难收敛。上游改了却留下旧的关键词、总结或页面，数据和线上展示会对不上。把这些约定记在本技能自己的项目记忆里，是为了以后接手的人和智能体不必再从对话里重新发现。

**How to apply:**

修改本技能的流程、契约、脚本、数据或站点渲染之前，把下面九条逐项过一遍。任何一条没有做完，都不要宣称这次改动已经完成。

### 1. 以技能为主体

流程由本技能串联，脚本只是各子步骤调用的工具。每个子步骤的说明文件都要写清生成命令、校验器、JSON Schema（用 JSON 写成的数据契约）以及输入和输出。根目录的 SKILL.md 是流程入口，不要在里面放脚本清单或对照表。

### 2. 不做兼容层

旧数据不符合新规则时，应当改数据或按新规则重新生成，不要在技能或站点里写专门兼容旧格式的分支。

### 3. 契约先行

新增或修改某一步的数据产物时，必须同步修改对应的 JSON Schema 和校验器，并按语义化版本（主版本号.次版本号.补丁号）提升本技能的版本号。每个阶段目录里的 stage.json 要记录生成时所用的技能版本，以便追溯是用哪个版本写出的这份数据。

### 4. 找出受影响的下游

先判断这次改动落在拉取（raw）、清洗（cleaned）、总结（summary）哪一步，再列出所有依赖它的下游，包括关键词、总结阶段的其他产物、站点页面渲染，以及已经发布的历史各期。这些下游全部重新计算并验证，不要保留旧结果。

### 5. 重跑用新的智能体

测试本技能时，应当交给一个没有本次对话上下文的新智能体，只给它本技能和输入，让它从头重新生成每一期。不要向它提示期望出现的条目或旧稿内容，也不要手工改写旧稿来冒充重新生成。

### 6. 订阅以 OPML 为准

新增或补录的信息源必须写进 OPML 订阅清单，否则按现行技能重跑时会丢失这些来源。曾经因为只补了某一期稿件、没有写进订阅清单，重跑后漏掉了 DeepSeek Harness 补录的三条。

### 7. 站点联动

站点只读取总结阶段目录（summary）里的数据。改动章节名称或字段时，要排查站点里写死的文案和字段名，例如「本周关键词」目前出现在 site/src/lib/summary-issue.mjs、site/src/plugins/remark-keyword-cloud.mjs 等处。改完后用手机与桌面、浅色与深色四种组合截图验收。

### 8. 严格按顺序

先改技能，再生成数据，最后改站点。上一步没有完成，不要并行开始下一步。

### 9. 一路做到上线

改动走独立分支和拉取请求。如果目标是发布，就要做到合并、部署和线上核验这一步才算结束。不要改每周定时例程（按时自动启动的任务定义）的执行时间。
