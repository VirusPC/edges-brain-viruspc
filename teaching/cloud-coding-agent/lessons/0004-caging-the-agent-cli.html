CLI 关进笼子

平台不自己写 Agent，而是把六家现成的 Agent CLI 装进 Sandbox、关掉它们所有的确认，再从它们的输出里把进度和会话编号捞回来。这一课拆开这层“适配”，并说清楚：既然 CLI 什么都能做，真正的笼子到底是什么。

第 4 课 · 约 12 分钟 · 研究对象：vercel-labs/coding-agent-template · 前置：第 1 课、第 2 课、第 3 课

学完这一课，你能做到

说出六家 CLI 各自怎么装、用什么参数跳过确认、提示词和密钥怎么递进去、MCP 写到哪个配置文件、追问时靠什么接上上一轮；讲清“Agent CLI 适配层”的设计和它的毛病；并且在被问到“你们怎么敢让 Agent 免确认跑”时，说出真正的边界是 Sandbox，以及密钥和外网这两个缺口今天怎么补。

先看全貌：一个入口，六个适配文件

后台流程在 Sandbox 建好、仓库克隆好、依赖装好之后，只调用一个函数 executeAgentInSandbox()（app/api/tasks/route.ts L590–L603）。它做三件事：

  1. 把用户的密钥临时塞进服务器进程的环境变量 index.ts 用户在个人设置里存了自己的密钥，就先改写 process.env，选 Copilot 时还把用户的 GitHub 令牌放进 GH_TOKEN；函数结束时在 finally 里改回去。各家适配文件之后都从 process.env 里读密钥。 lib/sandbox/agents/index.ts L49–L75 lib/sandbox/agents/index.ts L149–L158
  2. 按类型分发 index.ts 类型只有六种：'claude' | 'codex' | 'copilot' | 'cursor' | 'gemini' | 'opencode'。一个 switch 调到对应文件的 executeXxxInSandbox()。 lib/sandbox/agents/index.ts L12 lib/sandbox/agents/index.ts L77–L148
  3. 每个文件自己包办一切 agents/*.ts 先 which 看装没装，没有就装；写配置文件（模型、MCP）；拼出免确认的命令行；运行；读输出、抓会话编号；最后 git status --porcelain 看有没有改动，返回同一种结果对象（成功与否、输出、是否有改动、会话编号）。

这就是“适配层”：上面是统一的调用，下面每家一个文件，把这家 CLI 的脾气消化掉。但要注意，这里没有一个真正的接口类型。六个函数的参数个数都不一样（Gemini 只收 5 个，不收“是否续接”和会话编号，lib/sandbox/agents/index.ts L127–L128），共同的只有返回值的形状。日志、安装检查这些重复代码也是每个文件各抄一份。 第 1 课说过：用户第一次提交任务时，Sandbox 里一切都是现装的。所以这一课里的“安装时机”就是：每个任务、在依赖装完之后、Agent 开跑之前。

两个横向问题

一、不锁版本。六个安装命令都没写版本号，每个任务装到的都是当天最新版。CLI 的参数一改名、配置格式一变，模板就悄悄坏掉，上面那一列就是活例子。第 3 课说的“把 CLI 烤进镜像”，顺带也能把版本钉住。

二、工作目录不统一。Claude、Copilot、Cursor 明确在项目目录 /vercel/sandbox/project 里运行（lib/sandbox/agents/claude.ts L415–L423）；Codex 用 runInProject 先 cd 进去（lib/sandbox/commands.ts L66–L76）。但 Gemini 和 opencode 用的是不带目录的 runCommandInSandbox（lib/sandbox/agents/gemini.ts L237 lib/sandbox/agents/opencode.ts L356）。模板自己专门写了 runInProject 去 cd，说明默认目录不是项目目录，所以这两家看起来是在仓库外面启动的。这是读代码推断，没有实测。

提示词怎么递进去：命令行参数，外加一次粗糙的“消毒”

六家都把提示词当命令行参数传，没有一家用标准输入或文件。在交给 Agent 之前，后台流程先做一次处理：反引号换成单引号，删掉所有 $ 和反斜杠，以 - 开头的行前面补一个空格，免得被当成参数（app/api/tasks/route.ts L580–L585，追问接口里同样一段 app/api/tasks/[taskId]/continue/route.ts L259–L264）。

然后分两种走法：

  • 拼进 shell 字符串（Claude、Codex、Gemini、opencode）：… "${instruction}" 塞进一对双引号，交给 sh -c（lib/sandbox/agents/claude.ts L295 lib/sandbox/agents/codex.ts L308 lib/sandbox/agents/gemini.ts L234–L236 lib/sandbox/agents/opencode.ts L346）。删 $ 和反引号，是为了不让 shell 把提示词里的 $(…) 当命令执行。可双引号没人管：提示词里的引号如果成对，会被 shell 悄悄吃掉；只有一个，整条命令语法出错；有人刻意构造，还能在后面接上别的命令。
  • 参数数组（Copilot、Cursor）：提示词作为数组里的一个元素直接交给 sandbox.runCommand，不经过 shell，什么字符都安全（lib/sandbox/agents/copilot.ts L282–L290 lib/sandbox/agents/cursor.ts L451–L459）。但它们照样吃了前面那次“消毒”，用户写的 $HOME、正则里的 \d 都被删掉了，Agent 收到的是改过的需求。

有意思的是：这里的转义问题主要是正确性问题，而不是安全问题。因为 Agent 本来就被允许在 Sandbox 里执行任何命令，多注入一条命令，也拿不到 Agent 拿不到的东西。真正该担心的是需求被改坏、命令跑不起来。更干净的做法是全部改用参数数组，或者走标准输入：Codex 的 exec 支持用 - 从标准输入读提示词（Developer commands），Claude 的 -p 也能接管道输入（CLI reference）。 追问时情况更复杂：如果没能重连旧 Sandbox，追问接口会把最近几条对话（包括 Agent 自己之前的回复，每条截到 500 字）拼到提示词后面（app/api/tasks/[taskId]/continue/route.ts L266–L284）。也就是说，Agent 上一轮的输出会变成下一轮命令行的一部分。

“现在还是不是这样”：三处已经过时或可疑

一、Codex 这条路今天很可能直接启动失败。模板给网关写的是 wire_api = "chat"。Codex 在 2026 年 2 月删掉了对 chat/completions 的支持，今天源码里遇到这个值会报“wire_api = "chat" is no longer supported”并拒绝加载配置（codex-rs/model-provider-info，讨论 #7782）。模板又不锁版本，所以今天跑 Codex 加网关密钥，按推断会在读配置时就失败。我没有实测。

二、Claude 的 config.json 写在了官方不认的位置。Claude Code 文档里的用户配置文件是 ~/.claude/settings.json（Settings），没有 ~/.config/claude/config.json。按推断这个文件不起作用，真正生效的是命令前面拼的环境变量；它唯一确定的效果是在磁盘上多留了一份明文密钥。另外，Vercel 今天给 Claude Code 的推荐写法也变了：地址用 https://ai-gateway.vercel.sh/claude-code，密钥放 ANTHROPIC_AUTH_TOKEN，并把 ANTHROPIC_API_KEY 设成空字符串（Vercel 文档）。

三、opencode 的 auth add 不在官方命令列表里。官方文档里管理凭证的子命令是 opencode auth login（CLI 文档）。代码里失败了也只是“继续”，密钥还会通过环境变量传进去，所以按推断不影响运行。

MCP 怎么塞进各家 CLI

用户在网页上登记的 MCP 服务器存在 connectors 表里，分本地（一条启动命令 + 环境变量）和远程（地址 + 可选的 OAuth client id / secret）两种。任务开始时，后台流程查出当前用户所有“已连接”的服务器，解密环境变量和 secret，交给适配文件（app/api/tasks/route.ts L536–L578）。之后六家各写各的格式：

同一份数据，六种格式，六份手写的转换代码。这里藏着这一课最实在的几个 bug：

  • 四家拿不到本地服务器的环境变量。后台流程已经把解密后的 env 用 JSON.parse 变成了对象（app/api/tasks/route.ts L550），Copilot、Cursor、Gemini、opencode 却又对它 JSON.parse 一次（lib/sandbox/agents/copilot.ts L128–L134 lib/sandbox/agents/cursor.ts L204–L211 lib/sandbox/agents/gemini.ts L114–L121 lib/sandbox/agents/opencode.ts L174–L181）。对对象做 JSON.parse 会先把它变成字符串 "[object Object]"，然后报错，被 catch 住只打一条“解析失败”的警告。只有 Claude 和 Codex 用 Object.entries，拿得到。数据库字段的类型写的是字符串（lib/db/schema.ts L203），解密时却换成了对象，类型和实际对不上，才埋下这个坑。这是读代码推断。
  • Claude 的 MCP 可能登记错了项目。claude mcp add 不加 --scope 时默认是 local，按官方说法“只在添加它的那个项目里加载”（MCP · Local scope）。而模板跑 mcp add 用的是不带目录的 runCommandInSandbox，真正运行 Claude 时却在项目目录里。按推断，登记上的服务器在运行时不会被加载；用来检查的 claude mcp list 也是在同一个“错的”目录里跑的（lib/sandbox/agents/claude.ts L260），所以检查会显示正常。没有实测。另外，Claude 只在“这台机器上还没装 CLI”时才配 MCP（lib/sandbox/agents/claude.ts L213–L216）。
  • opencode 的配置文件位置不在官方列表里。官方的全局配置是 ~/.config/opencode/opencode.json，项目里是 opencode.json（Config · Locations），没有 ~/.opencode/config.json。按推断这份 MCP 配置不会被读到。
  • 小问题：各家“确认文件写成功了”的检查用 test -f ~/.cursor/mcp.json 这样的写法，却不经过 shell，~ 不会被展开，所以这条检查永远报“不存在”，只是影响日志（lib/sandbox/agents/cursor.ts L254）。

读输出时的三个隐患（都是读代码推断）

一、按“块”而不是按“行”解析。Claude 和 Cursor 都是拿到一块输出就按换行切开，逐段 JSON.parse，解析失败就丢掉。可输出块的边界不保证落在换行上，一行 JSON 被切成两半时，两半都会被丢掉。如果被切的恰好是 Claude 的 result 那一行，上面那个没有出口的循环就会一直等下去，直到 Sandbox 时长用完。正确做法是自己留一个缓冲区，攒到换行再解析。

二、Cursor 等 240 秒就不等了，但进程还在跑。到点以后直接去 git status，后台的 Cursor 可能还在改文件，后面的提交就可能只提交了一半。

三、“跑完”靠猜，不靠进程。Claude 和 Cursor 用 detached: true 启动，拿到的命令对象有 wait()，但没有用；失败时 CLI 可能根本不打 result 行（Cursor 文档明说失败时“stream may end early without a terminal event”，Output format）。

日志脱敏。所有日志都经过同一个函数 redactSensitiveInfo()：TaskLogger 每写一条都先过它（lib/utils/logging.ts L76–L82）。它是一串正则：ANTHROPIC_API_KEY=sk-ant-…、GITHUB_TOKEN=ghp_…、克隆地址里的令牌、Bearer …、任何名字里带 KEY / TOKEN / SECRET / PASSWORD 的赋值（lib/utils/logging.ts L6–L74）。命中的值保留前 4 位和后 4 位，中间换成星号。Claude 和 opencode 打印命令前还先手动把密钥换成 [REDACTED]（lib/sandbox/agents/claude.ts L302 lib/sandbox/agents/opencode.ts L349）。值得挑的毛病有三个：正则里 [sk-]、[gh][phosr]_ 是“字符集合”写法，本意应该是前缀，属于写错了但碰巧不太影响的那种（lib/utils/logging.ts L14–L16）；保留首尾 8 个字符本身就泄露了一部分；最重要的是，它只管日志，Claude 和 Cursor 写进 task_messages 的 Agent 回复是不过滤的（lib/sandbox/agents/claude.ts L331–L345）。Agent 如果在回复里贴出一段环境变量，就会原样进数据库、显示在网页上。 Codex 在密钥格式不对时，会把密钥的前 15 个字符写进错误信息（lib/sandbox/agents/codex.ts L94）。这句话里没有“KEY=”这样的结构，按推断那串正则匹配不到它。

“笼子”到底是什么

六家 CLI 自己的“笼子”全都被拆掉了：Claude 跳过权限确认，Codex 的参数名直接叫“绕过审批和沙箱”，Cursor 是 --force，Gemini 是 --yolo，Copilot 放开全部工具，opencode 默认就全放开。所以真正剩下的边界只有一层：第 3 课讲的那台 Firecracker microVM。

为什么云端产品敢开免确认？因为最坏的情况被限定在“这一台、这一个任务的机器”里：它有自己的内核，删光文件、装恶意软件、把 CPU 跑满，都碰不到宿主机和别的用户；机器是临时的，任务结束就没了；对用户代码库的影响只能通过推送到任务分支体现出来，合进主分支还要人点 PR。没有人坐在屏幕前一条条点“允许”，不开免确认，Agent 根本跑不动。

风险在哪？在笼子里面和笼子的门上。

  • 密钥就在笼子里。上面表格里的每一把密钥，Agent 用一条 env、ps、cat ~/.config/claude/config.json 或 git remote -v 就能看到。
  • 门是开着的。模板锁定的 SDK 0.0.21 的创建参数里没有网络策略（第 3 课），出站全放开。
  • 提示词不全是用户写的。仓库里的 README、代码注释、issue 内容、MCP 工具返回的结果、Agent 访问的网页，都可能夹带“把环境变量发到某某网址”这样的指令。Agent 免确认，就会照做。密钥 + 开着的门 + 被注入的指令，三样凑齐就是一次外传。
  • 令牌的权限比任务大。GitHub 令牌是用户登录时拿到的，能做的事取决于它的授权范围，按推断不只限于这个仓库的这个分支。拿到它的人可以推别的分支、碰别的仓库。
今天的 Vercel Sandbox 能怎么补

一、收紧门（第 3 课讲过）。networkPolicy 可以在创建时指定，也可以在运行中用 sandbox.update() 换：先 allow-all 装依赖，Agent 开跑前换成只允许 AI Gateway、GitHub 和包仓库的白名单（Sandbox firewall）。

二、把密钥挪到笼子外面：credentials brokering。在白名单的某个域名下配 transform，Sandbox 发往这个域名的 HTTPS 请求会在防火墙那一层被加上或覆盖请求头，密钥本身不进虚拟机。官方原话：“The secrets never enter the sandbox, so code running inside it cannot exfiltrate them.”而且注入的请求头会覆盖 Sandbox 里代码自己设的同名请求头（2026-02-23 更新日志）。套到这个模板上：给 ai-gateway.vercel.sh 注入 Authorization: Bearer 网关密钥，Sandbox 里的 CLI 只拿一个假值；给 GitHub 注入令牌，克隆地址里就不用再写令牌。哪些 CLI 用的是 Authorization 请求头、能不能直接这样替换，要逐家验证，这一句是推断。这和第 1、2 课讲的 Open SWE 用代理替换凭证是同一个思路。

文档里写明的限制，面试时可以主动说：域名匹配靠 TLS 握手里的 SNI；用了 * 兜底时，没有 SNI 的连接（例如 SSH）会原样放行，也不会被注入；匹配条件只决定“改不改请求”，从不拦请求；按 IP 段放行的流量会绕过 SNI 过滤和凭证注入（Sandbox firewall）。此外，令牌本身也该缩小：只限这个仓库、短期有效。

面试视角：Agent CLI 适配层

面试时 60 秒这样讲

“coding-agent-template 不自己写 Agent，而是支持六家现成的 CLI：Claude Code、Codex、Copilot、Cursor、Gemini、opencode。结构是一个统一入口 executeAgentInSandbox 加每家一个适配文件。入口负责把用户密钥临时换进环境变量、按类型分发；适配文件负责在 Sandbox 里现装 CLI（两家用官方 curl 脚本，四家 npm 全局装，都不锁版本）、写配置文件（模型、MCP，六种格式）、拼出免确认的命令行，比如 Claude 的 --dangerously-skip-permissions、Codex 的 --dangerously-bypass-approvals-and-sandbox，然后读输出。Claude 和 Cursor 用 stream-json，边读边把进度写进数据库，并从 result 事件里拿到 session_id 存起来，追问时用 --resume 接上；其余几家读普通文字，有的靠正则猜编号。模型请求方面，Claude 和 Codex 走 AI Gateway，其余直连。既然 CLI 被允许做任何事，真正的边界就是 Sandbox 这台 Firecracker microVM：它挡住宿主机和其他租户，但挡不住机器里明文的密钥被读走、再从默认全开的网络发出去。所以我会补两件事：Agent 开跑前用 networkPolicy 收成白名单，再用防火墙的凭证注入把密钥留在虚拟机外面。”

如果自己做，会怎么改（参考答法）

一、定一个真正的接口。每家只实现四件事：install()（返回要装的包和版本）、buildInvocation(prompt, model, resume)（返回参数数组和环境变量，不返回 shell 字符串）、renderMcpConfig(servers)（从同一份结构化数据生成这家的格式）、parseEvent(line)（把一行输出翻译成统一的“文字 / 工具调用 / 会话编号 / 结束”事件）。安装检查、日志、等进程退出、git status 这些公共逻辑放在外面，只写一份。

二、全部用结构化输出。今天几家都有：Codex exec --json（第一条事件就带会话编号），opencode run --format json，Gemini --output-format stream-json，Cursor 和 Claude 的 stream-json（Codex、opencode、Gemini）。解析时按行缓冲；“跑完了”以进程退出为准，事件只用来显示进度。

三、提示词不进 shell。用参数数组或标准输入，不做“删掉 $ 和反斜杠”这种会改坏需求的处理。

四、版本钉死，烤进镜像。CLI 和它的配置格式一起锁版本，升级时跑一组“契约测试”：每家用固定的小仓库跑一遍，检查参数还认不认、输出事件还是不是那几种。上面那一列“今天还是不是这样”，就是没有这组测试的代价。

五、密钥不进笼子。环境变量按命令传（runCommand 的 env），不改服务器进程的 process.env，避免第 1 课说的多个任务互相串；能用防火墙注入的就不放进 Sandbox；GitHub 令牌换成只限本仓库、短期有效的那种。

面试官可能的追问（附参考答法）

问：为什么不自己写一个 Agent，而要适配六家？
答：好处是省事、跟得上各家最新能力、让用户挑自己熟的那家。代价是平台对 Agent 内部几乎没有控制：没法统一做工具权限、没法在工具调用前插一道检查、输出格式各不一样，而且每家一升级就可能坏。Open SWE 走的是另一条路，自己用 LangGraph 写 Agent，控制力强，但要自己追模型和工具的进展。

问：免确认模式下，你怎么防提示词注入？
答：在 Agent 里面防不住，要在外面防。原则是“即使 Agent 被完全控制，它能造成的损失也有限”：机器是临时的、隔离的；网络只放必要的域名；密钥不在机器里，由防火墙在出站时注入；令牌权限只够推这个任务分支；合进主分支要人审 PR。日志脱敏只是最后一道遮挡，不是防线。

问：追问时怎么让 Agent 记得上一轮？
答：两种办法。一是续接 CLI 自己的会话：保存它给的会话编号，下次带上 --resume，前提是还是同一台机器、会话文件还在。二是把对话历史拼进新提示词，换了机器也能用，但会丢掉工具调用的细节，还占上下文。这个模板两种都用了，但判断条件是“有没有重连上旧机器”，而不是“这家 CLI 有没有真的续接上”，所以 Copilot 和 Gemini 会落在两头都没有的空档里。
