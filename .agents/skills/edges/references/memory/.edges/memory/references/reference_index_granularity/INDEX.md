# 原始报告 04 — 索引粒度的先验与阈值

- 调研日期：2026-08-25
- 调研范围：面向 LLM 的索引/摘要设计的可量化先验，含 IR 经典文献、llms.txt、sitemap、API 文档索引、MOC 实践
- 综合结论见 [`README.md`](../reference_prior_art/INDEX.md)
- 以下为子 agent 原始产出，未做删改
- **一处编者注**：报告在「可信度校准」一节称 Claude Code 文档里没有「最多加载 5 条」。文档确实没写，但源码 `src/memdir/findRelevantMemories.ts` 的 `SELECT_MEMORIES_SYSTEM_PROMPT` 原文含 `(up to 5)`，该数字成立，出处是源码而非文档。

## 一、直接量化的核心发现

### 1. 「只用标题做索引」的召回损失有实测数字：约 73%

这是唯一一个直接量化「标题 vs 标题+摘要」的研究，[发表于 JASIS](https://asistdl.onlinelibrary.wiley.com/doi/10.1002/asi.4630250606)，用真实用户 profile 做检索代理对比。

- 只用标题：命中率仅为「标题+摘要」的 **27%**（即丢失约 73% 召回）
- 只用摘要：命中率为 **69.5%**
- 多词查询下标题更差：**16.8%**；摘要 **40%**
- 精确率方面：三种代理都在 **48–57%** 区间，标题的精确率并不更高

**对本方案的含义**：`AGENTS.md` 索引行如果只写文件名或条目标题，理论召回上限约为「标题+一句摘要」的 27%。这条直接支持「索引行必须带一句职责描述」，而不只是列条目名。

### 2. Passage 级 vs 文档级：两级结合永远优于任一单独一级

Callan 1994（SIGIR，[PDF](https://www.cs.cmu.edu/~callan/Papers/callan794.pdf)）是这个问题的经典对照实验：

- 固定窗口 passage 检索 + 文档级证据结合：提升 **7% ~ 23.5%**
- 论文明确结论：**结合两级证据永远不差于单独任一级**
- 最佳 passage 长度：**150–300 词**（约 800–1600 字节）
- 论文原文提到过短的段落（如 50 词）表现明显下降

**对本方案的含义**：不该是「文件级索引」或「条目级索引」二选一。正确形态是保留文件级索引行（提供主题上下文），同时增加条目级索引（提供定位精度）。当前实测的 970 字节/条恰好落在 150–300 词的最佳区间内，说明**条目粒度本身是对的，缺的是索引层**。

### 3. Claude Code 自己的记忆索引有硬性上限：200 行 / 25 KB

来自 Anthropic 官方 memory tool 文档：

- `MEMORY.md` 会话开始时**自动读取**，其余记忆文件按需
- 上限 **200 行或 25 KB，先到者为准**；超出部分**静默丢弃**
- 官方明确的重组信号：接近 200 行时应把细节移入独立文件，`MEMORY.md` 只保留摘要与指针
- 索引条目的官方示例格式是「文件名 + 一句职责」：

```markdown
# Memory Directory
- `progress.md`: Current task status and completed steps
- `notes.md`: Key findings and observations
```

同时 Claude Code 的 `CLAUDE.md` 建议控制在 **200 行**以内（软目标，与 `MEMORY.md` 的硬上限是两回事），import 语法 `@path` 最多 **5 跳**递归。

**对本方案的含义**：本方案的 `AGENTS.md` 形式像 `CLAUDE.md`、功能像 `MEMORY.md`。既然功能等同索引，就应该采用 `MEMORY.md` 的硬上限（200 行 / 25 KB）而不是 `CLAUDE.md` 的软建议。当前索引 8 行远未触顶，但需要一个明确的触顶动作。

### 4. Agent Skills 的 description 上限：1024 字符

来自 Anthropic Agent Skills 文档：

- `name` ≤ 64 字符，`description` ≤ **1024 字符**，两者是唯一常驻系统提示的部分
- 官方要求 description 同时写明「skill 做什么」与「什么时候用」
- `SKILL.md` 正文建议 **500 行以内**，超出应拆到引用文件
- 官方明确的三级渐进披露：metadata（常驻）→ 正文（触发时）→ 引用文件（需要时）

**对本方案的含义**：1024 字符是「按需加载单元的描述」的绝对上限，但这是给 LLM 判断「是否加载」用的完整描述，不是索引行。索引行应远小于此。

### 5. llms.txt 的实践阈值：单行 ≤120 字符，每组 3–30 条

来自 [llmstxt.org](https://llmstxt.org/) 规范与 [第三方实践指南](https://www.aiwithcam.com/blog/llms-txt-optimization-guide-2026)（注意：120 字符与 3–30 条属实践建议，非规范硬性要求）：

- 格式固定为 `- [名称](URL): 一句描述`
- 描述建议 **≤120 字符**，理由是"safe"（可靠被解析利用）
- 每个 H2 分组 **3–30 个链接**，超过 30 应拆分新分组
- `## Optional` 分组语义特殊：**上下文紧张时可跳过**
- 规范强调「简洁、无歧义的语言，避免需要额外上下文才能理解的表述」

**对本方案的含义**：120 字符 ≈ 40–60 个汉字，这是索引行的合理长度目标。当前每行「文件名 + 一句职责」正好在这个量级。3–30 条/分组的建议意味着：单个 `.edges/` 文件下的条目数超过 30 时应该拆文件。

### 6. Anthropic 的 token 预算量化：~100 token metadata 换取无限扩展

来自 [Anthropic 官方工程博客](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)：

- 每个 skill 的 metadata 常驻成本"a few dozen tokens"，文中给出的具体数字是 **约 100 token**
- 关键论断："Skills 可以无限扩展知识，同时几乎不影响上下文窗口"
- 三级预算：metadata（~100 token）→ `SKILL.md`（<5k token）→ 引用文件（无上限）
- 上下文编辑 + 记忆工具的实测：100 轮工具调用任务上准确率 **+39%**，token 消耗 **-84%**

**对本方案的含义**：如果为每条 `## 条目` 生成一行索引，预算应控制在约 20–30 token/条（比 skill metadata 更紧，因为条目数量级更大）。这与 120 字符的建议基本吻合。

### 7. 上下文腐化的量化：干扰项数量与位置都显著影响准确率

来自 [Chroma 的 context rot 研究](https://research.trychroma.com/context-rot) 与 [Lost in the Middle](https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.arxiv2023.pdf)（TACL）：

- Lost in the Middle：答案位于上下文中间时性能最差；GPT-3.5-Turbo 在此情况下的表现**低于完全不给文档的闭卷基线（56.1%）**
- Chroma 在 18 个前沿模型上验证：**准确率随输入 token 增加而下降**，且在窗口占满之前就开始退化
- 干扰项的复合效应：**单个干扰项就使准确率低于 needle-only 基线，4 个干扰项时进一步下降**，且不同干扰项的影响不均匀
- 反直觉发现：**打乱的（不连贯的）上下文常常比逻辑连贯的上下文表现更好**——即结构良好的连贯上下文反而提供了更多似是而非的线索

**对本方案的含义**：「先读 `.edges/FEEDBACK.md`」这条无条件全量加载指令，在文件增长后会引入干扰项。基于 4 个干扰项显著劣化的数据，单次加载的条目数应控制在**个位数**，理想是 3–5 条。这比「省 token」的动机强得多——这是正确性问题。

## 二、其他有价值但量化较弱的发现

### Sitemap 的分片阈值（工业标准，可类比但需谨慎）

来自 [sitemaps.org 协议](https://www.sitemaps.org/protocol.html) 与 Google 文档：

- 单个 sitemap 上限 **50,000 条 URL / 50 MB**（未压缩）
- 超出用 sitemap index 分片，index 本身也是 50,000 上限，**最多两层**
- Google 明确建议按逻辑分组分片（按类型、按更新频率），便于定位问题
- `<priority>` 和 `<changefreq>` 已被 Google 忽略——**声明式的重要性/新鲜度标注在实践中不被信任**，实际信号来自 `<lastmod>` 这类可验证的事实

后一点对记忆系统有直接借鉴：agent 自己声明的「重要性评分」可能不如「最后修改时间」「被引用次数」这类客观信号可靠。

### API 文档索引的定位（相关但迁移性有限）

OpenAPI 的 `summary`（短，用于列表展示）vs `description`（长，用于详情）分离，正是「索引行 vs 正文」的对应。Stripe 的三级导航结构（分类 → 资源 → 端点）与本方案的「AGENTS.md → 文件 → 条目」同构。但 API 文档索引可从 schema 机械生成，记忆索引需要语义判断，这是本质差异。

### MOC 与 PARA（社区经验，无量化依据）

- MOC（Map of Content）的社区经验阈值：单个 MOC **10–15 条**开始考虑拆分，**25 条**是明确上限。来源是 Obsidian 社区实践，非研究结论。
- MOC 的核心主张对本方案有直接价值：MOC 应该给出**「为什么这些条目在一起」的上下文**，而不只是罗列链接。这与前述「标题-only 召回率 27%」的实测相互印证。
- PARA 按「可操作性」而非「主题」分类。本方案的 FEEDBACK / PROJECT / REFERENCE 三分法本质上已是可操作性分类（约束 / 状态 / 外部指针），这个设计与 PARA 一致。

### 递归摘要的原则性发现

来自 [OpenAI 的递归摘要研究](https://openai.com/index/summarizing-books/)：分层摘要必然逐层丢失细节，越高层越抽象。这对多层索引的含义是：**索引不应是正文的摘要，而应是正文的「路标」**。索引丢失细节是设计意图（否则就该直接读正文），但必须保留足够的路由信息。

## 三、对五个问题的直接回答

**Q1 索引粒度**：文件级 + 条目级两级并存，不要二选一。依据是 Callan 1994 的「两级结合永远最优」（+7%~23.5%）。条目级索引行应包含标题 + 一句「何时适用」，纯标题会丢约 73% 召回。

**Q2 常驻 vs 按需**：常驻部分严格设上限（Claude Code 的 200 行/25 KB 是可直接采用的具体值），且常驻内容应是路由信息而非事实内容。判据不是「重要性」而是「是否每次任务都需要」——Anthropic 的 ~100 token metadata 换无限扩展就是这个权衡的最优点。

**Q3 整合机制**：Sitemap 忽略 `<priority>` 的教训说明，声明式重要性不可靠；应基于客观信号（最后修改时间、被引用次数）。llms.txt 的 `## Optional` 分组提供了一个不删除也不常驻的中间态。

**Q4 过期与冲突**：调研中未找到针对「记忆与代码状态不一致」的量化研究，这是真空。可类比的是 `<lastmod>` 这类可验证事实优于声明式标注的经验。

**Q5 多层级作用域**：Claude Code 的 import 5 跳上限和 sitemap index 的两层上限，都指向「层级要浅」。Sitemap 的「按逻辑分组分片，便于定位问题」建议可直接用于目录级记忆的组织。

## 四、三个最值得采纳的具体做法

### 做法 1：给索引行设硬上限并实现触顶动作

采用 Claude Code `MEMORY.md` 的 **200 行 / 25 KB** 作为 `AGENTS.md` 受管区块的硬上限，并在脚本里实现：达到 150 行（75%）时警告，达到 200 行时拒绝新增并提示重组。重组动作明确为「把细节移入独立 `.edges/` 文件，索引只留摘要与指针」——这是 Anthropic 官方给出的重组方向。

单条索引行控制在 **120 字符 / ~30 token** 以内（llms.txt 实践值），格式固定为 `- 标题：一句何时适用`。这个格式经 JASIS 实测支持（标题+摘要的召回率是纯标题的 3.7 倍）。

### 做法 2：条目级索引与文件级索引并存，不替换

不要用条目级索引替换文件级索引行。Callan 1994 的核心结论是两级证据结合永远优于任一单独一级（+7%~23.5%）。具体形态：

```markdown
- `.edges/FEEDBACK.md` — 编码约束与禁止模式（12 条）
  - Tab 切换必须 keep-alive：涉及路由/缓存改动时
  - 收入接口不得并发调用：涉及 income API 时
```

文件级行提供主题上下文，条目级行提供定位精度。当某文件条目数超过 **30**（llms.txt 分组上限）时拆文件，而不是继续加深索引。

### 做法 3：把「单次加载条目数」作为核心约束，目标 3–5 条

这是本次调研中最反直觉但证据最硬的一条。Chroma 的实测显示：**1 个干扰项就使准确率低于 needle-only 基线，4 个时进一步下降**；Lost in the Middle 显示答案在中间位置时 GPT-3.5 表现低于闭卷基线。

因此「先读 `.edges/FEEDBACK.md`」这类无条件全量加载指令，在文件增长后是**正确性风险**而非成本问题。应改为：索引层负责把候选条目收窄到 3–5 条，再加载这些条目的正文。这个数字比任何 token 预算都更值得优先满足。

附带一个反直觉的推论：Chroma 发现打乱的上下文常优于连贯上下文，因为连贯上下文提供更多似是而非的线索。这意味着**把多条无关约束拼成一篇「读起来连贯」的文档，可能比保持条目彼此独立更容易诱发错误**。条目之间应保持明确的边界，不要为了可读性而写过渡性的连接语句。

## 五、可信度校准

**高可信（同行评议 + 实测数据）**：Callan 1994 的 passage/文档两级结合（SIGIR，明确实验对照）；JASIS 的标题 vs 摘要召回率对比（真实用户 profile）；Lost in the Middle（TACL，多模型验证）。

**中可信（厂商官方文档，规范性但无对照实验）**：Claude Code 的 200 行/25 KB 上限、1024 字符 description 上限、~100 token metadata 成本、5 跳 import 上限。这些是产品规范而非研究结论，但作为「已被大规模部署验证的工程选择」有参考价值。

**中低可信（第三方实践指南 / 二手转述）**：llms.txt 的 120 字符与 3–30 条建议来自第三方指南而非官方规范；Chroma 的 context rot 数据我通过二手来源获得（原始 research 页面未能直接访问），其「4 个干扰项」的具体数字建议在采纳前复核原文。

**低可信（社区经验，无量化依据）**：MOC 的 10–15/25 条阈值；PARA 的分类学。这些可作为设计参考但不应作为阈值依据。

**一处需要修正的先前认知**：Claude Code 文档中没有「最多加载 5 条记忆」的规定，我在调研中未找到该数字的官方来源。做法 3 里的 3–5 条是从 context rot 的干扰项数据推导的建议值，不是任何官方规范。
