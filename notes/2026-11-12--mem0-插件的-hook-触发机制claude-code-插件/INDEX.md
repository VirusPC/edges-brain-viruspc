# mem0 插件的 hook 触发机制（Claude Code 插件）

## 背景

2026-11-11，助手「通用-辅助」要弄清 mem0 的 Claude Code 插件何时把对话写成记忆、何时把记忆读回上下文。查证材料是当时的官方文档、CHANGELOG、仓库代码和 PR。插件版本会变，下面以查证当日的代码为准；查证日期是 2026-11-11。

## 主题

这篇记的是 mem0 插件在 Claude Code 里的 hook：写记忆和读记忆不是同一节奏。写是每轮先落本地，攒够再批量送给 Mem0；读在当前插件里只对会话的第一条足够长的提示检索一次。

- 难点一：每轮都有 hook 触发，容易理解成每轮都去云端检索。写路径的本地记录，和读路径的检索注入，要分开看。
- 难点二：读路径换过几版。最早每轮用用户原话检索，中间改成只注入检索规则，旧插件又加回每轮预取，当前 main 上换成 claude-code-plugin。只看某一版文档会对不上现在的行为。
- 难点三：同一次对话里，助手先说「每轮预取」，随后更正为「只在首条提示检索一次」。笔记如果沿用更正前的说法，会把已经不在 main 上的行为写成现状。

## 过程

### 时刻不详 先把召回说成每轮预取

查阅文档、CHANGELOG、仓库代码和 PR 的过程中，助手先把读记忆说成每轮预取。这一句后来被更正，不作为当前行为。

### 时刻不详 更正为只在首条提示检索一次

对照当前插件后，助手改口：main 上现在是 claude-code-plugin，不是已经离开 main 的 mem0-plugin。本笔记从这里起采用更正后的读路径。

当前读路径（召回）：

- UserPromptSubmit hook 每轮都会跑。
- 只有本会话的第一条提示，并且长度不少于 20 个字，才检索 `top_k=5` 并注入。最短字数可以用环境变量 `MEM0_CODE_MIN_QUERY_CHARS` 调整。
- 其余轮次只把内容记到本地，不发网络请求。之后要用记忆，靠模型自己调搜索工具。
- 检索调用 Mem0 云端 API。搜索 2 秒超时，整个 hook 最多 6 秒。超时就跳过注入，不阻塞对话。
- 这次没有找到实测延迟数据，笔记不补一个延迟数字。

### 时刻不详 写路径按轮次在本地记，再批量发送

写路径（记忆采集）和读路径同时被核对，规则是：

- 每轮都有 hook 触发。用户消息、模型回答、改过的文件，以及测试或构建结果，先记到本地。这一记本地的步骤不调模型。
- 每攒够 5 轮，才由后台进程批量发给 Mem0 抽取记忆。
- 会话结束、压缩上下文、空闲 5 分钟，也会各触发一次发送。

### 时刻不详 用历史版本解释两种说法为什么都出现过

读路径在仓库历史上换过几次。对话里把这些取舍都对过，顺序如下：

1. 最早：每轮用用户原话做语义检索，并把 top-5 塞进上下文。
2. 2026-05 的 PR #4992 第一次去掉这种每轮检索。当时的理由有三条：很多消息用不上记忆，调用被浪费；把原话当查询词，召回质量差；结果多为噪音，占上下文。改法是只注入「何时搜、怎么搜」的规则，由模型自己决定要不要搜。
3. 后来旧插件 mem0-plugin 的 `on_user_prompt.sh` 又把每轮预取加回来。`MEM0_PREFETCH` 默认开。加回的理由是保证相关记忆一定在上下文里。
4. 这个旧插件已经不在 main。现在换成 claude-code-plugin，读路径是上面写的「首条提示检索一次」。

助手更正前说的「每轮预取」，对得上第 3 步的旧插件，对不上第 4 步的当前插件。笔记保留这段历史，避免以后把旧插件的默认值当成 main 的现状。

### 时刻不详 顺带核对另外几处 hook

同一轮查证里还看到这些，它们不改变上面的写路径和读路径：

- CHANGELOG 去掉了用 Stop hook 把内容注入上下文。原因是 Stop 的输出无法可靠塞回对话。
- PreToolUse 用来拦截对 `MEMORY.md` 的写入，并给 mem0 工具强制加上 `user_id` 和 `app_id`。
- 插件里也带 Codex 和 Cursor 的 hooks 配置。对话没有给出这两家宿主上的触发次数。

## 结果

查证结论已经收成这篇笔记，采用更正后的读路径：claude-code-plugin 只在本会话第一条、且不少于 20 个字的提示上检索并注入；写路径仍是每轮本地记录，满 5 轮或遇到会话结束、压缩上下文、空闲 5 分钟再批量发送。

没有留下要改代码或要补测的事项。实测延迟没有数据，这里空着。插件以后改版时，以当时的代码为准，不把 2026-11-11 的行为写成永久规则。

## 所学

- 看到「每轮都有 hook」时，先问这一轮是在本地记账，还是在打 Mem0 的云端 API。当前插件里，这两件事的频率不同。
- 读路径前后有过四种做法：每轮原话检索 top-5、只注入检索规则、旧插件每轮预取、当前插件首条提示检索一次。去掉每轮检索，以及旧插件把预取加回来，各自有当时记下的理由。前三种不是现在 main 上 claude-code-plugin 的行为。
- 每轮原话检索被拿掉，是因为浪费调用、查询词质量差、噪音占上下文。旧插件把每轮预取加回，是为了让相关记忆一定出现在上下文里。当前插件两边都没沿用，改成首条提示检索一次，后面的轮次改由模型自己调搜索工具。
- 助手在同一次对话里先说错再更正。对外只保留更正后的当前行为，更正前的「每轮预取」只作为旧插件的历史，不作为现状。
- 超时边界是搜索 2 秒、hook 最多 6 秒，超时跳过注入。没有实测延迟，就不写「通常多少毫秒」。

## 行动指南

### 主题行动指南

#### 背景

要用 mem0 的 Claude Code 插件时，需要先知道记忆什么时候进得了上下文，而不是把 hook 名字当成「每轮都在检索」。

#### 核心问题

当前 claude-code-plugin 在什么条件下写记忆、什么条件下把记忆注入对话。

#### 核心解决方案

1. 写和读分开记。写：每轮把用户消息、模型回答、改过的文件和测试或构建结果先记到本地，这一步不调模型；满 5 轮，或会话结束、压缩上下文、空闲 5 分钟，再由后台批量发给 Mem0 抽取。读：UserPromptSubmit 每轮都跑，但只有本会话第一条提示、且不少于 20 个字，才检索 `top_k=5` 并注入。
2. 判断「现在是哪一版」时，以 main 上的 claude-code-plugin 为准。可选项是沿用旧插件 mem0-plugin 的 `MEM0_PREFETCH` 每轮预取：该插件已不在 main，默认开预取是为了保证记忆一定在上下文里，不把它当成当前行为。另一可选项是每轮用用户原话检索 top-5：2026-05 PR #4992 已经去掉，理由是浪费调用、原话当查询词召回差、结果多为噪音。
3. 第一条之后还要用记忆时，让模型自己调搜索工具。这些轮次只记本地，不发网络请求。
4. 检索超时就跳过注入，不阻塞对话。搜索超时 2 秒，整个 hook 最多 6 秒。没有实测延迟数据时，不补一个延迟数字。

#### 验收标准

- 能分开说出写路径（每轮本地记、攒批再发）和读路径（仅首条且不少于 20 字才检索注入）。
- 能指出当前 main 是 claude-code-plugin 的首条提示检索，旧插件 mem0-plugin 的每轮预取不算现状。
- 笔记里写着查证日期 2026-11-11，并写明版本会变、以届时代码为准。
- 超时只保留「搜索 2 秒、hook 最多 6 秒、超时跳过注入」，没有未经测量的延迟数字。

### 细节与其他

#### 若要改首条检索的最短字数

则调整环境变量 `MEM0_CODE_MIN_QUERY_CHARS`。对话里没有比较其它配置入口。

#### 若 Stop hook 的输出需要塞回上下文

则按查证到的 CHANGELOG，这条注入已经去掉，因为 Stop 的输出无法可靠塞回。对话里没有比较其它回注办法。

#### 若要拦住对 MEMORY.md 的写入，或给 mem0 工具补上身份字段

则看 PreToolUse：它拦截对 `MEMORY.md` 的写入，并给 mem0 工具强制加上 `user_id` 和 `app_id`。这里只记触发点，不写具体身份值。

#### 若要在 Codex 或 Cursor 上套用同一套触发次数

则对话只记下插件里带了这两家的 hooks 配置，没有给出触发次数。跨工具时 hook 事件名和返回值各家不同，见 [跨工具 skill 与 plugin 的一处编写多处安装](../2026-10-21--跨工具-skill-与-plugin-的一处编写多处安装/INDEX.md)。
