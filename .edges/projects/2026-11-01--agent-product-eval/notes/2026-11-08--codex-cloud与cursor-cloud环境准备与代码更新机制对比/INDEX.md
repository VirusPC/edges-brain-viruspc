# Codex Cloud与Cursor Cloud环境准备与代码更新机制对比

> 核对日期：2026-11-08（Asia/Shanghai）。重点：云端环境复用的是「准备好的磁盘状态」，代码新鲜度与依赖新鲜度是两条独立的线。

## 背景

2026-11-07 晚到 11-08 凌晨（Asia/Shanghai），用户在与 Grok Bot 的对话中想弄清楚 Cursor Cloud Agent 和 Codex Cloud 的云端环境到底怎么准备、怎么复用、仓库更新后怎么跟进，以便判断云端任务启动时拿到的代码和依赖是不是最新的。本笔记把那段问答整理下来，并在 2026-11-08 重新核对了官方文档；对话里先前说过、后来更正的地方也一并保留。

## 主题

这场对话在学两个云端编码 Agent 平台的环境生命周期：环境模板如何准备与保存，每个任务实例如何从模板启动，仓库有新提交时代码和依赖分别怎样更新。核心结论是两者都复用预先准备好的环境，不是每次重新拉仓库、装依赖，但「代码刷新」和「依赖重装」的触发条件不同。

- 难点一：代码新鲜度和依赖新鲜度是分离的。后台刷新代码不等于重跑安装命令，代码可能已是新提交，依赖却还是旧锁文件装出来的。
- 难点二：环境模板和任务实例是两层。改模板（Publish 或 Build）只影响之后新开的任务，已有任务保留自己的状态。
- 难点三：「镜像」比喻有边界。两者保存的是准备好的磁盘或文件系统快照，不是用户自己维护的 Docker 镜像；运行中的进程不保存，所以启动服务要单独配置。
- 难点四：刷新周期。Cursor 只说「定期检查」，Codex 新版只说「后台自动刷新」，都没有公开具体间隔，不能猜。
- 难点五：Codex 有新旧两套文档，旧版（Legacy）的 12 小时容器缓存加 setup / maintenance 脚本，不能套用到新版。

## 结果

整理成本笔记。对先前结论的核对如下（「文档事实」为官方原文支持，「推论」为据文档推断，「未公开」为文档没写）。

### Cursor Cloud Agents

- 文档事实：Build 是「已准备环境的可启动快照」。流程为触发 → 从基础镜像启动、按默认分支克隆所有仓库、运行 `install` → 保存磁盘状态并记录环境版本和每个仓库的提交 SHA → 成功后激活 → 新 Agent、自动化和代码审查从激活的 Build 启动。Cursor 预热激活 Build 的副本，把克隆和安装移出启动路径。
- 文档事实：Build 失败不替换当前激活的 Build，Agent 继续用上一个成功的 Build。首次成功 Build 之前，Agent 用 Cursor 默认镜像启动，不带环境配置。
- 文档事实：触发原因有四种：定期（Recurring）、保存配置或改 secrets、手动 Trigger build、Agent 请求的测试 Build。定期检查若默认分支无新提交且配置无变化就跳过，不跑 install；只有定期 Build 会被跳过。
- 未公开：定期检查的具体间隔。先前「每小时」的说法已更正，文档没有承诺。
- 文档事实：`install` 在每次 Build 时运行，须幂等；`start` 和 `terminals` 在每次 Agent 运行开始时执行。Build 只保存磁盘状态（含仓库检出和 `/var/lib/docker`），进程、shell 导出变量、内存缓存不保存。
- 文档事实（代码新鲜度）：默认分支运行从激活 Build 记录的提交开始；开启 Update stale builds 且 Build 超过 Staleness threshold 时，启动时拉最新默认分支代码；关闭时原样使用记录的提交。默认阈值 24 小时，设为 0 始终拉取。功能分支运行则在 Build 磁盘上检出所请求的分支，复用 Build 的依赖。
- 文档事实（依赖新鲜度）：启动时拉新代码不会因此重跑 install；功能分支改了依赖时，Agent 会拿到环境上下文和 install 命令，可自行刷新。可用 Cursor Cloud MCP 的 `environment-info` 查看本次运行用的 Build ID，以及是复用检出还是拉了新代码。
- 文档事实（镜像边界）：快照或 Dockerfile 只定义基础机器；Build 在其上克隆、install，再生成新的可启动快照。所以「环境 = Docker 镜像」不准确，更接近「基于镜像准备好的磁盘快照」。
- 文档事实（环境选择）：环境按仓库或仓库组自动解析，优先级为个人保存的环境 → 团队保存的环境 → 仓库里的 `.cursor/environment.json`（仅单仓）。Builds 页可以「从指定 Build 启动 Agent」用于测试或调试。`environment.json` 可写 snapshot ID。本次核对的两篇文档里没有找到「启动时按环境名或环境 ID 选环境」的说明，属于未在这两篇文档中确认，不下定论。

### Codex Cloud 新版

- 文档事实：环境是任务复用的配置（仓库、依赖、工具、访问设置）。Codex 检查仓库、安装依赖并和用户一起测试，审阅后 Publish；发布会保存准备好的文件系统，供新任务使用。每个新任务从已发布环境得到独立工作区。
- 文档事实：启动任务时在 Work in > Cloud 里按名称选择已发布环境（如 `acme-web`）；Slack / Teams 中可在提示里点名偏好的环境。
- 文档事实：可记录 Install script（安装依赖、准备资源）和 Start skill（启动服务并检查就绪）。
- 文档事实（代码新鲜度）：仓库刷新在后台自动进行，保留依赖缓存，不重跑安装或启动命令。
- 未公开：后台刷新间隔，以及是否保证每次新任务都拿到最新提交。
- 文档事实（依赖新鲜度）：要更新可复用的设置，需在 Settings > Codex Cloud > Environments 里 Edit，让 Codex 准备和测试，再 Republish；之后新开的任务才用新设置，已有任务保留自己的状态（含未提交改动和已装工具）。
- 文档事实：任务的 VM 状态默认在最后一次开始轮次或恢复后最多可找回 7 天。
- 推论：新任务启动不是从零克隆和安装，而是从已发布文件系统开始；文档没有逐字说明启动时是否执行 checkout。

### Codex Cloud 旧版 Legacy

- 文档事实：每个任务创建容器并检出所选分支或提交 SHA；运行 setup 脚本，恢复缓存容器时可选运行 maintenance 脚本。容器状态最多缓存 12 小时。改 setup、maintenance、环境变量或 secrets 会自动使缓存失效，也可手动 Reset cache。
- 文档事实：旧版目前仍用于 Code Review 以及 Linear、GitHub 集成，官方计划废弃。与新版是两套机制，不能混用。

无未闭环待办。周期未公开属于文档事实，不当作待办。

## 所学

- 先把「环境模板」和「任务实例」分开想。模板是 Cursor 的激活 Build 或 Codex 的已发布环境；实例是每次任务的独立机器或工作区。改模板影响以后的新任务，不追溯旧任务。
- 再把「代码新鲜度」和「依赖新鲜度」分开想。两个平台都能让代码比依赖新：Cursor 在 Build 过期后启动时拉代码但不重跑 install；Codex 新版后台刷新仓库也不重跑安装。依赖要变，Cursor 靠新的 Build（定期检查发现新提交或配置变化时会重跑 install），Codex 新版靠 Republish。
- 两者差异：Cursor 的定期 Build 会因默认分支新提交自动重跑 install，依赖能自动跟进；Codex 新版文档只写代码后台刷新，依赖变化要人工 Edit 后 Republish。Cursor 提供可调的过期阈值和 `environment-info` 溯源；Codex 新版没有公开类似阈值。
- 「镜像」比喻只能说到基础机器为止。真正复用的是磁盘或文件系统快照；服务进程每次启动重新拉起（Cursor 的 `start` / `terminals`，Codex 的 Start skill）。
- 讨论中先说过「每小时构建」，之后更正。教训是：没有文档承诺的周期不写具体数字。

## 行动指南

### 主题行动指南

#### 背景
云端编码 Agent 为了启动快，会复用提前准备好的环境快照，代码和依赖的更新各有触发条件。

#### 核心问题
如何确保云端任务用的代码和依赖都和预期一致，而不是默认它们一定最新。

#### 核心解决方案
1. 区分模板与实例：改环境配置或依赖后，先重建或重新发布模板，再开新任务验证；不要指望已在运行的旧任务自动跟上。
2. 依赖变更（锁文件、工具版本）后主动触发环境更新：Cursor 手动 Trigger build 或等定期 Build，Codex 新版走 Edit 再 Republish。只等代码刷新不够，因为代码刷新不重跑安装。
3. 对代码新鲜度敏感时显式控制：Cursor 把 Staleness threshold 调小或设为 0；Codex 新版周期未公开，在任务开头让 Agent 自己查看并拉取需要的提交。可选项是每次都全量重装依赖，但会抵消预热环境的速度优势，当时只在依赖变化时才这样做。
4. 安装脚本写成幂等，可在旧磁盘状态上反复执行；服务启动放到启动阶段，不放安装脚本里，因为快照不保存进程。
5. 排查环境问题时先查溯源：Cursor 用 `environment-info` 看 Build ID 与是否拉了新代码；Codex 看环境是否已发布、是否 Republish 过。

#### 验收标准
- 新任务里 `git log -1` 的提交符合预期。
- 新任务里依赖版本与当前锁文件一致，测试能跑通。
- 依赖变更后确有一次成功的 Build 或 Republish，且验证是在之后新开的任务里做的。
- 服务在任务启动后可用并通过就绪检查。

### 细节与其他

#### 若用的是 Codex 旧版集成
则按 Legacy 机制理解：12 小时容器缓存，恢复缓存时用 maintenance 脚本补装依赖；必要时 Reset cache。不要把新版的 Publish 机制套过来。

#### 若 Cursor 的新 Build 失败
则 Agent 仍从上一个成功 Build 启动；去 Builds 页看日志，或从失败的 Build 启动一个 Agent 复现。

#### 若想在 Cursor 指定环境
则依据文档，环境按「个人 → 团队 → `.cursor/environment.json`」自动解析，调试时可在 Builds 页从指定 Build 启动；按环境名或 ID 指定的方式在本次核对的文档中未确认。
