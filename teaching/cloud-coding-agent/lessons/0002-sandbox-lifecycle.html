Sandbox 的生与死

一台 Sandbox 什么时候开、开多久、什么时候真的关，追问时又是怎么找回来的。

第 2 课 · 约 10 分钟 · 研究对象：vercel-labs/coding-agent-template · 前置：第 1 课

学完这一课，你能做到

画出一台 Sandbox 的五种状态（创建、运行、空转、待命、停止），说清 Keep Alive 开和关分别走哪条路，并回答面试官最常追问的三件事：为什么不共用一台、成本和冷启动怎么取舍、中途超时会怎样。

先看状态图

第 1 课的第 3 步和第 9 步，就是一台 Sandbox 的出生和收尾。这一课把中间展开。

读图只要抓一句话：这份代码里，Sandbox 的寿命在出生那一刻就定死了，等于用户选的最长时长；之后平台能做的，只有“提前手动关掉”或“留着给追问用”。（这是因为模板锁定的 @vercel/sandbox 0.0.21 里还没有续时长的方法。现行 SDK 有 extendTimeout()，可以边跑边续到套餐上限；持久 Sandbox 每次恢复还会重新计时，见 JS SDK Reference 和 Vercel 官方指南。） “冷启动”指从零开一台新机器、拉代码、装依赖的这段等待。Keep Alive 开着，追问时就能省掉它。

四个关键时刻

  1. 出生：三个参数定下一生 creation.ts Sandbox.create() 收到的参数是：运行环境 node22、4 个 CPU 核、要开放的端口，以及存活时长 timeout。时长来自用户在界面上选的最长时长（5 分钟到 5 小时），后台流程把它拼成 "300m" 这样的字符串传进去，createSandbox 再去掉非数字、换算成毫秒。注意它没有传仓库地址，注释写明“我们自己手动克隆到 /vercel/sandbox/project”。建好后马上登记，方便用户中途叫停。 lib/sandbox/creation.ts L73–L103 app/api/tasks/route.ts L447–L466 components/task-form.tsx L724–L733
  2. 干活：浅克隆进项目目录 Sandbox 里 先 mkdir -p /vercel/sandbox/project，再用带令牌的地址 git clone --depth 1 进这个目录。之后装依赖、跑 Agent、推送，都在这个目录里进行。这段时间一直在消耗那份事先定好的时长。 lib/sandbox/creation.ts L111–L134 lib/sandbox/commands.ts L4
  3. 跑完：Keep Alive 决定岔路 route.ts 关：先从内存登记表里删掉，再调用 shutdownSandbox。它只是用 pkill 结束 node、python、npm、yarn、pnpm 进程，然后返回“成功”。机器本身还开着，直到时长用完，这就是图里的“空转”。出错时也走同一条路。
    开：什么都不做，只写一条日志“留给追问”。用户追问时，追问接口从数据库读出 sandboxId，用 Sandbox.get() 重连。重连报错才新开一台。 app/api/tasks/route.ts L668–L683 lib/sandbox/git.ts L75–L100 app/api/tasks/[taskId]/continue/route.ts L162–L190
  4. 死亡：只有两种死法 Vercel 一是时长到了，Vercel 自动停掉；二是用户在界面上点“停止 Sandbox”，后端用 Sandbox.get() 连上后调用 sandbox.stop()，再把数据库里的 sandboxId 清空。整个项目里，只有这里和内存登记表的 killSandbox 调了 stop()。 app/api/tasks/[taskId]/stop-sandbox/route.ts L35–L57 lib/sandbox/sandbox-registry.ts L25–L60
三处“文档和代码对不上”，面试里任选一处讲

一、“没有关机方法”是错的。git.ts 第 93 行注释说“当前 SDK 没有关机方法”。但项目锁定的 @vercel/sandbox 0.0.21（package.json L42）里，Sandbox 类本身就有 stop()（npm 包 dist/sandbox.js 第 219 行），同一个项目的停止接口也在用它。所以 Keep Alive 关闭时并不是“做不到关机”，而是没去关。

二、“关闭就不能追问”也不准。README 的对照表写 Keep Alive 关闭时“不能追问”（README.md L113–L120）。可追问接口并不看这个开关：重连不上，就新开一台、浅克隆、切回原来的任务分支，再把最近 5 条对话塞进提示里（app/api/tasks/[taskId]/continue/route.ts L192–L243、app/api/tasks/[taskId]/continue/route.ts L266–L284）。代价是又冷启动一次，Agent 也接不上原来的会话（以 Claude 为例，只有重连成功时才带 --resume，lib/sandbox/agents/claude.ts L280–L289）。

三、“最长 5 小时”其实被一个 5 分钟卡住。vercel.json 给 app/api/tasks/route.ts 设了 "maxDuration": 300（vercel.json L1–L8），这个数的单位是秒（Vercel 函数时长文档）。而 Next.js 文档写明，after() 里的活也只能跑到这个路由的时长上限为止（after() · Duration）。看起来，指挥 Sandbox 的后台流程最多活 5 分钟，Sandbox 却可能被设成 5 小时。这一点我没有实际部署验证，面试里要说“按文档推断”。

今天的 Vercel Sandbox 已经不一样了

这个模板的代码停在 2026 年 2 月。之后 Vercel 给 Sandbox 加了几件直接改变“生与死”的东西：

变化是什么意思出处
有名字的 Sandbox每台 Sandbox 有一个在项目里唯一的名字，用 Sandbox.get({ name }) 找回，不再靠随机编号（2026-03-26 先出测试版）。更新日志
默认持久化Sandbox 停下时自动把文件拍成快照，下次任何一条命令都会自动从快照“复活”。一台 Sandbox 可以跨很多次开机，每次开机叫一个会话。2026-05-26 正式发布。更新日志 · Persistence 文档
快照保存文件和装好的软件包，用来跳过安装、做存档点、给别人一份一样的起点；默认在最后一次使用后 30 天过期。Snapshots 文档
单次最长 24 小时2026-06-16 起，一个会话最长从 5 小时提到 24 小时（Pro / Enterprise；Hobby 是 45 分钟）。上限只管单个会话，不管整台 Sandbox。运行中还能用 extendTimeout() 加时。更新日志 · 价格与限制

把这些和模板对照，最值得说的一点是：今天“关机”和“丢文件”已经是两回事了。模板里 Keep Alive 是在“省钱（关掉）”和“追问快（留着）”之间二选一；有了持久化，可以任务一结束就 stop()，追问时再按名字找回，文件还在，只多一次开机的等待。另外，按官方迁移说明，新版 SDK 用 name 代替 sandboxId，老代码要改（迁移表）。

同类产品怎么管环境的一生

一台环境给谁用追问时状态留多久
coding-agent-template每个任务一台Keep Alive 开就重连；否则新开一台、重新克隆到最长时长为止，停了文件就没了
OpenAI Codex Cloud每个新任务从“已发布的环境”得到自己独立的工作区回到原任务，接着用它自己保存的文件，连没提交的改动也在默认在最后一次开始或恢复任务后，最多 7 天可恢复（Cloud environments）。旧版文档写的是容器状态缓存最多 12 小时（Legacy）
LangChain Open SWE每个对话一台持久的 Linux Sandbox追问复用同一个对话的上下文和 Sandbox（README L50–56）连不上时不悄悄换一台空的，因为那会丢掉没提交的改动；只有确认机器已经不存在才新建（sandbox-lifecycle.md）

Open SWE 那份生命周期文档是仓库里自动生成的说明（文件头写着 openwiki 生成），但它放在官方仓库里，并标出了对应的源文件。

面试时 60 秒这样讲

“在 Vercel 的 coding-agent-template 里，每个任务开一台 Vercel Sandbox，参数是 node22、4 核，存活时长直接等于用户选的最长时长，所以寿命在出生时就定了。代码被浅克隆到 /vercel/sandbox/project，Agent 在里面改完、推送。之后看 Keep Alive：关的话，它只 pkill 掉进程，机器其实空转到超时；开的话，机器留着，追问时用数据库里的 sandboxId 调 Sandbox.get() 重连，连不上就重新开一台、克隆任务分支。真正调用 stop() 的只有手动停止接口。这里的取舍是：留着机器，追问快、开发服务器还在，但空转也算钱；关掉，省钱但下次要冷启动。现在 Vercel 有了默认持久化、带名字的 Sandbox 和快照，单个会话最长 24 小时，可以做到一跑完就停、追问时按名字恢复文件，两头兼得。”

面试官可能的追问（附参考答法）

问：为什么不让所有任务共用一台 Sandbox，省掉冷启动？
答：三个原因。第一是隔离：第 1 课讲过，用户的 GitHub 令牌被写进了克隆地址，Agent 又是免确认模式在跑，共用一台就等于让一个用户的 Agent 能碰到另一个用户的代码和令牌。第二是干净：每个任务要从一份干净的代码和依赖开始，否则上一个任务装的包、改的文件会污染下一个。第三是出事范围：一台机器卡死只影响一个任务。冷启动的代价可以用别的办法降：Codex Cloud 用缓存好的环境给每个任务开独立工作区，Vercel 现在可以从快照开机，跳过装依赖。

问：Keep Alive 开着，成本和冷启动怎么权衡？
答：Vercel 按两样东西收费：真正用 CPU 的时间，和分配的内存乘以开机时长。后者在机器闲着时也照算（官方指南）。所以开着等追问，内存一直在计费；关掉，下次追问要重新开机、克隆、装依赖。有意思的是，这个模板的“关”只结束进程、不调 stop()，机器照样开到超时，省钱的效果打了折扣。更好的做法是用持久化：任务结束立刻 stop()，文件自动存成快照；追问时按名字恢复，只付一点快照存储费。

问：跑到一半时长到了，会怎样？
答：后台流程和一个同样长的计时器赛跑，计时器先到，就把任务标成出错，日志写“超时”（app/api/tasks/route.ts L276–L331）。但赛跑输了并不会让后台流程停下来，它会继续跑到 Sandbox 被 Vercel 停掉、命令失败为止。推送只在 Agent 正常结束后才做，所以没推送的改动就丢了。改进方向：长任务中途定期 commit 存档；运行中用 extendTimeout() 加时；打开持久化，让停机时自动留快照；再把指挥流程放到不受 5 分钟函数时长限制的地方（Vercel 文档对这种需求推荐的是 Workflows）。

问：Keep Alive 开着，但用户第二天才来追问呢？
答：机器早已超时停了。追问接口只在 Sandbox.get() 报错时才新开一台，它没有检查返回对象的状态，而 SDK 0.0.21 的状态里本来就有 stopped。所以看起来，一台已经停掉的 Sandbox 可能被当成“重连成功”，等到跑命令时才失败（app/api/tasks/[taskId]/continue/route.ts L169–L190）。这一点同样是读代码推断，没有实测。
