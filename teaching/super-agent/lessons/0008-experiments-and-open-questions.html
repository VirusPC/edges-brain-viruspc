先把实验的限度放在前面

原文写：由于实验基于合成负载与简化环境，部分设置还可以更加严谨，以下结果仅作为初步参考。编码工作用一个只消耗时间的工具代替，因此实验衡量的是系统的调度与协作能力，而非对单个任务的执行能力。课里如实记下数字，不把它们升级成普遍结论。 原文 · 第 7 节

7.1 消融：调度能力，不是写代码能力

实验用群聊和 GitHub CI 消息流同时驱动四种端到端方案。单次实验约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息。每种方案重复运行 5 次。对比的四种方案包括：完整的 Super-agent、去掉直通的 Super-agent，以及两种提示词配置下的「单 Session + Subagent」工具（中性提示，以及提示优先委派）。 原文 · 第 7.1 节

观察原文给出的数字或事实
Super-agent 完成时间p50 为 12.4 分钟，p95 为 15.7 分钟，显著优于带 Subagent 的单 Session
中性提示的单 Session五次运行一次都没有调用 Subagent，工作都在主 Session 中进行并不断被新消息打断，p95 达到 29.5 分钟
提示优先委派的单 Session五次中有四次进行了委派，完成时间有所缩短但整体仍慢于 Super-agent；剩下一次模型判断工作「很小」而自己执行，形成长尾
系统开销Super-agent 因维护多个独立会话，单次实验的读缓存 token 高于单 Session，是以更多的 token 消耗换取更短且更稳定的完成时间
去掉直通任务完成时间与完整版基本一致；Router 需要做出的决定约增 30%；读缓存 token 从 2323 万增至 3177 万，约增 37%

原文据此区分两件事。第一，相比于在单 Session 中依赖提示词工程和模型临场判断分不分工，双层架构通过让 Router 不直接执行具体工作、Worker 仅接收所订阅 Thread 的消息，在系统层面上缓解了这一问题。第二，在该实验负载下，直通机制不提高任务完成质量与速度，但为 Router Session 节省了可观的 token 与推理开销。

7.2 批处理：拥堵时单个决定更便宜

为了验证第 2.1 节中单个常驻 Router Session 的吞吐上限与批处理机制，作者单独对 Router 层做了压力测试：Router 调用真实模型，Worker 使用 Mock 模型，将需要决定的 Trigger 到达速率从每分钟约 1 条逐步提升至约 40 条。 原文 · 第 7.2 节

当到达速率从每分钟约 1 条升至约 40 条时，平均 batch 大小从 1.0 升至 2.8，而单次请求耗时仅从 2.5 秒增至 3.9 秒，增长慢于 batch 大小，从而使单个决定分摊的推理时间从 6.4 秒降至 1.6 秒。这意味着外部事件突发拥堵时，Router 层能够通过自动合并积压事件提高有效吞吐。这也解释了为什么在 7.1 节中，即使去掉直通使 Router 的峰值负载增加，仍未触及单 Router 的吞吐瓶颈。因此在他们当时的团队规模下，无需过早对 Router 层做水平切分而牺牲全局上下文的连续性。

第 8 节：开放问题保持开放

第 2 至第 6 节的五个模块构成了支撑 Super-agent 运转的基本架构，第 7 节的实验也验证了其中核心调度与路由机制在多任务并发下的效果。原文接着说：这套系统之所以能够以较低的复杂度运作，很大程度上是因为他们在当前阶段做出了一系列工程和场景简化。超出这些简化的适用范围后，仍有问题需要解决。下面四条都是开放问题，课里不编造答案。 原文 · 第 8 节

  • 8.1 如何扩展双层架构。「单常驻 Router Session + 订阅直通 + Worker 间不直接通信」覆盖了他们当时的大多数日常任务；当规模扩大、耦合度提高，超出单个 Router Session 的承载范围时，层内结构并无定论。Router 层何时需要水平切分、粒度如何划分，同层 Worker 何时需要直接通信、采用何种协作拓扑，仍有待检验。系统与模型的协同设计，以及跨月甚至更长周期时的长程记忆，也是制约可扩展性的问题。
  • 8.2 脱离 Session 之后如何与 Agent 协作。底层多会话管理对用户隐藏之后，如何向用户呈现任务并提供自然的交互与项目管理形式，成为新的问题。原文认为，以聊天窗口为中心的交互在一定程度上是路径依赖的结果；交互可能可以更多地发生在领域特化的界面中。同时，在模型能力演进的过渡期内，许多任务仍需要人类在中途参与，如何兼顾逐步干预与后台自主推进，同样值得探索。最终形态很可能高度定制化。
  • 8.3 如何划分上下文边界并进行 A2A 协作。前文讨论的是单个 Super-agent 实例内部，默认其服务范围内的信息都汇总在同一个全局上下文中。组织扩大时，配备 Super-agent 实际上是在划分上下文共享与隔离的边界。一旦存在多个彼此隔离的实例，跨边界的协同就是 Agent 间通信（A2A，不特指某个协议）。在互不共享底层上下文、各自代表不同权限边界的前提下，如何实现安全、可靠的 A2A，仍需进一步探索。
  • 8.4 如何保障安全与隐私。事件驱动增加了接触不可信输入的风险。原文写得很重：如果没有办法很好地解决安全与隐私问题，那么 Super-agent 只有在一个很小且可信的范围才能工作。第 5 节把 Agent Loop 放在云端、并在执行设备上安装轻量 daemon，这一设计默认建立在云端与端侧彼此受信任的前提之上；一旦云端因服务端入侵或提示词注入被攻破，其连接的全部端侧设备都面临被控制的潜在风险。即使云端未被攻破，只要端侧凭据能够进入模型的上下文，正常执行中同样存在凭据泄露的风险，因此还需要让 Agent 在完全不接触凭据本身的情况下使用凭据。

原文结语还写：他们并没有提出全新的理论，而是把计算机系统中经典的工程思想应用到了 Agent 系统的构建中；具体实现会随技术发展而演进，但系统设计思路有更长期的参考价值。部分设计已在 dsh-superagent-prototype 中实现——该插件只是为了验证技术路线而提供的原型，并非 DeepSeek 的正式产品。这些话用来收束全文，不改变第 8 节仍然开放的事实。 原文 · 第 9 节

合上原文，60 秒这样讲

「第 7 节是初步实验，基于合成负载和简化环境，测的是调度与协作，不是把代码写得有多好，结果只作参考。四种方案里，完整 Super-agent 的完成时间更短也更稳，p50 是 12.4 分钟，p95 是 15.7 分钟。单 Session 加 Subagent 很吃提示词：中性提示下五次都没调用 Subagent，p95 到了 29.5 分钟；改成优先委派后好一些，但仍慢，还出现一次自己下手的长尾。双层架构是在系统上缓解这件事，而不是把希望寄托在临场发挥。去掉直通后，完成时间差不多，但 Router 的决定大约多 30%，读缓存 token 大约多 37%，所以直通在这个负载下主要是省开销，不是提速。Router 的批处理则说明，事件越挤，单个决定分摊的推理时间反而可以下降。第 8 节把扩展、协作形态、A2A 和安全隐私都留作开放问题。尤其是安全：原文说，如果这个问题解决不好，Super-agent 只能在很小且可信的范围里工作。课里不编造答案。」
