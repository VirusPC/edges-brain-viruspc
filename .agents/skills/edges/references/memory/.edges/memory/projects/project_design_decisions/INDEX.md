# project-memory 设计决策记录

记录 `edges-memory-init` / `-ask` / `-remember` 三个 skill 成型过程中的关键取舍与依据。
「形状是什么」看 [`PROTOCOL.md`](../../../../references/PROTOCOL.md)，「实现长什么样」看 [`LAYOUT.md`](../../../../references/LAYOUT.md)，本文只回答「为什么是这样」。**那两份文件只说重点，所有论证都在这里**——早期章节里出现的 `memory-layout.md` 是 `LAYOUT.md` 的旧名，叙述保留原样。

按时间追加，不改写历史。2026-08-25 之前的章节记录的是初版形态，其中被 [2026-08-26 的结构改造](#2026-08-26改为-memory--索引内容分离)取代的结论已在该节列出，读到旧结论时先对照那份清单。

## 三个 skill 的分工

**决策**：init 管存储、ask 管检索、remember 管沉淀，共享资产归 init。

**理由**：remember 从一开始就引用 `<init-dir>/scripts/memory.py`，init 事实上已经是这组 skill 的共享家。后来抽出的 `references/memory-layout.md`、`references/templates/` 都放在 init 下，避免出现「脚本在 init、文档在别处」的两个家。

## 不为「记忆存储结构」单开第 4 个 skill

**背景**：索引结构这段知识三个 skill 都可能要用，考虑单独做成一个 skill 共享。

**决策**：不开 skill，做成 init 下的 `references/memory-layout.md`，另两个 skill 按相对路径引用。

**理由**：

- 纯事实性的 skill 没有触发条件。skill 靠 description 匹配加载，一份静态知识文档要么永不触发，要么为了能触发写得很宽泛而到处误命中；而每个 skill 的 description 常驻会话占预算。
- 本仓库已有惯例，且刚好不是 skill：`runa-sdd-shared/` 只有 `lib`/`prompts`/`scripts`、没有 SKILL.md，被 5 个 sibling skill 按路径引用。
- 三个 skill 需要的是同一套布局的三种投影——ask 要「索引怎么导航」，remember 要「kind → 文件路由」，init 要「受管区块的创建与幂等语义」，实际重叠比看起来小。
- ask 是热路径（几乎每次提问都跑），所以导航概要和「挑文件只看职责说明」这类每次都要用的判据仍内联在 ask 里，只把完整结构外提。

## 文案全部外提为模板

**决策**：脚本里不保留任何写死的输出文案，全部放 `references/templates/`，运行时读取。

**演进**：先抽 `.edges/` 的初始正文（原 `TEMPLATES` 常量），后来发现 `AGENTS.md` 三个受管区块的文案仍硬编码在 `build_index` / `build_root_policy` / `refresh_root_index` 里，与「改文案改模板」自相矛盾，一并抽出。

**关键约束**：

- 区块模板不能用 `.md` 后缀，否则会被 init 当成记忆文件复制进 `.edges/`。沿用 `module.tpl` 已有的 `.tpl` 约定，后缀因此有了语义：`.md` 复制、`.tpl` 按需填充占位符。
- 区块标记（`<!-- edges:start -->` 那些）留在脚本里，不写进模板。它们是幂等替换的锚点，放进模板后一旦被误改，重复执行会重复插入或匹配失败。
- 初始化模板按 `templates/*.md` glob 读取，所以加一个 Markdown 模板等于给每个新记忆目录多一份初始文件，不用改代码。
- 模板缺失一律报错，不静默产出空文件或空区块。

## 不做「一整个 AGENTS.md 模板」

**背景**：既然文案都外提了，为什么不是一份完整的 `AGENTS.md` 模板加占位符。

**证据**：只初始化子目录时，`sub/AGENTS.md` 里只有 `project-memory` 一个区块，而记忆根的 `AGENTS.md` 里是 `project-memory-policy` 加 `project-memory-index`、没有 memory 区块（根自己没建 `.edges`）。一次 init 写的是两个文件、两套不同的区块组合。

**决策**：维持区块级模板，只把「`AGENTS.md` 完全不存在时的骨架」抽成 `agents-scaffold.tpl`。

**理由**：

- 三个区块归属不同：memory 跟着每个有记忆的目录，policy 只在记忆根一份，index 只在有带记忆的下级时才出现。它们不是一个文件的三个段落。
- 刷新时机不同：`remember` 只调 `refresh_index` 刷 memory 区块；policy 和 index 只在 init 时动，且写的是另一个文件。没有哪个时刻是「整份渲染」。
- 文件不归我们所有。核心不变量是区块外正文一律保留——本仓库根 `AGENTS.md` 就是手写正文、runa-memory 受管块、本套区块三者共存。按区块正则替换是共存的前提。
- index 区块增量累加：条目一次 init 加一条，不传 `--description` 时保留已有条目的描述（返回 `preserved`）。整份渲染就得从磁盘重建全部兄弟条目，手工润色过的描述会被冲掉。

## 保留在脚本里的四条字符串

索引条目格式 `- [路径](路径) — 描述`、空目录时的「暂无记忆文件」、子目录入口条目、`## 标题` + 正文的组装。

**决策**：不外提。这些是数据拼装而非文案，抽成模板会让格式与解析规则分离——索引条目格式与 `refresh_root_index` 里判断「条目是否已存在」的正则是配套的，拆开容易失配。

## 记忆分类与命名对齐 Claude Code auto memory

**决策**：分类、命名、`kind` 枚举全部对齐官方 `type`，取三类：

| kind | 文件 | 官方定义（原文） |
| --- | --- | --- |
| `feedback` | `FEEDBACK.md` | Guidance from the user about how to approach work — what to avoid and what to keep doing |
| `project` | `PROJECT.md` | Information about ongoing work, goals, initiatives, bugs, or incidents not derivable from code or git history |
| `reference` | `REFERENCE.md` | Pointers to external systems where information can be found |

**触发原因**：原模板不够通用。官方有一条硬性否定规则——凡是能从代码推导的都不记——而原 `OVERVIEW.md` 模板写着「项目目标、架构、目录、数据流」，正撞在这条上，等于在鼓励记录代码里本来就有的信息。

**第四类 `user` 不落盘**：角色、专长、个人偏好是跨项目的个人信息，不属于仓库内记忆，remember 本来就明确不收。`module` 不是官方类型，是本地扩展，对应官方「一个主题一个文件」的做法。

**连带改动**：`MEMORY_FILE_DESCRIPTIONS` 必须同步改，否则 `AGENTS.md` 索引里的一行说明和文件正文各说一套；remember 的路由表加了「收什么」一列，否则 kind 名字换了、agent 的理解没换，`project` 照旧会被填进架构说明。

## `module` 保留，但索引描述改为从文件提取

**背景**：对齐官方三类之后，`module` 是否还有必要。

**观察**：跟官方比，`module` 才是对齐的那部分，三件套反倒是本地发明。官方没有 `module` 类型，因为它那边每条记忆都是独立 topic 文件、`type` 只是 frontmatter 字段，文件粒度永远是「一个主题一个文件」。

**决策**：两者都留。三件套的聚合形式适合我们的检索方式——官方靠 Sonnet 从 manifest 挑至多 5 条，文件多不是问题；我们靠 agent 读索引再 `rg`，文件少而密更好查，git 里 review 一个 `FEEDBACK.md` 的 diff 也比 review 二十个新文件容易。`module` 则解决两件三件套解决不了的事：跨目录的主题（代码分散、映射不到单一目录）没地方放；以及 `FEEDBACK.md` 是「先读」文件、每次都加载，什么都往里堆会让渐进式披露失效，主题文件是按需加载的泄压阀。

**修掉的缺陷**：`describe_memory_file()` 原先对非固定名一律返回同一句兜底文案，导致十个 module 文件在索引里长得一模一样——而 ask 唯一的挑文件判据就是「只看索引条目后面那句职责说明」。现在改为：固定名查 `MEMORY_FILE_DESCRIPTIONS`，其余取文件引言的首个引用行，都取不到才回退兜底。`module.tpl` 的首行相应改成占位提示，没替换时索引里会直接显示这句提示，等于一个显式的待办。

## 从官方只采纳了正文结构

**决策**：只给 `FEEDBACK.md` 和 `PROJECT.md` 加正文结构（结论 → `**Why:**` → `**How to apply:**`）。

**未采纳**：`feedback` 的「失败和成功都记」；`project` 扩展为 goals/initiatives/bugs/incidents 并加日期规则；排除清单扩写为官方那五条；「排除规则优先于用户明确要求」的门控——最后这条与现有的「用户说记就必须写」直接冲突，属产品取舍，留待定。

**实施要点**：模板里的提示只有读文件时才可见，而 remember 是走 CLI 写入的，所以必须在 remember 的步骤里也写一遍，这条结构才真正生效。`module.tpl` 没加，官方这条只针对 feedback 和 project。

## ask 的检索流程

**决策**：从「固定动作清单」改成「先交代索引结构 → 自由检索 → 末尾统一附来源」。

**理由**：原步骤把手段写死成 `rg -n -i`，而检索方式本该由 agent 按情况选（`rg`、整篇读都行）。索引结构则相反，必须讲清楚，否则 agent 只能猜哪些文件相关。

**目录树示例的取舍**：用占位符 `<子目录>` / `<module>.md` 而不是真实路径，避免绑定具体项目；子目录的 `.edges/` 折叠成一行，因为展开就是根级那四行的重复，会稀释这一段真正想表达的「每级各自持有 + 结构可递归」；递归用一层 `<子目录>/` 加 `└── ...` 表示，不真画三层。

**bullet 精简**：树的注释补上后，原四条 bullet 里有一半在重复树里已有的信息，压成三条，每条以要执行的结论开头，并把原先埋在句末的「挑文件只看职责说明」提到最前——这是整节唯一真正指导行为的规则。

## 顺带修掉的问题

- **`# None — 项目记忆`**：`remember()` 在目标文件不存在时一律用 `f"# {module} — 项目记忆"`，而 `module` 只有 `kind=module` 才有值。删过 `FEEDBACK.md` 再写入就会生成标题为 `# None` 的文件。改为走 `initial_document()`：固定文件回退到对应模板，模块文件才用 `module.tpl`。
- **新建 `AGENTS.md` 多一个空行**：旧代码 `f"# {name}\n"` 自带换行、后面又拼 `\n\n`，与走 `existing.rstrip()` 的路径不一致。模板经 `strip("\n")` 后两条路径统一。
- **死代码兜底**：`initial_document` 里「模板缺失就用 `# {stem}`」这个分支实际走不到（`resolve_memory_path` 返回的路径要么有模板、要么是已存在的 `.mdc`），改成明确报错，与「模板缺失不静默产出」一致。**注**：这三条描述的都是 2026-08-26 改造前的代码，`initial_document` 与 `.mdc` 分支现已不存在；「模板缺失即报错」这条结论仍然生效，落在 `refresh_entry_index` 与 `init_memory` 的前置校验里。

## 语言与文档风格

三个 SKILL.md 原本大量使用电报式省略句（`已验证、以后还能用 → 主动写`），统一改为完整中文；小标题从抽象名词（「调用」）改成读者的实际问题（「什么时候写」）；术语首次出现处交代来历（`<init-dir>` 指同级的 init skill 目录）。

frontmatter 的 `name` 和 `description` 一律不动——那是 skill 的触发条件，措辞已经准确，改动可能影响命中。

**`PROTOCOL.md` 与 `LAYOUT.md` 另有一条更严的约束：只写「是什么」，不写「为什么」。** 论证、辩护、对假想反问的回答、旁枝影响，一律不进那两份文件，全部落到本文。判据是「这句话删掉后，读者会不会照错的方式实现」——不会，就删。它们曾经写成思考记录（给每条约定配一段论证），读起来像草稿而不是契约。

## scaling 瓶颈（已识别，未决）

聚合式三件套的标度关系是反的：**读得越来越多，判得越来越差**。

实测（2026-08-25，本仓库 runa 版 `.edges`）：`CONSTRAINTS.md` 已是 8 条 H2 / 7753 B，约 970 B 一条，而它在 `AGENTS.md` 索引里始终只占一行。官方对照：12 条记忆的 `MEMORY.md` 索引共 14 行 / 2157 B，约 150 B 一条，正文只有被模型选中的至多 5 条才加载。

|  | 常驻加载成本 | 选择性 |
| --- | --- | --- |
| 本方案 | 随条数线性增长（索引首句即「先读 `FEEDBACK.md`」） | 固定 3~4 行，不随条数增长 |
| 官方 | 索引每条约 150 B，硬上限 200 行 / 25 KB | 每条一行，随条数增长 |

N=8 时常驻成本已是官方同规模的约 6 倍，差距随条数线性拉大。

**根因不是聚合本身**（聚合换来的 `rg` 友好和 git review 友好是真的），而是两件事：索引粒度停在文件级；以及用「先读 `FEEDBACK.md`」这种按需层手段去模拟常驻层。官方把 `Anything already documented in CLAUDE.md files` 排除在记忆之外，正因为常驻层就该是 `CLAUDE.md` / `AGENTS.md` 正文，记忆层只负责按需加载——我们两头各占一点，两头的好处都没拿全。

派生缺口：新鲜度机制做不了（聚合文件的 mtime 说明不了单条记忆的新旧，官方按条给 >1 天的 staleness 警告）；`upsert_h2` 靠标题精确匹配去重，近义标题会静默堆积，而官方有 AutoDream 在后台合并修剪。

候选方案，按性价比排序：

1. **索引下沉到条目级** —— 索引列出每个文件的 H2 标题，同时取消无条件「先读 `FEEDBACK.md`」。选择性随条数增长，聚合文件的体积只在真要读它时才付成本，读的时候还能 `rg` 到具体 H2。需要给索引加官方那样的行数/字节上限。
2. **容量阈值** —— 聚合文件超过 N 条或 M KB 时提示拆成 module 主题文件。改动小，缓解不治根，可作为 1 的补充。
3. **彻底对齐官方** —— 一条记忆一个文件，`kind` 降为 frontmatter 字段。scaling 最好，但是重写，且丢掉 `rg` 与 review 优势。

**外部调研（2026-08-25）**：四路独立调研均指向方案 1，见 [`prior-art/OVERVIEW.md`](../../references/reference_prior_art/INDEX.md)。三条改变结论的证据：

- **粒度不是越细越好**。LongMemEval 的消融是倒 U 形——中间粒度最优，再拆成原子事实反而丢信息。Callan 1994 则显示两级证据结合永远最好（+7%~23.5%）。所以方案 1 应是「文件级索引行**保留**、条目级索引**新增**」，不是替换。
- **问题定性要升级：这是正确性问题，不是账单问题**。Lost in the Middle 实测到答案埋在中间时准确率低于闭卷基线；Chroma 实测到单个似是而非的段落就能把准确率压到 needle-only 基线以下。所以「取消无条件先读 `FEEDBACK.md`」的优先级高于省 token。
- **别指望索引提升准确率**。arXiv 2607.26637 实测组织化只降低检索成本（4.0 分 → 1.4 分/查询）、不提高答对率。索引设计的目标函数应定为「最小化读进上下文的字节数」。

阈值取值、以及 `upsert_h2` 标题匹配缺口（basic-memory 的 permalink 式稳定 id）和新鲜度缺口（Graphiti 的失效不删除、Copilot 的 citation + 28 天 TTL）的具体做法，同见 [`prior-art/OVERVIEW.md`](../../references/reference_prior_art/INDEX.md)。

## 2026-08-26：改为 .memory + 索引/内容分离

上一节的 scaling 瓶颈由此结案，选的是候选方案 3（一条记忆一个文件）的变体——保留三个类型入口，没有退成官方那样的单一 `MEMORY.md`。

### 目录名 `.edges` → `.memory`

**理由**：`.edges` 是从 runa 那套沿用来的名字，通用含义是「测试脚手架」，读者猜不到里面装的是记忆。

**正向副作用**：与 `runa-memory-*` 仍在用的 `.edges` 天然隔离，两套目录可以在同一仓库并存，本次因此不需要数据迁移——project-memory 在本仓库还没落过数据，现存的 `.edges/`（`CONSTRAINTS.md` / `OVERVIEW.md` / `REFERENCES.md` / `single-note.md`）属于 runa，不动。

### 三个入口退化为纯索引，内容外移

**决策**：`FEEDBACK.md` / `PROJECT.md` / `REFERENCE.md` 只放一个由脚本重算的条目清单，正文移到 `<type>_<slug>.md`，一条记忆一个文件。

**为什么不是方案 1（索引下沉到条目级、内容仍聚合）**：方案 1 要在 `AGENTS.md` 里维护一份 H2 标题清单，同一份标题就存了两处，而 `upsert_h2` 的标题匹配缺口还在——标题一改，索引和正文各自漂移。内容拆成一条一文件后，条目身份变成文件名，索引可以从 frontmatter 全量重算，这个缺口结构性消失，不用再单独加稳定 id。

**为什么不退成官方的单一 `MEMORY.md`**：`kind` → 文件的路由关系保持显式，remember 只需重算一个入口；三个入口各自也更小。代价是多一跳（`AGENTS.md` → 入口 → 正文），但三个入口都很小，可以一次并读。

**与调研的对账**（[`prior-art/OVERVIEW.md`](../../references/reference_prior_art/INDEX.md)）：兑现了「条目级索引」、「文件级索引行保留而非替换」（`AGENTS.md` 仍列三个入口）、「取消无条件全量加载」、以及 permalink 式稳定 id。仍未兑现：索引行数硬上限、失效不删除、citation 读时校验、单次加载 3~5 条的强制手段——全部转入待议。

### 索引是派生产物，全量重算

**决策**：入口文件的条目区块每次写入都从全部 `<type>_*.md` 的 frontmatter 重算，不做增量插入。

**与前面「不做一整个 AGENTS.md 模板」那节的差异**：那节论证 `project-memory-index` 区块必须增量累加、不能整份渲染，理由是子目录描述来自人传的 `--description`、没有别的事实源，重算会冲掉手工润色。这里相反：条目描述的唯一事实源就是模块文件的 frontmatter，重算才是保证索引不漂移的手段。两处结论相反但判据一致——**看该字段有没有唯一事实源**。

### `kind` 收敛到三类，`module` 去掉

**取代**：上面「`module` 保留，但索引描述改为从文件提取」整节作废。

**理由**：那节留 `module` 的两条论据现在都自动消解了。「跨目录的主题没地方放」——现在每条记忆都是独立文件，`project_*` 就能放；「`FEEDBACK.md` 是每次都加载的文件，什么都往里堆会让渐进式披露失效，需要按需加载的泄压阀」——`FEEDBACK.md` 现在只是索引，不再是内容容器，泄压阀本身成了默认形态。

**连带**：前缀即类型，所以 `type` 字段与文件名前缀信息冗余。仍保留两者，与官方一致（官方 `project_commitlint_types.md` 里 `name` 和 `type` 同时存在），冗余换来的是 `rg 'type: feedback'` 可以直接筛类型，不用靠文件名通配。

### frontmatter 用扁平形态，`name` 等于文件名

**证据**：官方 `~/.claude/projects/*/memory/` 下 13 个模块文件里，10 个是扁平的 `name`/`description`/`type`/`originSessionId`，3 个是嵌套的 `metadata: {node_type: memory, type, originSessionId}`，两种形态按时间交错出现、不是一次迁移。嵌套那套的 `node_type: memory` 像是图谱写入器留下的。

**决策**：扁平，且 `name` 等于文件名去后缀。

**理由**：扁平少一层缩进，`rg` 一行能命中。`name` 钉到文件名是为了让它成为稳定 id——官方两种形态里 `name` 语义不一致（扁平的是中文标题，嵌套的是 slug），其中 `feedback_memo_at_item_layer.md` 的 `name` 甚至写成了 kebab-case 的 `feedback-memo-at-item-layer`，与文件名不符，这种漂移正是要钉死的原因。

**代价与补丁**：`name` 变成 slug 后，索引行的链接文字没有来源了（官方 `MEMORY.md` 里那些中文标题在 frontmatter 里查不到，是手写的）。故新增 `title` 字段，让索引行 `- [{title}]({name}.md) — {description}` 完全可机械生成。这个字段是本地新增，官方没有。

### `username` / `email` 取自 git 配置

**决策**：用 `git -C <target-dir> config user.name` / `user.email`，加 `-C` 是为了让仓库级 `.git/config` 的覆盖优先于全局 `~/.gitconfig`。

**语义是「最后修改者」**，与 `updatedAt` 配对，每次更新都覆盖。未采用「原始作者」语义：那需要同时加 `createdAt`，否则文件里会出现「A 的创建时间戳配 B 的名字」这种错位。

**取不到时整行省略**，不写空值也不报错（非 git 目录、没装 git、`user.name` 未配都算取不到）。这条与 `originSessionId` 同一套处理，也因此模块文件的渲染必须按行拼装，不能用纯字符串替换模板。

**隐私**：邮箱进 git 跟踪文件不构成新的信息暴露，同一个邮箱本来就在每条 commit 里。

### `originSessionId` / `agentClient` 从环境变量探测

原本以为脚本拿不到会话 id、只能由 agent 手传。实测否掉了这个前提：Cursor 下 `CURSOR_AGENT=1`、`CURSOR_CONVERSATION_ID` 就是会话 id（核实过它等于本次会话 transcript 的文件名）。Claude Code 下 `CLAUDECODE=1`，但会话 id 的环境变量名**未核实**，取不到就省略。

所以两个字段默认自动填，`--origin-session-id` / `--agent-client` 只作为覆盖手段存在。顺带删掉 `--source`（它渲染成正文末尾的「来源：」行，与 `originSessionId` 职责重叠）。

**一处踩到的设计缺陷**：出处字段的「更新时保留」最初实现成 `existing or detected`，结果显式传的 `--origin-session-id` 在更新时永远被忽略——写错了也没法改。正确的优先级是三段而不是两段：

- 出处字段（记「谁最先写的」）：`显式覆盖 > 已有值 > 本次探测`
- 审计字段（记「谁最后改的」）：`显式覆盖 > 本次探测 > 已有值`

审计字段兜到已有值是刻意的：`git config` 探测不到时（没装 git、全局未配）沿用旧署名，比清空更接近事实。

### 条目按 `name` 升序，不按 `updatedAt`

按 `updatedAt` 倒序会让每次写入都重排整个索引文件，git diff 噪声大到 review 不出实际变化。新鲜度看模块文件自己的 `updatedAt`，不靠索引顺序表达。

### 翻案：改做一整个 AGENTS.md 模板，并把 init 拆成两阶段

**新增两条前提假设**，写进 `memory-layout.md`：

1. **仓库是干净的**——init 不负责保留任何既有正文，因此可以整份渲染。
2. **`memory-layout.md` 真实反映当前版本的架构**——它同时是模板的规格说明和 refactor 的目标态；允许它和代码漂移的那一刻，refactor 就失去判据。

**这推翻了前面「不做一整个 AGENTS.md 模板」那一节，但只推翻一半。** 那节四条理由，在假设 1 下倒了两条——「文件不归我们所有、区块外正文要保留」和「index 区块要保留手工润色」。另两条仍然成立：三个区块归属不同、刷新时机不同（`remember` 只刷 memory 区块）。所以整份渲染**只用于文件尚不存在的场景**，已存在的文件依旧走区块级替换。`agents-scaffold.tpl` 被整份模板吸收后删除。

### 一份模板，标记也进模板

第一版没做到「一个模板」：`agents.tpl` 只放 `{memory_block}` / `{index_block}` / `{policy_block}` 三个占位符，区块正文仍是三个独立 `.tpl`，共四个文件。当时的理由是**保住「区块标记归脚本独占」**——怕标记进了模板被误改，破坏幂等替换。

**决策**：标记进模板，四个文件合成一个整份 `AGENTS.md` 模板。

那个顾虑用**加载时校验**解决即可：读模板时检查六个标记齐全、各出现一次、且顺序正确，不满足直接报错。这把「模板被误改」从静默损坏变成即时失败，比靠拆文件回避强。而拆四个文件的代价是真实的——改一处文案要先判断该动哪个文件，且没人能从任何单个文件看出最终 `AGENTS.md` 长什么样。

换来的性质：模板文件本身就是一份可读的 `AGENTS.md` 样例。脚本两种用法共用它——整份渲染时用不到的区块整段（连标记）删掉再折叠空行；区块级替换时按标记从模板里切出对应区块。标记字符串仍以脚本常量为准（它是匹配既有文件的身份，不是文案），模板里的那份由上述校验保证一致。

### 模板命名：产物名 + .tmpl.md

**最终决策**：模板名 = 产物名去掉后缀 + `.tmpl.md`，由 `template_path()` 独占实现。

```text
AGENTS.tmpl.md     → AGENTS.md
FEEDBACK.tmpl.md   → .memory/FEEDBACK.md
PROJECT.tmpl.md    → .memory/PROJECT.md
REFERENCE.tmpl.md  → .memory/REFERENCE.md
type_slug.tmpl.md  → .memory/<type>_<slug>.md
```

只有条目模板没法完全套用：产物名是 `<type>_<slug>.md`，而 `<` `>` 在 Windows 上是非法文件名字符、在 shell 里是重定向符，所以用角色词 `type_slug` 代替尖括号。

这个规则同时消掉了一个隐患：Cursor 和 Claude Code 会在编辑文件所在目录及其祖先里找 `AGENTS.md`，模板目录恰恰是我们在编辑的目录，所以目录里放一份真的 `AGENTS.md` 会让那份满是 `{title}` 和受管标记的模板有被当成真实指令加载的风险。`.tmpl` 后缀顺带解决，不必为此扭曲命名。

**到这个规则之前走了两次弯路，都记下来。**

第一次：弃用 `.tpl` 后缀。原先「`.md` 复制、`.tpl` 按需填充」这条后缀语义是被迫的——`load_templates()` 用 `templates/*.md` 通配，任何 `.md` 都会被 init 当成记忆文件复制进去，两个 Markdown 模板只能改叫 `.tpl`。能翻案是因为那个通配已经没价值了：索引文件名由 `INDEX_FILES` 显式声明，新增一个本来就要同时改模板、`INDEX_FILES`、`MEMORY_FILE_DESCRIPTIONS` 三处，通配省不掉任何一处，却反过来逼着模板换后缀。这一步的方向是对的。

（终局的 `.tmpl.md` 看着像绕回了 `.tpl`，其实不是同一回事：当初被弃用的是「靠后缀区分复制类与渲染类」这套语义，而且那时模板名**不是** Markdown 后缀结尾；现在后缀只表示「这是模板」，文件仍是 `.md`，编辑器照样按 Markdown 高亮。`.tmpl` 只是 `.template` 的缩写，不承载别的含义。）

第二次：落到小写 `agents.md` / `module.md`，这一步是错的。

1. **小写没有起到隔离作用**。选小写就是想避开真实的 `AGENTS.md`，但 macOS 文件系统大小写不敏感——实测 `cat AGENTS.md` 直接读到了 `agents.md`，两个名字指同一个文件。所以上面那个「被当成真实指令加载」的风险，小写压根挡不住，只是让人以为安全了。**教训：靠大小写做隔离，必须先验证文件系统是否大小写敏感。**
2. **大小写不一致背后其实有规律，只是没写出来**。当时的解释是「复制类取产物名故大写，渲染类取职责名故小写」——这在描述现象，不是规则。真正的规则是「模板名跟着产物名走」，`.tmpl` 后缀负责区分模板与产物；一旦这么表述，大小写自然一致，也不需要为渲染类另编一套命名。

顺带修掉 `module` 这个死词：那个 kind 早就删了，模板产出的是 `<type>_<slug>.md`。

### 区块顺序对齐模板

`upsert_block` 原先在区块不存在时一律追加到文件末尾，于是同一份 `AGENTS.md` 的区块顺序取决于哪个区块先建：根目录先 init 再加子目录，index 会排在 policy 之后；反过来则排在前面。模板声明了顺序，增量路径却不遵守。

**决策**：把顺序提成 `BLOCK_ORDER` 常量，补写缺失区块时插到「后续第一个已存在区块」之前，都没有才追加。

不是纯观感问题：两条路径产出不一致，意味着 `AGENTS.md` 的最终形态取决于 init 的调用历史，而 refactor 阶段要拿模板当目标态去收敛现状，前提就是「目标态唯一」。顺手把这个不确定性消掉，比留给 refactor 处理便宜。

实现上只加了一个 `insert_block()`，`upsert_block` 和 `merge_index_entry` 共用——后者原先自己拼字符串追加，是同一个 bug 的第二个副本。条目清单的 `edges-entries-local` 不在 `BLOCK_ORDER` 里，走末尾追加的退路，因为索引文件里只有这一个受管区块，没有顺序可言。

### 索引跟随记忆层级，逐级披露

对齐区块顺序时补测两层目录，发现实现与 `memory-layout.md` 不符：`sync_root_agents()` 一律把条目登记进 `resolve_root()` 给出的 git 根，于是任意深度的记忆目录都平铺在记忆根那一份索引里，中间目录即使自己有记忆也不会有下级索引。

**决策**：改代码，实现逐级披露。本级只登记**直接下级**的记忆目录，条目路径相对本级。

**先记一次误判**：我最初认定「文档错、实现对」，理由是逐级跳转有正确性缺口——中间目录不带记忆时链条会断，深层目录不可达——于是把文档改成了平铺。这个推理错在把「逐级」理解成了**目录层级**。文档说的是**记忆层级**：一个记忆目录的父节点是「最近的带记忆祖先」，不带记忆的中间目录直接跳过，所以链条根本不会断。原文紧接着的那句「路径上不带记忆的中间目录不会出现在索引里」正是在说这件事，我却把它读成了自相矛盾的证据。**教训：判定文档与实现冲突时，先确认自己对文档术语的理解，别急着改文档去迎合实现。**

平铺违背渐进式披露：读一份根索引就把整个仓库所有记忆目录全部展开，深层目录的存在感和顶层目录一样，而这套记忆的全部意义就是按需逐层加载。

衍生出来的问题见下一节。

### 记忆层级会漂移，所以索引条目要能归位

这是嵌套模型独有的代价，做平铺时不存在，值得单独记。

**问题**：一个目录挂在哪一级，取决于「当时最近的带记忆祖先是谁」，而这个答案会随别的目录获得或失去记忆而改变。`src/DC/deep` 先建时 `src/DC` 还没有记忆，于是挂在记忆根下；之后给 `src/DC` 也建了记忆，`deep` 就该改挂到 `src/DC`。

**实测比「不会自动改挂」更糟**：给 `src/DC` 建完记忆后，根索引里 `deep` 的旧条目原地不动；此时再重跑 `deep` 的 init，它会按新层级在 `src/DC` 里也登记一遍，于是**同一个目录同时出现在两份索引里**。对 ask 来说这是两条通往同一份记忆的路径，且其中一条的路径前缀是错的。

平铺模型没有这个问题：anchor 恒为记忆根，不存在「当时最近的祖先」这种时序依赖。所以这是为渐进式披露付的价钱，不是原本就有的 bug。

**候选方案**：

| 方案 | 结论 |
| --- | --- |
| 全量重算索引，像条目索引那样 | 否决。子目录描述没有唯一事实源——它只存在于索引条目自己那一行，没有 frontmatter 可依，重算会把所有描述冲掉 |
| 接受漂移，交给未来的 refactor | 否决。重复条目会让 ask 走错路径，不是「不好看」而是「读不到」，不能放着 |
| 先给子目录描述一个事实源（比如存进本级 `.memory/`），再走全量重算 | 未采纳，但留作后续演进方向。它能顺带解掉上面第一条的否决理由，代价是多一处需要维护的元数据，以及 init 的参数语义要跟着变。当前只有归位这一处需求，不值得为它引入新的存储位置 |

**决策**：init 时归位（`rehome_index_entries()`）。扫本级到记忆根的所有祖先索引，把本该归本级管的子孙条目搬下来（描述跟着搬），把本级自己滞留在应属层级之上的条目摘掉；区块被搬空就整个移除，不留空壳。

这是「目标态唯一」的延续——同一组目录不论以什么顺序 init，最终形态都该一致。这条原则前面在区块顺序上用过一次，这里是第二次，而且更要紧：区块顺序错了只是观感，层级错了会读不到。

**代价**：init 的写入范围从「目标目录 + 记忆根」扩大到「目标目录 + 记忆根 + 本级到记忆根之间的祖先」。`foreign` 的祖先跳过不动，所以不会踩别人的文件。JSON 里用 `inheritedEntries` / `detachedEntries` 回报搬动结果，让调用方能在汇报里说明「某个子目录条目被移动了」，否则这类改动对用户是隐形的。

**必须覆盖的四种情形**（都已验证）：中间层后加记忆导致条目下沉；条目滞留在 anchor 之上；兄弟子树不受影响；`foreign` 祖先完全不碰。前两种合起来才能保证幂等，漏掉任一种都会留下重复条目。

**归位不够，因为它只看「哪些条目该搬」**：归位由 init 触发，扫的是「本级和子孙的条目现在挂对了没有」。它从不问「这个条目指向的目录还在不在」。所以手工 `rm` 掉一个记忆目录之后，祖先索引里的死条目无人清理，重跑父级 init 也发现不了。这个缺口把职责边界暴露出来了，见下节。

### 模板尽可能体现内容结构，脚本只做占位符替换

前面「文案外提到模板」那条只解决了**文案**外提，没解决**结构**外提。`type_slug.tmpl.md` 曾经长这样：

```text
---
{frontmatter}
---

{content}
```

它是个反例：光看模板根本不知道 frontmatter 有哪些字段、什么顺序、哪些可选，这些全在脚本的 `ENTRY_FIELD_ORDER` 里。于是模板名义上是事实源，实际上只是个信封。

**原则**：模板要尽可能长得像产物本身；脚本只负责把值填进占位符。判据是「**盯着模板能不能说出产物长什么样**」。

按这条清掉四处结构泄漏：

| 泄漏 | 原先在脚本里 | 现在 |
| --- | --- | --- |
| frontmatter 字段清单与顺序 | `ENTRY_FIELD_ORDER` 九元组 + 逐行拼装 | 模板逐行列出九个字段，常量删除 |
| 记忆区块那三行 | `MEMORY_FILE_DESCRIPTIONS` + 遍历目录拼装 | 直接写死在 `AGENTS.tmpl.md`，常量与 `list_index_files()` 一并删除 |
| 下级索引的行格式 | 三处 `f"- [\`{x}\`]({x}) — {d}"` | `_entry_line.tmpl.md` |
| 条目索引的行格式 | 一处 `f"- [{title}](../%7Bfile%7D) — {d}"` | 同上，两者共用一份 |

**代价是要给「可选」发明表达方式**，否则模板没法把可选字段写出来。只加了两条替换规则，够用且都能从模板本身看懂：一行里所有占位符都空则整行消失；` — ` 后面空则连分隔符一起去掉。没有引入条件、循环之类的模板语法——那等于把脚本的复杂度搬进模板，换不来可读性。

**行片段是新出现的模板类别**，不对应任何产物，所以「模板名 = 产物名 + `.tmpl.md`」这条规则套不上。用 `_` 前缀标记，规则补一句「下划线开头的是片段」而不是推翻原规则。

**下级索引和条目索引共用同一份片段。** 起初拆成两份，因为下级索引的标签是反引号包住的路径、条目索引的标签是标题。但两者本质是同一个东西——一个链接加一句说明——差别只在标签写什么，那属于数据不属于结构。合并成 `- [{title}]({path}) — {description}` 一份，代价是下级索引的路径不再带反引号：想保留就得把反引号交给调用方拼，那正是刚清掉的那类泄漏，不能为了观感换回来。记忆区块那三行也跟着去掉反引号，否则同一份 `AGENTS.md` 里两种路径链接长得不一样。

合并连带改了解析：`INDEX_ENTRY_PATTERN` 原先靠反引号定位路径，现在**从链接目标取而不是从标签取**。这比单纯松开反引号更稳——标签写成什么都不影响解析，旧文件里带反引号的条目和手写条目一样认。已验证：把条目改回反引号形态，体检仍认得它，重跑 init 也不会重复登记。

**这里踩了一次，值得记**：合并后幂等立刻挂了，`init` 会把同一个子目录登记两遍。原因是行格式还有**第四处**泄漏——`merge_index_entry()` 里判断「这条是否已存在」的正则也硬编码了反引号形态。它是个**匹配器而不是写入器**，所以前面按 `f"- ["` 搜写入点时整个漏掉了。教训是：清理某个格式的泄漏时，写入端和匹配端都要找，而且两端必须共用同一条判据——现在都只认链接目标，不看标签。

**必须配一个反向校验**：结构挪进模板后，脚本产出了模板没声明的字段就会被静默丢掉——比原先更危险，因为原先 `ENTRY_FIELD_ORDER` 和产出字段在同一个文件里、改漏一眼能看见。所以 `render_entry()` 在替换前比对一次，发现未声明字段直接报错。已验证：删掉模板里的 `email:` 一行，`remember` 立刻失败并点名 `email`，而不是写出一份缺字段的记忆。

**顺带把一个不变量做实**：记忆区块那三行变成字面量之后，它就等于**断言**三个索引文件都在，缺一个就是死链。原先 `remember` 只重算它写的那一类，所以补了一句让它重算全部三个——`refresh_index()` 无变化时不写盘，代价几乎为零，换来「手工删掉某个索引文件后下次 `remember` 自愈」。

**这条原则也约束文档**：`memory-layout.md` 里原先复述了 frontmatter 的九行字段表和每个模板的占位符清单，现在改成指向模板，只留模板看不出来的部分——字段的值从哪来、更新时谁覆盖谁。复述一旦存在就会和模板漂移，而模板是脚本真正读的那一份。

**第五处泄漏：类型清单。** 收掉上面四处之后我一度断言 `INDEX_FILES`（kind → 索引文件名）没法只用模板表达，那是没找就下的结论。实际上记忆区块静态化之后，那几行本身就是「本级有哪些索引」的权威声明，`index_files()` 直接从中推导即可，常量删除。**新增一个类型于是只改两处，都在模板里**：记忆区块补一行、放一份同名模板；`--kind` 的可选值也跟着变。已验证：加一个 `glossary` 类型，脚本一行没动，`remember --kind glossary` 直接可用。

选它而不是扫 `templates/` 目录，是为了不推翻「脚本按名字精确取模板，不通配目录」那条决定——通配的话往模板目录放一份 `README.tmpl.md` 就会凭空多出一个类型。**类型必须是被显式声明出来的，不是被扫出来的。** 代价是脚本要从一份模板的正文里解析配置，比读常量间接；换来的是「加类型不碰代码」，且声明处正好是人最可能去看的地方。配套两个前置校验：声明了却没给模板、以及一条声明都没有，都在动文件之前报错。

顺带一个连带修正：`--type` 的可选值现在来自模板，所以建 argparse 也会读模板，`build_parser()` 必须挪进 `main()` 的 try 里，否则模板坏掉时抛的是 traceback 而不是约定的 JSON 错误。

### 这个 skill 叫 `doctor`，不叫 `tidy`，更不叫 `dream`

命名先后走过 `refactor` → `tidy` → `doctor`。前两步的理由记在下面两节，这里记最后一步，以及为什么否掉了 `dream`。

**否掉 `dream`：那是个已被占用的术语，指的是另一件事。** [`prior-art/03-oss-frameworks.md`](../../references/reference_oss_frameworks/INDEX.md) 记着 Letta 的 "dreaming" 是后台 subagent 在独立 git worktree 里整理记忆再 merge 回主分支；[`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md) 记的那个「agent 记忆 = git 仓库」的系统更直接——它**同时**有 `/doctor`（审计放置错误、重复、token 占用）和 `dreaming`（后台并发整理），两者是分开的。本 skill 对应的是前者。

判据是**它从不打开任何条目文件的正文**：六类诊断全在 `AGENTS.md` 的受管区块和索引条目上，一个字的记忆内容都不读。而 `dream` 在文献里恰恰指内容层的合并、抽象、遗忘。叫 `dream` 会让 agent 和人都预期它去动正文，是过度承诺。

**而且这两件事性质不同，不该合成一个命令**：结构修复是机械的、确定性的、幂等的、信息不丢；内容整合要判断、要 LLM、有损、不幂等。本 skill 的卖点之一就是「跑完再跑一次应该零 `findings`，不是的话说明有 bug」——把一个有损的非确定性操作塞进来，这条保证立刻失效。

**选 `doctor` 而不是继续用 `tidy`**：`tidy` 只说了「弄整齐」，没体现「默认只诊断、确认后才修」这个最重要的行为约定，而那恰恰是它区别于 init 的地方（第一个会删东西的操作）。`doctor` 同时表达了诊断与修复的两段式，且有上面那份调研作为先例。连带把 `needs-tidy` 改成 `needs-doctor`。

### `kind` 统一成 `type`

同一个概念第三次出现两个词。frontmatter 字段写的是 `type`，模板文件名也叫 `type_slug.tmpl.md`，只有命令行参数和脚本内部叫 `kind`——而这两者恰恰是人最常接触的地方。判据和前两次（entry / index、refactor / tidy）一样：**模板是事实源，所以模板里的词赢**。

`--kind` 改成 `--type`，JSON 里 remember 回报的 `kind` 键也改成 `type`，和 frontmatter 对齐。

**顺手发现 `kind` 在脚本里其实是一词两义**：除了条目类型，整理的诊断结果也叫 `kind`（`dead-entry`、`misplaced` 之类）。那是「诊断的类别」，和条目类型毫无关系，只是当时随手取了同一个词。改叫 `issue`，JSON 键一并改。如果只做前一半改名，`kind` 会从「有两个词」变成「有两个意思」，问题没解决只是换了个形状。

**Python 标识符写 `entry_type`，不是 `type`**：`type` 是内建名，用作参数名会遮蔽它。这不算引入第三个词——对外（命令行、JSON、frontmatter、文档）一律是 `type`，`entry_type` 只是躲开内建名的写法，且和已经统一过的 entry / index 术语一致。脚本顶部留了一句注释说明这件事，免得下一个人以为是两个概念。

### init 管不了的那一类问题：视野，而不是先后顺序

原先把脏仓库收敛叫做 `refactor`，当成 init 的「第二阶段」——即先后顺序的关系。上面的死条目缺口说明这个划分不对：**init 无论排在第几步都发现不了它**，因为 init 只知道自己那一个目标目录，而「条目指向的目录还在不在」「哪个记忆目录没人登记它」这类事实需要全树视角。

所以分界线是**视野**：init 单目标、只往前写；整理扫全树、双向收敛。这也顺带解释了为什么归位该留在 init 而不是移进整理——漂移是 init 自己这次动作造成的，当场修掉才能保证 init 单独跑完就是干净的；挪出去会让 init 先产出重复条目、等下一次整理才收敛。

**决策**：拆出一个独立 skill，`memory.py doctor` 子命令。诊断六类不一致：

| 诊断 | 只有全树视角才能判定的原因 |
| --- | --- |
| `dead-entry` | 要知道条目指向的目录现在还有没有记忆 |
| `unregistered` | 要枚举所有记忆目录，才能反查谁没被登记 |
| `misplaced` / `duplicate` | 要同时看到所有持有索引的层级，才能判断哪一级才是对的 |
| `foreign-agents` | init 会为此返回 `needs-doctor` 并拒绝动手，得有人接 |
| `missing-policy` | 记忆根的策略区块被删了，单目标 init 只在恰好以根为目标时才会补 |

**同时把 `needs-refactor` 改名成 `needs-tidy`**，代码和事实型文档里的 `refactor` 一并换掉。理由和前面 entry / index 那次一样：一个概念两个词，早晚漂移。`design-decisions.md` 里保留 refactor 的历史叙述，因为那记录的是当时的想法。

**默认只诊断，`--apply` 才写**。这是本套 skill 里第一个会**删东西**的操作（删索引条目、改写别人的 `AGENTS.md`），和 init / remember 的「只增不减」性质不同，所以默认值取保守的一侧。诊断与修复共用同一份 `collect_tidy_findings()`，报告里说的就是要改的，不会出现「诊断一套、动手另一套」。

**`foreign` 只追加不改写**：手写正文和别的工具的受管块（本仓库根 `AGENTS.md` 就是 `runa-memory:*`）原样保留，只补挂本套区块。已验证。这让整理对「多套记忆工具共存」是安全的——否决过「让整理去理解并迁移别人的内容」，那要猜别人的语义，猜错就是丢数据。

**修复必须分三段**，一次遍历做不完：先做全部删除与区块修补，再把 `misplaced` 按原描述登记回正确层级，最后重扫一遍补掉仍未登记的。`misplaced` 删掉后就变成了未登记，这个新状态在同一次遍历里看不见——实测漏了第三段会把条目删干净却不补，比不修更糟。删除时要顺手抄走描述，否则重新登记时会退化成兜底文案。

**未解**：`unregistered` 重新登记时只能用兜底描述，原描述已经随目录一起没了。这仍然指向「子目录描述缺少独立事实源」那条演进方向。

### entry / index 术语归位

模板一度叫 `entry.tmpl.md`，而脚本里 `ENTRY_FILES` 指的是 `FEEDBACK.md` 这三个索引文件，`entry` 一词两义。虽然模板名后来又改成了 `type_slug.tmpl.md`，这次术语清理仍然有效——`entry` 该指什么这个问题本身是独立的。

**决策**：`entry` 专指单条记忆，三个索引文件在代码和文档里都改叫 index。

- `ENTRY_FILES` → `INDEX_FILES`，`list_entry_files` → `list_index_files`，`refresh_entry_index` → `refresh_index`
- `MODULE_*` / `render_module` / `build_module_fields` / `list_module_files` → 对应的 `ENTRY_*` / `render_entry` / `build_entry_fields` / `list_entry_files`
- 文档里「入口文件」→「索引文件」，「模块文件」→「条目文件」；「子目录入口」那层含义不变，仍叫入口
- JSON 输出的 `entryIndex` 字段改叫 `index`

**顺带发现已经写进生成文件的 `edges-entries-local` 标记反而更贴切了**：它圈的正是索引文件里的条目清单，而条目就是单条记忆。所以这次改名不需要动任何已生成文件的标记，没有迁移成本。

术语最终是三层，和目录树一致：**索引文件**（`FEEDBACK.md` / `PROJECT.md` / `REFERENCE.md`）→ **条目**（索引里的一行）→ **条目文件**（`<type>_<slug>.md`）。条目和条目文件一一对应。

**两阶段的价值在于 init 的第三个分支**。`AGENTS.md` 存在但不含本套标记时返回 `needs-refactor` 且不动文件，把「脏仓库」从 init 的职责里彻底摘出去。本仓库根 `AGENTS.md` 正是这种情况（手写正文 + `runa-memory:*` 区块），所以这个分支立刻就有真实用例。代价要说清楚：**refactor 落地前，对本仓库根目录执行 init 只会得到 `needs-refactor`，等于 init 在这里暂时不可用。**（后来由 CLI `edges memory doctor` 接管 `needs-doctor`。随包技能 `project-memory-doctor` 已删除，见 ADR 0049，不要再调用。）

### remember 走后台 subagent

> **已被翻案**，见后面「翻案：remember 的主路径改回内联，subagent 退成逃生舱」。本节保留原始推理，因为翻案正是从它内部的矛盾找出来的。

**决策**：主 agent 只判断值不值得记、组织素材、派后台 subagent；去重检索、字段拟定、CLI 调用、回读验证都在 subagent 里做。

**为什么不是让脚本异步**：算过成本分布——一次 remember 里 95% 以上是「agent 想清楚要记什么并组稿」的 LLM 轮次，Shell 往返是几十毫秒，脚本 IO 是几毫秒。把 IO 丢后台省的是毫秒，代价是丢掉 `path`/`action` 回报和回读验证，是笔亏本买卖。真正堵住主流程的是 LLM 那段，只能靠换执行者。

**省不掉的那部分**：只有主 agent 有对话上下文，所以「记什么」必须由它在委派时说清楚（结论、起因、怎么应用、目标目录）。这一点在 SKILL.md 里明写，否则主 agent 会把素材交得太含糊，subagent 只能瞎编。

**同一份 SKILL.md 服务两个角色**，必须显式分节并在开头点明「按自己的角色只读对应那一节」，否则主 agent 会顺着往下把全套同步跑完，委派就白设计了。

### 全量重算顺带买到并发安全

每次写入都是「先落模块文件，再从磁盘全量重算索引」，所以最后一个重算的必然看到全部已落盘的模块文件。多个后台 subagent 并行写不会丢更新，不需要文件锁。

这是全量重算相对增量 upsert 的额外收益，而且正好补上「派后台 subagent」带来的并发风险——两个决策互为前提，如果当初选了增量 upsert，后台委派就得先解决加锁。

### ask 和 remember 该不该存在，还是都折进 AGENTS.md

**问题**：init 已经往 AGENTS.md 写了 policy 区块，那检索和沉淀的指令是不是也该一并写进去，省掉两个 skill。

**判据**是两轴：常驻还是按需、不变还是项目特定。目标函数沿用 [`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md) 那条——**最小化读进上下文的字节数**。量出来的体积：policy 区块 8 行常驻，ask 35 行 / 2325 字节，remember 89 行 / 5709 字节；全内联就是约 124 行、8 KB 每轮常驻。

**结论是不对称的。**

`remember` **留成 skill**，但这一节最初给的理由已经作废——当时写的是「写入走后台 subagent，subagent 是独立上下文，只能读稳定路径的文件」。subagent 随后被降级成逃生舱（见下面「翻案：remember 的主路径改回内联」），这条理由的基础就没了。接着补的第二个理由「CLI 契约需要一份可加载的文件」也不成立（见「CLI 契约的事实源是 `--help`」）。真正立得住的只有一条，见「两个 skill 落在同一根轴上」。

`ask` **的账接近平的**，这才是真正可争论的一个。它触发在多数实质轮次上，按需加载省不下字节还多一次往返；它又是纯散文，没有脚本也没有 subagent，文件能给的提示词一行也能给。核对内容后重合度更高：policy 里「先按 `AGENTS.md` 索引读入口，再按条目说明取正文，不要一次加载全部」已经覆盖了「三层导航」与「挑条目只看说明」；`SKILL.md` 29–30 行又和 `memory-layout.md` 的 78、82 行几乎逐字重复（`init/SKILL.md:42` 还有第三份）。真正独有的只剩四条：主动触发与跳过条件、关键词自己提炼别照抄原句、复合问题拆开、末尾附来源且查空要直说。

**决策**：两个都留，但都砍。`ask` 删掉整个「索引怎么组织」小节（那是 `memory-layout.md` 的职责，正文已经链过去），四条独有纪律搬进 policy 区块，skill 只剩一个壳。

**反转判据写死**：砍完若 `ask` 掉到 8 行以下，就没必要单独立文件，把那四条折进 policy 区块、删掉 skill。

**判据触发了，但被有意否决。** 实测独有内容正好四条（提问时主动查、关键词自己提炼别照抄原句、复合问题拆开、末尾附来源且查空要直说），远低于 8 行门槛，按判据该整个删掉。选择留壳，唯一的理由是**保住 `$edges-memory-ask` 这个显式调用入口**——纪律折进 policy 后仍然生效，删掉 skill 只会让用户没法主动喊它。这里明确记一笔，是为了让后来的人知道这不是漏改：判据仍然有效，只是被一个判据没覆盖的维度（人工调用入口）压过。

### 翻案：remember 的主路径改回内联，subagent 退成逃生舱

**决策**：内联是主路径，一次 CLI 调用写完。subagent 只留给两种情况——一次沉淀多条（长会话结束时跨几个目录写好几条），以及目标目录还没初始化、要先 init 甚至 doctor 兜一遍。SKILL.md 的双角色分节随之取消。

**翻案是从原始理由内部的矛盾看出来的。** 「remember 走后台 subagent」一节先说「真正堵住主流程的是 LLM 那段，只能靠换执行者」，紧接着又说「只有主 agent 有对话上下文，所以『记什么』必须由它在委派时说清楚」。两句合起来的结论是：**能委派出去的恰好只剩不贵的那部分。** 昂贵的 LLM 工作因为绑定上下文而无法移动，subagent 接到的是机械活儿，而机械活儿本来就不需要移动。

委派提示词要求主 agent 填的字段是 `结论` / `起因` / `怎么应用`，而条目正文的结构是「一句结论 → `**Why:**` → `**How to apply:**`」——**这两个是同一个东西**。主 agent 已经做完了全部思考和绝大部分撰写，subagent 的边际 LLM 工作只剩一次去重判断加一句 description。而去重它还做得更差，因为它看不到对话，判断不了「这条和已有那条是不是一回事」的细微差别。

**内联之所以便宜，是因为五步里有两步站不住**：

| 原步骤 | 判定 |
| --- | --- |
| 5. 再 `search` 一次确认能召回 | 冗余。索引是全量重算的，脚本返回了 `path` 和 `index` 就已经证明索引里有它，`action` 还直接报了 created / updated |
| 2. `search` 去重 | 通常免费。索引文件很小，而 policy 要求检索时先读索引，ask 阶段大概率已经在上下文里；真撞了 slug，`action: updated` 事后也会讲 |

剩下 init 检查一步条件判断，加一次 CLI 调用，几十毫秒。**非阻塞这个原始诉求没有变，只是换了个更便宜的满足方式**：不是把活搬走，而是把活缩小到没什么可阻塞的。代价那边则是实的——一次完整的额外模型调用要计费，双角色 SKILL.md 是文档自己标过的坑，fire-and-forget 失败了很晚才知道或根本不知道。

### CLI 契约的事实源是 `--help`，不是 SKILL.md

**决策**：SKILL.md 不再抄参数清单，只写「跑 `memory.py remember`，参数见 `--help`」。前提是 argparse 的 help 字符串必须完整，所以给 `--target-dir` 和 `--content` / `--content-file` 补上。

**这条推翻的是我自己前一步的论证。** 我曾用「CLI 契约需要一份可加载的单一事实源」来论证 remember 必须是 skill——11 个参数、互斥必填组、`--title` 新建必填更新可省，agent 确实猜不出来。但 argparse 本身就是那个事实源，`--help` 永远和实现一致。而 SKILL.md 里那段调用示例是**第二份副本**：加参数、改名字，argparse 变了它不会变。我拿来反对「把契约复制进每个项目 AGENTS.md」的那个漂移风险，已经存在于我自己的方案内部了。

先例是现成的：`--kind` 改名成 `--type` 那次，如果契约已经复制到 N 个仓库的 AGENTS.md 里，那 N 份会同时开始教 agent 跑一条会失败的命令，而 `doctor` 发现不了——它只检查区块在不在、条目登记得对不对，从不读区块里的正文。

### 两个 skill 落在同一根轴上：纪律违反的可逆性

前两节把 remember 的机械理由全部拆掉之后，它和 ask 就变成了同一种东西：**一份纪律清单，问题只是常驻好还是按需加载好。** 判据是纪律被违反时的可逆性。

| | 违反的代价 | 结论 |
| --- | --- | --- |
| 检索纪律 | 挑错文件白读一遍，这一轮结束就没了 | 常驻够用，纪律进 policy 区块 |
| 沉淀纪律 | 写进 git 是永久的，而且**坏条目会自我强化**——它以后会被检索到并当成已确认的结论用，却没人回头审计它当初该不该写 | 值得那次刻意加载，留成 skill |

举个具体的：任务中顺手记一条「正在改 WorkTabV2 的弹窗逻辑」，两周后这事早结束了，但它还在索引里，每次相关任务都被读出来误导判断。所以「不要写」那份清单（临时进度、猜测、能从代码或 git 推出的事实）是整个系统里价值最高的一段内容——[`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md) 记着规模化的头号失败模式就是记忆膨胀与 context collapse。

关键问题于是变成 **agent 在真正动手写的那一刻有没有在读它**。放 AGENTS.md 里它常驻，但那是一份讲项目的长文档，清单是里面几条 bullet，和其他所有内容一起竞争注意力；放 skill 里，agent 是在决定要写之后、动手之前专门加载它，读到时它就是「我现在要做的这件事的说明书」。

**remember 因此瘦成一个纯闸门**，89 行砍到 42 行，剩下的全是判断——什么时候写与不要写、怎么挑 `type` 和 `slug`、怎么去重、`description` 怎么写、正文结构，机械部分只剩一行「参数见 `--help`」。原先的「路由」表删掉（它是 `memory-layout.md` 三类记忆表的第四份副本），「frontmatter 字段」表移进 `references/`（那是脚本自动填值的行为说明，正常路径根本用不到，只在改错值时才查）。

### 纪律只在记忆根写一次

> **后半条已被翻案**，见「部分翻案：纪律归 skill，时机归 policy」。「不在每个子目录重复」仍然有效。

**决策**：每个目录都有的 `project-memory` 区块只列本级索引，不再带「检索」「沉淀」两个小节；全部纪律集中到只在记忆根出现一次的 `project-memory-policy` 区块。

这两个区块原先各写了一遍检索和沉淀，是同一份模板内部的重复。子目录的 `AGENTS.md` 是被懒加载进一个**已经受根 policy 指导**的上下文里的，在那里重复一遍纪律没有任何增益，只是按目录数量放大常驻字节。

同时定住 policy 区块的预算：吸收 ask 的四条后从 8 行到 10 行左右，**到此为止**。允许 ask 折进来的前提正是「常驻字节数最小化」这条目标函数，如果折完 AGENTS.md 变胖了，这笔交换就白做了。

**递归也不用文字讲。** 每份 `AGENTS.md` 的 `project-memory-index` 区块列出自己的直接下级，顺着跳就到底——递归是数据，不是指令。所以 policy 里只留一句「往深层顺着子目录索引一级级跳」，结构细节继续由 [`PROTOCOL.md`](../../../../references/PROTOCOL.md) 承担，agent 没把握时去读，不必常驻。

### 契约是产物格式，不是 skill 之间的文件引用

**决策**：四个 skill 通过**产物**通信，不通过互相引用文件。由此分成两种角色。

| 角色 | 谁 | 权限 |
| --- | --- | --- |
| 格式拥有者 | `init`、`doctor` | 拥有 `LAYOUT.md`、`templates/`、`scripts/blocks.py`；彼此耦合正当，因为 doctor 的职责就是把现状收敛到那份目标态 |
| 格式消费者 | `ask`、`remember` | 必须自足，只能假设下面那份冻结契约，不引用拥有者的 `references/` |

**要买到的东西是版本偏斜容忍**：任一 skill 单独升级后其余仍能工作。即使 init 升级、现存 `AGENTS.md` 还是旧格式，ask 和 remember 也不受影响。

**冻结的核心契约**现在单独成文，见 [`PROTOCOL.md`](../../../../references/PROTOCOL.md)（抽离过程见下面「协议单独成文」一节）。

**其中「按实际读到的内容走」那条是整套东西成立的关键**，而它成立是因为消费方是 LLM 而不是 parser：读 markdown 不需要知道标记名，看见链接就能跳。所以契约可以定得足够弱，弱到几乎不可能被格式升级破坏。

**代价是一处受控的重复**：消费方的 `SKILL.md` 里仍留一句「形状」（入口 + 两类索引），让它不读协议也能开工。这是有意的——对协议本身也做渐进式披露，`PROTOCOL.md` 是权威，那一句只是入口。

### 部分翻案：纪律归 skill，时机归 policy

上一节的自足性要求撞上了「纪律只在记忆根写一次」，后者被**部分**翻案：

| 原决策的两半 | 现状 |
| --- | --- |
| 不在每个子目录的 `AGENTS.md` 重复纪律 | **继续有效**。子目录是被懒加载进已受指导的上下文的 |
| 纪律集中进 `project-memory-policy` 区块 | **推翻**。检索纪律搬回 `ask/SKILL.md`，policy 区块只留调用时机 |

**为什么不冲突**：「纪律违反的可逆性」那一节的结论是检索纪律**可以**常驻，不是**必须**常驻。自足性是硬要求，可逆性只是许可，所以硬要求赢。字节账上也不亏——policy 少三行，而 ask 根本不常驻。

**但有一处确实退化了，得认**：细纪律（关键词自己提炼、复合问题拆开、末尾附来源）不再常驻，agent 如果没走 ask 就看不到。policy 只保住最要紧的那条反贪心（索引分层、按链接逐级取、不要一次加载全部）。换来的是这些纪律不再依赖 `AGENTS.md` 是哪个版本。

### 脚本不按 skill 拆

**问过能不能让每个 skill 各带自己的脚本，结论是不能，而且拆了会制造它想避免的那种漂移。**

依赖形状是一个共享核心（模板渲染、区块 upsert、索引全量重算、`AGENTS.md` 渲染、frontmatter、记忆根解析）加三块专属逻辑（init 的 rehome/anchor、doctor 的全树扫描、remember 的 git 身份与字段合成）。`search` 几乎零依赖，但它本来就能被 `rg` 替代。

决定性的一点：**`remember()` 写完条目文件后必须重算三个索引并同步 `AGENTS.md` 的记忆区块**——那是格式拥有者的活，不是「追加一个文件」。按 skill 拆就等于把格式逻辑复制进消费方，于是 init v2 改了索引行格式而 remember v1 还在写 v1 行，同一份 `AGENTS.md` 里出现两种格式。

**真正的解耦已经在正确的层上**：remember 只知道「跑这条命令，参数见 `--help`」，不知道什么是区块标记。CLI 是接口，格式是接口背后的实现。所以脚本继续留在 `init/scripts/`，耦合由 `--help` 中介；指令层（`SKILL.md` 散文）才是版本偏斜真正会咬人的地方，也是本轮唯一动的地方。

### 协议单独成文

**决策**：抽出 [`PROTOCOL.md`](../../../../references/PROTOCOL.md)，只写冻结的抽象约定；`memory-layout.md` 降为「当前实现」。

**动机是 `memory-layout.md` 混了两种变更频率的东西**：嵌套树、入口文件、两类索引这些几乎永不变；而具体索引文件名、四个区块标记、frontmatter 字段清单、模板命名会随实现升级。混在一份文件里，消费方就没法只依赖不变的那部分——上一轮我把「冻结契约」塞进它开头，是把协议写在了实现文档里，位置错了。

**判定什么进协议，用的是「变更频率」而不是「抽象程度」**：一条约定如果改了会让所有 skill 跟着改，它是协议；如果改了只影响拥有者自己，它是实现。按这条，`AGENTS.md` 和 `.memory/` 这两个名字反而属于协议（它们是消费方的落脚点），而 `FEEDBACK.md` 这类具体索引名属于实现。

**协议末尾给了正反例表**，因为「什么算破协议」比「协议是什么」更难判断。

**这张表第一版写错了一行，值得记下来。** 我把「改区块标记名」列进了安全侧，理由是消费方不认标记名。但标记名不只是给消费方看的——它**已经写进了各个仓库的现存 `AGENTS.md`**，而 `classify_agents_file()` 是精确字符串匹配、没有别名容忍，所以改名会让所有旧文件被判成 `foreign`、init 拒绝再碰。**判据里漏了一个维度：不只看「谁读它」，还要看「它有没有已经落盘的历史数据」。** 标记名是写进用户仓库的线格式，属于后者。

**同一次修正还补实了协议第七条。** 原文只写「工具只拥有自己用标记划出的区域」，却没说标记长什么样——那条承诺是空的：两个工具对语法没有共识，「共存在一份文件里」就无法兑现。所以第七条现在明确三件事：标记是 HTML 注释（渲染后不可见，不干扰人读）、名字带工具前缀（多工具共存、各动其块）、已发布的区块名冻结。而区块的**集合**与各自**装什么**仍属实现——新增区块自由，重命名不自由。

### 判据修正：不是「零跨 skill 引用」，是「不依赖易变的东西」

上一轮解耦时我把「消费方的 `SKILL.md` 零跨 skill 链接」当成了验收标准，那是错的——它把手段当成了目的。

真正的目标是**版本偏斜容忍**，威胁只来自依赖**会变**的东西。所以正确的标准是：

| 消费方可以依赖 | 消费方不能依赖 |
| --- | --- |
| `PROTOCOL.md`（冻结，改它就是破兼容） | `LAYOUT.md`（随实现升级） |
| `memory.py` 的 CLI，契约是 `--help`（自描述，永远和实现一致） | `frontmatter-fields.md`、`templates/`（实现细节） |

按错的标准，本轮给 ask 和 remember 加回 `../edges-memory-init/references/PROTOCOL.md` 这个链接会被判为回退；按对的标准，它完全合法，因为链的是冻结物。**校验脚本也要跟着改**：不再断言消费方零跨 skill 链接，而是断言它们不出现 `LAYOUT` / `frontmatter-fields` / `templates`。

### frontmatter 只必需 `description`，另有三个含义固定的可选键

**决策**：协议必需的只有 `description`（索引里那句说明）。另有三个**可选但含义固定**的保留键——`name`（等于文件名去后缀）、`type`（分类，供去重与归类）、`updatedAt`（最后更新时间，供按时序取舍）。剩下五个（`title`、`originSessionId`、`agentClient`、`username`、`email`）纯属实现。

**上一版把 `name` 也写成必需，是错的，靠反例抓出来**：Cursor rule 的 frontmatter 只有 `description` 之类，**身份靠文件名**——`name` 一旦必需，rule 当场不合规，而「rule 也是记忆条目」恰恰是这轮想要的泛化，等于自己掐掉自己。何况 `name` 的值就等于文件名去后缀，**信息在文件名里已经有了**，frontmatter 那一行是冗余的：有则用，没有就从文件名推。这次在协议落地前抓到，零代价。

**「可选但含义固定」是这次引入的概念**，像 HTTP 的可选头：不写没关系，写了就必须是这个意思。否则两个实现拿 `type` 各干各的，协议就白定了。

**为什么值得把 `type` 与 `updatedAt` 提进协议**：它们让写方多做事而不必读 `LAYOUT`。`type` 支持按分类去重与归类，`updatedAt` 支持按时序取舍（`dream` 的遗忘因子要它，见「待议」）——这两件事目前都得问 init 才知道怎么做；协议给了含义，`remember` 这类命令就能在只依赖协议的前提下用上。

**这不违反上一节的棘轮，但要分两档**：**必需键是硬棘轮**（所有实现都得产出它），**可选键是软棘轮**——只占用名字、不强制存在，`LAYOUT` 完全可以无视，代价仅是 `type` 这个名字被订走、不能挪作他用。而 `name` 从必需降为可选是**放松**，放松永远安全。

**三处独立证据支持这几个键值得标准化**：调研里的参考实现是「frontmatter（`name` + `description`）+ markdown + grep」（[`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md)）；本仓 18 份 `SKILL.md` **全部**含 `name` 与 `description`，其中 8 份就只有这两个，另外 10 份分五种组合、都是在这两个之上加可选项（`argument-hint`、`user-invocable`、`model` 等），无一例外；Cursor rule 则只有 `description`（本仓无 `.cursor/rules/`，未就地取证）。**三方独立落到「一句描述 + 各自扩展」这同一形态**，说明它是「按描述挑选、按需加载」这类产物的自然最小集。协议因此顺带获得泛化能力——**skill、rule 这类东西本身就是协议合规的记忆条目**，将来纳入索引不必改协议。

**但要同时写下边界：同形不同权。** skill 是会被加载执行的**指令**，记忆条目是供判断的**证据**。形状可以统一，权限不能——否则 agent 会把一条记忆当命令照做，或者把一份 skill 当成可随意改写的数据。谁能改、谁被执行，仍按各自体系的规则走。

### 协议与实现按同一组对象对齐，各自收敛到三条

**决策**：`PROTOCOL.md` 由八条平行约定改成**从外到内走一遍**——树 → 入口文件（含索引）→ 记忆文件；实现文档用**同一组小节**逐节给出细节，并由 `memory-layout.md` 改名 `LAYOUT.md`，与 `PROTOCOL.md` 配对。

**索引不单独占小节**：形状上它是三层之一，但协议对它只有两句话（`description` 是索引与记忆文件共用的同一个东西、挑条目只看那句说明），撑不起一个标题；它又天然是入口文件指向的东西，所以并进「入口文件」，`LAYOUT` 跟着并。并完还有个附带收益：`LAYOUT` 的受管区块表恢复成完整四行，`edges-entries-local` 不必再拆出去单独讲。

**原来八条是把思考顺序当成了结构**：嵌套树、节点入口、两类索引、逐级披露、补充而非覆盖，五条讲的都是同一件事——树长什么样、怎么走。

**第一版收敛成三条（树 / 记忆文件 / 入口文件）仍然不对**，因为三条是并列的，读者看不出它们是同一个结构的不同层次。改成先讲树、再点明「一个节点内部分三层」、然后按入口 → 索引 → 记忆文件依次展开，读下来就是一条从外到内的路径。

**最终把「节点」定成文件，不是目录。** 中途曾定成目录（入口 / 索引 / 记忆文件算目录**内部**的三层），但那样「叶子节点」这个词就没法用，只能绕开——我甚至为此专门记了一条措辞禁忌。改成节点即文件后，一棵树只有两种节点，叶子 / 非叶子直接成立，那条禁忌随之作废：

- **非叶子是 `AGENTS.md`**：只列子节点、给每项一句说明、自己不带内容。树根就是记忆根目录的那一份。
- **叶子是记忆文件**：内容全在这里，frontmatter 必需 `description`。

**索引文件与 `AGENTS.md` 同属非叶子**，因为它们干的是同一件事。这给「索引为什么不单独占小节」换了个更硬的理由：不是它话少，而是**它不是独立的一类**。协议因此只说「`AGENTS.md` 与记忆文件之间还可以再夹一层索引，顺着链接走、别假设中间隔了几层」，几份索引、按什么分，全归 `LAYOUT`。

**中途给这一类起过一个统称「路标」，后来废掉了。** 起它是因为「非叶子」这一类里既有 `AGENTS.md` 又有索引文件，需要一个词同时指两者。但它是自造词，读者在任何标准语汇里查不到，摆在冻结契约里成了理解门槛。废掉之后发现根本不需要造词：**类名用「非叶子节点」**（标准树术语，两个小节标题本来就这么写的），**中间那层用「索引」**（标准词，而且它就是索引）。两个小节标题因此改成 `## 非叶子节点：AGENTS.md` 与 `## 叶子节点：<memory>.md`——用文件名点题比用抽象类名更直给，读者不必先建立词汇表。**这个词的来路也值得记**：它是从调研笔记里漂进来的——[`prior-art/04-index-granularity.md`](../../references/reference_index_granularity/INDEX.md) 转述 OpenAI 递归摘要研究时用了「索引不应是正文的摘要，而应是正文的路标」这个说法，[`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md) 记另一套系统时也用了它。在那两处是**转述别人的比喻**，没问题；被我顺手搬进契约当正式术语就不行了。**教训：给一类东西造统称之前，先确认标准词真的不够用；比喻留在调研笔记里，别升进契约。**

**「非叶子不需要 frontmatter」这句现在可以正面写了。** 之前只能拐着弯说「主语限定在一条记忆一个文件上」，因为按当时的术语，「非叶子」指的是目录，而目录当然没有 frontmatter，这句话会变成废话。

**核心思想提到 H1 正下方**：「一棵随项目目录结构生长的文件树，非叶子是 `AGENTS.md`、叶子是记忆文件」几句话讲完形状，下面的小节只是展开它。放在最前是因为这是整套方案的立意——记忆挂在项目结构上，而不是自成一套目录。原来它埋在「树」一节里，前面还压着一段「本文件是冻结的」的文档治理说明，读者要往下翻才看到主张。治理说明退到第二段。

**补上「记忆与项目结构的关系」这个洞。** 收敛后的前几版只说了记忆**存在哪里**（挂在目录上）和**怎么走**（顺着索引跳），从没说一份记忆**是关于什么的**。补两句：一份 `AGENTS.md` 管的是这个目录连同其子树的事（所以越深越窄）；作用范围决定一条记忆写在哪一级。另外把「只有需要独立记忆的目录才有 `AGENTS.md`」明写出来——记忆是稀疏的、按需长出来的，否则实现者可能给每个目录都建 `.memory/`。

**这个洞原先由消费方在替协议兜着**：`remember/SKILL.md` 的「写到与结论作用范围最贴近的那一级」是从这条未声明的语义推导出来的纪律。协议补上之后二者是正常的分工——协议给规则，skill 给判断（含「拿不准就写记忆根」这类兜底），属于那类有意保留的受控重复。

**也顺带化解了「第一条粒度偏粗」那条顾虑**：小节有名字，引用时说「树」那一节即可，不再依赖「第一条」这种会指代不清的编号。

**图第一版把下级节点标成「子目录」，是错的**：树是稀疏的，一条下级链接可能跨好几层目录，「子目录」紧挨着边上的「直接下级」会让人以为记忆层级等于目录层级——正是「树」那节否掉的事，也正是我当年读岔文档的那个坑（见「记忆层级会漂移」一节的误判记录）。节点改标「子树内某个目录」，并在「树」一节把 `直接下级` 这个词**定义**出来：按记忆层级算，不是目录上的直接子级。这个定义 `init/SKILL.md:47` 早就有，协议一直缺，等于把术语的定义留在了下游。`ask/SKILL.md` 同一处松散一并收紧。

**形状交给一张 mermaid 图**，散文只留图上看不出来的部分。图承接了「两类子节点」「只列直接下级」「递归下去」这三件原本各占一句的事——它们本来就是空间关系，画出来比说清楚省。留在散文里的是图画不出的语义：一份 `AGENTS.md` 管多大范围、下级是补充不是覆盖、哪句说明等于哪个字段。**代价是图与散文可能漂移**，所以图上只放协议真正冻结的东西（`AGENTS.md`、两类边、可递归），实现细节（几份索引、文件名长什么样）一律不入图，用一句「图上略去了」交代。

**图上的节点最终全是文件名**，这是用户手改后定下的，推翻了上一段「文件名长什么样不入图」的一半。理由是：这本来就是一棵**文件**树，节点混着「`AGENTS.md`」和「记忆入口」两种说法时，读者得先在脑子里建一层「记忆入口是哪个文件」的映射才看懂图，而这层映射恰好是图该省掉的事。语义由分组框标题（本层记忆 / 下层记忆）承担，边标签因此可以全部去掉。**但名字必须是占位式的**：入口写 `MEMORY_TYPE_A.md` 而不是真名 `FEEDBACK.md`——真名会把「有哪些 `type`」这个明确划给实现的东西画进冻结协议里，也会被当成命名规则去对照（实测第一版写了 `MEMORY_INDEX_TYPE_A.md`，既非真名又长得像真名，是最坏的一档）。

**小节从「叶子 / 非叶子」两类改成三种文件各一节**，标题统一成「文件名 — 解释」：`AGENTS.md — 本层记忆入口` / `MEMORY_TYPE_*.md — 本层不同类型记忆入口` / `memory_*.md — 详细记忆内容`。**解释语要把三者的分工写进标题**：前两个都是「入口」，都限定在「本层」（两者都不跨层，跨层靠下层链接），靠「不同类型」区分第二跳；第三个用「详细记忆内容」点明它是唯一承载正文的一层。**用文件名当标题是为了跟图对上**——图上的节点全是文件名，标题写角色名（「记忆入口」）读者就得自己建映射，而这层映射正是图该省掉的。代价是占位名进了标题，所以「边界」那句加了「和小节标题里」，把免责范围一起盖住。`树` 与 `边界` 不套这个格式：它们不是文件，保持裸标题正好把「文件小节」和「非文件小节」分开。这**推翻了上面「索引不单独占小节，因为它不是独立的一类」那条**：抽象归类是对的（它们确实都只列子节点、不带内容），但代价是记忆入口从头到尾没被正面讲过一次，它的规定散在别处——而它恰好是这轮刚提升为协议的那一层。图接过了归类的活儿（谁是末端一眼能看出来），归类就不必再占标题；「只列子节点、自己不带内容」降为 `树` 一节里的一句共性（`树` 一节后来也撤掉了，见下文「`树` 一节撤掉」）。「叶子 / 非叶子」这套词因此在两份文件里彻底消失，只留在本文件的历史记录里。

**按对象组织的原则没变，只是把对象定得更细。** `LAYOUT` 已按同样的三节重排完（协议定稿后才动，避免跟着中间态反复改）：标题用本实现的真名——`AGENTS.md` / `FEEDBACK.md 等三份` / `<type>_<slug>.md`，区块表里 `edges-entries-local` 那行化进入口一节的正文，`type` 表从原「叶子节点」移到入口一节，记忆根定义与条目路径规则移到 `AGENTS.md` 一节。

**对齐的校验方式随之换了。** 标题用真名之后 H2 文本不再逐字相同，`diff '^## '` 失效。改为**只比破折号后的解释语**，两份必须逐字一致：

```bash
diff <(rg -o '^## .*— (.*)' -r '$1' PROTOCOL.md) <(rg -o '^## .*— (.*)' -r '$1' LAYOUT.md)
```

这比原来那版更强：既锁住了节数与顺序，也锁住了「同一个对象在两份文件里叫同一个角色」，同时放开了文件名——正是协议冻结角色、实现自由命名的分工。

**那棵 ASCII 目录树移到第一个 H2 之前**，与 mermaid 图在协议里的位置相同。它是**整体图**而不是某一节的内容：三种文件加嵌套一次画完，正好补上协议撤掉 `树` 之后的空缺。两份文件因此形状相同——图在上，三个文件小节，各自的尾节（边界 / 模板）。

**这轮唯一差点丢掉的规范陈述**：「一份 `AGENTS.md` 的父节点是最近的带记忆祖先」。它是「跳层」那条从下往上看的同一件事，删了显得省字，但少了它，实现可以把下级挂到任意祖先上还算合规——协议的删减是**放宽**，比新增更危险。已合回「下级」那句的尾巴，占十几个字。

**图从「插图」升为主干,散文改成围着图讲。** 之前是散文先把形状讲一遍、图再画一遍,前言那句「非叶子只列子节点、按 `type` 分成几份入口」与图完全重复。改成:前言只说图画不出的那件核心事（记忆附属于项目结构、作用范围等于目录子树）,然后一句「**协议就是这张图**」把读者交给图;此后每节先点名自己讲图上的哪一块（三份 `AGENTS.md` 与两份入口 = 非叶子、`memory_*.md` = 叶子、两个分组框 = 两类子节点、「递归下去」那个位置 = 整棵树）,再补图上看不出的语义。`树` 一节因此重排成「图只画了一层 → 图上看不出来的三件事」。约束集一条没动,只换了组织方式。

**代价与对策**：这么写会加深图与散文的耦合——图一改，散文的点名就可能失效。对策是散文只点名图上**协议冻结**的元素（`AGENTS.md`、两类边、入口层、递归），不点具体名字与数量，那些在「边界」一节统一声明为占位。

**散文只能引用图上可见的标签，不能引用 mermaid 节点 id。** 第一版写了「`Root → Sub1` 那条边」「`Dots` 那个位置」——`Root`/`Sub1`/`Dots` 只存在于源码，渲染后读者看到的是标签文字，对不上号。agent 读的是源码所以无感，人预览图时就断了。改成「图上记忆根指向下级的那条边」「「递归下去」那个位置」。

### 受管区块改成两层，自动化策略移出记忆区域

**三个平级区块改成「外层 `project-memory` 包住两个记忆区块」**：`edges-local`（本层分类型入口清单）与 `edges-descendants`（下层索引），顺序恒为 local → children。理由是让文件里的形状与协议一致——协议说 `AGENTS.md` 列两类子节点，那就该看见两个区块被一个「本套拥有的区域」括起来，而不是三个平级块靠命名自觉。附带好处：`classify_agents_file()` 从查三个标记退化成查一个区域，`doctor` 的 `foreign-agents` 也变成「追加一整块区域」。

**`-index` 改名 `-children`**：原来一个按内容命名（index）、一个按位置命名，两个内层块不对称。改成 `local` / `children` 后正好对上协议的「本层 / 下层」，而 children 在树的语境里就是「直接下层」的标准词。

**自动化策略移出记忆区域，改名 `project-memory-auto`，与外层平级。** 它讲的是**工具怎么被调用**，不是记忆内容——留在记忆区域里会让「外层 = 记忆」这个等式不成立。但它必须留在根 `AGENTS.md`：它是自动调用的**发现机制**，靠的是 `AGENTS.md` 被各家 harness 无条件常驻（见下节「`AGENTS.md` 同时充当 `MEMORY.md`」）；只留在 `SKILL.md` 里就得指望 harness 主动去读 skill 描述。JSON 字段（`policyAction` → `autoAction`）与 doctor 的 issue 名（`missing-policy` → `missing-auto`）一并跟上，避免出现「区块一个名、报告另一个名」的对不上。

**空外层不留壳。** 只持有索引、自己没有 `.memory/` 的目录（记忆根常这样）在条目清空后，外层会连同 children 一起消失，不留一对空标记。这是嵌套引入的新状态，`drop_index_entries()` 与整份渲染都要收口，否则文件里会残留无意义的空区域。

**嵌套没有引入解析风险，但改变了写入语义。** `block_pattern()` 用非贪婪匹配，内外名字不同就不会误配；真正要改的是**写**：`upsert_block()` 原来对任何区块都整体替换，套在外层上会把内层连带冲掉。现在按归属分派——两个记忆区块走 `insert_inner_block()`（落在外层内部，必要时先建壳），其余走顶层。已验证的路径：手工删掉内层区块后 init 把它补回**外层内部**而不是文件末尾；手工删掉策略区块后 doctor 补回**外层之外**。

**这次改名迁移成本仍是零**（全仓没有 `project-memory:*` 存量产物），所以顺手把产物文案也对齐了：`## 项目记忆` 改成 `## 本层记忆`，与 `## 下层记忆索引` 对称。**外层区块没有标题**——它是容器，加标题反而会让人以为它自己有内容。

**`树` 一节撤掉，内容并进 `AGENTS.md` 一节，正文改成 bullet。** 用户手改的：那几条（稀疏、挂在哪、管多大范围、下层是补充）讲的本来都是 `AGENTS.md` 的位置与作用域，独立成节反而让人先读一段抽象的树论。协议因此只剩三种文件 + 边界。**代价**：`LAYOUT` 的 `树` 一节（那棵 ASCII 目录树）失去对应节；重排时把它提到第一个 H2 之前，与协议里 mermaid 图的位置对齐。

**手改时掉了两条协议，已补回。** 两条都不是措辞，是消费方直接依赖的契约：一是**「按描述挑下一跳，不要把一层整个拉进来」**（渐进式披露的纪律，整套方案省 token 的根据），它原本在 `树` 一节里管着「两层入口」，随 `树` 一起没了，现在落在 `AGENTS.md` 一节并写明「两层入口都一样」，避免在两节里各写一遍；二是**「共享文件、工具只拥有标记划出的区域」**，本文件早有一条专门记录说它不能下放 `LAYOUT`。**这暴露了一个真实风险**：正文重排时，「跨节生效的条款」最容易随着它暂居的那一节一起消失。19 条清单这类逐条核对不能省。

**`type` 的说明里不写大小写。** 手改版曾写成「与 `MEMORY_TYPE_*.md` 的 type 保持一致，小写」，但命名与大小写归 `LAYOUT`，而且协议里的 `MEMORY_TYPE_*.md` 本身是占位名，拿它当基准是循环定义。

**`name` 一度被提为必需，又改回可选。** 手改版写成「必需字段：`name`（同文件标题，文件名去掉后缀）、`description`」，问过之后回到只有 `description` 必需。两个理由：`name` 完全可从文件名推导，零信息量的必需字段只会带来与文件名不一致的风险；门槛压到只有 `description`，才保住「cursor rules / skills 也算记忆」这条泛化能力（Cursor rules 通常只有 description）。**顺带纠了一处概念混用**：实现里 `name` 是文件名去后缀（snake_case，形如 `feedback_api_error`），人类可读标题是另一个字段 `title`，而 `title` 只属于实现、没进协议——所以「同文件标题」这个解释在当前实现下不成立。

**层级用词从「级」统一到「层」**：`本层 / 下层 / 上层`，涉及 PROTOCOL、LAYOUT、`ask`、`init`、`doctor`、`memory.py` 的注释与 `--help`，以及 `AGENTS.tmpl.md` 的索引区块标题。起因是标题解释语定成「本层记忆入口」，而正文与图当时是「本级」——「下级」还是协议里有定义的术语，不统一等于把定义架空。`remember/SKILL.md` 里的「同级的 skill 目录」不在此列：那说的是文件系统同辈目录，与记忆层级无关。

**这次要不要改，取决于一个先查清的事实：`init` 从不按模板重渲染已存在的受管区块**（`merge_index_entry()` 只追加或改写条目行），所以模板里的标题改了名，存量 `AGENTS.md` 里的旧标题永远留着。**我一度把本仓库根 `AGENTS.md` 的 `## 子目录记忆索引` 当成了这条债的实例，是错的**——那行在 `runa-memory-index` 区块里，属于另一套工具。全仓搜 `project-memory:*` 零命中，本套还没有任何存量产物，所以这次改名的迁移成本是零。**教训：拿「现存文件里的旧名」当证据前，先确认那个文件是谁产的**；两套工具的模板同源，文案长得像，很容易认错。

**债本身仍然存在，只是尚未发生，所以按机制记而不按实例记**：写进 `doctor/SKILL.md` 的「已知缺口」，并注明它**不参与解析**（脚本靠区块标记和条目行定位，标题写什么都不影响），因此不算 `finding`、不进修复表，只在用户问起时顺手改。LAYOUT 顶部那条「改已发布产物的名字要给 doctor 加旧名识别」补一句指向它——原来那条只覆盖标记名、文件名、条目前缀，漏了区块内的固定文案这一类。

**图上的用词要跟着协议的定义走**：分组框一度写成「本层 / 下层」，而「树」那节专门定义了「**下级**按记忆层级算，不是目录上的直接子级」。换一个字就把那条定义架空了，且「层」更容易被读成目录层——正是那条定义要否掉的读法。这类漂移只在图与散文用词不一致时暴露，H2 diff 查不出来。

**记忆文件节点不带尖括号**（写 `memory_1.md` 而非 `<memory_1>.md`）：mermaid 标签默认按 HTML 解析，尖括号有被当未知标签吞掉的风险。手改版用 `< memroy_1 >.md`（带空格）恰好能规避——因为标签名不能以空格开头——但那是巧合而非可依赖的写法。

**「附属于项目结构」是这轮补上的核心事实**，原文只用一句「记忆放在目录里」带过。它是记忆能被发现（站在任何目录都知道记忆在哪）、层级能表达作用域（下级更窄）的根因，值当标题。

**新增的「记忆文件」条与「入口文件」条要互相点名**：索引里那句说明**就是** frontmatter 里的 `description`，同一个东西的两个位置；不写明会有人以为要维护两份。

**原第八条（弱依赖）降为结尾段**，与「什么算破协议」合并——它是关于协议本身的元陈述，不是协议的一条。同时删掉正反例表的「安全」整列（是弱依赖的同义反复）、「第七八条不冲突」整段、每行表格后的逐条解释。**论证性散文一律迁到本文件**：契约文件里出现「这条为什么成立」就变成了思考记录。

**一一对应本身可校验**：两份文件 H2 列表直接对着 diff，缺哪节就是哪条协议没有实现说明。模板作为不编号的尾注留在对应关系之外——它是三节的来源，不对应任何一条协议。

**本轮动了协议，所以要说清哪种动法不算破。** 八条并三条只是重排：约束集一条没少、也没改口，任何按旧八条写的实现在新三条下依然合规。真正的实质增量只有一条——新增的「记忆文件」条，它第一次要求了 `description`（另订了三个可选键，代价小一档，见下节）。**而增量是单向的**：协议每长一条，实现下一轮可动的空间就少一块，且没有回头路（撤掉一条协议就是破兼容）。所以「合并可以随时做，新增要有证据」，这道棘轮由下面「判据再修正」那节守着。

### 翻案两次：先改平级，又退回上下级

本轮对两份文件的关系试了两个说法。**先**把「冻结契约 / 当前实现」改成**平级互补**（PROTOCOL 是读方要的形状、LAYOUT 是写方要的编码），判据从易变性换成角色；**再退回上下级**——`LAYOUT` 就是 `PROTOCOL` 的实现。退回的理由是更简单：「实现」一个词已经说完两者关系，不需要再造「读方 / 写方」这层解释。

**平级那轮不算白跑**，它逼出了「按对象分节」，而这个结构在上下级下反而更有用，因为它让「逐条实现」成立。留下的是结构，丢掉的是说法。

记这段是因为它连带决定了标记语法的位置，那项本轮搬了三次，见下一节。

### LAYOUT 不冻结任何东西，区块名的兼容代价改由 doctor 承担

**决策**：`LAYOUT.md` 里**不写任何冻结**。标记语法留在实现文档（对应协议的「入口文件」条），协议只留原则句「工具只拥有自己划出的区域」。

**这一条推翻了上面「协议单独成文」一节的结论**——那里把「已发布的区块名冻结」补进了协议第七条。当时的事实判断是对的（`classify_agents_file()` 精确匹配标记名，改名会让各仓库现存 `AGENTS.md` 全部被判成 `foreign`），但**结论下错了**：那是兼容性约束，不是形状约束；塞进协议只是因为当时认为实现文档「可以自由变」所以放不住。

**换个方向解**：形态还在探索，`LAYOUT` 必须保持完全可改，任何一处冻结都会挡下一轮。所以把「禁止」翻译成**义务**——凡改动已发布产物的名字，同步给 `doctor` 加旧名识别与改写。

**这个义务有天然归属**：doctor 的职责本就是把现状收敛到目标态，认旧标记并改写与它已有的 `foreign-agents`、`dead-entry` 同类。而且**问题不是标记名独有的**：改索引文件名会留下孤儿文件，改条目前缀同理；标记名只是最锋利的一个，因为它兼任身份检查。义务写在 `LAYOUT` preamble（谁改它就会看到），finding 本身未实现（见「待议」）。

**受害者始终只是自己的历史数据，不是消费方**——消费方按协议结尾段只认实际读到的内容，压根不认标记名。这正是 `LAYOUT` 敢完全自由的依据。

### 判据再修正：确定的才升进协议

「什么进协议」这个判据本轮改了第三次：**变更频率 → 角色（读方 / 写方）→ 确定性**。

现在的标准是：**已经验证过的才升进 `PROTOCOL`，还在探索的一律留 `LAYOUT`。** 形态未定本身就是最强的约束，叠上新增协议那道单向棘轮（见「协议与实现按同一组对象对齐」末段），推论就是不要急着往协议里提东西。

现有三条都有支撑：树与逐级披露在本项目跑通过（见「索引跟随记忆层级」「记忆层级会漂移」两节），frontmatter 那几个键有三处外部收敛（见「frontmatter 只必需 `description`」一节）。

前两版判据不是错的，是不够：变更频率漏了「有没有已落盘的历史数据」这个维度（上面「协议单独成文」一节记过这次踩坑）；角色划分则在退回上下级后失去前提。

### 收敛这两份文件时留下的顾虑与自查

**frontmatter 的要求必须限定主语。** 已核：`AGENTS.tmpl.md` 与 `FEEDBACK.tmpl.md` 都以 `# ` 开头，**没有 frontmatter**，只有 `type_slug.tmpl.md` 有。所以不能泛泛写成「记忆文件都有 frontmatter」，得说清是哪一层——节点分类定清之后，这句话落成了「叶子必需 `description`，非叶子不需要 frontmatter」。

**「非叶子不需要」是下限，不是禁令**，所以它不挡将来给 `AGENTS.md` 加 `description`：那是可选项，加了也没违反「不需要」。这个区别要留住，因为下面这个方向是已知要修的。判据是**闭集还是开集**：

- **索引文件是闭集**。有哪几个类型由 `AGENTS.tmpl.md` 定义，脚本还反过来从那几行推导 `type` 与索引文件名。模板既然是「有哪些类型」的事实源，把它们的描述也放在模板里不是重复，是放在定义处。所以 `FEEDBACK.md` / `PROJECT.md` 不需要自带 `name` / `description`。
- **下级 `AGENTS.md` 是开集**，运行时发现，成员不可预知。描述放在父级就会丢——**这正是「待议」里那条 bug 的根因**（体检修 `unregistered` 时只能给兜底描述，原描述随目录一起丢了）。按这个判据，`AGENTS.md` 反而是最该自带 `description` 的：有了它，下级索引就能像条目索引一样全量重算，而不是靠 init 时传入的一次性参数。

**给 `AGENTS.md` 加 `description` 仍留在待议**——它是未验证的行为变更，按「确定的才升进协议」不能顺手带进这轮；协议那句下限已经给它留好了门。

**`description` 必需这条与实现已经对齐，不需要迁移。** 已核：新建时省略 `--description` 直接报错「新建记忆必须提供 --description」，更新时省略则沿用旧值，所以本工具产出的每个条目文件都有它。这是按「确定的才升进协议」那条判据做的取证——先验证实现，再往协议里写，不是先写协议再指望实现跟上。

**可选键「只标含义、不写用途」与提升它们的动机有张力。** 把 `type` / `updatedAt` 提进协议是为了让写方多做事而不必读 `LAYOUT`，但按文风约束，协议里只写「`type` 是分类」而不写「供去重归类」。判断是：**含义就是契约，用途归写方自己决定**——协议保证了字段名和含义，一个写方拿它去去重、另一个拿它去分组，都不违约。用途写进协议反而会把某种用法固化成义务。

**~~第一条的粒度偏粗~~ 已解决。** 原顾虑是「树」那一条塞了七项断言、以后引用「协议第一条」会指代不清。改成命名小节后引用有名字了，这条不再成立（见「协议与实现按同一组对象对齐」一节）。

**「两份 H2 对着 diff」只是形状校验，不是完整性校验。** 它能发现 `LAYOUT` 少了一节，发现不了某节里对应的实现说明是空的或写错的。这个校验值有限，别把它当成对齐的保证。

### 派子 agent 精修协议正文，以及它踩出来的一个教训

**做法**：给独立上下文的子 agent 一份任务书——只改四个 H2 小节的文字组织，标题与顺序不许动，**并附上 19 条规范陈述的清单**，要求条条都还能在改完的文件里读到。结构上的收益是真的：`树` 从「稀疏 + 下级定义焊在一句」拆成一段一件事；非叶子那节按「结构 → 读的纪律 → 文件性质」重组，那一段攒了三件不相干事情的尾巴散掉了。

**但它把 S9 的意思改掉了，而自查报告说 S9 还在。** S9 指的是 `AGENTS.md` 与记忆文件**之间**可以再夹一层索引；它改成了「下级里还可以是非叶子」，变成同义反复——下级 `AGENTS.md` 本来就是非叶子——真正的含义没了。它还顺手删了「（图上略去了）」，而图上确实没画那一层，于是留下一处无声的矛盾。

**教训：清单能防漏，防不住变味。** 「19 条是否都还在」是一个存在性检查，靠关键词就能自称通过；语义有没有漂，只能逐句重读原意去比。所以委派契约类文本的润色时，验收不能只看它的对照表，必须自己把每条改动后的句子读回去。这次是清单里明确写了 S9 的完整含义、我才比出来的——**任务书里把每条陈述写全，本身就是验收工具**。

**另外两处我改回来了**：它把「哪些属于实现」的四个短名词拆成四行 bullet，一节里于是出现两个相邻列表，把「属于实现」和「算破协议」在视觉上摆成了同一层的东西，而这两者性质完全不同；四个短名词串在一句里本来也不难读。它自己也标了这处可退回。行数 57 →（它改完）65 → 58。

**它提的四点存疑，裁定如下**：

- **S11 后半（受管区块的写入语义）该不该下放 `LAYOUT`**：不下放。「非叶子是共享文件、工具只拥有自己划出的那块、区块外原样保留」是消费方真正依赖的契约——`remember` 靠它敢写、`ask` 靠它知道不能整份重写；而**标记长什么样**才是实现。「存在一块被划出来的属地」与「界桩是什么形状」分属两层，正是协议与实现的分界线本身。
- **S10「非叶子不需要 frontmatter」像补丁、建议挪到记忆文件那节**：不挪。协议是**按对象组织**的（树 / 非叶子 / 叶子），不是按话题组织；把两条 frontmatter 规定凑到一起是话题组织，会破坏与 `LAYOUT` 的对象级对齐。
- **`## 协议之外` 这个标题不贴切**：它说对了，已改名 `## 边界`。该节装着三样东西——哪些不属于协议、看不到本套结构怎么办、什么算破协议，最后一样恰恰是协议**内**的规定，「之外」把它排除掉了。「边界」两边都盖得住：既是协议管到哪儿为止，也是越过去就算破。`LAYOUT` 没有对应节，不影响两份文件的一一对应。
- **S19 与 S5 / S6 正反重复**：有意保留。正面陈述给读者，破协议清单给实现者当判据，两者受众不同；而且清单是**升级实现时唯一要对着看的东西**，让它自足比让它去引用前文更可靠。

### 「子目录」清成「下级」

**决策**：产物文案、CLI 提示与调用方文档里的「子目录」一律改成「下级」，与协议里定义的术语对齐；老仓库不追。

协议定完「下级按记忆层级算」之后做了一次全仓复查，发现这个词在**六个位置**还留着旧说法，其中两处顺带暴露了别的陈旧：

- `--description` 的 help 除了「子目录」，还写着「用于**根** `AGENTS.md` 的记忆索引」——那是实现逐级披露之前的行为（当时条目一律平铺到记忆根），也把区块名说错了（下级条目在 `project-memory-index`，不在记忆区块）。一句 help 里三个错。
- `merge_index_entry()` 的 docstring 同样说「子目录入口」。

**教训不是「术语要统一」这种废话，而是术语改动的波及面比看起来大**：协议里改一个词，等于让所有复述过这个概念的地方同时失真，而 CLI help 和 docstring 是最容易漏的两类——它们既不在文档树里、也不会被链接检查扫到。这次是靠 `rg '子目录'` 才捞全的。

**老仓库不追，是你的判断，我核过代价**：`merge_index_entry()` 只把新条目插在 `INDEX_END` 之前，**不重渲染区块正文**，所以旧标题「## 子目录记忆索引」会永久留在已落盘的文件里。能这么放的前提是——脚本的识别一律靠区块标记与链接目标，从不匹配这些文案，所以漂移纯属观感。这也正是 `LAYOUT` 里那条迁移义务只针对「名字」（标记、文件名、前缀）而不针对文案的原因。

**兜底描述仍然硬编码在脚本里**（`agents.py` 的 `normalize_index_description()`），违反「文案进模板、脚本只做占位符替换」。这轮只改字不搬位置：搬它要为一句话新开一个模板文件，收益不抵成本。列入待议。

### 记忆入口层提进协议，`type` 从元数据升为结构

**决策**：协议新增一层——`AGENTS.md` 不直接列本级记忆文件，而是按 `type` 分成几份**记忆入口**，每份只列该类型的记忆文件。于是从 `AGENTS.md` 到本级正文**固定两跳**。

**这推翻了两条旧决定，得说清**：

- 原先「索引不单独占小节」，理由是协议对它只有两句话、且它天然属于入口文件那一节；现在它是协议里的一个独立对象。
- 原先协议只说「非叶子之间还可以再嵌非叶子，**顺着链接走、别假设中间隔了几层**」，把层数和分法都留给实现（`LAYOUT` 才规定三份）。固定两跳之后这句话自相矛盾，已删。**这是本轮唯一被删掉的规范陈述**，其余只增不减。

**没有一起冻的东西**（有意留在 `LAYOUT`）：**有哪些 `type`**、入口文件叫什么名字。所以「新增一个类型只需补一行模板再放一份同名模板」这条扩展路径还在。冻的是「有按 type 分的入口层」这个形状，不是「有哪三类」。

**`type` 在 frontmatter 里仍然可选**，因为它现在被结构编码了——一条记忆归在哪份入口下就是它的 `type`，和 `description` 一样「同一个东西的两个位置」。`ask` 因此被告知：判断类型看它归在哪份入口下，比读 frontmatter 可靠。

**为什么分类型（依据在「记忆分类与命名对齐」与「官方源码取证结论」两节，这里只说它换来什么）**：

1. **三类的寿命和失效方式根本不同，所以维护策略也不同。** 源码里 `project` 要求把相对日期转成绝对日期（「周四」→「2026-03-05」），这条最能说明它是**带时间戳的观察**，会过期；`feedback` 是长期规则，正文结构固定为结论 + `**Why:**` + `**How to apply:**`；`reference` 是指针，它的失效方式是链接坏掉。**把它们混在一处，就没法给任何一类定淘汰规则**——这正是「待议」里 `dream`（整合与遗忘）能不能做的前提。
2. **类型是挡记忆膨胀的闸门。** 官方的「不要记什么」清单是按类型给判据的，每类「收什么、不收什么」写在对应入口模板的引言里，写方才有得可依。反例是自家踩过的：原 `OVERVIEW.md` 模板写着「项目目标、架构、目录、数据流」，直接撞在「凡是能从代码推导的都不记」上——**一个分类错的容器会主动招来垃圾**。而 [`prior-art/01-academic-papers.md`](../../references/reference_academic_papers/INDEX.md) 记着规模化的头号失败模式就是记忆膨胀与 context collapse。
3. **类型是检索的第一道过滤器。** 入口层进协议之后，读方可以在打开任何正文之前先按问题性质挑入口：问「这活儿该怎么干」走 feedback，问「现在在做什么」走 project，问「文档在哪」走 reference。分类型分片还让每份入口都小——`FEEDBACK.md` 这类是「先读」文件，什么都往里堆会让渐进式披露失效。
4. **分界判据一句话**（源码取证）：`feedback` 管「活儿该怎么干」，`project` 管「在干什么、出了什么事」。官方第四类 `user`（角色、专长、个人偏好）是跨项目的个人信息，不落仓库。

**代价**：协议每长一条，实现可动的空间就少一块，而且没有回头路——撤掉一条协议就是破兼容。这一条是靠「三类各自的寿命不同」这个已取证的事实换来的，不是审美偏好；判据仍是那句「合并可以随时做，新增要有证据」。

### `AGENTS.md` 同时充当 `MEMORY.md`

**事实**：本方案的 `AGENTS.md` **形式像 `CLAUDE.md`、功能像 `MEMORY.md`**（调研早有此判断，见 [`prior-art/OVERVIEW.md`](../../references/reference_prior_art/INDEX.md) 与 [`prior-art/04-index-granularity.md`](../../references/reference_index_granularity/INDEX.md)，这里把它升成一条决策）。Claude Code 里这是**两个文件、两套机制**：`CLAUDE.md` 是人写的常驻指令，`/memories/MEMORY.md` 是记忆工具维护的索引。我们把两个角色合进了同一份文件。

**合并换来的最大好处：加载机制白拿。** 记忆体系最难的一环从来不是「怎么存」，而是「agent 凭什么会去读」。官方的记忆工具为此专门规定了「每次会话开始只自动读 `MEMORY.md` 这一个文件」。而 `AGENTS.md` 的加载语义**已经被各家 harness 内建了**：根那份无条件常驻，子树那份在「读到该子树的文件」时才加载（[`prior-art/02-coding-agents.md`](../../references/reference_coding_agents/INDEX.md) 记着官方原话 "not at launch, but when Claude reads files in those subtrees"，Amp 用 41 份 `AGENTS.md` 验证过这个规模）。把索引直接写进 `AGENTS.md`，于是**发现机制和渐进加载都不必自己造**——这正是整套方案能只用「文件 + `rg`」、不需要任何常驻进程或向量库的原因。

**受管区块因此不是便利，而是这次合并的成立条件。** 一份文件同时装人写的常驻正文和工具维护的索引，只有在「工具只拥有自己划出的区域」这条约定下才不会互相破坏。这也是上一轮裁定 S11 必须留在协议里的根据：它不是实现细节，它是合并本身的前提。

**代价一：常驻层的字节要算在每一次会话头上。** `MEMORY.md` 只在会话开始读一次且可以很小，而根 `AGENTS.md` 是无条件常驻的。所以策略区块只在记忆根出现一份、索引只列直接下级——这两条设计都是被这个代价逼出来的，不是审美选择。也因为功能等同索引，该采用的是 `MEMORY.md` 的**硬**上限（200 行 / 25 KB，超出静默丢弃）而不是 `CLAUDE.md` 的软建议 200 行。**尚未实现**，见「待议」第一条。

**代价二：官方那条排除规则在合并后变得含糊。** 官方明确把 `Anything already documented in CLAUDE.md files` 排除在记忆之外——常驻层归 `CLAUDE.md` 正文，记忆层只管按需加载。可当两者是同一个文件时，这条规则字面上会自我吞噬。合并后它的正确读法是：**受管区块里只放索引，人写的常驻结论留在区块外的正文，一条记忆不要重述正文已经说过的话。** 这条纪律目前没有写进任何 skill，也没有体检项，只在这里记着。

## scripts 从单文件拆成分层模块

**决策**：1096 行的 `memory.py` 拆成十个文件，四层，依赖只朝下：

| 层 | 文件 | 职责 |
| --- | --- | --- |
| CLI | `memory.py` | 参数、JSON 输出、错误收口 |
| 操作 | `init.py`、`remember.py`、`doctor.py` | 三个子命令各一份，与三个 skill 对齐 |
| 节点 | `agents.py`、`entries.py` | 协议里的两类节点：入口文件与记忆文件 |
| 公共件 | `blocks.py`、`templates.py`、`paths.py`、`provenance.py` | 标记与区块、模板与占位符、路径与落盘、出处字段 |

**理由**：单文件到这个规模，代价不在阅读而在**每改一处都得把全文读进上下文**。拆完之后「改区块结构」只读 `blocks.py`、「加一个 frontmatter 字段」只读 `entries.py` + `provenance.py`。节点那一层照协议的名字切，所以「这个函数放哪」有客观判据，不靠手感。

**依赖只朝下是唯一硬约束**：反向依赖立刻变循环 import，会当场炸，不需要靠纪律维持。这也顺带证明了分层是真的——公共件不知道操作的存在。

**入口仍叫 `memory.py`**：三份 SKILL.md 写的都是 `scripts/memory.py`，它是已发布契约。这跟 `LAYOUT` 里的产物改名同类，区别是这个没有 `doctor` 兜底，所以不改。

**顺带处理的两件事**：删掉 `search` 子命令（`rg -i` 完全覆盖，留着还得维护两条检索路径，`ask` 早已不提它）；加 `scripts/.gitignore` 挡 `__pycache__`——sibling import 会在技能目录里生成字节码，而这个目录是要被复制进别人仓库的。

**验证方式值得单独记**：拆之前先跑一遍完整场景（干净建树、幂等重跑、层级归位、`foreign` 追加、`missing-auto` 修复、`remember` 新建与更新）并快照全部产物与 CLI JSON，拆完逐字节比对。纯搬迁的重构只有这一种可信判据，读代码自查不算。

## 协议向外用了一次：`runa-memory-ask` 不再写死记忆目录名

**事实**：团队知识库检索那个 skill（`runa-memory-ask`，与本套无关，只共用「本地记忆优先」这条仲裁）原先写的是「本地 `AGENTS.md` 与 `.edges/` 已足以回答时优先用本地」。`.edges/` 是上一代 runa 的 LAYOUT 细节，写在这里等于让一个纯消费方绑定了某一代实现——换成 `.memory/` 它就得跟着改。改成「各级 `AGENTS.md` 及它逐层索引进去的记忆文件」，两代都成立。

**意义在于这是协议的第一次对外验证**：`AGENTS.md` 逐层索引这一条足够支撑「本地优先」的仲裁，消费方不需要知道目录名、区块标记名或索引文件名。之前「格式拥有者 / 格式消费者」的划分只在本套四个 skill 内部试过，这次证明它对**不同代、不同作者**的工具同样成立。

**顺带**：那份 skill 里约 39 行是纯重复（九个 tool 参数在表格外又列一遍、`pages` 格式讲两次、`next_steps` 与并行调用各自又开一节、精筛数量在三处出现），一并收掉，206 → 173 行。这部分与协议无关，只是同一套「不要流水账」的标准。

## 协议的边界：什么该进、什么不该进

这条线纠结最久，判据本身改过三次，中途还翻过案。这一节只留收敛后的判据，过程记录仍在上面各节，不重复。

### 判据的三次修正

| 版本 | 判据 | 为什么不够 |
| --- | --- | --- |
| v1 | 变更频率：改了会让所有 skill 跟着改的是协议 | 漏了「有没有已经落盘的历史数据」这一维，区块名那次就栽在这里 |
| v2 | 角色：读方要的形状归协议，写方要的编码归实现 | 两份文件退回上下级关系之后，这个划分失去了前提 |
| v3 | **确定性：已经验证过的才升进协议，还在探索的一律留 `LAYOUT`** | 现行 |

现有三条都拿得出验证：树与逐层披露在本项目跑通过，frontmatter 那几个键有三处外部收敛。**形态未定本身就是最强的约束**——想不清楚就是「还不该进」。

### 判据为什么必须保守：棘轮是单向的

协议每长一条，实现下一轮可动的空间就少一块，而且没有回头路——撤掉一条协议就是破兼容。由此三条推论：

- **合并与重排可以随时做，新增要有证据。** 八条并三条时约束集一条没少，任何按旧八条写的实现在新三条下依然合规。
- **删减比新增更危险**，因为它是无声的放宽。「一份 `AGENTS.md` 挂在最近的带记忆祖先下层」这句差点被当成冗余删掉，少了它，实现把记忆挂到任意祖先上都算合规。
- **字段分两档**：必需键是硬棘轮，所有实现都得产出；可选保留键是软棘轮，只订走名字与含义、不强制存在。要往协议里加东西，软棘轮是最便宜的一档。

### 四道筛子

1. **消费方不知道它就会做错事吗？** 「`AGENTS.md` 是共享文件，工具只拥有自己划出的那块」进协议——`remember` 靠它敢写、`ask` 靠它知道不能整份重写。而**界桩长什么样**（标记是 HTML 注释、叫什么名字）是实现。「存在一块属地」与「界桩什么形状」分属两层，这就是分界线本身。
2. **它是形状，还是命名与数量？** 「有按 `type` 分的入口层、从 `AGENTS.md` 到正文固定两跳」是形状，进；「有哪三类、入口叫 `FEEDBACK.md`」是命名，留 `LAYOUT`——所以「加一个类型只改模板」这条扩展路径才还在。
3. **信息是不是已经在别处了？** `name` 的值等于文件名去后缀，frontmatter 那一行是冗余的，于是从必需降为可选。降级是放宽，永远安全。
4. **外部有没有独立收敛到同一形态？** `description` 必需有三处独立证据（调研里的参考实现、本仓 18 份 `SKILL.md`、Cursor rule）。反过来，正是「Cursor rule 只有 `description`」这个反例掐掉了「`name` 必需」——一旦必需，rule 当场不合规，而「rule 也是记忆」恰恰是这轮想要的泛化。泛化的边界是**同形不同权**：形状可以统一，但 skill 是会被执行的指令、记忆是供判断的证据，权限不能跟着统一。

### 三类东西看着像协议，其实不是

- **兼容性约束。** 「已发布的区块名冻结」一度被写进协议，事实判断没错（`classify_agents_file()` 是精确匹配，改名会让存量文件全被判成 `foreign`），但那是自己历史数据的迁移问题，不是形状问题。现在把禁止翻译成**义务**：`LAYOUT` 不冻结任何东西，改名就得同步给 `doctor` 加旧名识别。**受害者始终是自己的历史数据，不是消费方**——消费方只认实际读到的内容，压根不认标记名。
- **用途。** 协议只写「`type` 是分类」，不写「供去重与归类」。含义就是契约，用途归写方；把用途写进去，等于把某一种用法固化成义务。
- **自造的统称。** 「路标」曾用来同时指 `AGENTS.md` 与索引文件，它是从调研笔记的比喻里漂进来的。比喻留在调研笔记没问题，升进冻结契约就成了理解门槛。造统称之前先确认标准词真的不够用。

### 守这条线时反复犯的错

- **把思考顺序当成结构**：最早那八条里有五条讲的都是同一件事——树长什么样、怎么走。
- **把真名画进协议**：图上的入口曾写成 `MEMORY_INDEX_TYPE_A.md`，既不是真名又长得像真名，会被当成命名规则去对照，是最坏的一档。现在图与小节标题里的名字全是占位式的，由「边界」一节统一声明。
- **拿存在性清单当验收**：把 19 条规范陈述交给子 agent 做对照表，它自称条条都在，实际把 S9 改成了同义反复。清单能防漏，防不住变味。

**最后一道兜底在协议自己身上**：末尾那句「按实际读到的内容走，看不到这个形状就当项目还没建记忆」，是整条边界的安全网。有了它，线划偏一点也不会让消费方硬崩——这同样是 `LAYOUT` 敢完全自由的依据。

## 部分翻案：`ask` 可以吃 `LAYOUT`，代价换成一条同步义务

**决策**：`ask` 内联当前三份入口的名字与条目前缀（`FEEDBACK` / `PROJECT` / `REFERENCE` 与 `feedback_*` 等），并链到 `LAYOUT.md` 取更多细节，同时声明「读到的和表对不上就按实际读到的走」。这推翻了「判据修正：不是零跨 skill 引用」那张表的一半——`remember` 那半仍然成立，它经 CLI 落盘，`--help` 就是全部接口。

**第一个理由：耦合本来就在，只是没承认。** 旧版 `ask` 一边声明「不要假设标记名或入口文件叫什么」，一边硬编码 `.memory/` 去跑 `rg`。声明与行为对不上时，代价不会消失，只会变成看不见的——挑入口只能靠语义猜（旧版写的是「找用户反馈那类、项目动态那类」），猜错就读错文件。承认依赖才能把代价标价、找到归属。

**第二个理由：`ask` 是每次提问都走的路径。** 不内联只有两个选择：每次多读一份 `LAYOUT`（那是常驻成本，和「`AGENTS.md` 同时充当 `MEMORY.md`」一节里算的字节账同类），或者继续靠语义猜。一处同步义务比这两样都便宜。

**第三个理由：版本偏斜的威胁之前被高估了。** `ask` 与 `LAYOUT` 同仓发布、一起升级，文档级偏斜几乎不存在。真正会偏斜的是**落盘产物**——本仓根 `AGENTS.md` 此刻还是上一代 runa 的 `.edges/` 形态，`LAYOUT` 描述的 `.memory/` 在这里一份都不存在。而那种偏斜靠「按实际读到的内容走」兜，与消费方读不读 `LAYOUT` 无关。**把两种偏斜混成一件事，是原判据保守过头的根源。**

**分档比一刀切准：链接免费，内联才收费。** 链接指向的永远是当前版本，不可能过期；内联是把事实抄一份出来，才产生同步义务。这轮两样都用了——表内联（为了让每次提问都自足），细节走链接。

**判据因此改成**：消费方不能内联 `LAYOUT` 里**还在探索**的东西；已经稳定、且**每次检索都要用**的，可以内联，但必须在 `LAYOUT` 开头登记同步义务。义务已写在那条给 `doctor` 的旧名识别义务旁边——改这三个名字或前缀的人，一处就能看到全部下游。

**没有变的部分**：区块标记名仍然没有任何消费方认，所以改标记名的代价和这轮之前一样，只欠 `doctor`。

## 再翻案：`ask` 依赖产物，不依赖任何文档

**决策**：抽掉 `ask` 里内联的入口表，改成「按你正在读的那份 `AGENTS.md` 里每项后面那句说明挑」；`LAYOUT` 开头那条刚加的同步义务收回；`PROTOCOL` 只留形状兜底。这推翻了上一节的**做法**，但没推翻它的**分析**——三档依赖那个框架成立，错的是把 `ask` 放进了第三档。

**触发问题**：「是不是把工作放到写时加 `doctor` 就好，省运行时。」顺着它把运行时的工作分三类，余量在哪立刻清楚：

1. **与问题无关的知识**（有几份入口、各叫什么、各收什么）——可以预计算。
2. **与问题相关的判断**（该往哪层跳、该打开哪几条）——**定义上不可预计算**，输入就是问题本身。
3. **派生物的一致性**（索引与文件对不上、死条目）——本来就是 `doctor` 的活，已经在做。

**关键事实：第一类早就在写时完成了，信息就在产物里。** `AGENTS.tmpl.md` 的本层记忆区块每行就是「链接 + 这份收什么」，落盘之后一直在那儿；而根 `AGENTS.md` 无条件常驻、子树那份在读到该子树文件时加载（见「`AGENTS.md` 同时充当 `MEMORY.md`」一节）。所以挑入口所需的全部信息，在 `ask` 开始干活之前已经免费躺在上下文里。上一轮那张内联表是同一事实的**第三份拷贝**（模板里、落盘文件里、`ask` 里），而且是唯一一份会过期的。

**于是 `ask` 也够得着「自描述」那一档，取舍直接取消。** `remember` 的自描述接口是 `--help`，`ask` 的是**产物本身**——每项后面那句说明由 `remember` 写入、`init` 全量重算，永远和磁盘一致。两个消费方都回到第一档，「依赖 `PROTOCOL` 还是 `LAYOUT`」这个问题不必回答。

**跨代验证，而且是在本仓就地取证**：这个仓库的根 `AGENTS.md` 至今是上一代 runa 的形态（`.edges/CONSTRAINTS.md` 等），每项后面同样带一句说明。「按产物说明挑」在这里直接就对，而写着 `.memory/FEEDBACK.md` 的内联表在这里全是死路。**两代产物唯一共享的最小约定就是「一个链接加一句说明」**——这反过来印证了协议该冻结的正是这个，不是名字。

**判据升级**：「消费方该依赖谁」的正确问法是「**有没有一个自描述的东西可以依赖**」。CLI 的 `--help`、产物里的描述都算。只有在确实找不到自描述物时，才需要在冻结文档与活文档之间取舍——而那时候答案基本都是「别内联」。

**代价说清**：挑入口的准确性从「写死的映射」变成「读产物描述」，于是**描述质量成了运行时性能的变量**。这个方向是对的（成本转移到写时，一次投入长期受益），但目前 `remember` 只强制 `description` 存在、不管质量，`doctor` 也没有对应检查项。列入待议。

**顺带记一个不该往写时挪的**：预计算一份全树扁平清单让 `ask` 一次搜完。那正是「渐进式披露」否掉的平铺，还多一个要 `doctor` 维护的派生物——而 `rg` 就是它的零维护运行时等价物。**「能不能挪到写时」之外还得问「挪过去要不要维护」**：产物里的那行说明是写记忆时顺手产生的，扁平清单是凭空多出来的一份状态。

## 补上「工作范围」这个缺失的中间概念

**事实**：协议早就规定了「读把相关的各层叠加、写按作用范围选一层」（`AGENTS.md` 那节），但两个消费方都没把「相关」与「作用范围」落成可操作的东西——`ask` 写的是「顺着链接往任务相关的那层走」，`remember` 写的是「与结论作用范围最贴近的那一层」。两句都把判断丢给了直觉，缺的是同一个中间概念：**这次任务的工作范围**（用户点名的路径、当前在改的文件、上一轮动过的目录）。

**缺了它，读方会系统性变差。** 没有工作范围，`ask` 只能自上而下从记忆根逐层猜「要不要往下走」，每一步都是一次判断，依据还只有下层条目那一句说明。有了工作范围，方向反过来：**一个文件相关的记忆，就是从记忆根到它所在目录这条祖先链上的每一层**——查表，不是猜。范围里有几个目录就取几条链，取并集。

**这条链多半是零额外读取**：harness 读到某子树的文件时会自动加载那份 `AGENTS.md`（见「`AGENTS.md` 同时充当 `MEMORY.md`」一节），所以按祖先链取，需要的层大概已经在上下文里；自上而下猜反而会打开工作范围外的兄弟层。**这也是「渐进式披露」在读侧的正确执行方式**——渐进不等于每层都停下来判断一次，而是只取覆盖工作范围的那几条链。

**写方那侧要补一条容易搞错的边界：作用范围 ≠ 改动范围。** 改动集是**线索**，不是判据。这次只改了某个模块，但结论若是关于构建工具或团队规范的，作用范围仍然是整仓。判据始终是「这条结论对哪些代码成立」，改动集只用来提候选。不写清这条，「按改动目录写」会把项目级结论钉死在一个模块里，别的任务永远读不到——而这类错误没有任何检查能发现，因为文件本身完全合规。

**顺带修掉两处 `级` 的残留**：`remember` 的小标题「写哪一级」与正文「最贴近的那一级」说的都是记忆层级，上一轮全量改名时漏了（当时只核到「同级的 skill 目录」，确认它指文件系统同辈目录）。教训与「「子目录」清成「下级」」一节同源：术语改名的波及面里，**小标题和正文里的量词最容易漏**，`rg` 单个词捞不全。

## 常驻策略区块的触发条件

**这个区块的地位决定了取舍**：它无条件常驻（字节算在每一次会话头上），同时又是 `ask` / `remember` 的唯一触发面。所以判据是——**只装「不写就永远不会被想起」的那几条**，其余一律下放给两个 skill 的正文。

**改动一：检索的触发从「用户提问」扩到「回答问题或动手改代码之前」。** 编码 agent 的主场是任务而不是问答，而 `feedback` 类记忆装的正是「这活儿该怎么干、什么不能做」——需要它的时刻是**动手前**。按原措辞，一个被要求实现功能的 agent 可以完全合规地跳过记忆，因为「没人提问」。**这类漏的失败是闷的**：表现只是它又踩了一遍上次纠正过的坑，没有任何报错。同时补一句「本轮查过就别重复查」，防住扩大触发面之后的反向失败（每次编辑都查一遍）。

**改动二：把「用户纠正了你」列为沉淀触发。** 原措辞「有已验证、以后还用得上的结论就沉淀」描述的是一个**事后回顾**的状态，而 `feedback` 记忆的真实来源是一个**当场发生的事件**——用户说「不对，应该用 X」。那一刻 agent 正在改代码，不会主动往「我是不是该沉淀」上想。

**故意没写「用户明确要求记住」**：它精度最高，但完全不需要提示——用户那句话本身就会把 `remember` 拉起来。常驻的字节只花在不提示就想不起来的条目上，这是这个区块所有取舍的同一条判据。

**顺带统一标题**：`## Memory 自动化` → `## 记忆自动化`，与旁边「本层记忆」「下层记忆索引」一致。区块内文案不参与解析（见「「子目录」清成「下级」」一节末段），改了只影响新生成的文件。

## 翻案：`auto` 收回外层区域内部

上一轮把自动化策略挪出了记忆区域、与外层平级（见「三个平级区块改成……」一节末段），理由是「它讲工具怎么被调用，不是记忆内容，留在里面会让『外层 = 记忆』这个等式不成立」。这一轮翻掉了：**改的不是 `auto` 的性质，是「外层 = 什么」的定义。**

两种读法只能选一个：

- 外层 = **记忆区** → `auto` 不该进，它不是记忆。
- 外层 = **本套在这份共享文件里的属地** → `auto` 必须进，共享文件里本套拥有的东西该是一整块连续区域，而不是两处飞地。

选后者。它和受管区块的**初衷**一致——那个机制存在的理由就是「在别人的文件里划一块属地」（见「`AGENTS.md` 同时充当 `MEMORY.md`」一节），而不是「标出哪里是记忆」。上一轮的等式其实是把协议的结构要求（`AGENTS.md` 列两类子节点）错当成了区块的所有权语义：**协议管形状，区块管归属，两件事**。协议依然只要求那两个记忆区块，`auto` 属于本实现的额外内容，待在属地内不破协议。

**代码跟着塌了一层**：顶层从此只有外层一个区块，顶层排序变成空命题——两级顺序表退化成一张 `INNER_BLOCK_ORDER`（local → children → auto），`place_block()` 退化成 `append_block()`。这是判据选对之后的附赠，不是理由。

**留下一处形状漂移。** `upsert_block()` 按标记定位，所以存量文件里待在外层之外的 `auto` 会被原地替换、留在原处：不报错、不影响解析（`classify_agents_file()` 认任一标记，`doctor` 的 `missing-auto` 只查标记在不在），但嵌套与新模板不一致。今天成本为零——本套还没有存量产物（见「「子目录」清成「下级」」一节的结论），所以只登记不实现。

## scripts 四层从平铺改成按层分目录

**决策**：拆文件时已经按四层切了，但十个 `.py` 仍平铺在 `scripts/` 里，打开目录看不出层。改成三个子目录，入口不动：

```text
scripts/memory.py          → CLI（已发布契约，路径不改）
scripts/operations/        → init / remember / doctor
scripts/nodes/             → agents / entries
scripts/lib/               → blocks / templates / paths / provenance
```

**理由**：分层的价值是「改区块只读 `blocks.py`」，但平铺时先得从十个文件名里把层认出来。目录把层变成打开就能看见的结构；import 写成 `from lib.blocks import`、`from nodes.agents import`，反向依赖会立刻变成找不到模块，跟原来「反向依赖当场炸」同一条硬约束。

**不改的**：`python3 …/scripts/memory.py` 仍是三份 SKILL.md 的调用入口。`lib` / `nodes` / `operations` 都是常规包（各有一份只写职责的 `__init__.py`），运行时靠脚本目录在 `sys.path` 上，不需要 `python -m`。

**模板路径**：`templates.py` 搬进 `lib/` 后不再用 `__file__` 往上两层猜 skill 根，改由 `lib/paths.py` 的 `SKILL_DIR` 提供（`parents[2]`：lib → scripts → skill 根）。

## 2026-09-02：Init 只允许用户手动调用

**背景**：Remember 会在有可复用结论时主动跑。旧写法是目标目录还没 Init 时，agent 先跑 `$edges-memory-init` 再写。等于一次「这条值得记」的判断，顺手给仓库装上 `AGENTS.md` + `.memory/`（进 git）。

**决策**：Init 只在用户明确要求时运行。Remember / Ask / Doctor 都不得代为调用。没 Init 时 Remember 拒写，问用户要不要 Init，同意后再跑；不要自己建。

**理由**：

- Init 是「这个项目要不要用这套记忆系统」，Remember 是「这条结论要不要落盘」。两件事不能绑在一次 agent 判断里。
- 自动 Init 还容易把写入目标选成刚改过的子目录，记忆随改动集裂开。协议说拿不准写记忆根、树要稀疏；自动建目录把闸门拆了。
- 用户说「记住」也一样：先问要不要 Init，不要替他启用。

这翻掉「remember 的主路径改回内联」里把「目标目录还没初始化、要先 init」列为 subagent 逃生舱那一条。现在没 Init 不是委派理由，是停下来问要不要启用。

## 2026-09-06：类型正文分目录，`packages/skills/` 只声明兼容边界

**决策一：索引留在 `.memory/` 根部，正文按类型分目录。** `FEEDBACK.md`、`PROJECT.md`、`REFERENCE.md` 与新增的 `SKILLS.md` 仍是本层的四个类型入口；`feedback`、`project`、`reference` 的正文分别移入同名小写目录。也就是说，入口维持一层可见，类型内部不再全部平铺在 `.memory/` 根部。

这保留了 `AGENTS.md → 类型入口 → 正文` 的固定两跳，同时让目录本身成为类型边界。入口如果跟着正文一起下沉，读方要先知道各类型目录的位置才能找到入口，等于在已有索引层前又加了一层没有检索价值的导航；所以「每类一个目录」只作用于内容，不作用于入口。

**决策二：新增 `skills` 类型，但不由项目记忆定义技能内部格式。** `.memory/skills/` 作为常规 Agent Skills 根目录存在，`SKILLS.md` 只负责把它接入本层记忆入口。`LAYOUT.md` 只声明这条兼容边界，不展开技能目录内有哪些文件、frontmatter 有哪些字段，也不复制当前版本的 Agent Skills 结构。

理由是**协议归属要单一**：这里拥有的是「项目记忆如何索引 skills」的决定，不拥有「一个标准 skill 长什么样」。复制外部协议会制造第二份事实源；一旦 Agent Skills 演化，本项目会在没有自身行为变化时被迫修改布局文档，还可能因更新不及时产生伪兼容。`packages/skills/` 的内部结构因此始终以其自身协议为准，本实现只消费，不重新定义。

**普通记忆与 skills 不强求同形。** `feedback`、`project`、`reference` 继续使用 `<type>/<type>_<slug>.md` 和本实现的条目模板；`skills` 只共享「有一个类型入口」这层抽象。为了表面统一而让 skills 套 `type_slug.tmpl.md`，会破坏它作为常规 skills 根目录直接复用、发现和分发的目标。

**落地顺序按 [开发流程](../project_development/INDEX.md) 执行。** `PROTOCOL.md` 的三层形状没有变化，所以保持不动；init 负责创建四份入口与四个类型目录，普通记忆改写入对应子目录，`skills` 只通过薄适配重算索引。remember 的 `--type` 仍只开放三种普通记忆，不生成 skill；ask 继续按产物说明走，不需要知道这次布局变化。

**存量迁移最后交给 doctor。** init 发现旧版平铺记忆时在写入前拒绝继续，避免先重算出一份漏条目的索引；doctor 把旧文件原样移入类型目录，再补目录、入口和本层清单，最后全量重算。新旧位置存在同名文件时只报告冲突、不覆盖，修复后再跑一次必须零 finding。这样迁移权仍集中在唯一拥有全树视野且要求显式 `--apply` 的地方。


## 2026-09-06：类型集合再确认——不加 docs / user；目录改复数

详见 [`project_type_set.md`](../project_type_set/INDEX.md)。这里只记裁定，不重复论证。

**决策**：可写类型维持 `feedback` / `project` / `reference`；`skills` 继续只索引。否掉 `docs` 类型。否掉把官方 `user` 放进仓库树（含 gitignore + 按人一个 md）。不改 `project` / `reference` 入口引言去迁就已有文件。`.memory/` 下类型目录改为复数，与已有的 `packages/skills/` 对齐。

**对「记忆分类与命名对齐」一节的补充，不是推翻**：`user` 不落盘的理由仍然是「跨项目、不属于仓库内记忆」。gitignore 只解决公开仓库推送，不解决作用域；按人拆文件会把人名写进路径和索引。`docs` 切的是载体，过不了「检索问题 × 寿命 × 闸门」三件套。

**对「2026-09-06：类型正文分目录，packages/skills/ 只声明兼容边界」的补充**：`skills` 与三类不抢内容，抢的是入口说明「操作流程与使用规范」。`.memory/skills/` 与 `packages/skills/` 是两套根，职责未划清之前入口只是空导航。目录名改为 `feedbacks/` / `projects/` / `references/` / `packages/skills/`；`--type`、索引文件、条目前缀仍用单数，打破「类型目录名取 type 原值」。落地是 LAYOUT 变更，doctor 认旧单数目录并迁移。

**Hermes 对照**：它的整体是学习环（同一轮 review 可写 memory 和 skill），不是混桶。Memory 靠硬上限把流程挤去 skill；`USER.md` 在 agent 家目录。不抄 2200 字上限（那是个人助手常驻 prompt 的账）。

## 2026-09-06：硬约束种子收成聚光灯，不是时机说明书

**决策**：硬约束种子只留两句——ask / remember 聚光灯，以及「硬约束写在本区块」。各层仓规手写追加。不把查/记的做法抄进入口，不点名 init / doctor / reshape。ask / remember 的 description 补上「动手前也要查」「被纠正也要记」。

**这收窄上一节「时机纪律并进硬约束」。** 发现机制仍要常驻，否则两个日常 skill 会淹在海量 skill 里。但常驻的是点名，不是把 auto 区块整段搬进 important。封面负责匹配时机，入口负责不被淹没。

## 2026-09-06：撤销独立 auto 区块，时机纪律并进硬约束

**决策**：删掉 `project-memory-auto`。检索与沉淀的时机三条写进硬约束种子，每层新建入口都带。doctor 认旧标记为 `stale-auto` 并删除。PROTOCOL 的三类（硬约束、本层索引、下层索引）不变。

**这翻掉「常驻策略区块的触发条件」和「翻案：auto 收回外层区域内部」。** 发现机制仍要常驻——根 `AGENTS.md` 无条件加载，没有时机句 agent 不会去读 skill。但独立成块是第四类内容，和协议「入口里有三类东西」打架，也把 skill 操作纪律又抄了一份。放进 important 种子：还是常驻、还带 `$edges-memory-ask` / `$edges-memory-remember` 触发名，不再多一个区块。外层靠 important + local 撑着，不靠 auto。

**区块外正文不是第四类记忆。** reshape 收紧为标题、身份、指向真理源的指针；长规范进 important 或 README。本仓根 `AGENTS.md` 按这个收过，隐私表搬进 README。

**JSON 去掉 `autoAction`。** 只给 agent 看，与 init 1.3.0 同发。
