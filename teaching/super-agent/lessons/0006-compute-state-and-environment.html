计算、状态与环境的分离

「持久」要先解开计算、状态与环境的绑定：计算上云且无状态，状态进数据库，执行环境留在原地，用轻量 daemon 按需接入。

第 6 课 · 约 10 分钟 · 主来源：DeepSeek Harness 团队 · Super-agent 设计探索（第 5 节）

学完这一课，你能做到

能讲清：本地 Agent 怎样把计算、状态和环境绑在同一台设备上，以及这会怎样破坏「持久」；第一层解耦如何把无状态计算和持久化状态分开；第二层解耦为什么让执行环境留在原地、只在端侧放一个不保存会话状态的 daemon；以及原文自己怎样写下与 Anthropic「脑手分离」的一致和场景区别。

三件事绑在同一台设备上，就谈不上持久

现有的本地 Agent 默认将推进 Agent Loop 的计算、需要持久保存的会话状态，以及代码仓库与本地工具链等执行环境绑定在同一台设备上。一旦设备休眠或离线，Agent 就会停止运行，且无法访问其他设备上的环境。要让 Super-agent 做到持久在线并灵活接入各类真实工作环境，原文借鉴计算机系统中存算分离的思想，分两步解耦这三者的绑定。 原文 · 第 5 节

第一步：计算做成无状态，状态放到数据库

推进 Agent Loop 的计算可以做成无状态的，需要持久保存的是会话状态。因此，第一层解耦是将推进 Agent Loop 的计算放入云端无状态的弹性计算容器中，而将 Session 等持久化状态存入数据库。无状态计算容器可以水平扩展、重启或替换，会话与任务的连续性则由持久化存储保障，从而使 Agent 摆脱单台本地设备的生命周期限制，实现云端持久在线。 原文 · 第 5.1 节

第二步：环境留在原地，用轻量 daemon 按需接入

在 Agent Loop 与会话状态常驻云端后，进一步的问题是如何访问任务所需的执行环境。模型工作所需的上下文，很大一部分要通过工具调用从代码仓库、本地文件、依赖服务等执行环境中获取；从这个意义上说，广义的上下文也包含了执行环境本身。 原文 · 第 5.2 节

围绕这一问题，原文写了两种常见思路，并说明为什么不够好。一种是在云端启动沙箱、拉取代码并尝试重建和同步环境，但由于真实工作环境往往包含未提交的本地修改、私有凭据、内网服务依赖以及特定的硬件或工具链，同步这样的环境不仅成本很高，还容易出现信息遗漏；另一种是直接要求用户放弃本地环境、迁往云端工作，但对很多用户来说迁移成本过高。

既然难以复制和同步的是环境本身，就不必让执行环境跟着 Agent Loop 上云。第二层解耦是让 Agent Loop 在云端运行，而让重状态的执行环境留在原地，仅在端侧部署一个不保存会话状态的轻量 daemon，它只负责执行命令与返回结果。相当于把执行环境留在云端之外，由 Agent 按需读取其中的上下文。

原文自己写下的对照：脑手分离，但场景不同

原文写：这一思路与 Anthropic 提出的「脑手分离」一致，同样让 harness 保持无状态，把会话日志存放在 harness 之外，并通过统一接口按需接入执行环境。两者的区别在于场景。Anthropic 那篇文章描述的是托管服务，主要讨论按需创建的沙箱和客户 VPC；这里首先要接入的是用户日常使用、可能间歇在线的个人机器，上面有未提交的修改和本地凭据。因此，这种设计既支持 BYOM（Bring Your Own Machine），即把用户日常使用的开发机或个人电脑接入云端 Agent，也支持接入云端托管机器或按需创建的计算环境。 原文 · 第 5.2 节 Anthropic · Scaling Managed Agents: Decoupling the brain from the hands

由此，一个 Agent 不再受限于单台机器，而是可以在不同的执行设备之间切换，根据任务需要选择环境来执行命令并获取环境中的上下文。它甚至能够支持间歇在线的设备：例如在用户的某台个人设备重新上线后，再由云端 Agent 自动触发并完成需要在该设备上执行的任务。

本课只按原文记下这一对照和区别，不把它扩展成一门对比课。第 5 节也还没有解决长期运行中的异常自愈，那是下一课 Watchdog 的任务。

合上原文，60 秒这样讲

「要支撑「持久」，先得解开本地 Agent 把三件事绑在同一台设备上的做法：推进 Agent Loop 的计算、要持久保存的会话状态，以及代码仓库和工具链等执行环境。设备一休眠或离线，Agent 就停了，也到不了别的设备上的环境。原文分两步做存算分离。第一步，计算放进云端无状态的弹性容器，Session 等状态存进数据库，连续性由存储来保障。第二步，不要把难以复制的执行环境跟着上云——在云端重建沙箱容易遗漏未提交修改、私有凭据和内网依赖，强迫用户迁到云端成本又太高。于是 Agent Loop 在云端跑，环境留在原地，端侧只放一个不保存会话状态的轻量 daemon，负责执行命令并返回结果。原文说这与 Anthropic 的「脑手分离」一致，但场景不同：那边是托管服务里的沙箱和客户 VPC，这里首先要接可能间歇在线的个人机器，所以既支持 BYOM，也支持云端或按需环境。」
