Permissions

无人值守却握着访问权：凭证走环境外的 proxy，危险动作可拦住，要人拍板时把一次调用完整往返。

第 5 课 · 约 10 分钟 · 主来源：William Hu · Building always-on agents

学完这一课，你能做到

能画出一次 deferred tool call 的完整往返：结束这次 run 并保存 session，请求交给用户，答复回到 inbox，新 run 接着原来的 session。你还能说明凭证为什么走环境外的 credential proxy，auto mode 怎样拦住危险动作、却不能代替人做最重要的决定，以及等待期间 worker 为什么不会被堵住。

这里的风险最高

原文把 permissions 写成 always-on agent 风险最高的地方。一次 run 握着用户的访问权，而且本来就是在无人值守时运行。每一次工具调用，都要决定：自己继续、把它拦住，还是等待批准。 原文 · Permissions

permissions 所用的组件，和其他 Agent 是同一套。原文着重写了三件：credential store、auto mode，以及 deferred tool calls。 原文 · Permissions

凭证走环境外的 credential proxy

always-on agent 常常需要敏感的用户凭证，例如密码或访问令牌，才能把事情做完。原文推荐的做法，是把一个 proxy 放在 Agent 环境外面，给外发请求补上真实凭证。Agent 发出的请求本身不带凭证，由这个 proxy 在转发前注入。 原文 · Permissions

本课沿用术语表里的说法，把这种模式叫做 credential proxy。原文这一节的标题是 credential store，两种叫法指的是同一套「钥匙不进 Agent 环境」的安排。

auto mode：能拦住危险动作，不能代替最重要的决定

always-on agent 应当能够在不必每次都等人点头的情况下工作。原文用 Claude Code 里的 auto mode 作为一个已经处理过的例子。auto mode 使用 classifier 审查较高风险的动作，并挡住那些被判定为危险的，好让模型改走更安全的路。 原文 · Permissions

即便如此，最重要的决定仍然需要人来看。不要把 auto mode 说成可以代替人做那些决定。 原文 · Permissions

deferred tool call 是一次完整往返

在 Claude Code 里，一个 hook 可以先推迟一次工具调用，等待用户补充说明。同一模式也适用于 always-on agent：在采取某些行动之前，它可能需要澄清或批准。 原文 · Permissions

  1. 这次 run 结束，session 保存在调用做到一半的地方调用被推迟时，并不是让当前这次 run 一直挂着空等。 原文 · Permissions
  2. 请求交给用户原文举的例子是一张可交互的卡片，例如用 MCP Apps 来做。这是原文里的示例，不是本课要求你实现的产品形态。 原文 · Permissions
  3. 答复作为事件回到 inbox用户的回答不会直接灌进一个还在空等的 run，而是先回到 event inbox。 原文 · Permissions
  4. 新的 run 接着原来的 session，并带上用户的输入因为这是接着先前工作的答复，它会续上那份已经保存的 session。 原文 · Permissions 第 2 课里「用户答复续上已有 session」的规则，在这里再次用上。

等待期间，worker 仍可拾起别的事件，所以 Agent 不会被堵住。 原文 · Permissions

合上原文，60 秒这样讲

「permissions 是 always-on 风险最高的地方：一次 run 握着用户的访问权，而且无人值守。每次工具调用要决定自己继续、拦住，还是等人批准。凭证走环境外的 credential proxy，Agent 发出的请求本身不带钥匙。auto mode 用 classifier 审查较高风险的动作并挡住危险的，但最重要的决定仍要人看。需要澄清或批准时，用 deferred tool call：结束这次 run 并保存 session，请求交给用户，答复作为事件回到 inbox，新的 run 接着原来的 session。等待期间 worker 仍可处理别的事件。」
