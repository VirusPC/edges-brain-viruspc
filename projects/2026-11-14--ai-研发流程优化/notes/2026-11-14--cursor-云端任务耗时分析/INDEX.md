# Cursor 云端任务耗时分析

2026-11-14（Asia/Shanghai）对一次 Cursor 云端任务做的墙钟拆分。Cursor UI 上的环境初始化四步合计约 0.9 秒。从第一条 Langfuse 观测起，时间主要花在模型推理：前 5 分 54.8 秒在读 skill、记忆和代码，中间夹着十几秒到约四十秒的模型间隙；依赖安装、测试和类型检查都很短。

这是一条任务、一个 session 的观测，不是 Cursor 云端任务的总体分布。

## 观测盲区

有四段时间，这次数据拆不开。

- UI 上的启动四步、排队、拉 VM 和环境快照都不进 Langfuse。云端不触发 sessionStart / sessionEnd hook。
- 发起（约 19:49 之后）到第一条观测（19:51:07.183）之间约一分多钟没有分项。要看这段，需要 Cursor 自己的时间线。
- 插件把主 turn 整轮对话记成一条 LLM generation，时长就是这 847.531 秒。记录里没有 modelId，没有 TTFT，看不到单次模型调用。
- 两条 turn 之间的 44.179 秒没有观测。素材只标明第二条 turn 是在汇报 PR 的 CI，没有写这 44.179 秒里发生了什么。

## 结论

这次 UI 上的环境初始化合计约 0.9 秒，不到 1 秒，不是这趟任务的瓶颈。

从第一条观测起，时间主要花在模型推理。前约 6 分钟（计到 19:57:01.987 为 5 分 54.8 秒）在读 skill、记忆和代码，期间有大量十几秒到约四十秒的模型间隙。列出的 `pnpm install --frozen-lockfile` 是 3.416 秒，两次测试是 12.383 秒和 6.308 秒，`pnpm exec tsc --noEmit` 是 2.834 秒；其余测试、git 和 push 每次 0.6–2.0 秒。

启动前那约一分多钟仍然没有分项。这个结论不覆盖排队或拉 VM，只覆盖 UI 已显示的四步，以及第一条观测之后的墙钟。

## 待验证的改进假设

下面几条还没有对照数据，不作为已经生效的改进。

1. 任务说明里直接点名要改的文件、入口和要跑的测试，用来减少 Agent 自行摸索。要验证的话，用同类任务对比第一条观测到第一次 Shell 的墙钟，并核对改动仍落在被点名的入口上。
2. 在仓库 AGENTS 里补更精准的入口索引。这一条要和上一条分开测：只改索引、不改任务说明，再看大范围读仓库的时间是否下降。
3. 补齐观测。记下任务发起时刻，并记录单次模型调用的 modelId 和 TTFT。下一次同类任务若能拆出启动前等待和每次模型调用耗时，这条就算做到。
4. 用同类任务做前后对比。第二份观测写入同一 Project 之前，无法判断前三条有没有用。
