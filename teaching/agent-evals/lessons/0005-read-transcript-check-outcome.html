这一课你要带走什么

会按「先证据、后归因」处理一次失败 trial：核对 outcome → 阅读 transcript 与 grader 给出的 score（一次评分结果）→ 才判断责任落在 Agent、grader，还是 task / 环境。

关系链（半句版）

task（一条用例）跑多次 trial（一次尝试）。每次留下 transcript 与 outcome。grader（判分逻辑）按规则检查这些证据，得到 score；规则可以是代码断言，也可以是带 rubric（事先写好的评分细则）的模型裁判——不是所有 grader 都用 rubric，也不是只看 transcript。metric（你要报告的测量量）可以汇总多次 score（如通过率），也可以直接测耗时、token 等。

从小规模真实任务开始

原文建议早期用大约 20–50 道简单任务起步：改动效应大，小集合往往就够看见信号。这是实践建议，不是「统计上已充分」的样本量证明，也不是只能收失败案例。

  • 优先：真实失败、支持工单、缺陷跟踪里的问题。
  • 也来：你发版前本来就在手工检查的行为、用户常见路径。
  • 题面要无歧义；grader 检查的内容应能从题面读出。有参考解可证明题可解、grader 配得对。

假设示例：退款（标清：教学虚构）

Task：给已认证用户退款 ≤100

  1. Trial A：transcript 里 agent 说「已退款」；查库 refunds.status 仍是 pending → outcome 未达成。先别信自述。
  2. 继续读 transcript：从未调用 process_refund → 更像 Agent 失败（漏动作）。
  3. Trial B（假设）：库里已 processed，路径合法但与出题人预想的工具顺序不同；只允许固定顺序的代码 grader 判挂 → 更像 grader 过脆误杀。
  4. Trial C（假设）：多 trial 都因沙箱内存耗尽在同一步崩；彼此不独立 → 更像 环境/题面问题，不宜当成能力差。

原文亦提醒：失败应显得公平；分数不涨时，要确信是 agent，而不是 eval（含题面歧义、刚性评分、harness 约束）。例如 CORE-Bench 曾因评分过脆等从约 42% 修到约 95%——说明先修 eval 再骂模型。

诊断口诀

  • ① 核 outcome（库、测试、文件）——自述不能代替状态。
  • ② 读 transcript：做了什么、漏了什么、是否被合法创新。
  • ③ 对照 grader：规则是否过脆、题面是否歧义、环境是否串扰。
  • ④ 证据不足 → 标「待查」，不要硬判。
