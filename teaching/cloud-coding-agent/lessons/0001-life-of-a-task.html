任务的一生

跟着一个任务，从“提交”走到“PR”，再到 Sandbox 被收走。

第 1 课 · 约 10 分钟 · 研究对象：vercel-labs/coding-agent-template

学完这一课，你能做到

不看笔记，用 60 秒讲清一个云端编程 Agent 产品里，一个任务从提交到 PR 的九个步骤，并且能说出其中最关键的两三个文件在哪里。这是面试里讲“云端编程 Agent 怎么搭”的骨架，后面几课都往这副骨架上加肉。

先看全貌

这个项目是 Vercel 官方实验室做的一个模板。用户在网页上选一个 GitHub 仓库，写一句需求，再选一个 Agent（Claude Code、Codex CLI、Cursor CLI、Gemini CLI、GitHub Copilot CLI 或 opencode）。平台会开一台临时的 Linux 虚拟机，把代码拉进去，让这个 Agent 在里面改代码，最后把改动推送到一个新分支。README.md L1–3

整个流程只涉及六个部件，见图 1。

读图时只需要抓住一点：真正干活的地方是 Sandbox，指挥它的是 Next.js 应用，而两边沟通进度靠的是数据库。 Sandbox 是 Vercel 提供的隔离 Linux 虚拟机，每台都有自己独立的系统内核，所以就算 Agent 在里面乱跑命令，也碰不到别人的机器。Vercel Sandbox 官方说明

九步走完一个任务

  1. 提交：写一行记录，马上回话 Next.js 浏览器调用 POST /api/tasks。服务器先检查用户有没有登录、今天的次数有没有用完，然后把任务写进 tasks 表，状态设成 pending，接着立刻把结果回给浏览器。用户这时就能看到任务页面了，哪怕后面的活一件还没干。 app/api/tasks/route.ts L48–91 app/api/tasks/route.ts L245
  2. 回完话再干活：after() Next.js Next.js 的 after() 允许“先回话，再接着干活”。这里放了三件后台的活：用 AI 起一个分支名、用 AI 起一个标题、真正执行任务的 processTask。代码注释说得很直白：不包一层 after()，Vercel 的服务器函数一回完话就会被停掉。 起分支名 L93–155 processTask L220–243
  3. 建 Sandbox Vercel Sandbox Sandbox.create() 开一台新虚拟机，参数是：团队和项目的编号、一个 Vercel 令牌、存活时长（等于用户选的“最长时长”）、运行环境 node22、4 个 CPU 核。建好后先登记一下，方便用户中途叫停。 lib/sandbox/creation.ts L81–103 调用处 route.ts L447–477
  4. 克隆代码、建分支 Sandbox 里 平台把用户自己的 GitHub 令牌塞进仓库地址，然后在虚拟机里执行 git clone --depth 1，只拉最新一版，放到 /vercel/sandbox/project。用户勾选的话，还会装依赖、启动开发服务器。最后配置提交人姓名，并切到第 2 步起好的分支上。 令牌进地址 config.ts L69–86 clone L120–127 建分支 L840–978
  5. 运行 Agent CLI Sandbox 里 按用户选的 Agent，分发到 lib/sandbox/agents/ 下六个文件中的一个。每个文件都做同样三件事：没装就装（官方安装脚本或 npm install -g）、写配置（告诉 CLI 模型请求发到哪、用哪个模型）、用“不要问我”的参数运行。比如 Claude Code 带 --dangerously-skip-permissions，Codex 用 codex exec --dangerously-bypass-approvals-and-sandbox。敢这样放手，正是因为它关在 Sandbox 里。 分发 index.ts L78–148 lib/sandbox/agents/claude.ts L278 lib/sandbox/agents/codex.ts L282
  6. 日志回到网页 数据库 这里没有用长连接推送。每条日志都通过 TaskLogger 追加进 tasks.logs 字段；Claude 的输出是一行一行的 JSON，平台边读边把文字写进 task_messages 表。网页那边每 5 秒请求一次任务详情，看到什么就显示什么。 task-logger.ts L16–55 解析输出 L310–405 每 5 秒 use-task.ts L73–83
  7. 提交并推送 Sandbox → GitHub Agent 结束后，平台用 git status --porcelain 看有没有改动。有的话就 add、commit、push 到任务分支。提交说明也是 AI 写的：它通过 AI Gateway 调一个小模型 openai/gpt-5-nano。 git.ts L5–73 route.ts L636–666 commit-message-generator.ts L42–46
  8. 开 PR：要用户点一下 Next.js → GitHub 主流程不会自动开 PR。用户在界面上点“创建 PR”，前端调用 POST /api/tasks/[taskId]/pr。后端用用户自己的 GitHub 令牌，通过 Octokit（GitHub 官方的 JavaScript 库）调用 pulls.create，再把 PR 地址和编号写回 tasks 表。 components/create-pr-dialog.tsx L64 pr/route.ts L60–83 client.ts L116–124
  9. 收走 Sandbox Vercel Sandbox 如果 Keep Alive 关着，平台会调用 shutdownSandbox，但它其实只是结束掉 node、python 这些进程，注释写着“当前 SDK 没有关机方法”，虚拟机本身要等时间到了才会停。如果 Keep Alive 开着，虚拟机会留下来，用户追问时平台用 Sandbox.get() 按编号重新连上它。 git.ts L75–100 route.ts L668–683 continue/route.ts L169–189
一个值得在面试里提的细节

README 说 Keep Alive 关闭时，Sandbox 会“立刻关掉”（README.md L74–84）。但代码里，只有用户手动点“停止 Sandbox”时才真的调用 sandbox.stop()（stop-sandbox/route.ts L36–44）。而 Vercel 现在的文档写明 SDK 提供 stop()（Sandbox Concepts）。“文档说的”和“代码做的”不一致，这种地方最能说明你真的读过源码。

两条设计思路

一、数据库就是传话筒

任务的状态、进度、日志全都存在 tasks 表的一行里（schema.ts L76–114），后台流程往里写，网页定时来读。好处是简单：不需要额外的消息服务，部署在 Vercel 这种“用完就停”的服务器上也不怕。代价是每写一条日志，都要先把整串日志读出来、加一条、再整串写回去（lib/utils/task-logger.ts L37–48）。日志一多就慢，两处同时写还可能互相覆盖。

二、不自己造 Agent，只管“环境 + 密钥 + git”

平台本身不写“想一步、做一步”的 Agent 逻辑，而是把现成的 Agent CLI 装进 Sandbox 里跑。平台负责的只有四件事：准备环境、发放密钥、管理 git、记录过程。所以加一个新 Agent，基本就是多写一个 lib/sandbox/agents/xxx.ts。对照一下：OpenAI 的 Codex Cloud 也是“开容器、拉代码、跑 Agent、看改动、再开 PR”这几步（Codex Cloud 文档），而 LangChain 的 Open SWE 则是自己用 LangGraph 写 Agent 的规划和检查（Open SWE 介绍）。

面试时 60 秒这样讲

“我读过 Vercel 的 coding-agent-template。它的结构很清楚：用户提交任务时，Next.js 接口先把任务写进 Postgres 的 tasks 表，马上回话，然后用 after() 在后台跑真正的流程。后台流程先用 Vercel Sandbox 开一台隔离的 Linux 虚拟机，把用户令牌放进地址里浅克隆仓库，切到 AI 起好名字的分支。接着安装用户选的 Agent CLI，比如 Claude Code 或 Codex，把它的模型请求指向 AI Gateway，用免确认模式运行。运行过程中，日志一条条追加进数据库，前端每 5 秒拉一次。跑完后平台自己 commit、push，用户再点一下，后端用 Octokit 开 PR。最后按 Keep Alive 决定要不要留着虚拟机给追问。它的核心取舍是：不自己造 Agent，只做环境、密钥和 git 的编排；用数据库当消息通道，换来简单，代价是实时性和写入效率。”
