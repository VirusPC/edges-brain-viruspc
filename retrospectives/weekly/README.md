# 周复盘

命名：`retrospectives/weekly/<周一日期>--周复盘/INDEX.md`（周一到周日，日期取该周周一；例 `retrospectives/weekly/2026-10-05--周复盘/INDEX.md`）。同一周一只保留一篇。

`INDEX.md` 的一级标题是 `# <YYYY-MM-DD> 周复盘`。下面各节都是二级标题，顺序固定。

周复盘由 [周复盘 routine](../../.edges/routines/weekly-retrospective/INDEX.md) 产出，经 PR 写入本目录。入口是 Compose 工作区根 `VirusPC/edges-workspace-viruspc`，正文落在本仓。例程运行时只看 GitHub；对话层由主聊天逐个助手补进后再合成。正文 `INDEX.md` 写定后不改，后续评论记同目录 `COMMENTS.md`。

本仓公开。不写个人身份细节、未公开 IP、鉴权链接、凭据、私人生活细节。原始对话记录不进本目录。细则见根 [README](../../README.md) 的「隐私与脱敏」。

## 范围

一两行：时间窗，以及看了哪些来源（仓库、各助手对话）。

## 本该怎样

本周事先的目标，加上上期周复盘「下次做什么」里的行动。没有就写明没有，不事后画靶。

## 实际怎样

可核对的事实，带链接。上期行动逐条标：做成、没做成，或卡住（写原因）。

在「实际怎样」里，必须单独盘点本周沉淀的 memory、skill、task、routine、note、project（2026-11-16 用户要求）。不要只把它们埋在发版或开卡数量下面。每一类写清：本周实际落仓了什么（附 PR、路径，有对话依据就附原话），以及只开了卡、尚未做成的是什么。没有的类型就写没有，不要凑条。
不能只盘已落仓的条目，还要根据会话、代码和能读到的 trace 挖出该沉淀却未写成模块的新内容，放到「建议补充内容清单」。

## 为什么

差距的原因，用「可能因为…」口吻。至少一条做得好、该保持的。

## 下次做什么

至多 3 条。每条写清怎么算完成。

## 展望

本周会话和仓库里已经冒出、但还没收成可执行路线的下一步方向。不要把上期未完成项再抄一遍，也不要把已开卡写成已做成。每条都要有依据，并写清它与「下次做什么」的区别。

## 建议补充内容清单

该进 Harness 但没进的 Memory / Skill / Note / Task / Routine / Project / `AGENTS.md` 硬约束候选。来源不只是已落仓条目的缺口，还必须根据本周会话、代码和能读到的 trace 新挖「该沉淀却还没写成模块」的内容。每条写清楚：这条是什么、建议放到哪里、为什么值得补、不补会付出什么代价、处理结果（已写入路径、待确认、不做原因，或留待触发条件）。没有就写明没有。读不到 trace 时，在「范围」写明，不要猜。
