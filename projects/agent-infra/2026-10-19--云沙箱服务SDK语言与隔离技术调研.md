# 云沙箱服务 SDK 语言矩阵与隔离技术调研

> 一句话摘要：为云端 coding Agent 选型沙箱时，先看 **TS / Python / Go / Java** 是否有官方 SDK，再看隔离层（Firecracker / gVisor / Hyper-V / 容器）和是否可自托管；国内厂商常做 E2B 协议兼容。

资料核对时间：2026-10-19（Asia/Shanghai）。下文只写公开文档或官方仓库能核到的内容；推断标「推断」，核不到标「未核实」。厂商常改 SDK 与产品名，引用前请回原文复核。

相关笔记：[云沙箱 Agent 开源产品的 Agent 内核](2026-10-19--云沙箱Agent开源产品的Agent内核.md)（偏产品内核路线）；本篇偏 **Sandbox 供应商、SDK 语言、隔离技术、大厂 Agent 产品公开用法**。

## 图例

- **官方**：Sandbox 厂商文档或官方仓库维护的 SDK。
- **社区**：第三方兼容实现（例如阿里云为自家 Agent Sandbox 维护的 E2B 兼容 Go / Java SDK）。
- **无**：公开资料未见该语言的专用客户端 SDK（通常仍可用 REST / HTTP API）。
- 包名尽量写可安装坐标（npm / PyPI / Go module / Maven）。

## 中国侧观察：E2B 兼容趋势

阿里云 Agent Sandbox / 函数计算云沙箱、腾讯云 Agent Runtime / AGSX、百炼 Code Interpreter 等，公开文档大量采用 **E2B 数据面兼容**（改 `E2B_API_URL` / `E2B_DOMAIN` 等，继续用上游 Py / TS SDK）。同时存在独立开源栈：OpenSandbox、AIO Sandbox、SandboxFusion。面试可概括为：协议层跟 E2B，隔离层跟 Firecracker 或容器，SDK 矩阵看是否补齐 Go / Java。

## 面试向 takeaways

1. **要官方 Go + Java 客户端**：优先 Daytona、阿里 OpenSandbox；其次腾讯有官方 Go，阿里 Agent Sandbox 有官方维护的 E2B 兼容 Go / Java（不是上游 E2B）。
2. **只要官方 Go（无 Java）较常见**：Modal、Fly Sprites、Blaxel、AIO Sandbox。
3. **默认仍是 TS + Python**：E2B、Vercel、Runloop、Morph、CodeSandbox、Cloudflare（仅 TS）。大厂云多为 Py / TS 高阶 SDK，再加通用云 SDK 或 REST。
4. **大厂自建倾向 microVM / 硬件隔离**：Cursor → Firecracker；Claude / Codex → 托管 VM；Azure → Hyper-V；Modal → gVisor（另有 VM）；E2B / Vercel / SPACE → Firecracker。产品公司常采购 E2B / Modal（如 Manus、Lovable）或自研（Perplexity SPACE、Cursor）。
5. **选型顺序建议**：先定隔离强度与冷启动，再定 SDK 语言是否覆盖控制面语言，最后看是否要自托管 / E2B 兼容迁移路径。

## 明确「未核实」清单

- Devin 云端 Sandbox 的具体供应商。
- Kimi、豆包（Doubao）、扣子（Coze）云端执行环境的底层供应商。
- Northflank、Blaxel、CodeSandbox 精确使用的 hypervisor。
- AWS AgentCore 官方文档是否点名 Firecracker（文档写 microVM；第三方博客称 Firecracker）。
- Google Vertex Agent Engine Code Execution 在 Go / Java 客户端上是否已完整暴露 sandbox API。
- Daytona 主仓库曾被报道归档；当前托管产品与 SDK 文档仍在更新——以当日官方站点为准，历史 star / 归档状态可能变化。
