面向人的交互

双层架构保证了跨信道连续，但交互还要同时做到连续与高效：用异步 ReAct Loop 解开阻塞，再用匹配信道的输出避免过载。

第 5 课 · 约 10 分钟 · 主来源：DeepSeek Harness 团队 · Super-agent 设计探索（第 4 节）

学完这一课，你能做到

能讲清：第 2 课的双层架构已经在上下文上保证跨信道连续，但交互还要同时做到连续与高效；经典同步 run() 怎样把前台对话堵住；异步的 start() 和 stop() 怎样把前台响应和后台执行拆开；以及 IM 与 GitHub、邮件、文档为什么不能用同一套输出习惯。

连续和高效，还要落在交互上

第 2 节的双层架构从上下文层面保证了跨信道的连续，但要在实际的人机交互体验中同时做到连续与高效，还需要在交互方式与交互渠道上解决两个问题：一是如何通过异步 ReAct Loop 消除后台耗时操作对前台对话的阻塞，使会话无需等待上一个命令或任务完成即可随时接受新指令；二是当交互发生在用户熟悉的不同工作信道时，如何让系统的输出方式匹配对应信道的带宽与人的使用习惯。 原文 · 第 4 节

从半双工到全双工

在经典的 ReAct Loop 中，模型发起一次同步的 run() 工具调用后，循环会阻塞，直到工具执行完毕并返回最终结果，在此期间会话无法响应任何新的用户输入。要消除这一阻塞，需要把对话从一问一答的半双工模式转变为全双工模式。 原文 · 第 4.1 节

为此，原文把耗时的命令与子任务工具调用改为异步的 start() 和 stop()，构成异步 ReAct Loop。模型调用 start() 后立即收到「已启动」的返回，循环不再等待该工具；在后台工具执行完成后，系统再将最终结果作为一条新的事件消息投递进会话；同时，模型也可以根据上下文调用 stop()，主动终止执行时间过长的后台命令。

由此，前台对话响应与后台任务执行得以解耦，Agent 在后台运行耗时任务的同时也能响应人类输入。新输入在当前推理步结束后即被处理，不必等待后台工具完成。

原文补充了一句产品事实：这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。课里只如实记下这句话，不把它展开成产品配置说明。

输出要匹配信道的带宽和习惯

不同工作信道具有不同的信息密度与交互习惯，系统的输出需要与之匹配。如果把面向单人终端的交互方式直接搬入群聊，把冗长的推理过程与密集的工具调用原样输出，在多人协作中极易造成信息过载。 原文 · 第 4.2 节

双层架构已经解决了其中一部分问题：具体任务中冗长的推理过程和密集的工具调用都被隔离在 Worker Session 内部，不会直接输出到外部信道，而由 Router 层统一负责对外交互。在此基础上，系统还需要接入用户日常使用的各类工作环境，并通过提示词针对不同信道定制交互规范：

  • IM 等即时通讯信道：侧重低打扰的轻量沟通，像人类同事一样只在需要决策或验收时发送通知，只问直接问题、给简短结论。原文验证过的一条简单有效的硬性规定，是单次回复不超过 100 词。
  • GitHub、邮件与文档等异步信道：侧重结构化、高信息密度的异步交付，例如在创建或更新 Pull Request 时按项目规范撰写完整的问题背景、改动说明与验证结果，或在个人助手场景下直接起草结构化的邮件与文档摘要。
合上原文，60 秒这样讲

「双层架构已经让用户侧始终面对同一个 Super-agent，但交互还要同时做到连续和高效。经典 ReAct Loop 里，同步的 run() 会把循环堵住，工具没返回前会话无法响应新输入。原文把耗时调用改成异步的 start() 和 stop()：start() 立即返回已启动，完成后结果作为新事件进入会话，必要时也可以 stop() 掉拖得太久的命令。这样前台对话和后台执行就拆开了，新输入在当前推理步结束后就能处理。输出还要匹配信道：IM 里低打扰、短结论，原文验证过单次回复不超过 100 词；GitHub、邮件和文档里则要结构化、高密度地交付。Worker 的长推理本来就不会直接打到外部信道上。」
