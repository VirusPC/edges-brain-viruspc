框架只是加速器：异常时查哪里？

选 Harbor / Langfuse / Inspect 等 evaluation harness（跑评测的端到端基础设施）能省工程量，但原文写明：框架再好，也只和你放进去的 task 与 grader 一样好。

这一课你要带走什么

看到「分数怪了」时，能判断更像框架/基础设施、任务设计还是grader问题，并说出下一步查什么——而不是先换框架碰运气。

原文怎么说框架

附录列举 Harbor、Braintrust、LangSmith、Langfuse、Arize 等，方便离线评测与/或可观测。关键原意是：框架可加速与标准化，但它们只和你跑的评测任务一样好；宜尽快选一个贴合工作流的，然后把精力投在高质量用例与 grader 上。（Anthropic 2026-01-09）

文中没有点名 Anthropic 内部固定使用哪一个开源框架；评价「一个 agent」时评的是 agent harness + 模型，与选用哪个 eval 框架是两件事。

例：Harbor Rewardkit（已核验文档，非「银弹」）

官方 Judge criteria 支持 TOML 声明式 criterion（binary / likert / numeric / rubric levels）、权重与聚合、多次采样取中位、guard 防提示注入等——这是便利层。它不替你决定该评什么业务能力，也不自动保证与人类专家对齐；对齐仍要靠抽样人工与读 transcript。

三种异常 → 先查哪一层（假设场景）

  1. 分数很高，线上用户狂投诉 → 并列查：任务是否偏离真实用法、覆盖是否偏科；以及 grader 是否过松、是否与人对齐。补真实失败/工单题，抽样人工复核；自动评测之外再加生产监控与用户反馈（多层防护，像瑞士奶酪模型那样叠层拦截）。
  2. 只换框架，同一套题分数大变（假设） → 先对齐隔离环境、超时、默认 grader 聚合与日志；再比对同一 trial 的 transcript / outcome，区分基础设施噪声与真正能力差。
  3. 套件几乎全过、分数不再动 → 警惕能力评测 饱和：加难题，或把已经稳定通过的题毕业迁入回归套件；并读 transcript，确认不是 grader 过松。

无论哪一层，都要读 transcript、核 outcome；失败应显得公平。分数不涨时，先怀疑评测本身（题面歧义、刚性判分、运行环境约束），再骂模型。

六课闭环（间隔检索也可用）

主链条：先定 task（题目）→ 同一题跑多次 trial（尝试）→ 每次留下 transcript（过程记录）与 outcome（环境终态）→ 用 grader 判分：可以是 代码断言、带评分细则的模型裁判，也可以是 人工评分（human grader）；可评过程与/或终态，得到 score（分数）。

指标（metric）：可以汇总这些 score（例如通过率），也可以不经过 score、直接统计耗时或 token 等。

两类套件：能力评测（capability）起步通过率宜低，用来爬山改进；回归评测（regression）通过率宜接近满分，用来守住已会的行为。能力题稳定通过后可毕业迁入回归。多 trial 时用 pass@k（至少一次成功）与 pass^k（次次都成功）。起步约 20–50 道简单任务是建议，不是充分样本量。

自动评测只是一层；原文还强调生产监控、A/B 测试、用户反馈与系统化人工复核组合，多层叠防。
