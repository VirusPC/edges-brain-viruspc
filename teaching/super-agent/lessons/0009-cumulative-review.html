先凭记忆把骨架画出来

先不要往回翻目录。用一张纸写出：四个基础特征各自的原文含义，五个模块的名字和职责指向，然后补上一条事件从 Trigger 到用户看到回复的路径。写完再对照答案。

请写出：四个特征、五个模块，以及一条事件的大致路径（从进入系统到用户收到回复）。

四个特征：连续——在熟悉界面里感觉始终只有一个 Agent，不必去想信息在哪个 Session 里；高效——响应快，并能并行、高质量完成多个复杂任务，不必等上一件做完再接受新指令；主动——持续观察环境事件并推进值得处理的事项，不需要时保持安静；持久——始终在线、接入真实工作环境，异常时能自动恢复。

五个模块：双层架构兼顾连续与高效；事件驱动实现主动；面向人的交互让连续和高效落在交互体验上；计算、状态与环境的分离，与 Watchdog 一起支撑跨设备的持久在线与异常自愈。

一条路径：环境事件作为 Trigger 进入，先经程序层再经语义层过滤；尚未订阅的新事件由 Router 分派并创建 Worker、建立 Thread 订阅，已订阅的后续事件直通 Worker。Worker 在隔离上下文中执行，必要时用 Inline & Spill 和链式召回取上下文，也可以在后台投机执行。Worker 不直接对用户说话，而向 Router 汇报，由 Router 按信道习惯回复。计算在云端无状态运行，状态在数据库，执行环境经端侧 daemon 按需接入；Watchdog 在主系统外定期检查基础设施和任务进展。

交错练习：三条情景

下面每条都先自己答，再对照。它们穿插了前面几课，不是按章节顺序出现的。

情景 A　先在 IM 里说用方案 A，随后在 GitHub Pull Request 评论里改成方案 B

这主要在考验四个特征里的哪一个？用户需不需要自己去想「方案 A 记在哪个 Session 里」？

这是原文用来说明「连续」的例子：用户在熟悉的不同工作界面里交互，感觉始终只有一个 Agent，不必去想某条信息在哪个 Session 的上下文里。它能理解并调整执行方向。实现上，这依赖 Router 层维持跨信道的全局连续，而不是让用户手动切换 Session。这个例子在原文里属于内部实例，用来说明形态，不是产品功能介绍。

情景 B　某个 GitHub Pull Request 已经有一个 Worker 在跟，又来了一条新的评审评论

这条新评论会先到 Router 再转发，还是直通 Worker？Router 还能不能看到它？

同一 PR 下的连续事件构成一条 Thread。Worker 已经订阅之后，后续事件由程序直通该 Worker，无需 Router 再次调用工具转发。Router 仍可观测全部事件以掌握全局状态，但只负责分派尚未被订阅的新事件。若这条评论超出了当前任务范围，Worker 也可以取消订阅或交回 Router 重新分派。输出侧，Worker 仍把关键结论汇报给 Router，由 Router 统一回复。

情景 C　用户的某台个人电脑刚才离线，现在重新上线了，上面还有未提交的修改

按第 5 节的设计，云端的 Agent Loop 停没停？要在这台机器上执行的任务，怎样才能继续？

计算和会话状态已经在云端分开存放，所以一台个人设备离线，并不等于 Agent Loop 停止。执行环境留在原地，通过不保存会话状态的轻量 daemon 按需接入。原文写：它甚至能够支持间歇在线的设备，例如在用户的某台个人设备重新上线后，再由云端 Agent 自动触发并完成需要在该设备上执行的任务。未提交的修改正是环境留在原地、而不是强行同步到云端沙箱的原因之一。安全与信任前提仍是第 8.4 节的开放问题，不要把「设备重新上线就能继续」讲成安全问题已经解决。
