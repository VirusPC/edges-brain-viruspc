## 过程

### 22:42 对照原文核对笔记

文章把记忆分成四层：会话转录（session transcript）→ memory notes → wiki → 注入上下文。核心机制是做梦：在会话之间离线整理，回头核对、纠错、建表示，再把少量高价值内容提升到每轮预加载的顶层。

对话里核对过的评测数字如下：

- 搜索单独是 53%。
- wiki 加搜索在只梦了 2 个 session（103 页、766 条链接）时就已经是 54%，几乎没增益。
- 真正拉开的是 wiki 长到 128 个 session（222 页、12,893 条链接）之后，组合方案到 61%，并大约省 2 万 token/题。
- wiki 单独则是从 13% 爬到 48%，一直低于搜索。

因此，54%→61% 不能读成「一加上 wiki 就升上去」。这也对上对话里写下的用法：跨文档整合用 wiki，答案就在单文档里时直接搜更划算；wiki 过大、抽象失败时甚至会比原文还长。

开放问题在对话里也站得住：即时写记忆会抢当前任务的注意力，做梦又不能立刻用上；记忆会写错、会过时，需要拿原始 transcript 回放校对。

### 22:43 映射到 Edges，并给出可先做的几步

对话把上述机制映射到 Edges：

- `AGENTS.md` 这类强约束应当保持短。文章里 Claude Code 的 `MEMORY.md` 只注入前 200 行或 25KB。

## 所学

- 记忆系统的关键往往不是「再多记一点」，而是会话之间的离线整理：核对、纠错、建表示，再把少量内容提到预加载层。
- wiki 的增益和规模有关。只梦了 2 个 session 时，wiki 加搜索几乎等于搜索单独；长到 128 个 session 之后，组合方案才到 61%，并省 token。wiki 单独一直低于搜索。
- 用法要对题：跨文档整合用 wiki，答案在单文档里时直接搜更划算。wiki 过大或抽象失败时，可能比原文还长。
- 即时写入会抢当前任务注意力；离线做梦又不能立刻用上。记忆会错、会过时，要用原始 transcript 回放校对，并用线上失败案例回写。
- 强约束（如 `AGENTS.md`、`MEMORY.md`）应当短，注入要限长；仓库里搜索和整理层都要有。评估不要只看「有没有记忆」，要把只搜索、只 wiki、两者分开看。

## 行动指南

### 主题行动指南

#### 背景

要把这篇对 agent memory 的拆解用到 Edges 的沉淀和评估里，避免把「加上 wiki」理解成必然涨分，也避免小任务一结束就立刻写记忆。

#### 核心问题

四层记忆和做梦分别解决什么问题，哪些数字说明 wiki 何时有用，以及 Edges 可以先改哪几步。

#### 核心解决方案

1. 按四层来理解，而不是按「多记」。会话转录是原料；memory notes 和 wiki 是整理层；只有少量高价值内容进入每轮预加载。做梦是会话之间的离线整理，用来核对、纠错、建表示和晋升。
2. 解释 54%→61% 时，必须带上规模。搜索单独 53%；wiki 加搜索在 2 个 session（103 页、766 条链接）时是 54%；128 个 session（222 页、12,893 条链接）后组合方案到 61%，约省 2 万 token/题。wiki 单独从 13% 到 48%，一直低于搜索。可选项是把「加上 wiki」直接写成稳定增益：对话已说明这是读偏。
3. 选型按任务：跨文档整合用 wiki；答案就在单文档里时直接搜。wiki 过大或抽象失败时，不要假定它一定更短或更好。
4. 在 Edges 里先做三件事：小任务不要立刻写记忆；给做梦单独的离线节奏，用 transcript 纠错并晋升到 `AGENTS.md`；注入层严格限长（对话援引的上限是 `MEMORY.md` 前 200 行或 25KB）。评估时分开看只搜索、只 wiki、两者。

#### 验收标准

- 能说出四层和做梦的分工，而不是「多记就更好」。
- 能正确解释 54%→61%，并写出搜索单独、小 wiki 组合、大 wiki 组合、wiki 单独这四组数字。
- 能区分 wiki 适用（跨文档整合）和搜索适用（答案在单文档）的情况。
- 映射到 Edges 的先做事项只包含对话里出现过的：小任务不立刻写记忆、离线做梦并限长注入、评估分组；不把未核对的做法写成已采纳规则。
