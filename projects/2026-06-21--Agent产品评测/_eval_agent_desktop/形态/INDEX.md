## 三种形态对比

|维度|CLI|Web|Desktop|
|---|---|---|---|
|**本地文件系统**|原生|无（需上传/云端 repo）|原生|
|**本地 git worktree**|手动，需自己管|不可用|自动隔离，每 session 一份|
|**沙箱/权限边界**|OS 进程级，粗|云端容器，隔离好但离本地远|OS 级（Seatbelt/Landlock/seccomp）+ 可分层|
|**computer use**|不可能|只能操作云端虚拟桌面|可操作本机任意 GUI 应用|
|**并行 session 管理**|tab/tmux 硬扛，无全局视图|天然支持，但重上下文切换|侧边栏 + 状态标签，一屏掌控|
|**artifact 渲染**|纯文本，图片/网页/图表全部出局|全支持|全支持 + 可与本地文件互操作|
|**diff review**|文本 diff，无法逐行评论|完整|完整 + 可直接跳本地编辑器|
|**长任务托管**|关终端即断（除非 nohup/tmux）|最强，关笔记本照跑|需进程常驻，但可与云端接力|
|**延迟**|最低|网络往返|低|
|**可组合性**|最强（管道、脚本、cron、CI）|最弱（封闭）|中等（多数保留 CLI parity）|
|**自动化/被调用**|天然（`claude -p`、`codex exec`）|需 API/webhook|通常仍靠底层 CLI|
|**离线**|除模型调用外可用|完全不可用|除模型调用外可用|
|**心智模型**|一次调用一个进程|提交任务，稍后回来看|常驻控制平面|

## 结合表看，深层原因是什么

**表里最关键的信息不是某一列赢了，而是 CLI 和 Web 的短板落在了完全不同的地方。**

看这张表你会发现，CLI 的失分集中在**上半部分之外**——它的本地能力那几行全是满分，塌方发生在"并行管理、artifact 渲染、diff review"这三行。而 Web 的失分正好相反：编排和渲染全满，塌在"本地文件、worktree、computer use、离线"这几行。

**两者的短板没有交集。** 这就是 Desktop 出现的结构性理由：它不是"比 CLI 好一点"或"比 Web 方便一点"的渐进改良，而是唯一一个能同时覆盖两组能力的形态。在长任务能力跨过阈值之前，这两组能力不需要同时出现——所以 Desktop 也就没有存在的必要。

具体拆成三步：

**第一步，长任务能力让"并行管理"这一行从无关紧要变成致命。** 任务只跑 2 分钟时，CLI 那行"tab 硬扛"根本不构成问题——你压根不会想开 5 个。任务能跑 30 分钟到几小时之后，这一格的空缺才开始致命。同一行的分数没变，权重变了。

**第二步，artifact 从文本扩展到多模态，让"渲染"这一行变成 CLI 的硬出局条款。** 注意这一行的措辞：CLI 不是渲染得差，是物理上做不到——纯文本 I/O 装不下网页、图表、设计稿、浏览器验收结果。而验证一个非文本产物必须"看见"它。**这一行单独就足以判 CLI 死刑**，跟它在本地能力上有多强毫无关系。

**第三步，本地那四行让 Web 无法接盘。** 到这里 GUI 已成定局，问题变成 Web 还是 Desktop。答案在表的最上面四行：本地文件、worktree、沙箱、computer use——Web 全部不可用或严重打折。Codex 的 background computer use 是最极端的例子，它要求 agent 用自己的光标操作本机上那些**根本没有 API** 的应用，这件事在浏览器沙箱里从定义上就不成立。

所以完整的逻辑是：**长任务能力提升 → "并行管理"和"多模态渲染"两行的权重暴涨 → CLI 出局 → 但"本地能力"四行 Web 补不上 → 只剩 Desktop。**

## 表里还藏着两条容易被忽略的信息

**一是 CLI 没有死，它下沉了。** 看"可组合性"和"自动化/被调用"这两行——CLI 在这两项上仍然碾压另外两者，而且大部分桌面端都保留了 CLI parity。这不是兼容性妥协，是分工：CLI 变成了**执行内核与自动化接口**（cron、CI、`claude -p` 管道），Desktop 变成了**人机交互的控制平面**。Desktop 取代的是 CLI 的"人用它"的那一面，不是"程序调它"的那一面。

**二是 Web 也没死，它接走了长任务托管这一行。** 这是表里 Web 唯一的满分项，也确实是 Desktop 的相对弱项（进程要常驻）。所以现在的实际形态是接力：Desktop 做交互与监督，Cloud 做"关掉笔记本也在跑"。Boris Cherny 早上用手机启动 session、本地和 web 之间用 `&`/`--teleport` 来回切，就是这个分工的日常版本。

**最终格局不是三选一，是三层栈**：CLI 是执行与自动化内核，Web 是长任务托管，Desktop 是控制平面。这也解释了为什么各家桌面端都强调"从 CLI/IDE 继承 session 历史与配置"——它们要的不是替代，是收编。

对你做 L3 harness 的实际含义：**这三层的边界应该是设计输入而不是产品选型题。** 真正稳定的抽象在最底层——session、context、tool call、verification 结果——把这层做成三种前端都能消费的形态，上面挂什么壳就成了可替换的表皮。反过来，如果 harness 的核心逻辑被绑进了任何一个壳，你会在下一次形态迁移时重写一遍。
