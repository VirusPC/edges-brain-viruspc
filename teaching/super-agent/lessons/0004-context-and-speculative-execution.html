上下文组织与提前行动

事件经过过滤与路由、进入目标 Session 之后，还要决定往上下文窗口里放多少信息，以及要不要根据环境信号在后台先动起来。这是原文第 3 节的后两个问题。

第 4 课 · 约 10 分钟 · 主来源：DeepSeek Harness 团队 · Super-agent 设计探索（第 3.3–3.4 节）

学完这一课，你能做到

能讲清：为什么浪费上下文窗口就是浪费模型的智能；Inline 和 Spill 分别是什么，以及怎样从最少信息开始、按局部性逐步内联、超出就 Spill；链式召回怎样沿引用图按需展开；投机执行为什么可以先做后取舍，以及「有价值就交付，没有价值就丢弃」这条原则。

上下文窗口要当 Cache 来管

事件经过过滤与路由、进入目标 Session 后，下一个问题是应当向模型的上下文窗口注入多少信息。由于系统输入从有限的人类提示词，转向了环境持续产生的半结构化事件，工具调用与事件注入的结构设计变得更加重要。注入过多会挤占窗口、稀释模型注意力，注入过少又会迫使模型反复调用工具读取，增加执行步数。原文的判断是：浪费上下文窗口，就是浪费模型的智能。 原文 · 第 3.3 节

为此，可以把有限的上下文窗口当作 Cache 来管理。原文借用编译优化与计算机系统中的概念，把上下文注入归纳为两个基本操作：

  • Inline：把近期很可能用到的信息直接内联进当前上下文窗口，以省去额外的工具调用往返。
  • Spill：把超出窗口预算或低频使用的完整信息留在上下文窗口之外，仅在窗口内保留引用或摘要，供模型按需读取。

再结合局部性，就可以用 Inline & Spill 逐步优化事件注入和工具调用。原文给出的顺序是：最初只提供当前对象的 ID 和内容摘要；再把近期很可能用到的信息逐步 Inline，先附上紧密关联对象的 ID，再附带时空相邻的内容，例如内容前 50 字、IM 消息的前后相邻消息与所回复的消息，或代码评论所在评审讨论中的相邻评论；对无法全部 Inline 的长内容设定较小的长度上限，将超出部分 Spill 到窗口之外。一种简单直接的做法，是截断超出部分并保留续读入口，模型需要完整内容时再调用工具读取。

链式召回：按需沿着引用往下走

在大量后续事件直通 Worker、且系统在长期运行中累积了许多历史任务后，Router 层既不能把所有任务的全量历史都放入自己的上下文窗口，又需要在用户跨信道提起某个旧任务时找回上下文。把 Inline & Spill 一致地应用到系统中的各类对象后，就得到一种按需展开的多跳检索机制，即链式召回。 原文 · 第 3.3 节

具体来说，系统为 Trigger、Thread 和 Worker Session 等对象赋予唯一 ID，并在注入时内联紧密关联对象的 ID，使这些对象在底层构成一张引用图。由于每一次调用工具召回的对象本身同样遵循 Inline & Spill，其返回结果中又会内联下一跳关联对象的摘要与 ID，模型便可以从当前事件出发，顺着引用关系逐步按需召回上下文。例如从一条当前消息读取所在 Thread，再从 Thread 内联的 ID 追踪到相关的 Worker Session，进而找到该 Worker 关联的另一个代码评审 Thread。

投机执行：先在后台尝试，有价值再交付

借鉴计算机系统中的投机执行思想，Agent 可以在还不确定结果是否会被采用时，根据环境信号在后台提前尝试，通过消耗额外的后台算力来减少人类的等待与介入成本。结果有价值就交付，没有价值就丢弃。 原文 · 第 3.4 节

在个人助手场景下，当收到一封会议邀约邮件或待办消息时，Agent 可以先在后台核对日程冲突、搜集相关背景资料并备好回复草稿，待用户过目后即可直接确认发出。在研发协作场景下同样如此。原文举了他们在公司 DeepSeek Harness 内部用户群中配置的一条「静默复现并修复」策略：当群里有人反馈问题或讨论改动方案时，Agent 先在后台尝试复现并寻找修复方案，只有在确认问题并找到简单的修复方案后，才会把结果交付给用户，否则全程保持安静。配图说明里还写到：群内还在讨论解决方案时，Super-agent 已在后台提交了修复 Pull Request。这仍是原文内部实例中的例子，不是产品功能介绍。

合上原文，60 秒这样讲

「事件进了目标 Session 之后，还要决定往窗口里放多少信息。放多了会挤占注意力，放少了又会逼模型反复读。原文把上下文窗口当作 Cache：Inline 是把近期很可能用到的信息直接放进窗口，少打一轮工具；Spill 是把超出预算或很少用的完整信息留在窗外，只留引用或摘要。做法是从最少信息开始，先给 ID 和摘要，再按局部性逐步内联关联对象和相邻内容，超出上限就截断并留下续读入口。大量后续事件直通 Worker 之后，Router 既不能装下全部历史，又要在用户跨信道提起旧任务时找回上下文，于是把同一套 Inline & Spill 用到 Trigger、Thread、Worker Session 等对象上，做成沿引用图按需展开的链式召回。此外，还可以投机执行：还不确定结果会不会被采用时，先根据环境信号在后台尝试，有价值就交付，没有就丢弃；不需要介入时保持安静。」
