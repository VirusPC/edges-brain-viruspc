预制环境与隔离

每个任务都从零装一遍，慢在哪里、今天怎么提前做好；以及 Vercel Sandbox 底下到底是不是 Docker。

第 3 课 · 约 10 分钟 · 研究对象：vercel-labs/coding-agent-template · 前置：第 1 课、第 2 课

学完这一课，你能做到

说清“基础镜像 → setup 脚本 → 快照”三层预制环境各放什么、各自什么时候过时；说出密钥为什么只能出现在 setup 阶段；并且在面试官问“Vercel 底下是不是 Docker”时，讲清容器和 microVM 的区别，以及为什么跑 AI 写的代码更适合 microVM。

先看现状：模板每个任务都从零装一遍

第 2 课讲过，模板给每个任务开一台全新的 Sandbox。这一课把“开好之后、Agent 动手之前”这段展开看，它每次都要做下面五件事：

  1. 开一台“空”机器 creation.ts Sandbox.create() 只传了 runtime: 'node22'、4 个 CPU 核、端口和时长，没有镜像，也没有快照。注释写明“不带 source 创建，我们自己克隆”。 lib/sandbox/creation.ts L81–L103
  2. 浅克隆仓库 Sandbox 里 git clone --depth 1 到 /vercel/sandbox/project。 lib/sandbox/creation.ts L111–L127
  3. 装项目依赖 Sandbox 里 有 package.json 就判断用 pnpm、yarn 还是 npm，没有这个包管理器就先全局装一个，再装依赖；有 requirements.txt 就先确保有 pip，再 pip install -r。 lib/sandbox/creation.ts L165–L324
  4. （可选）装浏览器的系统库 Sandbox 里 用户勾选浏览器功能时（默认关），先 sudo dnf 分组装 25 个 Chromium 需要的系统库（nss、nspr、libX* 一串、mesa、gtk3 等），再 npm install -g agent-browser 并下载 Chromium。 lib/sandbox/creation.ts L513–L565
  5. 装 Agent CLI agents/*.ts 六个 Agent 文件都是同一个套路：先 which 一下，没有就装。Claude 和 Cursor 用官方的 curl … | bash，其余四个用 npm install -g。注释说这是“为恢复的 Sandbox 检查”，但新任务的机器总是全新的，所以每次都装。 claude.ts L69–L81 codex.ts L40–L52 cursor.ts L62–L85 gemini.ts L55–L64 copilot.ts L45–L62 opencode.ts L71–L88

为什么不提前做好？因为当时做不到。模板锁定的 @vercel/sandbox 0.0.21（package.json L42），创建参数里只有 runtime（只支持 node22 和 python3.13）、source（只有 git 和 tarball 两种）、端口、时长和 CPU 核数。没有 image，也没有 snapshot。我是解开 npm 包、读 dist/sandbox.d.ts 第 8–57 行确认的（unpkg 上的同一文件）。 “冷启动”的代价全落在这五步上：每个任务、每次追问时新开的机器，都要把它们重来一遍，而且每一步都在消耗第 2 课说的那份最长时长。

两处值得在面试里提的细节

一、dnf 是对的，apt-get 那条后路是坏的。注释写“Fedora 系的 Sandbox”，所以用 dnf。按 Vercel 今天的说明，用已弃用的 runtime 参数创建的 Sandbox 跑的是 Amazon Linux 2023，包管理器确实是 dnf；新的默认镜像才是 Ubuntu、用 apt-get（Vercel 知识库）。但装 pip 失败时的备用方案调用了 apt-get，而且把 '&&' 当成普通参数传给它（lib/sandbox/creation.ts L274–L282）。runCommand 不经过 shell（lib/sandbox/commands.ts L21–L27），系统上也没有 apt-get，看起来这条后路永远不会成功。这是读代码推断，没有实测。

二、反过来，今天的默认镜像会让 dnf 那段失效。如果把模板升级到新 SDK、又不指定镜像，机器会从 Ubuntu 的 vercel/sandbox/universal 启动，那 25 个 dnf 包就装不上了。升级 SDK 不只是改参数名，系统都换了。

今天的 Vercel Sandbox 能怎么提前做好

能力是什么意思出处
自定义镜像在 Dockerfile 里写好系统、系统包、语言工具链，用 vercel vcr build docker . my-repo:latest --push 推到 VCR（Vercel 的镜像仓库），再 Sandbox.create({ image: 'my-repo:latest' })。只能用 linux/amd64 的镜像。不会运行 ENTRYPOINT 和 CMD，进程要创建后用 runCommand() 自己启动；WORKDIR 会被用作命令的起始目录。Images 文档

快照把一台跑着的 Sandbox 的文件系统和已装的软件包存下来，下次 source: { type: 'snapshot', snapshotId } 直接开机，跳过安装。默认最后一次使用后 30 天过期；只能在它所在的区域使用。Snapshots 文档

通用做法：三层预制

把所有同类产品抽象一下，做法都是把“准备环境”拆成三层，越往下变得越慢、越适合提前做；任务阶段只剩真正要干的活。

取舍多做预制的好处代价
冷启动从快照开机，省掉克隆和安装；Vercel 文档说从快照恢复比新开一台还快快照不在缓存里时恢复会慢一些，等待算进创建时间（Snapshots）
新鲜度—快照停在拍下那一刻：lockfile 变了、默认分支往前走了、安全补丁出了，它都不知道。所以要有“过时就重拍”的规则，或者像 Codex 那样每次恢复后跑一个 maintenance 脚本补差
可复现镜像用 tag 或 digest 固定，同一份 Dockerfile 谁来建都一样快照是“跑出来的结果”，里面有当时网络上下载到的版本，很难说清它到底装了什么；所以底层用镜像、上层才用快照
存储成本—快照按 GB·月收费，而且比原 Sandbox 活得久，删了 Sandbox 快照还在计费；可以用 keepLastSnapshots 只留最近几份（保留策略）

两条安全规则。第一，密钥只在 setup 阶段出现，绝不进快照或镜像。快照和镜像存的是整个文件系统，令牌一旦写进 .npmrc 或 .env，以后每台从它开机的机器都带着它。Codex Cloud 的文档写明：secrets 只给 setup 脚本用，Agent 阶段开始前就移除（Codex 文档）；Cursor 也提醒，拍快照时 .env.local 会被一起存下（Cursor 文档）。第二，Agent 阶段把网络收紧。setup 要联网装包，Agent 改代码时通常只需要 git 和模型接口。Vercel Sandbox 的 networkPolicy 默认是 allow-all，可以在 setup 之后用 sandbox.update({ networkPolicy }) 换成白名单或 deny-all（JS SDK Reference）。

Vercel 底下是不是 Docker？不是，是 microVM

这一点有官方原话。Vercel 的 Sandbox 概念页写着：“Unlike Docker containers, each sandbox runs in its own Firecracker microVM with a dedicated kernel.”，后面还有一句“调用 Sandbox.create() 时，Vercel 在它的基础设施上开一台 Firecracker microVM”（Understanding Sandboxes · Sandboxes vs containers）。

容器（Docker）gVisormicroVM（Firecracker）
内核和宿主机共用一个内核在用户态再实现一个“应用内核”，挡在应用和宿主内核之间每台有自己的内核
靠什么隔开内核的 namespaces 和 cgroups（Docker 安全文档）拦截系统调用，自己处理（gVisor 文档）硬件虚拟化（KVM），外加 jailer 做第二道防线（Firecracker 官网）
被攻破意味着一个内核漏洞就可能逃到宿主机要先突破 gVisor，再碰宿主内核还要再逃出虚拟机边界
代价最省：没有第二个内核系统调用变慢，部分程序不兼容每台要多一个内核的内存；官网写 VMM 额外开销 <5 MiB、启动 <125 毫秒

那为什么能用 Dockerfile？因为 Docker 镜像（准确说是 OCI 镜像）本质上只是“一叠文件系统层 + 一份配置”。规范里说，镜像由若干文件系统层组成，解开后拼成最终的文件系统；而 Entrypoint、Cmd 这些属于配置，是给容器运行时看的（OCI Image Spec）。Vercel 只拿走前者，当作 microVM 的根文件系统来开机（文档原话：“boots the sandbox from that image's filesystem”）。机器里没有容器运行时替你执行启动命令，所以 ENTRYPOINT / CMD 不会运行。E2B 也一样：构建模板时先按定义建一个容器，再“提取容器的文件系统”放进 microVM（E2B 文档）。 E2B 自己的安全页写着“Every E2B sandbox runs in its own Firecracker microVM with its own kernel”（e2b.dev/security）；Firecracker 官网的使用者名单里也有 E2B。

为什么 AI 写的代码更适合 microVM？多租户平台上，一台物理机同时跑着很多客户的 Agent，而 Agent 是免确认模式、会执行它自己生成的任何命令，还可能被仓库里的文字提示注入。共用内核时，一个内核漏洞就是所有租户的事；Firecracker 本来就是 AWS 为了让不同客户的 Lambda 函数安全地挤在同一台机器上而做的。今天它启动快、开销小，“每个任务一台虚拟机”在成本上也说得过去，所以 Vercel、E2B 都选了它；不想换虚拟机的平台，会用 gVisor 这种折中方案。

面试时 60 秒这样讲

“coding-agent-template 每个任务都开一台空的 Vercel Sandbox，只指定 runtime node22，然后克隆、装依赖、需要浏览器时再用 dnf 装 25 个 Chromium 系统库、最后装 Agent CLI。全部在任务时间里重来一遍，因为它锁定的 SDK 0.0.21 没有镜像也没有快照参数。今天通用的做法是三层：底层是 Dockerfile 建的基础镜像，放系统包和 CLI，按周重建；中间是按仓库的 setup 脚本，可以联网，私有仓库的密钥只在这里出现；上层是把 setup 结果拍成快照，lockfile 变了就重拍。任务阶段只做真正的活，没有密钥，网络收紧。Vercel 现在支持推到 VCR 的自定义镜像、快照、带 onCreate/onResume 的 getOrCreate，Codex、Cursor、Copilot、E2B 也都是这个模式。另外，Vercel Sandbox 不是 Docker：官方文档写明每台 Sandbox 是一台有独立内核的 Firecracker microVM，Dockerfile 只是用来生成根文件系统，所以 ENTRYPOINT 和 CMD 不会运行。跑 AI 生成的、不可信的代码，多租户下用 microVM 比共用内核的容器安全得多。”

面试官可能的追问（附参考答法）

问：快照什么时候会过时？怎么发现？
答：四种情况。一是依赖变了：lockfile 或包管理器版本变了，快照里的 node_modules 就不对了，最常见的做法是用 lockfile 的哈希当快照的标签，哈希变了就重拍。二是代码往前走了：快照里的仓库停在旧提交，任务开始时要 git fetch 再切分支，差太多就重拍，Codex 用 maintenance 脚本补这一段。三是 setup 本身变了：脚本、环境变量、secrets 改了，Codex 会自动作废缓存。四是基础镜像该打补丁了。另外 Vercel 的快照默认 30 天没用就被删，持久 Sandbox 的快照过期后 getOrCreate 会重建并重跑 onCreate，所以 setup 必须能重复跑（Cursor 文档直接要求 install 脚本幂等）。

问：为什么不能把密钥烤进镜像或快照，用起来多方便？
答：镜像和快照是会被复制、共享、长期保存的文件。Vercel 的快照比 Sandbox 活得久，可以被任意多台新机器拿来开机，镜像还能分享给别的团队甚至设为公开。密钥进去了，就等于发给了所有将来从它开机的 Agent，而 Agent 是免确认模式，可能被提示注入，把文件读出来发出去。轮换也很难：换一次密钥就得重建所有镜像和快照。正确做法是 setup 时从密钥管理处临时注入、用完不落盘；Agent 阶段需要的凭证，用短期令牌或在 Sandbox 外面的代理替换，就像第 1、2 课说的 Open SWE。

问：既然 microVM 更安全，为什么大家还用容器？代价在哪？
答：容器最省：不需要第二个内核，内存开销小，一台机器能塞得更密，生态也最成熟，跑的是自己信得过的代码时完全够用。microVM 每台要多一份内核和预留内存，还要求宿主机的 CPU 支持硬件虚拟化（Firecracker 官网写明只支持带硬件虚拟化的 64 位 Intel、AMD、Arm），平台得自己准备这样的机器，运维比容器复杂。Firecracker 把这些代价压得很低（官网写启动 <125 毫秒、VMM 开销 <5 MiB），所以对“随时开一台给不可信代码用”的场景，安全换来的价值远大于成本。gVisor 是中间路线：不要虚拟化，但系统调用变慢、部分程序不兼容。

问：那 Sandbox 里还能跑 Docker 吗？
答：可以。microVM 有自己的内核，你在里面装 Docker、起容器都行，这些容器共用的是这台 microVM 的内核，而不是宿主机的。Vercel 文档还专门提醒，里面的容器不会继承 Sandbox 的代理证书（Understanding Sandboxes）。
