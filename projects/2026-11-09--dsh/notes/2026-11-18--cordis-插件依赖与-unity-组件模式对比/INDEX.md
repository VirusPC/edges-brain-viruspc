# Cordis 插件依赖与 Unity 组件模式对比

> DeepSeek Harness 底层的 Cordis 用服务名做运行时依赖，而不是让插件互相引用。这次把依赖声明、静默等待、热插拔失败模式，以及和 Unity 组件模式、Pi 小工具集的差别记下来，避免以后把「一切皆插件」理解成编译期那种依赖管理。

## 背景

2026-11-18，peng cheng 在「Coding Agent 专家」里先找 DeepSeek Harness 和 Pi 的架构对比文章，随后抓住 DSH「一切都是插件」的问题：插件之间有依赖时，如何保证被依赖的插件已经在、递归依赖怎么处理，以及复杂应用会引入哪些失败模式。接着把这套设计和游戏引擎、尤其是 Unity 的组件模式作比较，并问换掉 agent loop 时是不是只要事件名不变就行，最后核对 Pi 默认只有四个工具。

## 主题

弄清 Cordis 如何用服务名声明和等待依赖、运行时增删插件时会发生什么，以及它和 Unity 组件模式、Pi 小核心扩展路线分别差在哪里。

- 难点一：插件不直接依赖另一个插件，缺服务时不会报错，而是一直停在等待状态，问题从启动崩溃变成悄悄没生效。
- 难点二：TypeScript 版官方文档里没查到循环依赖的检测与拒绝，只能确定会死锁；第三方 Rust 移植版的环检测不能当成 DSH 本体行为。
- 难点三：换 agent loop 时，不能只保证事件名字不变，还要保住事件模式、轮次语义、会话日志和 Agent 接口整份契约。
- 难点四：Unity 传统组件模式和 ECS 不是一回事；先按 ECS 类比会偏，用户随后明确说的是 Unity 那种 GameObject 加组件的架构。

## 过程

### 17:48 先找对比文章

用户问有没有比较好的 DeepSeek Harness、Pi 架构对比文章。助手给出几篇：Composio 的正面对比（从运行时、扩展、沙箱、会话格式比到他们自己的小样本评测：30 题里 Pi 过 21 题，DSH 过 20 题，并提醒这是 Composio 自己的小样本）；O'Reilly 的《Choose Your Coding Harness by What You Need to Control》（按想控制什么来选：Pi 让人控制循环本身，DeepSeek 靠组合插件换掉整块部件）；DeepSeek Harness 官方的三角色能力设计（服务定义、服务实现、以工具形式暴露给模型的使用方）；仓库里的 Cordis 教程（连 agent 循环本身都是插件）；以及 GitHub 讨论 #2261 里维护者讲 pi2dsh 桥接层。当时的概括是：Pi 是很小、好读的核心加 TypeScript 扩展；DSH 是能整块替换部件的运行时，体积更大，且仍是开发者预览。助手提议整理成对比卡放进面试题库，用户没有接，而是转到插件依赖问题上。

### 17:55 依赖怎么保证、循环怎么处理

用户指出：一切皆插件时，插件之间往往有依赖，如何保证被依赖的插件已经安装，以及如何解决递归依赖。助手查了 Cordis 的做法：插件不直接引用另一个插件，只用 `inject = ['shell']` 这样声明要哪些服务；缺哪个服务，插件就一直停在 PENDING，`apply` 不会执行，所以一旦进了 `apply`，对应服务一定可用。由此带来三个效果：`cordis.yml` 里的先后顺序无所谓；这种检查不是只在启动时做一次，提供服务的插件在运行中被卸载或热替换时，依赖它的插件会自动卸载，服务回来后再重新加载，换实现也走同一机制；可有可无的依赖不写进 `inject`，用的地方再 `ctx.get('x')` 探一下，没有就降级。

代价是「静默不启动」：把提供服务的插件删掉，依赖方会一直卡在 PENDING，不报错也不崩，进程甚至可能以退出码 0 结束且什么都不打印。官方教程专门有一章讲如何诊断这种状态。

循环依赖时，两个插件都会永远 PENDING，变成死锁。TS 版官方文档里当时没找到处理方式。助手能查到的是两个第三方 Rust 移植版（ares-cordis、rust-cordis-core）：加载时按声明建依赖图，用深度优先搜索找环并报出来；运行中新增注入如果成环，就直接拒绝，并在 PENDING 诊断里标明原因。这一点只能当参考，不能当成 DSH 本体行为。

另外要分清：Cordis 管的是运行时依赖；npm 包有没有装、版本兼不兼容，仍然靠 npm 和 `package.json`，Cordis 不管安装。

### 17:56 运行时能否装卸插件

用户问是否支持运行时卸载或加载插件。助手的答复是支持，而且这是 Cordis 的核心卖点：可以按配置在运行中挂上、重新加载、移除。卸载时，插件在 `apply` 里做的注册（例如注册工具、监听事件）由 Cordis 记成 effects，会逆序撤销，不留下悬空的工具或监听。某个服务一消失，所有用 `inject` 依赖它的插件会跟着卸载，服务回来后再自动加载。限制是：这里的「运行时加载」指把已经装好的包挂进运行时，下载和安装新的 npm 包不归 Cordis 管；热替换期间依赖方会短暂下线再重启，正在进行中的调用会怎样，取决于插件自己有没有处理好清理逻辑。

### 17:59 复杂应用里的失败模式

用户认为复杂应用里这种依赖很难管理，会引入失败模式。助手同意：这套设计等于把编译期就能暴露的错误，推迟到运行时才冒出来。当时归纳的典型失败模式是：静默不启动；连锁卸载（底层服务一抖，上面一串插件跟着卸载再重载，正在跑的 agent 回合可能中途丢工具）；反复抖动（某个服务一直加载失败又重试时，依赖方被反复拉起、撤下）；契约漂移（只按服务名匹配，换了一个接口不完全兼容的实现也能挂上，要到调用时才出错）；难以推理（某个时刻哪些插件是活的，只能看运行时状态，光读配置看不出来）。当时查到的缓解手段主要是 PENDING 诊断，以及第三方移植版里的环检测；版本约束和健康检查没有看到成体系的方案。这也是 Composio 那篇说它仍是开发者预览的原因之一。当时提到比较稳的做法是让核心插件集合固定，并在启动前做依赖校验（缺服务或成环就直接失败，而不是一直等），只有边缘能力才做热插拔；Pi 选择小核心加扩展，是另一边的取舍。

### 18:00 依赖怎么声明、顺序会不会自动管、成环会怎样

用户连续问了三件事。依赖声明：插件之间不直接声明依赖，而是一方提供服务、另一方用服务名挂钩。使用方导出 `inject` 列出必需的服务名，提供方在自己的 `apply` 里把实现注册成同名服务，两边互不 import。可选依赖不写进 `inject`。依赖关系分散写在各个插件里，没有一张集中的依赖清单，也不声明版本；要看全局依赖图，只能运行时去问 Cordis 当前状态。提供方注册服务的具体 API，当时没看到原文，没有写死。

加载顺序：会自动管理，不必在 `cordis.yml` 里排。使用方可以先进入等待，等提供方注册后再执行 `apply`；教程里对调两行，输出一样。卸载时也是提供方一走，依赖方先被撤下。它不自动保证的是：依赖缺失只会一直等，不会报错；循环依赖在 TS 版官方文档里没看到会自动检测。所以「顺序自动」不等于「依赖关系正确」被自动保证。

循环依赖的具体表现：不崩溃、不报错，这两个插件提供的服务都不会出现，上层依赖它们的插件也一起卡住，看起来像是功能缺了。运行中新增依赖也可能成环。第三方 Rust 移植版还提到，如果放任这种环存在，卸载时双方会互相等对方先清理完，同样会死锁，所以它们在建立依赖时就直接拒绝。当时能确定的只有 TS 版 DSH 本体「会互相等住」。常见解法是把两边共用的部分抽成第三个服务，或者把其中一边改成可选依赖，用到时再 `ctx.get()`。

### 18:02 是不是像 ECS，以及和 Unity 组件模式比

用户先说这套思想有点像游戏引擎里的 ECS。助手认为更像依赖注入容器，或 OSGi 那种插件框架，和 ECS 不太一样：两者都追求组合优于继承，核心本身很薄；但 ECS 的核心是数据（实体只是 ID，组件是纯数据，系统按组件组合批量处理），Cordis 的核心是服务契约（按服务名做依赖注入，再加生命周期和依赖追踪）。更准确的类比是 Spring 或 Angular 的依赖注入，加上 OSGi 的动态服务注册。ECS 里「系统查询带某些组件的实体」，只是有点像 DSH 按事件挂钩的方式，例如 `tools/pre-execute`，属于形似。

用户随即补充「Unity 那种架构」。助手改口：说的是 Unity 传统的 GameObject 加 MonoBehaviour 组件模式，确实更像。像的地方：都是空壳加挂载的组件（GameObject / 很薄的 Context）；都有生命周期回调（Awake、Start、OnDestroy / apply 与卸载时自动清理）；都能在运行时增删组件；都有类似依赖声明的东西（`[RequireComponent]` / `inject`）。不同的地方：Unity 缺了依赖会在编辑器里自动补上，Cordis 缺了就一直等、不会自动装；Unity 用 `GetComponent<T>()` 按类型在同一个对象上找，Cordis 按服务名在共享 Context 上找，而且可以跨插件替换实现；Unity 组件被删后，别人手里的引用会变成空，需要自己判断，Cordis 会主动把依赖方一起撤下，等服务回来再拉起。一句话：Cordis 像是 Unity 组件模式加上了服务定位和自动依赖追踪。

### 18:03 哪个更成熟，以及 Unity 强在哪里

用户问哪个更成熟。助手的判断是 Unity 的组件模式成熟得多：从 2005 年前后用到现在，工具链、调试和社区经验完整，执行顺序、引用失效这类坑也有成套约定。Cordis 从 Koishi 机器人框架演化而来，在那个生态里跑过一段时间，但用在 DeepSeek Harness 上，Composio 的评测明确说仍是开发者预览，依赖诊断、环检测这类配套在 TS 官方文档里还不完整。两者解决的问题也不一样，不能直接比优劣：Unity 是在一个对象内部组合组件，Cordis 是在整个运行时里替换服务；论设计思想，Cordis 更接近 OSGi 这种动态模块系统。

用户要求详细对比 Unity 相比 Cordis 强的地方。助手从八个方面讲，并说明 Cordis 的核心设计并不差，差的是成熟度和工程配套：

1. 依赖缺失时，Unity 会在编辑器里自动补上；Cordis 一直 PENDING，要事后诊断。
2. Unity 的生命周期阶段固定，还可用 Script Execution Order 或 `[DefaultExecutionOrder]` 显式排序；Cordis 的顺序完全由依赖推出，想强制某个插件先跑，没有那么直接的手段。
3. Unity 有 Inspector 和 Profiler；Cordis 主要靠日志和 PENDING 诊断，没有成熟的图形化工具看当前谁活着、谁依赖谁。
4. Unity 按类型查找，编译期就能发现不少错误；Cordis 按字符串服务名匹配，名字写错或实现不兼容，要到运行时才暴露。
5. Unity 组件挂在具体对象上，作用域局部、好推理；Cordis 的服务挂在共享 Context 上，接近全局，规模大了依赖图更难看清。
6. Unity 销毁后的「假 null」有约定写法；Cordis 连带撤下更彻底，但底层服务一抖，上面一串都会重启，对正在跑的 agent 回合影响更大。
7. Unity 有近二十年的商业项目和最佳实践；Cordis 在 DSH 上仍是开发者预览。
8. Unity 大部分组装在编辑期完成，运行时变动相对少；Cordis 的组装和变化都在运行时发生，灵活，出错时机也被推迟。

反过来，Cordis 强在能整块替换实现、服务消失时自动连带撤下和恢复、热插拔是一等公民，这正是 agent 运行时需要的，例如换沙箱或模型适配器。当时的概括是：Unity 把复杂度留在编辑期，用工具和约定兜住；Cordis 把复杂度推到运行时，用自动依赖追踪兜住。后者更灵活，但需要补上诊断、环检测和契约校验，才能接近前者的工程确定性。

### 18:09 换 loop 是不是只要事件不变

用户问：DSH 好像主要依赖事件广播，换掉 loop 只要保证事件不变就行了吗？助手核对官方说法后的结论是：事件是换 loop 的主要接口，但要保证的是整份契约，而不只是事件名字不变。需要一并保住的有：事件模式（是 `emit`、`serial` 还是 `waterfall`，模式一变，原来能拦截请求的插件就会失效）；轮次语义（官方把一轮规定成固定流程：`turn/start` 领取输入，再走 `agent/pre-step`，可以拒绝或进入步骤，然后 `step/start`、`agent/request`、`llm/stream`，工具走 `tools/pre-execute` 到 `tools/post-execute`，最后 `agent/turn-stopping` 和 `turn/end`）；持久日志（`turn/`、`step/`、`user/message`、`assistant/message`、`tool/*` 不是普通内存广播，而是写进会话日志的事实，且模型看见的内容都必须能从日志重建）；以及新 loop 还要实现 `ctx.agents` 这套接口，包括 inbox 领取、模型选择快照、取消和收尾顺序。当时还有一个现成警告：`agent/request` 已被标成弃用，说明事件契约本身也会变，换 loop 不是签一次字就一劳永逸。

### 18:13 Pi 默认的四个工具

用户记得 Pi 有四个最简单的工具。助手核对：Pi 默认只给模型 `read`、`write`、`edit` 和 `bash`；搜索、找文件、git 都交给 bash 去调 `rg`、`find`、`git`，系统提示词也很短。作者的思路是：前沿模型本来就会用 shell，工具越少，占的上下文越少，也越好预测。DSH 正好相反，Composio 那篇里数到它内置了 53 个工具，外加沙箱、子 agent、MCP 等。要扩展 Pi，是用 TypeScript 扩展加工具，而不是让核心变大。

## 结果

这场对话把 Cordis 的依赖模型、运行时装卸、失败模式，以及和 Unity 组件模式、Pi 工具集的差别谈清楚了。没有写成对比卡，也没有入库或开任务。仍未从 TypeScript 版官方文档里确认 DSH 本体是否做环检测；提供方注册服务的具体 API 当时没对照原文。

## 所学

Cordis 解决的不是「先装好再启动」，而是「运行时按服务名等待」。好处是顺序不用手排、实现可热替换、卸载能连带清理；代价是依赖缺失和循环依赖从报错变成静默不启动，复杂应用里还会出现连锁卸载、契约漂移和难以从配置推理当前状态。

不要把它直接理解成 ECS。ECS 关心数据怎么摆、怎么批处理；Cordis 关心谁依赖谁、什么时候能启动。和 Unity 传统组件模式更像，但 Unity 缺依赖会自动补、组装多半在编辑期完成；Cordis 缺了就等，组装发生在运行时。所以「哪个更成熟」比的是工程配套和失败时的确定性，不是核心思想谁更高级。

换 loop 时，事件名只是契约的一部分。事件模式、轮次节奏、可重建的会话日志和 Agent 接口都要对齐；`agent/request` 已经弃用，说明这份契约还会变。

Pi 和 DSH 是两种扩展路线：Pi 把核心保持在四个文件工具加 bash，扩展走 TypeScript 插件；DSH 把循环本身也做成插件，内置工具和能力更多，也更依赖运行时的依赖管理。当时没有把其中一条判成必须采用的方案。

第三方 Rust 移植版的环检测，只能说明「这类问题可以用依赖图在加载时拒绝」，不能写成 DSH 已经这么做了。

## 行动指南

### 主题行动指南

#### 背景

以后再读 DSH、自己做插件，或把「一切皆插件」借鉴到别的 agent 运行时，需要先分清运行时服务依赖和安装期包依赖，并看清失败会以什么形式出现。

#### 核心问题

如何在可替换、可热插拔的插件运行时里管理依赖，既不用手排启动顺序，又能发现缺服务、成环和契约不兼容，而不是让功能悄悄消失。

#### 核心解决方案

1. 用服务名声明必需依赖，用探测调用处理可选依赖；不要让插件直接引用另一个插件的实现。当时未比较在 Cordis 之外另做一套静态依赖清单，因为讨论的就是这套已有机制。
2. 把「进了 apply 就保证服务可用」当成运行时约定，同时把 PENDING、退出码 0 且无输出，当成缺依赖或成环的首要排查信号，而不是当成启动成功。
3. 核心插件集合尽量固定，并在启动前做校验：缺服务或成环就失败退出。热插拔留给边缘能力。可选项是像现在这样一直等待，或像 Pi 那样把核心收小、扩展另走插件；当时认为一直等待会把错误推迟到运行时，核心过大又会放大连锁卸载和契约漂移。
4. 替换 agent loop 时，逐项核对其事件模式、轮次语义、会话日志能否重建模型可见内容，以及是否实现 Agent 接口；不要只核对事件名字。
5. 需要环检测、版本约束或健康检查时，先查 TypeScript 版官方文档和实现，不要把第三方移植版的行为写成 DSH 本体保证。

#### 验收标准

- 能说明 `inject`、PENDING、可选的 `ctx.get`，以及 npm 安装不归 Cordis 管这三件事的差别。
- 能举出静默不启动、连锁卸载、契约漂移这些失败会怎么表现。
- 能说明为何不宜用 ECS 来理解 Cordis，以及 Unity 组件模式像在哪里、成熟在哪里。
- 能列出换 loop 时除事件名以外必须保住的契约项。
- 涉及环检测时，能区分「DSH 会互相等住」和「某些移植版会拒绝成环」。

### 细节与其他

#### 若要声明插件依赖

则：必需服务写进 `inject`，可选服务在用到的地方 `ctx.get`。不要为了「保险」把可选依赖写成必需，否则提供方不在时自己会一直 PENDING。提供方注册服务的具体 API 以 Cordis 教程第 3 章为准，这次没有对照原文。

#### 若运行中要换一个服务的实现

则：先卸掉旧实现再挂上新实现，依赖方会按设计被撤下再拉起。不要假定正在进行中的调用会自动安全切换，清理逻辑要插件自己处理。当时未比较先停掉整场 agent 再切换的做法。

#### 若遇到两个插件互相等待

则：先按死锁来查，看能不能把共用部分抽成第三个服务，或把其中一边改成可选依赖。不要指望 TypeScript 版 DSH 已经自动报环。

#### 若要把这套设计和游戏引擎类比

则：优先用 Unity 的 GameObject 加组件，不要用 ECS 的「实体 ID 加纯数据组件」来硬套。若只是想讲「按事件横切处理一类事情」，可以提到和 ECS 系统查询的形似，但要说明核心抽象不同。

#### 若只是想控制循环、保持核心很小

则：Pi 默认的四个工具是 `read`、`write`、`edit`、`bash`，扩展用 TypeScript 加能力，而不是先上 DSH 那种可整块替换的运行时。这条是当时对两条路线的对照，不是对某个项目的选型结论。
